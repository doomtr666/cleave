# Type Inference: What the First Pass Actually Does

*A record of what `cleave/src/infer.rs` builds and why, written after the fact rather than planned up front — complements `hld.md` (architecture) and `grammar.md` (surface syntax). Not a spec: a few real gaps were found by testing along the way and are called out here exactly as they were found, not smoothed over.*

The algorithm family throughout is **Hindley-Milner (HM) Algorithm W**, extended to "HM + qualified types" (see "Qualified types" below) — every section uses **HM** as shorthand for Hindley-Milner from here on.

## Scope: one function body at a time — plus a whole-program pass over top-level `fn`s

`Infer::infer_fn(&FnDecl) -> Result<Ty, TypeError>` and `Infer::infer_impl_fn(...)` each infer one function body in isolation from every *other* `fn`/`impl` method — no cross-function signature lookup happens inside `infer.rs` itself. A call to another declared `fn` that isn't resolvable through what `env` already holds (a `let`-bound lambda in the same body, or a name an `algebra`/`impl` can resolve) returns an explicit `Ty::Con("<unresolved-call:name>")` placeholder rather than silently guessing. A lambda *nested inside* the function being inferred is inferred as part of the same pass — only calls that cross a top-level `fn`/`impl` boundary can be unresolved this way.

Two things this restriction does *not* mean, addressed by machinery layered on top of `infer_fn`/`infer_impl_fn` rather than inside them:

- **Self-recursion** (a top-level `fn` calling itself, directly or through its own nested lambdas) *is* resolved — `infer_fn` binds its own name to a monomorphic placeholder before inferring its body (see `infer_fn`'s own doc comment). A self-recursive `let`-bound lambda (`let g = fn(n) { g(n) };`) is *not* — a lambda has no name to publish a placeholder under until it's already bound, the chicken-and-egg this specific restriction reflects.
- **Mutual recursion between separately-declared top-level `fn`s**, in any declaration order, *is* resolved — by `callgraph.rs`, a whole-program pass built on top of `infer_fn`'s own internals (`infer_fn_raw`, `generalize`) rather than inside `infer_fn` itself. See "Whole-program inference over top-level `fn`s" below.

What's still genuinely out of scope: `algebra`-impl methods (dispatch is entirely signature-driven there — see below for why that was never actually a gap); and, for *inherent* methods specifically, an unannotated method's real inferred return type ever reaching a caller *outside* its own impl block (self- and mutual recursion *within* one block are both resolved — see "`impl` methods: algebra dispatch is unaffected, inherent methods now share a block-level pass" below for exactly what it does and doesn't cover). Also out of scope, unrelated to `impl` methods: a constraint on a type that's neither pinned to something concrete nor captured by some binding's `Scheme` by the time its enclosing scope finishes has nowhere further to travel — left unchecked, not because that's correct, but because there's no propagation beyond that scope for it to travel *into* (see "Qualified types" below).

## The core engine: types, substitution, unification

`Ty` is the internal type representation — deliberately distinct from `ast::TypeKind` (the surface syntax a program actually wrote):

```rust
pub enum Ty {
    Var(TyVar),              // an unresolved type variable
    Con(String),              // a concrete, nullary type ("i32", "bool", "Vec2", ...)
    App(String, Vec<Ty>),      // a generic type applied to its own arguments ("Complex<f64>", "Matrix<f32,2,3>")
    Fn(Vec<Ty>, Box<Ty>),      // a function's type: parameter types + return type
    Array(Box<Ty>, Box<Ty>),  // element type + size (itself a Ty -- Const, Var, or a mismatch)
    Const(ConstValue),        // a resolved const-generic value: ConstValue::Int(u64) | Bool(bool)
}
```

`Con` is short for *type constructor* here in the classical Hindley-Milner (**HM**, the abbreviation used throughout the rest of this document) sense (a nullary one — a concrete named type with no arguments) — standard terminology in HM implementations (`TCon`, `Con`, `Ground` depending on the textbook), not anything specific to this project. `App`/`Array`/`Const` grew the enum well after the original three-variant sketch above — see "Generic structs: `Ty::App` and const-generics" below for what each closes and why it's shaped the way it is.

`Subst` is a union-find-style map from type variables to types, extended in place by `unify` (the standard Robinson unification algorithm) — with the **occurs check**, rejecting e.g. `unify('a, ('a) -> Int)`, which would otherwise produce an infinite type. `Subst::apply` and the occurs check both recurse into `Ty::Fn`'s parameter/return types; missing that recursion would silently defeat the occurs check the moment lambdas are involved, since a variable can occur *inside* a function type just as easily as anywhere else.

`unify` itself carries no source location — it's a pure type-level operation with no notion of "which expression". Every caller inside `Infer` attaches a `Span` via `unify_at`, producing a `TypeError { span, kind }` — the one place a bare `UnifyError` becomes something a `Diagnostic` can point at (see `diag.rs`).

## Literal defaulting

An unsuffixed numeric literal (`1`, `1.0`) gets a fresh type variable, not an immediate concrete type — the final type (from an explicit `:f64` suffix, from unification with something else, or from a default) is entirely a type-inference concern, never decided at parse/lowering time (see `grammar.md`, "Type conversion"). If that variable is still unresolved once the whole function has been inferred, `apply_defaults` forces it concrete: `i32` if the literal's own text has no `.`/exponent, `f32` otherwise — mirroring Haskell's numeric-literal defaulting. This is purely a fallback for "nothing else ever decided" — a literal's own *enforcement* comes from a real constraint, not from defaulting; see the next section.

## A literal's shape (`Int`/`Float`) is a real, checked constraint — not just a defaulting hint

Found the hard way, across several rounds of direct testing (not designed up front): a first version only ever consulted a literal's shape (`.` present or not) *inside* `apply_defaults`, as a same-priority tiebreak among literals that were each independently being defaulted. That version missed a whole class of real cases, all variations on the same root problem — a merge between two type variables reaching a concrete type through *any* other route (a real, external unification; a scheme a caller later instantiates) never checked whether a literal's own shape was actually consistent with the type it ended up as:

- `add(fibonacci(42), fibonacci(42.0))` — two *separate calls*, each with their own fresh instantiation of `fibonacci`'s scheme, forced to the same type by `add`'s shared generic `T`. Neither call site is itself "defaulting" anything at the point they're merged, so a defaulting-only check never even ran.
- A declared return type (`fn f() -> f64 { 1 }`) pins a literal's variable concrete through a completely different, *real* unification — indistinguishable, from inside `apply_defaults` alone, from "a sibling literal's own default already decided this," which is a case that correctly *should* be silently permissive.
- A variable shared by two members of a mutually-recursive group, quantified (generalized) rather than defaulted at all — see "A generalized variable must never be defaulted" above — never went through `apply_defaults`'s shape-comparison in the first place, so two differently-shaped literals feeding a shared, generic return type across the whole group went unchecked no matter how (or whether) that scheme was ever later instantiated.

**The actual fix, suggested directly rather than found by trial and error: give a literal's shape the exact same treatment `Num` already gets, instead of inventing a second, narrower mechanism for it.** `stdlib/num/num.cleave` now declares `algebra Int<T> {}` and `algebra Float<T> {}` alongside `Num<T>`, each independently `impl`'d for their own subset of numeric types (`Int`: `i8`/`i16`/`i32`/`i64`; `Float`: `f32`/`f64`) — deliberately **not** `algebra Int<T>: Num` at the time this was written — algebra-bound inheritance wasn't implemented anywhere in the registry/inference yet then; see "Algebra-bound inheritance" below for where it landed later, and `stdlib/num/num.cleave`'s own current form (which *does* use the bound now, and no longer needs `Int`/`Float` to each carry a redundant, hand-written copy of `Num`'s own impls). A bare literal's own type variable still gets *two* independent constraints pushed at once, kept explicit rather than relying on the now-available inheritance path — see the module-level `NumberLit` comment for why — `Num` (as before) *and* `Int` or `Float`, depending on its own text — in `infer_expr_kind`'s `NumberLit` branch. `check_pending_constraints` already checks *any* named algebra uniformly, regardless of how a variable ended up concrete (a real declared type, a default, or a scheme's own quantified variable once some caller instantiates it) — so `Int`/`Float` get exactly the same correctness `Num` already had, with **zero special-casing added to `apply_defaults` itself**, which went back to the simple form it had before the grouping-based attempt (default each still-open, non-quantified variable to its own shape's preferred type, full stop — no comparison against siblings needed, since a genuine conflict now surfaces as an ordinary `MissingImpl` from `check_pending_constraints` instead).

Grounded in an explicit language rule, not an implementation convenience: cleave has no implicit conversions anywhere, integers and floats included — a bare `1` genuinely cannot become `f64` just because the surrounding context asks for it, the same way `f64`/`i32` themselves never implicitly convert. `fn f() -> f64 { 1 }` is consequently now a real, correct rejection (`no impl Int<f64>`) — a behavior change from earlier in this same session, when the old grouping-based fix still let a literal's shape lose silently to any real external unification. Write `1.0`, or suffix it (`1:f64`, which bypasses shape-checking entirely — a suffixed literal is pinned directly to a `Ty::Con`, no variable, no constraint, see `NumberLit`'s `Some(suffix)` branch), when the context genuinely needs a float.

**A real, if surprising-at-first, consequence for functions defined with bare literals in their own body:** `fn fibonacci(x) { if x > 2 { fibonacci(x-1) + fibonacci(x-2) } else { x } }`, written with plain `1`/`2` (no `.`), is not actually `Num`-polymorphic — its own body's arithmetic requires `Int` specifically, and that requirement is part of the generalized scheme it ends up with. Calling `fibonacci` with an `f32` argument, which used to silently "work" (report `f32`, no error — the exact repro that started this line of testing) is now correctly rejected (`no impl Int<f32>`). `fibonacci` remains genuinely polymorphic *within* the `Int` family (`i8`/`i16`/`i32`/`i64`, whichever has an `impl` for whatever the surrounding algebra needs) — it just isn't polymorphic over `Float` too, because nothing in its own definition would ever have made that sound.

### A shared quantified variable needs its constraint *copied* into every scheme that needs it, not moved

A second, independent bug surfaced while testing the `Int`/`Float` split against a genuinely mutually-recursive group: `generalize`'s constraint sweep used to *remove* a matched constraint from `self.constraints` once one scheme claimed it. That was never observably different from copying it for an ordinary `let` — no other binding ever shares a `let`'s own quantified variables, since any later reference goes through `instantiate`, which always mints fresh ones. It breaks for `callgraph.rs`'s per-group `generalize` loop, though: two members of the same mutually-recursive group can legitimately still share the very same *raw, not-yet-instantiated* quantified variable (two different `if`/`else` branches, one in each function, both feeding a value into the group's shared, mutually-tied-together return type). Whichever member's `generalize` call ran first "stole" the shared constraint, leaving the other member's own scheme with an empty constraint list for a variable it was just as responsible for — so instantiating *that* member's scheme (but not the first one's) missed the check entirely.

Fixed by making the sweep non-destructive: `generalize` now *copies* a matching constraint into the scheme without removing it from `self.constraints`. The original, un-removed entry is left behind — still referencing the now-quantified variable, never touched by anything else again directly — so `check_pending_constraints` now explicitly skips any constraint whose type resolves to a variable in `self.quantified` (the exact same guard `apply_defaults` already had), rather than relying on the sweep to have already removed it. Every scheme that quantifies a shared variable gets its own correct copy of what it requires; the leftover original is inert, correctly superseded by whichever scheme(s) actually carry the constraint onward to be checked at their own future instantiation sites.

## `let`-generalization (real HM polymorphism)

`Env` maps names to a `Scheme` (`∀vars. constraints ⇒ ty` — see "Qualified types" below for the constraint part), not a bare `Ty`. A plain, immutable `let` whose right-hand side is a **syntactic value** — a literal, a variable reference, or a lambda (`is_syntactic_value`) — gets generalized at the binding site (`Infer::generalize`): any type variable free in its type but free *nowhere* in the surrounding environment is universally quantified. Every later reference instantiates a fresh, independent copy of the scheme (`Infer::instantiate`):

```
fn f() { let id = fn(x) { x }; id(1); id(true) }
```

Without generalization, `id`'s single type variable gets pinned by the first call and the second one fails to unify. With it, `id` carries the scheme `∀t. t → t`, and `id(1)`/`id(true)` each instantiate their own independent `t` — this is exactly why it's called *`let`*-polymorphism, not "lambda"-polymorphism: a lambda passed as an ordinary function argument stays monomorphic for the call's duration; only a name bound via `let` (or a top-level `fn`, an implicit `let`) gets to be generalized. This restriction — never generalizing under a binder, only at `let` — is exactly what keeps Damas-Milner inference decidable and syntax-directed with no annotations; full System-F-style polymorphism is undecidable to infer.

One restriction on generalization, deliberate: **`let mut` is never generalized**, regardless of what its value looks like — checked structurally (the `mutable` flag on the `Let`), not by trying to prove a given `mut` binding is never actually reassigned. A generalized mutable binding could be reassigned at one instantiation's type and read back at another's — the classical ML ref-cell-polymorphism unsoundness (a mutable binding's scheme is computed once, at the `let`, and never recomputed after a later reassignment — so if it were generalized, a call site relying on the frozen scheme could remain "type-correct" on paper while the value actually stored underneath it, after mutation, has since become something incompatible). Simpler and safer than reasoning about aliasing through the value's shape.

**A number literal's own type variable is generalized exactly like any other free variable — this took a wrong turn and a correction to get right, worth recording.** A first version of `generalize` excluded a literal's type variable from quantification outright, reasoning that `apply_defaults` (see "Literal defaulting" above) would otherwise force it concrete "after the fact" and silently collapse whatever had just been generalized. That reasoning didn't hold up: `instantiate`/`substitute` never consult `self.subst` for a scheme's own quantified variables — they substitute directly over the frozen `scheme.ty` tree — so defaulting an already-quantified, now-orphaned variable afterward is inert; nothing downstream ever looks at it again.

Worse, the exclusion actively broke something real. `x + 1` unifies `x`'s type variable with the literal's — after that unification they're *the same variable* — so excluding "the literal's variable" from generalization also excluded `x`'s own genericity right along with it, the moment a bare numeral appeared anywhere in the body:

```
fn add_one(x) { x + 1 }
```

With the exclusion in place, `add_one` was silently forced monomorphic — usable at exactly one numeric type, decided by whichever call happened to pin it down first, and rejecting every other type afterward. This is precisely the C++/Rust generic-numeric-literal pain (`num_traits::One`/`Zero`-style boilerplate exists in Rust specifically because a bare literal *isn't* generalizable there) — and it's exactly the kind of friction this project doesn't have to inherit, since HM generalization already has the right shape for it. The fix was to stop excluding the literal's variable and instead let its `Num` constraint (see "Qualified types" below) travel into the scheme right alongside it: `add_one` now generalizes to `∀t. Num t => (t) -> t`, not the unsound fully-unconstrained `∀t. (t) -> t` a naive fix might have produced — the constraint is what keeps "usable at any type" honest, restricting `t` to whatever concrete types actually have a registered `Num` impl.

## Function types as first-class values

`Ty::Fn(Vec<Ty>, Box<Ty>)` already existed internally — every lambda has always had one — but there was no way to *write* one as a type annotation until `TypeKind::Fn` (see `grammar.md`, "Function types") gave it surface syntax. `ty_from_ast_mapped` gained the matching arm, so `fn apply(f: (i32) -> i32, x: i32) -> i32 { f(x) }` type-checks `f(x)` exactly like calling any other function value — `f`'s own `Ty::Fn` unifies against the call's argument/return shape the same way a `let`-bound lambda's type already did, no new unification logic needed, just a new way to *name* the shape that was always there.

## Generic structs: `Ty::App` and const-generics

**`Ty::App(String, Vec<Ty>)`** — a struct name applied to type arguments (`Complex<f64>`, `Matrix<f32, 2, 3>`) — is what actually makes a generic struct constructible and inferable, not just parseable. Before it existed, `Pair<T> { a: T, b: T }` parsed fine but construction was rejected outright: `Ty` had nothing to represent "this generic instantiated at this argument" with. `Pair(a: 1.0, b: 2.0)` now infers `Pair<f64>` by unifying both fields' values against the struct's own shared `T` — ordinary unification, the generic argument itself never needs to be written down anywhere the way it does in a language without inference.

**`Ty::Const(ConstValue)`**, where `ConstValue` is `Int(u64) | Bool(bool)` — a const-generic's own *value*, not its declared width, flowing through the exact same `Ty::Var`/unification machinery an ordinary type generic does. An array's own size (`[T; N]`) was the first real consumer: `N` resolves to a `Ty::Const` the same way any other generic argument resolves to a concrete `Ty`, with an `Int` constraint pushed at the point it's actually *used* as a size (not at its own declaration — a real, previously-existing bug this generalization fixed along the way: hard-coding `usize` at declaration time was wrong the moment a const-generic needed to be anything else, like a `bool` compile-time flag). `ConstValue` being an enum rather than a bare integer is what makes `struct Flagged<const B: bool> { ... }` (a compile-time boolean parameter, not a size) representable through the identical mechanism, with no separate "const-generic kind" system needed. It stayed the *only* consumer for a long stretch — see "Const generics as ordinary values" below for what broke, three separate times, the moment a const generic also became referenceable as a plain value (a `for` loop bound, say), not just a shape.

**Turbofish exists specifically because construction alone can't always pin every generic.** `Vec::<f64, 3>(data: [1.0, 2.0, 3.0])` — the array literal already tells inference the element count, but an *empty* array (`Vec::<f64, 3>(data: [])`) or a zero-field generic marker has nothing to infer a generic argument *from* at all; turbofish (see `grammar.md`) supplies it directly, checked against — never silently overriding — whatever the constructor's own field values would otherwise imply.

## Control flow gets real inference

`while`/`for` parsed long before they had any type-checking behind them (`grammar.md`'s own "funnel" note) — inferring them was a real, later increment, not automatic.

- **`while cond { body }`**: `cond` is unified against `bool`; `body` is inferred (and its result discarded — there's no `break value` mechanism, so a `while` can never itself produce a value). The whole expression is always `Ty::Con("()")`.
- **`for var in start..end { body }`**: `start` and `end` are unified together (so `0..n` requires both sides to agree on one concrete numeric type), with an `Int` constraint pushed on that shared type — no hard-coded width, mirroring how `Index`'s own array-index type already works. `var` is bound in the body's own scope via `Scheme::mono` (monomorphic — a loop variable is never generalized, the same restriction `let mut` already has and for a related reason: it changes value across iterations). Also always `Ty::Con("()")`.

Both used to return an unconditional `<loop-not-yet-inferred>` placeholder, never even visiting `cond`/`body` — meaning a type error *inside* a loop body went completely unnoticed. Neither can currently produce a value the way an `if`-expression can (no `break value`, no accumulator-as-tail-expression convention) — `let mut` plus an ordinary post-loop read of the accumulator is the idiom for now.

## Reassignment into a field/index chain, not just a bare name

`StmtKind::Assign` used to carry a bare `name: String` — `arr[i] = v;`/`s.field[i] = v;` had no representation at all, only `x = v;`. The fix generalizes the target to an ordinary `target: Expr` (the same `Path`/`FieldAccess`/`Index` shapes an ordinary *read* of the same location would use), lowered by reusing `lower_postfix_op` directly rather than duplicating its logic — `assign_target`'s own grammar (`ident ~ assign_suffix*`) is exactly `postfix`'s shape minus the call-args/method-call alternative (you can't assign through a method call).

Inference shrinks rather than grows: the old arm did a bespoke `env.get(name)` plus a hand-built `UnknownName` error; the new one is just `self.infer_expr(&env, target)?` unified against the value's type. `ExprKind::Path`'s own inference arm already does the identical lookup and raises the identical error, and `Index`'s own arm already extracts the correct element type — so `arr[i] = v` checks `v` against the array's element type for free, no new inference logic at all. No new mutability enforcement was added: a plain `name = value` was never checked against `let mut` either (`mutable` only ever gates *generalization* — see "What's still explicitly not done"), so indexed assignment doesn't regress or improve on that pre-existing gap.

## A repeat-count that names a const generic, not just a literal

`[value; N]` (repeat sugar) desugars to `N` literal copies of `value` at *lowering* time — cheap and correct when `N` is a `numeric_lit` token, since lowering can read the count directly off the source text with no type information at all. But a *generic* array (`fn fill<T, const N: i32>(v: T) -> [T; N] { [v; N] }`) needs the exact same sugar with `N` naming one of the enclosing declaration's own const generics — unknowable as a literal count until monomorphization resolves `N`, long after lowering has already run.

The grammar narrows rather than broadens to fit this: `array_repeat = { expr ~ ";" ~ (numeric_lit | ident) }` — deliberately *not* a general `expr` slot. The count names a compile-time integer (a literal, or a const-generic reference) — never a computation; that restriction is what keeps lowering purely syntactic for the literal case and keeps the generic case tractable for inference to resolve later, rather than opening the door to `[v; f(x)]`-style arbitrary expressions with no defined meaning. A literal count still desugars exactly as before (`ArrayLit`, N eagerly-cloned copies, each with its own fresh `NodeId`); an `ident` count instead lowers to a new `ExprKind::ArrayRepeat { value, count }` node, left as a real, still-symbolic AST shape for inference (and, later, monomorphization's ordinary node-type substitution) to resolve — no eager expansion attempted, since there's nothing to expand yet.

Inference for it is almost embarrassingly small: `elem_ty = infer_expr(value)`, `count_ty = infer_expr(count)`, result `Ty::Array(elem_ty, count_ty)` — mirroring `ArrayLit`'s own arm exactly, just reading the size off `count`'s own inferred type instead of `elems.len()`. The one real piece of new plumbing this depends on is covered next.

## Const generics as ordinary values — and the `Ty::Const`/`Ty::Con` split that assumes they never are

`[v; N]`'s own `count` is an ordinary `ExprKind::Path` — for it to resolve to anything, `N` has to be *bound in `env`* like any other name. It never was: a const generic's own fresh variable only ever lived in the *type*-position mapping `fresh_generics_mapping`/`ty_from_ast_mapped` builds (`HashMap<String, Ty>`, consulted only when resolving a `Type` annotation), never in the value-level `Env` an ordinary expression's `Path` resolves through. `seed_const_generics` closes this: at every real "about to infer a body" entry point (`infer_fn_raw`, `infer_impl_fn_generic_with_env`, `infer_inherent_impl_fn_raw` — the same three places already seed ordinary parameters), each `GenericParam::Const { name, .. }` also gets `env.insert(name, Scheme::mono(mapping[name].clone()))` — the *same* fresh var already used in shape positions, now also reachable as a plain value reference.

This is exactly why the repeat count's own grammar stays `ident`, not a general expression: `N` genuinely is the same var everywhere it's spelled, in both a shape position (`[T; N]`) and a value position (`for i in 0..N`, once this reaches an ordinary expression) — one binding serving both roles, not two parallel mechanisms.

**Making a const-generic reference usable in an ordinary value position immediately exposed that `Ty::Const` was never designed to survive contact with ordinary, value-typed machinery — three separate times, in three different mechanisms, each found only by direct testing on a real body:**

1. **`check_pending_constraints`** — `for i in 0..N { arr[i] = v; }` unifies `0`'s own (`Num`/`Int`-constrained) literal variable with `N`'s own shape-slot variable, via `ExprKind::For`'s `unify_at(start_ty, end_ty)`. Once a caller pins `N` to a real literal (`fill::<f32, 4>(1.0)`), the carried-forward `Int`/`Num` constraint resolves to a bare `Ty::Const(Int(4))` — and `has_matching_impl` has nothing to check that against: impls are declared for real types (`i8`/`i32`/`f32`/...), never for one specific constant value. Rejected as `no impl Num<4>`, even though `N`'s own declared type (`const N: i32`) plainly *is* `i32`.
2. **`apply_defaults`** — the same merged variable, *inside a single impl method's own declaration-time inference* (no caller/instantiation needed at all to trigger this one — dispatch-style impl methods never go through `generalize`/`instantiate`), gets defaulted for real: `apply_defaults` only ever guarded against `self.quantified` (a top-level-`fn`-only concept), so it happily committed `N := Ty::Con("i32")` — a *type*, permanently overwriting the `Ty::Var` `N` needed to stay as until monomorphization could resolve it to a concrete `Ty::Const`. Found via `examples/matmul.cleave`: the corrupted shape then failed to unify against a real call site's own `Ty::Const(2)` during monomorphization, a structurally different `Ty` shape than `apply_defaults` had already locked in.
3. **`Registry`'s own multi-target impl key** (found immediately after fixing (1) and (2), inside the *same* example) — a different flavor of the identical "designed for one shape, broken by a second" story; see "Monomorphization" below for why this one lived in `monomorphize.rs`, not `infer.rs`.

**The general fix for (1) and (2): track each const generic's own declared width, and thread it through exactly the same `generalize`/`Scheme`/`instantiate` journey a `Constraint` already travels — not a per-`Infer`-instance side table, which would go stale the moment a constraint (and the shared var it mentions) gets copied into a fresh instantiation.** `Scheme` gains `const_widths: HashMap<TyVar, Ty>` alongside `vars`/`constraints`; `Infer` gains a matching field. `fresh_generics_mapping`'s own `GenericParam::Const` arm — which already resolved a const generic's declared type via `ty_from_ast_mapped`, purely to queue a `pending_type_name_checks` entry, and then *discarded the result* — now also records it: `self.const_widths.insert(var, resolved_width)`. `generalize` copies matching entries into a produced scheme's own `const_widths` exactly like it copies matching constraints (same `var_set` already computed there); `instantiate_with_mapping` re-keys them through the same fresh mapping used for everything else, so a constraint re-queued at some later call site can still recover the *real* declared width, not a guess. `check_pending_constraints`, when a constraint's resolved type turns out to be `Ty::Const`, looks up its original (pre-resolution) var in `const_widths` and checks the bound against that declared width instead of against the bare constant — falling back to this project's own conventional default int representation only for an *untracked* `Ty::Const` (an ordinary array-literal-length, e.g. `[1,2,3]`'s own size, never tied to any declared const generic). `apply_defaults` gets the much simpler twin fix: skip a variable already present in `const_widths`, exactly like it already skips one present in `quantified` — this variable belongs to const-generic resolution, not to ordinary numeric-literal defaulting.

Two independent things had to both be true for `[v; N]` to work at all cleanly: `N`'s *shape*-position uses (array sizes, const-generic argument slots) needed no change whatsoever — they still just unify a `Ty::Var` against another `Ty::Var`/`Ty::Const`, exactly as before this session. Only the *bridge* — what happens once that shared var is checked against an ordinary algebra bound, or handed to a defaulting pass that assumes every variable it sees is an ordinary numeric literal — needed teaching. Neither fix touches `Ty::Const` itself, or any of the many places that already correctly assume it only ever appears in a shape position.

## Constant folding (`const_eval.rs`)

A separate, forward-looking need surfaced in the same conversation: `[T; 4+3]` (and, eventually, `[T; N+M]` once both operands are concrete) requires actually *evaluating* an arithmetic expression at some point, not just resolving a bare literal or a bare const-generic reference — `const_value_from_expr` used to handle exactly those two cases and fall back to an unconstrained variable for anything else, silently, including pure-literal arithmetic that had nothing generic about it at all.

Deliberately kept as a small, standalone module (`cleave/src/const_eval.rs`, mirroring this project's existing one-pass-per-file style — `monomorphize.rs`, `callgraph.rs`, `registry.rs`) rather than folded inline into `infer.rs`'s own match arm: `const_eval::eval_binop(op: &str, a: ConstValue, b: ConstValue) -> Option<ConstValue>` operates purely on `ConstValue`, no `Ty`/`Expr`/`Infer` dependency at all, so it stays reusable wherever constant folding is needed later (an eventual codegen pass, say), not tied to how `infer.rs` happens to discover an expression is worth folding. Starting operator set is deliberately narrow — `"add"`/`"mul"` only, the exact names `+`/`*` already desugar to (see `ast.rs`'s own `Call` doc comment — no new grammar or AST needed for arithmetic itself) — structured as a plain match on the operator name, so adding `"sub"` or anything else later is a one-line addition with no signature change and no caller update.

`const_value_from_expr` becomes the thin type-inference-side adapter: its existing literal/bare-const-generic-`Path` cases are unchanged, plus one more — `ExprKind::Call(path, _, [a, b])` where `path` names an operator `const_eval` knows — recursing on `a`/`b` through *itself* (so nested arithmetic, `4+3+N`, folds too) and delegating to `eval_binop` once both resolve to `Ty::Const`. Either operand still abstract, or an operator not yet supported, falls through to the same permissive "unconstrained variable" default this always had — no new failure mode, just a new case that folds when it can.

**Deliberately out of scope, and likely to stay a separate, larger effort:** folding a computed expression that only becomes concrete *later* — `fn concat<T,N,M>(a: [T;N], b: [T;M]) -> [T; N+M]`, where `N+M` is still abstract at `concat`'s own declaration time and only resolvable once instantiated or monomorphized. `Ty` itself has no representation today for "a deferred arithmetic expression over what might currently be `Var`s" — only a resolved `Const` leaf or an unresolved `Var`, nothing symbolic in between that could be re-evaluated once its own operands eventually resolve. Doing this properly would mean `Ty` growing a small expression-carrying shape, touched by `unify`/`substitute`/`occurs`/`free_vars`/`Display`/`is_fully_concrete`, and monomorphization's own substitution walk — materially bigger than the two fixes above, and not needed for `MatMul`'s own shapes, which only ever reference bare `N`/`M`/`K`, never a sum.

## Algebra-backed operator resolution

Operator calls (`add`, `sub`, `eq`, `and`, ...) resolve against a real `crate::registry::Registry` — a queryable index, built once from a whole compilation's merged `Program`, over every declared `algebra` and `impl` (see `registry.rs`, `driver.rs`). `infer_call` checks the registry *before* falling back to anything else:

- **Zero algebras** declare a matching name+arity → treated exactly like calling any other undeclared name (an honest `Ty::Con("<unresolved-call:name>")` placeholder — see "What's still explicitly not done" below). An earlier version special-cased `add`/`sub`/`lt`/`and`/... here with a permissive built-in fallback (unify every argument to one shared type, no membership check at all) as a temporary bridge before a real registry existed. Keeping it after the registry existed was actively harmful, not merely redundant: it meant ordinary arithmetic (`x + 1`, completely unremarkable code) silently accepted *any* type combination as long as nothing algebra-based existed to check against — which, absent a full stdlib, was every program. Found in practice: `fn f(a: bool) { let x = 1; x + a }` type-checked, "bool arithmetic" accepted outright. Removed — an operator name with zero registered candidates is now exactly as unresolved as calling an undeclared function, no quieter about it.
- **Exactly one** candidate algebra → real resolution (`infer_algebra_call`): the algebra's own generic parameter (`T` in `algebra Ring<T> { fn add(a: T, b: T) -> T; }`) is instantiated with a *fresh* type variable per call — not treated as a literal concrete type spelled `"T"` — the declared signature's parameter types are unified against the actual arguments, and every parameter type that ends up concrete is checked against the registry (`has_impl_named`) for a matching `impl`. A parameter type still abstract at that point is deferred as a `Constraint` (see below) rather than silently skipped.
- **Two or more** candidates → a hard error (`AmbiguousOperator`), immediately, no attempt to guess a "best" one. This is **not** a signal that someone is trying to illegitimately override an existing algebra — root-ownership scoping (a separate, static check on rewrite rules, discussed in `hld.md`) already rules that out at declaration time. Two independent, legitimately-scoped algebras can both declare their own `add` for genuinely different reasons (a Boolean ring's `add = XOR` vs. a Boolean lattice's join, wrapping vs. saturating arithmetic, a vector space's componentwise `add` vs. a tropical semiring's `min`) — this is an ordinary name collision, resolved exactly like Rust's ambiguous trait methods: reject, require explicit qualification. (There is no qualified-call syntax wired to bypass this yet, so today it's an unconditional hard stop, not just the default.)

## Heterogeneous algebra dispatch: more than one type parameter

`algebra Ring<T>` — every parameter, and the return type, collapse to the *same* `T`. That shape can't express matrix multiplication: `NM * MK -> NK` genuinely needs three independent types related to each other, not one type used three times. `algebra MatMul<A, B, C> { fn mul(a: A, b: B) -> C; }` (see `grammar.md`, "Heterogeneous algebras") is the surface syntax; the interesting part is what dispatching a call against it actually requires.

**A per-parameter check, tried first, cannot get this right.** The natural-looking extension of `infer_algebra_call`'s existing single-type logic — check `A` against `has_matching_impl`, then `B`, independently — was tried and found broken by direct testing: `Matrix<f32,2,3> * Matrix<f32,3,5>` (a genuinely valid multiplication) reported `no impl MatMul<Matrix<f32, 2, 3>>`, a single-type error, never even attempting a real three-way match. Two separate reasons, both real:

1. **Nothing connects the trial substitution used to check `A` to the one used for `B`.** A shared impl-generic (`M`, appearing in *both* operands' shapes: `Matrix<T,N,M>` and `Matrix<T,M,K>`) could get bound to two *different* concrete values across two independent checks with neither one noticing — a shape-mismatched `Matrix<f32,2,3> * Matrix<f32,4,5>` (the middle dimensions disagree) could pass both checks independently while the call's own result type stayed an unconstrained variable.
2. **`C` (the return-type-only generic) never appears in any parameter at all.** Gating "is this generic ready to check" on "is it concrete yet" — the natural per-parameter approach — can never open for `C`: it starts, and stays, a bare free `Ty::Var` right up until dispatch itself resolves it. The *only* way to ever learn what `C` is is from a successful match's own bindings.

**The actual mechanism: `Infer::match_impl(algebra, query: &[Ty], commit: bool)`**, checking a whole *tuple* of query types together, positionally, against `Registry::all_impls` (every impl of an algebra — single- or multi-target, generic or fully concrete alike), in one shared trial `Subst`. `infer_algebra_call` first partitions the algebra's own generics into **input-determined** (free in at least one parameter — `A`, `B`) and **output-only** (`C`): only the input generics gate readiness, exactly the fix (1) above needed. Once every input generic is concrete, dispatch runs against the **full** tuple (input types concrete, output types still bare vars) — real unification against the matched impl's own target pattern binds the output generic(s) as a natural side effect of unifying, not a special case.

`commit` is what distinguishes this from an ordinary existence probe: `has_matching_impl` (used for bound-checking, `T: Ring`-style) never wants to commit to *which* impl matched, only *whether* one does — a failed candidate must never leave partial bindings behind for the next one to trip over. Real dispatch is different: once a match succeeds, its bindings need to become real (that's the only way `C` ever gets resolved), and this is sound specifically *because* `check_no_overlapping_impls` (below) already guarantees at most one impl's target pattern can ever coherently match one query tuple — there's no "arbitrary pick among several" the way an uncommitted probe has to stay neutral about.

```
struct Matrix<T : Float, const R : i32, const C : i32> { values : [T; R, C] }

impl<T: Float, const N: i32, const M: i32, const K: i32>
    MatMul<Matrix<T,N,M>, Matrix<T,M,K>, Matrix<T,N,K>> {
    fn mul(a, b) { /* ... */ }
}

fn f() {
    let a = Matrix::<f32,2,3>(values: [...]);
    let b = Matrix::<f32,3,5>(values: [...]);
    let c = a * b;  // Matrix<f32, 2, 5> -- N and K each come from a different operand, M cancels
}
```

`a * b`'s result correctly infers `Matrix<f32, 2, 5>` — `2` from `a`'s own `N`, `5` from `b`'s own `K`, and `3` (the shared `M`) appearing in neither. Calling it with a mismatched middle dimension (`Matrix<f32,2,3> * Matrix<f32,4,5>`) is correctly rejected, reporting the still-unresolved output type honestly (`no impl MatMul<Matrix<f32, 2, 3>, Matrix<f32, 4, 5>, 't43>`) rather than hiding it.

**`check_no_overlapping_impls` had to grow the same way.** Two impls overlap only if *every* target position could coincide simultaneously, in one shared trial substitution — checking each position independently would miss a real overlap where, say, the first two targets structurally coincide but the check never notices because it's comparing them to a *different* trial run for the third.

### A *deferred* dispatch needs the same "whole tuple together" treatment the ready path already got

The fix above (`match_impl` checking a whole tuple positionally, in one shared trial) only ever covers the **ready** case — every input generic already concrete, dispatch runs immediately. A call whose own generics are still abstract at the point it's inferred (any use *inside* a still-generic function or impl method) takes a different path entirely: `infer_algebra_call`'s "defer" branches, which — until this was found and fixed — pushed **one `Constraint` per generic**, independently: `for ty in resolved_generics { self.constraints.push(Constraint { algebra, ty, span }) }`. For a single-generic algebra (`Ring<T>`, this document's own worked examples throughout) "per generic" *is* the whole check, so this never showed a problem. `MatMul<A,B,C>` was the first multi-generic algebra ever called from a context that had to defer — deferring `A`, `B`, `C` as three *independent* constraints, each later checked alone via `check_pending_constraints` → `has_matching_impl(algebra, one type)`, can never verify a *combined* impl like `MatMul<f32,f32,f32>` exists: checking `f32` alone against a target list of three can't structurally match a 3-target impl at all. Found by direct testing, building a dedicated `examples/matmul.cleave` with a real, loop-based body (rather than the stub bodies used everywhere else in this project) — its own element-wise scalar multiply, `a.values[i,k] * b.values[k,j]`, dispatches to `MatMul` too (the *same* algebra, a second, concrete `impl MatMul<f32,f32,f32>`), and — since both operands are still `T`, abstract at the enclosing generic impl's own declaration time — has to defer. It was flatly rejected, `no impl MatMul<f32>`, despite the concrete impl existing right there in the same program.

**The fix generalizes `Constraint` itself** — `ty: Ty` becomes `tys: Vec<Ty>` — so a deferred, multi-generic dispatch can carry its whole tuple as *one* constraint, checked together later by the same `match_impl` engine the ready path already trusts, instead of being flattened into independent single-type constraints at the moment it's pushed. An ordinary single-generic bound/shape check (`Int`/`Num`/`Float` from a numeral, `for`, `Index`, a generic's own declared `bounds`) becomes `tys: vec![ty]` — no behavior change, just the same shape a multi-generic algebra also needs. `has_matching_impl`/`has_matching_impl_inherited` generalize the identical way (`ty: &Ty` → `tys: &[Ty]`) — their one remaining genuinely single-type caller, a type parameter's own declared bound inside `match_impl` itself, passes a one-element slice, since a single parameter's own bound is always naturally one type regardless of how many generics the *enclosing* algebra declares. `generalize`/`constraints_touching`/`instantiate_with_mapping` all thread the *whole* tuple through their existing sweeps rather than a single type, mirroring exactly what they already did — `check_pending_constraints` resolves every type in the tuple, skips the constraint if any element is still abstract or a placeholder (same "not everything is known yet" posture the ready path's own gating already has), and otherwise checks the whole resolved tuple against `has_matching_impl` in one call, joining it with `", "` for the error message exactly the way the ready path's own failure message already does.

This is the fully general fix the ready-path fix's own comment had already anticipated needing eventually ("that would need a multi-`Ty` `Constraint` variant this increment doesn't add") — any future multi-generic algebra gets correct deferred-checking for free, not a special case for `MatMul` alone.

## `impl` methods are checked against their algebra's own signature

Found missing by hand, not designed up front: `infer_fn` alone has no notion of "this function happens to be inside an `impl <algebra><target>` block" — it infers a `FnDecl` in total isolation, exactly as documented. That's fine for a top-level `fn`, but for an `impl`'s own method it's a real gap: `impl TestAlg<i32> { fn add(x, y) { x + y } }`, with no annotations at all, used to infer `x`/`y` as bare, mutually-disconnected type variables — nothing tied them to `i32`, even though the enclosing `impl` unambiguously determines them via `TestAlg`'s own declared signature.

`Infer::infer_impl_fn(algebra, target, f, fallback_span)` is the real fix, not a patch: it treats the algebra's declaration as the *single source of truth* for what an `impl` method's shape must be.

- The algebra's own generic parameter is bound directly to the impl's target type (`T` becomes literally `i32` throughout, via the same `ty_from_ast_mapped` substitution `infer_algebra_call` already uses for the reverse direction — resolving a *call*).
- An unannotated parameter is seeded with what the algebra expects (mapped) — not a fresh, disconnected variable.
- An annotated parameter is *checked* against what the algebra expects, never trusted as an independent second truth: `impl TestAlg<i32> { fn add(x: f64, y: f64) -> f64 { x } }` is now rejected, a mismatch between what's written and what the algebra requires for this target.
- The same holds for the return type, and arity is checked too.
- An `impl` method whose name the algebra never declared at all (`TypeErrorKind::NotDeclaredByAlgebra`) is now caught — nothing did before; a method was only ever resolved by name at *call* sites, never checked against its own algebra's declared shape.

Whether to annotate an `impl` method's parameters at all is now genuinely optional — the algebra's declaration is authoritative either way, matching the same "don't repeat a fact that could silently drift from its one real source" instinct that shaped the rest of this project.

`FnDecl` itself still carries no `Span` (only the enclosing `Item` does — see `ast.rs`) — `fallback_span` (the caller-supplied enclosing `impl` `Item`'s own span) is what a whole-signature problem (wrong arity, an undeclared name) points at, since there's nothing more precise available for those specific cases.

## Inherent impls: methods with no algebra behind them at all

Not every method belongs to an operator-dispatch story (`v.len_sq()` has no business being resolved through an `algebra`/candidate-search mechanism the way `add`/`sub` are) — `impl struct Vec2 { fn len_sq(v) { ... } }` (see `grammar.md`, "Inherent impls", for why the literal `struct` keyword is there) is a much simpler case: exactly one method per `(struct, name)` pair, no overloading, no candidate search, no `AmbiguousOperator` to worry about — `Registry::inherent_method` is a plain, total lookup.

**`ExprKind::MethodCall` dispatch (`v.len_sq()`)** resolves `v`'s own type, extracts the struct name (`Ty::Con`/`Ty::App`), looks up the one matching entry, and — the one piece of real machinery here — treats `v` as filling the method's **first positional parameter**, explicit, no magic `self`. An unannotated first parameter defaults to the impl's own target type, mirroring exactly how an unannotated algebra-impl parameter already falls back to that algebra's declared signature (see above) — the closest equivalent an inherent impl has, since there's no separate signature to fall back to.

**A second-order bug, found only once generic structs were involved, worth recording as its own thing:** `Boxed<T>.get() -> T` was coming back as a bare, unconstrained variable instead of the concrete type `b` actually had. The call site was building `param_tys[0]` (what `b`'s value gets checked against) as a *disconnected* fresh variable rather than one derived from the impl's own `impl_mapping` — unifying it against `b`'s resolved type bound *that* variable correctly, but never fed anything back into `impl_mapping["T"]`, a completely different variable that `get`'s declared return type (`T`) actually resolves through. Fixed by building `target_ty` — and therefore `param_tys[0]` — *from* `impl_mapping` in the first place, so unifying it against the receiver directly pins the impl's own generic. The identical bug, and the identical fix, existed independently on the *declaration* side (`infer_inherent_impl_fn_generic`) — the two code paths build their own `param_tys` completely separately and needed the fix twice.

**Method-call return type, when the method has no `->` annotation, stays an honest placeholder — dispatch never re-runs the callee's own body.** Unlike an algebra call (a real declared signature, return type included, always available) or a top-level `fn` call (inferred once by the whole-program pass, then generalized — see below), `v.len_sq()` has nowhere else to look if `len_sq` never wrote down what it returns; defaulting that to `()` would be silently *wrong*, not just imprecise, so it defers as `<not-yet-inferred>` instead, the same posture every other genuinely-unresolved case in this file takes.

### Self-recursion, and the narrower gap that's left

**A self-recursive inherent method used to fail outright, not silently — found by direct testing.** `fn countdown(w) { if w.n == 0 { 0 } else { w.countdown() } }` (unannotated) rejected with `type could not be fully determined (<not-yet-inferred>)`, even though the exact same shape written as a top-level `fn` infers fine. The reason is structural, not incidental: a top-level `fn`'s self-recursion resolves because `infer_fn` seeds its own name into `env` before inferring its body (see "Self-recursion" above) — but a recursive `w.countdown()` call goes through `ExprKind::MethodCall`'s own dispatch, which never consults `env` for its callee at all. Algebra-impl methods never hit this: a recursive call inside one (`impl Ring<i32> { fn add(a,b) { ... add(a-1,b) ... } }`) goes through ordinary operator dispatch, which is signature-driven (the algebra's own declared `fn_sig`) and genuinely doesn't care whether the callee's body has finished being inferred — only an inherent method, with no externally-declared signature to fall back to, was actually exposed.

Fixed with `Infer::in_progress_methods: HashMap<(String, String), (Vec<Ty>, Ty)>` — the impl-method equivalent of `infer_fn`'s own seeded self-placeholder. `infer_inherent_impl_fn_generic` registers `(struct, method) -> (param_tys, ret_var)` under this key *before* inferring its own body, and removes it afterward; `ExprKind::MethodCall`'s dispatch checks this map *first*, before the registry's static, declared-signature lookup — a hit reuses the enclosing invocation's own already-resolved param types and return-type placeholder directly, rather than re-deriving a fresh instantiation. `countdown`'s own declaration now correctly infers `-> i32`.

**What this does *not* close, stated plainly rather than smoothed over:** a call to a *different*, separately-declared, similarly-unannotated inherent method — genuine mutual recursion between two methods, neither of which is the one currently having its own body inferred — still falls through to the placeholder. `in_progress_methods` only ever has an entry for whichever *one* method is presently mid-inference; it doesn't build a call graph the way `callgraph.rs` does for top-level `fn`s. Closing that fully would mean giving inherent methods the same whole-program, generalize-once treatment top-level `fn`s already get (a second SCC-grouped pass, or a unified graph spanning both namespaces) — a substantially bigger change than this fix, not attempted.

**Also still open, unrelated to recursion at all:** an *external* caller of an unannotated inherent method (a different function entirely, not a recursive call from inside the method itself) still only ever sees the placeholder. `dump.rs` infers every top-level `fn` (via `callgraph.rs`) *before* it ever touches an inherent impl's own body, so even after the self-recursion fix above, nothing propagates a method's real, inferred return type *out* to some other caller — only a call from *inside* the method's own body (the recursive case) benefits. An explicit `->` annotation sidesteps this entirely and is the recommended style for any inherent method whose return type another function actually depends on.

## Placeholders must never become a silently "successful" answer

A second gap found by hand, this time by actually running the CLI on a real file rather than by inspection: `fn main() { let f = fn(x) { x + 1 }; f(1) }`, with no `Ring` algebra registered anywhere, used to type-check *successfully* — `main`'s own reported type came back as `Con("<unresolved-call:add>")`, no error at all. A placeholder (`is_placeholder`/`find_placeholder_name` — `<unresolved-call:...>`, `<not-yet-inferred>`, and friends) is explicitly "we don't know", generated in a handful of documented, deliberately-non-fatal spots (an operator with zero candidate algebras, a call to a cross-function `fn`, field access, ...) so the *rest* of a function can still be checked even when one part of it can't yet. Letting that placeholder flow all the way out to become the function's own *reported, apparently-successful* type was never actually intended — it just wasn't checked for.

`infer_fn`/`infer_impl_fn` now both finish by checking whether the fully-resolved return type or any parameter type still contains a placeholder anywhere within it (recursing into `Ty::Fn`, so `(t) -> <unresolved-call:add>` is caught exactly like a bare placeholder would be) — if so, that's `TypeErrorKind::Unresolved`, not a quiet success. The check happens once, at the very end, after every other unification has had a chance to resolve or reject things — a placeholder that gets overridden by a genuine conflict earlier (an ordinary `Unify` mismatch) was already being caught before this existed; this only adds a safety net for what nothing else was catching.

## Qualified types: constraints, generated, checked, and propagated

This is the actual "HM + qualified types" extension (Mark Jones' *Theory of Qualified Types*) that the rest of the design had been pointing at since the type-inference discussion began — the mechanism that lets `fn add(a, b) { a + b }` infer `T: Ring` from nothing but how `a`/`b` are used, with zero annotation and no special-casing of `add` itself.

A `Constraint { algebra, ty, span }` means "`ty` must implement `algebra`". Two places generate one:

1. **A number literal's own type variable** always gets a `Num` constraint alongside the existing defaulting entry (`fn f() { 1 }` pushes both a `pending_defaults` entry *and* a `Constraint{algebra: "Num", ...}` on the same variable).
2. **`infer_algebra_call`**, for any parameter type that's still abstract once its own arguments are unified against the algebra's signature.

A constraint doesn't resolve itself on the spot — three things can happen to it:

- If its type is already concrete, it can be checked immediately (this is what `infer_algebra_call` still does eagerly when possible — best error locality, pointing straight at the call).
- Otherwise it sits in `Infer::constraints` (a flat pending list) until something resolves it.
- At the end of `infer_fn`, after literal defaulting, `check_pending_constraints` sweeps whatever's left: if a constraint's type has since become concrete (through *any* later unification, not just the one at its origin), it's checked then; if the constraint names an algebra the registry has never heard of at all (`"Num"` with no stdlib loaded — most programs today), the check is skipped outright, same reasoning as the zero-candidate operator fallback: nothing to check against isn't the same as a check that failed.

The part that makes this genuinely *qualified* types rather than just "constraints that happen to get checked eventually": `generalize` sweeps `Infer::constraints` at the same time it computes free type variables. Any pending constraint whose type mentions a variable being quantified travels *into that binding's own `Scheme`* rather than staying in the flat pending list — so `Scheme` is really `∀vars. constraints ⇒ ty`, not a bare `∀vars. ty`. `instantiate` renames a scheme's constraints by the same fresh-variable mapping it uses for the type itself and re-queues them in `Infer::constraints`, exactly as if freshly generated at that call site — each instantiation gets its own independent copy of the constraint, checked or propagated on its own.

Worked example:

```
fn f() { let g = fn(x) { x + x }; g(true) }
```

Assume `algebra Ring<T> { fn add(a: T, b: T) -> T; }` is declared with only `impl Ring<i32>`. Inside the lambda, `x + x` resolves against `Ring` (exactly one candidate), and since `x`'s own type variable is still abstract at that point, a `Constraint{algebra: "Ring", ty: <x's variable>}` is generated instead of being checked on the spot. `let g = ...` generalizes the lambda — `x`'s variable is quantified, and the pending `Ring` constraint travels with it into `g`'s scheme: `∀t. t: Ring ⇒ (t) → t`. Calling `g(true)` instantiates a fresh copy of both the type variable *and* the constraint, unifies the fresh variable with `bool`, and by the time `infer_fn` finishes, `check_pending_constraints` finds that variable now resolves to `Con("bool")` — checks `Ring<bool>` against the registry, finds no `impl`, and rejects it with `MissingImpl { algebra: "Ring", ty: "bool" }`.

The same mechanism closes the literal gap that motivated this whole extension — though removing the operator-resolution fallback (see above) already catches the *simplest* version of it on its own, worth being precise about which layer does what:

```
fn f(a: bool) -> bool { let x = 1; x + a }
```

With no algebra declaring `add` at all (most programs today), this is now an honest "unresolved call" — no membership check even needs to run, since operator resolution itself no longer has a permissive path for `add` to take. That alone is a real improvement over the old behavior (this used to silently type-check and infer `bool`), but it's not yet the qualified-types machinery doing anything — it's just `infer_call` refusing to guess.

`Num`'s own constraint earns its keep in a sharper case: suppose `algebra Ring<T> { fn add(a: T, b: T) -> T; }` is declared with an `impl Ring<bool>` (so `add` resolves fine and unifies `x` with `a`), *and* `algebra Num<T> {}` is declared with `impl Num<i32>` but no `impl Num<bool>`. `Ring<bool>` alone would happily accept this — nothing about `Ring`'s own shape says its operands must be "numeric" in any sense. `1`'s independent `Num` constraint is what still rejects it: it resolves to `bool` via the same unification `Ring` just approved, and `check_pending_constraints` catches what `Ring` structurally couldn't have — that a `bool` was fed into an expression built around what's supposed to be a numeral. Without a registered `Num` at all, this half is skipped (nothing to check against), same reasoning as the zero-candidate operator fallback.

## Algebra-bound inheritance: `algebra Int<T> : Num { ... }`

`AlgebraDecl::bounds` (see `grammar.md`, "Algebra bounds") was parsed and carried across `driver.rs`'s file merges for a long stretch with nothing anywhere actually consulting it — `stdlib/num/num.cleave` used to declare `Int`/`Float` as flat, independent marker algebras, each with their own full, separately-written set of `impl Num<...>` *and* `impl Int<...>`/`impl Float<...>` declarations, specifically *because* this gap existed; the doc comment there said so directly. It's real now.

**The semantics chosen: an impl of the narrower algebra counts as an impl of the wider one, at *use* sites — not "every impl of the narrower one must additionally have a matching impl of the wider one somewhere, checked at declaration time."** `impl Int<i32>` alone is sufficient; no separate `impl Num<i32>` needs to exist anywhere. This is Rust's own supertrait relationship (`trait Int: Num` means "anything implementing `Int` can be used wherever `Num` is required," derived automatically, not "you must also write a from-scratch `impl Num`") — chosen over a from-scratch-impl-required interpretation because the entire motivation was to let `stdlib/num/num.cleave` stop declaring `Num`'s own impls redundantly by hand, which only the "counts as" reading actually achieves.

**Where it lives, deliberately not in `Registry`:** `Registry::algebra_bounds`/`algebras_bounded_by` are pure data accessors (the forward and reverse lookup: which algebras a given one requires, and which algebras require a given one) — the actual check is `Infer::has_matching_impl_inherited`.

**Scoped deliberately to existence checks, not dispatch.** `dispatch_algebra_call`/`match_impl` (the machinery that resolves an actual operator *call* to a real, runnable impl) don't get this inheritance walk — only `has_matching_impl` does, which is what backs a generic bound (`T: Num`) and `check_pending_constraints`. The reasoning: `Num`/`Int`/`Float` are marker algebras with no methods at all (`algebra Num<T> {}`) — existence is the entire question. A *real* algebra with actual methods to dispatch (`Ring::add`) can't "borrow" an implementation from some other algebra it merely bounds itself on; the method body genuinely has to exist for *that* algebra specifically. Conflating the two would have let a bound relationship silently stand in for a missing, real implementation.

```
algebra Num<T> {}
algebra Int<T> : Num {}
impl Int<i32> {}

fn f<T: Num>(x: T) -> T { x }
f(5:i32)   // accepted -- Int<i32> alone satisfies the Num bound
```

### Two directions, not one — and why the second one needed a guard

`algebra X : Y` doesn't say which side ends up with the real, concrete `impl` — either can, and both turned out to be needed, found by a direct follow-up conversation about whether a `Ring` should be built from two separate `Monoid`-shaped pieces (one for `+`, one for `*`) rather than declaring `add`/`mul`/`neg` in one monolithic algebra:

- **Reverse witness** (the case above): a *more specific* algebra that itself bounds on `Y` has a real impl. `impl Int<i32>`, with no separate `impl Num<i32>`, still satisfies a `Num` bound.
- **Forward aggregate**: `X` itself bounds on two or more other algebras, and *every one* of them is independently satisfied — `impl AdditiveMonoid<i32>` and `impl MultiplicativeMonoid<i32>` together satisfy `algebra Semiring<T> : AdditiveMonoid + MultiplicativeMonoid {}`, with no separate (even empty) `impl Semiring<i32>` anywhere. The mirror image of the reverse case: there the concrete impl sits on the more-specific side, here it sits on the more-general side(s).

**Gated on *two or more* bounds specifically, not "any non-empty bound list" — a real regression, found by testing the naive version immediately after it landed.** `Int<T> : Num` and `Float<T> : Num` are *siblings*, each with a single bound on the same parent. A version that aggregated through any non-empty bound list let `i8` (a real `Int`) also satisfy a `Float` query: checking `Float<i8>` asked "is `Num<i8>` satisfied", which is true — via `Int`, not `Float` — and a single-bound aggregate had no way to tell those apart, since it just re-asks the same question the reverse-witness direction already answers when checking the *parent* directly. A single bound is a rename/specialization relationship, already fully covered by the reverse direction; it never legitimately needs a forward direction of its own. Two or more bounds is different in kind: no single sibling can accidentally satisfy a multi-ingredient conjunction the way one sibling can satisfy a shared single parent.

A shared `visited: HashSet<String>` guard, threaded through *both* directions of the same recursive walk, still prevents a cyclic bound declaration from looping forever — including a cycle that mixes both directions (a reverse hop into something whose own forward-aggregate check circles back).

## Whole-program inference over top-level `fn`s (`callgraph.rs`)

The motivating example, found by actually running the CLI: `fibonacci` calling itself always fell through to the `<unresolved-call:fibonacci>` placeholder — not because self-recursion is conceptually hard, but because `infer_fn` builds `env` from nothing but `f.params`, and a top-level `fn`'s own name was never in it while its own body was being inferred. Scaling that up, arbitrary mutual recursion between two or more separately-declared `fn`s (in either declaration order) needed a real answer, "de façon définitive" — not a further-deferred gap.

### The shape actually built, and why it isn't quite the shape first sketched

The first design sketched in conversation was a single, fully lazy recursive walk: when inference hits a call to some other top-level `fn`, recurse *right there* into inferring that callee, memoized by name in a table of `nom -> EnCours(index, low_link) | Fini(scheme)`, with Tarjan's cycle-detection bookkeeping (index/low-link/stack) fused directly into that same recursion — no separate graph-construction pass at all.

That exact shape doesn't survive Rust's ownership rules unchanged. The recursive trigger would have to fire from *inside* `infer_call`, which only ever holds `&mut self` on the *one* `Infer` currently inferring the current function's body — there's no way for it to also reach back into an external table of *other* functions' in-progress state without threading that state through every single inference method (`infer_expr`, `infer_block`, ... — all of them, since a call can be arbitrarily deeply nested) just to serve this one caller.

What's built instead keeps the substance and only changes *when* the graph is known:

1. **A cheap, type-free scan** (`collect_calls_block`/`collect_calls_expr`) walks each function's own body collecting which *other* known top-level `fn` names it references — as a call, or as a bare value (`ExprKind::Path`, e.g. passing a function by name without calling it — still a genuine type-dependency edge). No inference happens here at all; this may harmlessly over-approximate the real call graph (a name shadowed by a local `let` would still register as an edge), which only ever costs a slightly-too-large group being generalized slightly later than the ideal — never an incorrect grouping.
2. **Tarjan's SCC algorithm** (`Tarjan::run`), an ordinary, self-contained graph algorithm with no `Infer` involved, runs over that static graph. It determines both which functions are mutually recursive and the processing order — which, for a DFS following call edges, is always "callee's group before caller's group": a group can only be popped once every function it calls has itself already been assigned to some group.
3. **The real type inference** is still one mechanism, run once per group: `Infer::infer_fn_raw` (see below), memoized in the sense that matters — a group is inferred exactly once, and every later caller only ever sees its *finished*, generalized `Scheme`.

The grouping is worked out first rather than interleaved with inference; the inference itself is still the same recursive-shaped core the original sketch called for.

### One shared `Infer` per group; a growing `global_env` between groups

Two mutually-recursive functions can end up sharing type variables *through* their calls to each other (`is_even`/`is_odd`, each calling the other with the other's own decremented parameter) even though they start out as textually separate `Param` bindings — unifying those variables together requires one shared `Subst`, so every member of one strongly-connected group is inferred with the *same* `Infer` instance. Only *between* groups does the boundary become "just a finished `Scheme` crosses over, a fresh instantiation at every use" — the same boundary `let` generalization already relies on. `global_env: Env` accumulates one `Scheme` per finished top-level `fn`, grown monotonically as groups are processed in Tarjan's callee-before-caller order — so by the time a group is processed, every function it calls (outside its own group) already has a real, usable scheme sitting in `global_env`.

Each group's members are seeded *before* any of their bodies are inferred: `Infer::fresh_fn_shape` computes a function's parameter types (annotated → concrete, else fresh) and a fresh return-type variable, and every member of the group gets a monomorphic placeholder `Scheme` for its own name inserted into a shared `group_env` (`global_env` plus this group's own siblings) — visible to every other member (mutual recursion) and to itself (self-recursion), before `Infer::infer_fn_raw` (the body-inference core factored out of `infer_fn`, stopping short of defaulting/constraint-checking — see next) is called for each one in turn.

### Defaulting and constraint-checking run once per *group*, not once per member

An earlier draft of this called `infer_fn`'s full sequence (raw inference, then immediately default/check-constraints) for each group member in turn. That's a real bug, not just an inefficiency: `apply_defaults`/`check_pending_constraints` consult `self.pending_defaults`/`self.constraints`, which for a mutually-recursive group are only *complete* once every member's body has been walked. Running them after just the first member can default a numeric literal, or check a constraint, before a still-pending sibling has contributed everything it might additionally unify against that same shared variable. The fix: `infer_fn_raw` runs for every member first (raw, no defaulting/constraint-check at all), *then* the defaulting/constraint/placeholder-check sequence runs exactly once, for the whole group together — mirroring how a single function's own `finish_fn` already only defaults/checks once its *entire* body has been walked, just scaled up to "entire group" instead of "entire function".

### Top-level `fn`s are generalized too — found by testing, in the wrong order at first

Once a group's raw inference is done, every successfully-inferred member is generalized — the same `Infer::generalize` a `let` already uses, called against `global_env` (schemes finished by *earlier* groups), deliberately *not* against the group's own `group_env` (which still holds this group's own siblings as monomorphic placeholders — counting those as "free in the environment" would wrongly block generalizing a variable two siblings still genuinely share). This is the actual payoff of treating top-level `fn`s this way: `fn identity(x) { x }` becomes usable at `i32` by one caller and `f64` by another, exactly like a generalized `let`-bound lambda already was — top-level functions are `let`-polymorphic too, not a second, weaker kind of binding.

Getting the *order* right took a real bug and a test to catch it, worth recording exactly like the earlier "excluding a literal's variable from generalization" mistake this document already tells the story of. The first version called `generalize` *after* `apply_defaults`/`check_pending_constraints` for the group. That's backwards: `apply_defaults` permanently binds any still-bare type variable in `self.subst` the instant it runs, including one that would otherwise have been quantified — so `fn add_one(x) { x + 1 }`, processed alone in its own singleton group with nothing yet forcing `x` concrete, got silently defaulted straight to `i32` and permanently monomorphized *before* `generalize` ever got a chance to see its variable as free. A later caller needing `add_one` at `f64` then failed to unify, exactly the `num_traits::One`-style friction this project isn't supposed to have. Caught by a test built specifically to exercise cross-type reuse of a generalizable top-level function (`a_generalizable_top_level_function_is_not_defaulted_before_it_can_generalize`, `cleave/tests/callgraph.rs`), not by inspection. The fix: `generalize` runs for every parameterized member *before* `apply_defaults`/`check_pending_constraints` run for the group — mirroring, once again, how a `let`'s own `generalize` call always happens during body inference, strictly before `finish_fn`'s defaulting.

### Nullary functions are never generalized — the Monomorphism Restriction

A **nullary** (zero-parameter) top-level `fn` is deliberately *not* generalized at all, regardless of what its body looks like. This is Haskell's Monomorphism Restriction, adopted for the same reason it exists there: a binding with no parameters can't accept any caller-supplied type information at its call sites the way a parameterized one can, so "generalizing" it would only mean silently recomputing a fresh, possibly differently-defaulted result at every use — surprising, and pointless for something that takes no input to begin with. It also keeps `main` itself (always nullary) reporting a concrete signature rather than a spuriously "generic" one. `fn one() { 1 }` reports `() -> i32`, defaulted directly, never `() -> 't0`.

### A generalized variable must never be defaulted — including inside its own body's `node_types`

An earlier version of this pass let `apply_defaults` bind *any* still-bare variable it found in `self.pending_defaults`, generalized or not — reasoning (recorded here even though it turned out wrong, since the failure mode is worth remembering) that this was harmless: `instantiate` substitutes over a `Scheme`'s frozen `ty` tree directly and never consults `self.subst` for the scheme's own quantified variables, so a *future caller* instantiating `fibonacci` was never at risk. What that reasoning missed: `node_types` (what `--dump-inference-pass` renders for a function's own body) is read through `self.subst` too — so `fibonacci`'s own body showed `x:i32` throughout (an arbitrary default — none of its own internal literals happen to have a `.`) while its own signature, read *before* defaulting, correctly showed `(x: 't6) -> 't6`. Same variable, two contradictory answers depending only on *when* it was read. Reported directly, with the exact repro: `fibonacci`, generic over `TestAlg`, `impl`'d for both `i32` and `f32`, called as `fibonacci(42.0)` — the call correctly resolved to `f32` with no error (proving `fibonacci` genuinely was polymorphic), while its own dumped body insisted `x` was `i32`, making it look like the very call that had just succeeded shouldn't have been possible.

Fixed with `Infer::quantified: HashSet<TyVar>` — every variable `generalize` ever quantifies is recorded there, and `apply_defaults` refuses to bind one. Two levels of subtlety in getting this actually right, both found by testing rather than by reasoning it through up front:

1. **Ordering**: `generalize` must run *before* `apply_defaults` for a given variable to ever end up in `quantified` in time — see "Top-level `fn`s are generalized too" above, the same ordering bug in a different guise.
2. **Resolve to the union-find root before checking membership.** `self.pending_defaults` stores a literal's *original* `TyVar` — by the time `apply_defaults` runs, that variable may have become a mere alias (`self.subst` chains it to some other, still-unbound variable) rather than the root `generalize` actually recorded. Checking `quantified.contains(&var)` against the raw, pre-resolution `var` let the guard miss exactly the case it existed for: `unify` (called right after, to actually bind the default) *also* resolves both sides through `subst` first, so it silently bound the real root anyway, regardless of what the membership check had just decided. The fix resolves `var` through `self.subst` first and checks `quantified` against *that* — `self.subst.apply(&Ty::Var(var))`, matched against `Ty::Var(root) | _`, either finding a variable still worth defaulting, or a `Ty::Con` that's already concrete through genuine unification (nothing to default at all, a case the old code's `matches!` check already handled correctly, just conflated with the membership check that didn't).

### Debug rendering: type variables get per-function letters, not raw indices

Separate from any of the correctness fixes above, but reported in the same breath ("`'t6` ... pas très informatif dans le debug") once the signature/body inconsistency above stopped hiding it: `--dump-inference-pass` used to print a still-open type variable as its raw internal index (`'t6`), which encodes nothing but allocation order within the whole compilation and carries no meaning to a reader. `dump.rs`'s `TyVarNames` now assigns short, stable, per-function letters the first time each variable is seen while rendering one function — standard ML/Haskell-style pretty-printing (`val id : 'a -> 'a`) — shared across that one function's signature *and* body, so the same variable gets the same letter everywhere (`fn fibonacci(x: 'a) -> 'a { ... x:'a ... }`). Two unrelated functions each reusing `'a` for their own first free variable is correct, not a collision — they really are independent. Purely a rendering concern — `Ty`'s own `Display` impl (used by ordinary `TypeError` messages elsewhere) is untouched, still raw `'t6`-style, out of scope for this pass.

With both fixed, `fibonacci`'s body now consistently shows `x:'t6` everywhere its signature does too — never a contradictory concrete default. This applies just as much to a plain `let`'s own generalization as to a top-level `fn`'s: `fn f() -> i32 { let x = 1; x }` now dumps `let x = 1:'t1; x:i32` — the `let` line correctly still-generic (nothing pins `x` to a *specific* number at that point), the tail correctly concrete (a *fresh* instantiation, independently pinned to `i32` by `f`'s own declared return type — a real unification, not a default).

### A nullary function's own returned type can still leak a real constraint — found the hard way

**A genuine soundness hole, not just an imprecision, found by testing a scenario the rest of this section's own careful design didn't anticipate.** Ordinary cross-function constraint propagation — a parameterized function's own pending constraint traveling into its `Scheme` via `generalize`, then re-queued fresh at every instantiation via `instantiate` (see "Qualified types" above) — turns out to already work correctly even for two- and three-hop chains and genuine mutual recursion between separately-declared functions, verified directly: `fn double(x) { add(x, x) } fn main() -> bool { double(true) }` correctly rejects with `no impl Ring<bool>`, and the same holds through an extra hop (`level2` calling `level1`) and through an actual mutually-recursive pair sharing the constraint only through unification (`f`/`g` calling each other, only `f` touching `add` directly). This machinery is solid.

**What actually broke: a *nullary* function returning a closure with a still-open constraint on it.**

```
fn make_adder() { fn(x) { add(x, x) } }
fn main() -> bool { let f = make_adder(); f(true) }
```

This used to type-check *successfully*, with no `impl Ring<bool>` anywhere. The reason is structural: a nullary top-level `fn` is never `generalize`d (Monomorphism Restriction, above) — it's inserted into `global_env` via a bare `Scheme::mono`, which by construction carries **zero constraints**. `make_adder`'s own `Ring` constraint on the lambda's parameter was genuinely still open (never pinned to anything concrete) at the point `make_adder`'s own group finished — `check_pending_constraints` correctly skipped it (still abstract, nothing to check yet, its own long-documented "real gap" case) — but since nothing carried it *forward* either, it simply vanished the moment that group's own `Infer` instance (and its `self.constraints`) was discarded. Each Tarjan group gets a *fresh* `Infer`, so the only thing that can survive across a group boundary at all is whatever got embedded in a `Scheme` — and an unquantified `Scheme::mono` embeds nothing.

Fixed with `Infer::constraints_touching(ty)` — every currently-pending constraint sharing a free variable with `ty`, copied (not removed, same reasoning as `generalize`'s own sweep — a shared variable must stay checkable from every type that exposes it). Unlike `generalize`'s own sweep, this doesn't filter by "free in `ty` but not in some enclosing environment" — nothing is being quantified here, just forwarded for a later caller to check once it pins the variable concrete. `callgraph.rs` now calls this for every nullary member, *before* `apply_defaults`/`check_pending_constraints` drain `self.constraints` for the group (matching the ordering the real `generalize` loop already needed to get right — see "Top-level `fn`s are generalized too" above), and attaches the captured constraints to the nullary member's own `Scheme` (still with an empty `vars`, still never fresh-instantiated per call — only the constraint list changes).

### `impl` methods: algebra dispatch is unaffected, inherent methods now share a block-level pass

`algebra`-impl methods dispatch through the registry (`infer_call` → `infer_algebra_call`), not by bare name lookup in `env` — so a recursive or mutually-recursive *algebra*-impl-method call "resolves" already, in the sense that dispatch is entirely signature-driven and never needs the callee's own body to have finished. `callgraph.rs` itself still doesn't touch `impl` methods at all — `dump.rs` still infers each algebra-impl method independently, one at a time, exactly as before this pass existed.

**Inherent methods are different now.** `Infer::in_progress_methods` (a single self-only slot — see "Inherent impls: methods with no algebra at all" above) closed self-recursion, but structurally couldn't reach genuine mutual recursion between two *separately-declared* methods on the same struct — `is_even`/`is_odd`-as-methods, neither one self-recursive, each calling the other:

```
impl struct Wrap {
    fn dec(w) -> Wrap { Wrap(n: w.n - 1) }
    fn is_even(w) {
        if w.n == 0 { true } else { w.dec().is_odd() }
    }
    fn is_odd(w) {
        if w.n == 0 { false } else { w.dec().is_even() }
    }
}
```

Before the fix, each method was inferred with its own fresh `Infer` (`dump.rs`'s own per-method loop) — a recursive call to the *other* method, still mid-inference in a completely different `Infer` instance, always deferred to `<not-yet-inferred>`, which then failed to unify with the `if`'s other branch. Both `is_even` and `is_odd` were rejected outright.

**`Infer::infer_inherent_impl_block`** fixes this by giving one impl block's *entire* set of methods the same treatment `callgraph::infer_program` already gives a mutually-recursive group of top-level `fn`s: one shared `Infer`/`Subst`, every member's placeholder seeded into `in_progress_methods` *before* any body is inferred (so every method is visible to every other, and to itself), bodies inferred raw (`infer_inherent_impl_fn_raw`, factored out of the existing single-method path), then `apply_defaults`/`check_pending_constraints`/`check_no_placeholder` run once for the whole block — the identical "once per group, not once per member" reasoning `callgraph.rs` already established, for the identical reason (draining `self.constraints`/`self.pending_defaults` per-method would check a still-pending sibling's contribution too early). `dump.rs` was restructured to match: one `Infer::infer_inherent_impl_block` call per impl block, not one `Infer::new` per method.

Unlike `callgraph.rs`, this doesn't build a real call graph or run Tarjan's algorithm — there's no *generalization* to order correctly here (an inherent method's own generics are re-instantiated fresh at every call site via `impl_mapping`, dispatch-style, never through a reusable `Scheme`), so simply seeding every member up front and inferring the whole block together is already correct; no ordering concern to resolve, unlike the top-level case.

**What still doesn't work, stated plainly:** an inherent method's real inferred return type still isn't visible to an *external* caller (a different function, not a recursive call from inside the impl block) when the method has no `->` annotation — `dump.rs` infers every top-level `fn` (via `callgraph.rs`) *before* it ever touches an inherent impl block, so nothing propagates a method's real, block-internal return type *out* to an unrelated caller. `main` calling `w.is_even()` (from the example above, still unannotated) still sees the placeholder; adding `-> bool` to both `is_even`/`is_odd` closes it, since the registry's own static signature then answers the call site directly, without needing the method's own body at all. Closing this without the annotation would need exposing each block's inferred results somewhere `ExprKind::MethodCall`'s dispatch can consult across impl blocks — not attempted here, since it wasn't the actual problem (mutual recursion) this increment was scoped to.

## Monomorphization (`monomorphize.rs`)

`callgraph.rs` produces real HM polymorphism for top-level `fn`s — `fn identity(x) { x }` generalizes to `∀t. t -> t`, reusable at `i32` by one caller and `f64` by another — but a genuinely polymorphic term isn't something an eventual backend (CPS/e-graph/MLIR) can accept directly; it needs every type fully concrete, no free type variables anywhere. `monomorphize.rs` closes that gap for top-level `fn`s: a worklist pass that generates one fully concrete specialization per instantiation actually reached from a concrete entry point, dumpable via `--dump-monomorphized`.

**No AST cloning needed.** `node_types: HashMap<NodeId, Ty>` is read as a parameter by every render function (`dump_block` etc.), never baked into the AST. A generic function's `Block` stays one shared, unmodified reference across every instantiation of it — each specialization just gets its own separate `node_types` map, built by substituting the *original* declaration's own (still-generic) node types through that instantiation's own `TyVar -> Ty` mapping. No fresh `NodeId`s, no deep-cloning `Expr`/`Block`/`Stmt` — a small realization that turned what looked like a large feature into a much more contained one.

**No `Infer`/`TyVarGen` instance needed either.** The hard part looked like it would be recovering *which* concrete types a call site instantiated a generic callee at — nothing records this today; `infer_call`'s own `instantiate_with_mapping` builds exactly this mapping and discards it on the spot. The fix: unify the callee's own `scheme.ty` (already `Ty::Fn(params, ret)`, using its own existing `TyVar`s directly — no fresh re-instantiation) against `Ty::Fn(arg_tys, ret_ty)` built from the *caller's* own already-concrete `node_types`, in a throwaway `Subst::default()` used once and discarded. Read `scheme.vars`' own resolved bindings back out of that throwaway `Subst`. Each call site gets its own fresh scratch `Subst` — no shared `TyVarGen`, so no risk from different top-level `fn`s' own `TyVar` ids numerically colliding (each `callgraph::infer_program` *group* mints its own fresh `Infer`, so raw `TyVar` ids are not globally unique across different functions in the first place — this is fine as long as a substitution mapping built from one function's own `Scheme` is only ever applied to that same function's own body, which the pass is careful to do).

This elegantly handles self- and mutual-recursion for free, with no special-casing: within one generic function's own body, a recursive/mutually-recursive call was already unified against the same monomorphic self-placeholder during that function's own declaration-time inference (`infer_fn_raw`) — so reverse-deriving its instantiation from `node_types` naturally recovers the *same* concrete type as the enclosing instantiation. Verified directly: `is_even`/`is_odd`, both generic (`algebra Ord`/`Ring`-bounded), each called once at a concrete type, produce exactly one specialization apiece — `is_even<i32>`, `is_odd<i32>` — each correctly typed `bool`, with no duplication and no infinite expansion.

**The worklist algorithm** (standard shape, the same one rustc/any monomorphizing compiler runs): seed from every function whose own scheme has `vars.is_empty()` (never generalized — nullary members, or a parameterized function with nothing left free) by scanning its already-concrete `node_types` for calls into a generic callee. Processing a work item `(name, concrete_tys)` — deduplicated by its own display string (`"identity<i32>"`, which doubles as the specialization's mangled name, avoiding needing `Ty: Hash`) — builds that instantiation's own substituted `node_types`, then re-scans *that* (now fully concrete) map for further calls into other generic callees, pushing new work items exactly as the seed step does. Terminates naturally for any program with a finite type-argument space; not specially guarded against pathological/unbounded generic growth, consistent with this project's existing posture elsewhere (a cheap guard is added where one was already needed — see the `has_matching_impl` cycle-guard — not preemptively everywhere).

**Now covers generic `algebra`-impl methods too, not just top-level `fn`s** — the same worklist, extended after a direct conversation established the two cases weren't as different as first assumed. The genuine, irreducible difference is the *front end*: a top-level `fn` call resolves via a direct name lookup (`env.get(name)` → one `Scheme`); an algebra-dispatched call (`a * b` → `mul(a, b)`) resolves via a *structural* search instead (`check_no_overlapping_impls` guarantees at most one impl can coherently match, but *finding* it means trying candidates). Once a candidate is found, the core algorithm — reverse-unify a pattern against a call site's concrete `node_types`, substitute the winning bindings through the body, recurse — is identical, shared by both worklists.

An impl's own "pattern" — since there's no stored `Scheme` for it — is built once per (impl, method), before either worklist runs, by calling `Infer::infer_impl_fn_generic_with_env` (the exact entry point `dump.rs` already uses for `--dump-inference-pass`) and reading back a new `Infer::target_types` field alongside the usual `param_types`/`node_types`. All three share the *same* fresh `impl_mapping`, which matters concretely: `MatMul`'s own `C` (appearing only in the impl's target, `Matrix<T,N,K>`, never in a parameter) would never get a binding at all if `target_types` used an independently-minted mapping — unifying `param_patterns` against a call's own concrete args wouldn't touch `C` in that case. `derive_impl_instantiation` accordingly reads back bindings for every free variable across `param_patterns`, `ret_pattern`, *and* `target_patterns` together, not just the parameters.

A non-generic impl (`impl Ring<i32>`) needs no specialization and renders its own real body unchanged, same as before. A generic impl's specializations are named by their own concrete *target tuple* (`"MatMul::mul<Matrix<f32, 2, 3>, Matrix<f32, 3, 5>, Matrix<f32, 2, 5>>"`), not by its internal generic names — a reader thinks about a `MatMul` call in terms of the shapes involved, not the impl's own `T`/`N`/`M`/`K`.

**A real, pre-existing bug this surfaced, worth recording.** The stub bodies used throughout this project's own examples/tests (`fn mul(a, b) { a }`, standing in for a real matmul implementation — see "Where cleave is today" in `user_guide.md`) declare a return type (`C`) they don't actually produce (they return `A`) — declaration-time inference silently unifies the two, merging `M` and `K` in the impl's own template. A *square* call (`M` happens to equal `K`) monomorphizes fine by coincidence; a genuinely *rectangular* one (cleave's own `examples/test.cleave`, `Matrix<f32,2,3> * Matrix<f32,3,5>`) hits a real unification conflict the moment monomorphization tries to match the (now wrongly `M=K`-merged) template against a concrete, non-square query — correctly reported as "no specialization found", not silently accepted with a wrong shape. Not a monomorphization bug: the type checker was already permissive about this at declaration time (nothing pins `M`/`K` apart when they're still abstract); monomorphization is simply the first thing that ever asks the impl to prove itself at a genuinely rectangular concrete shape. The real fix is a real (non-stub) matmul body, not anything in this pass.

**A concrete impl of a *multi*-target algebra needs the same structural, whole-tuple recognition a generic one gets — a single-type name lookup can't see it.** `derive_impl_instantiation` originally short-circuited "a concrete impl already covers this call, no specialization needed" via `Registry::has_impl_named(algebra, one_type.to_string())`, checked independently per argument/return type — correct for a single-generic algebra (`TestAlg<i32>`'s own registry key really is just `"i32"`), but silently wrong for a multi-target one: `Registry`'s own key for `impl MatMul<f32,f32,f32>` is the *concatenation* of all three targets (`"f32f32f32"`), never any individual `"f32"` alone, so the check never found it and every scalar dispatch inside the generic `Matrix` impl's own body was (once the fix above let it get this far) wrongly reported as needing a specialization that didn't structurally exist. Fixed by building an `ImplTemplate` for **every** impl now, concrete or generic (`build_impl_templates` no longer skips `d.generics.is_empty()`), reusing the exact same `infer_impl_fn_generic_with_env` call already proven correct for the generic case — a concrete impl's own `param_patterns`/`ret_pattern` come back fully resolved, no free variables at all. `ImplTemplate` gains `is_generic: bool`; `derive_impl_instantiation`'s existing per-template unification loop (already checking the whole parameter/return shape together, not one type at a time) now needs no separate short-circuit at all — a match against a *non*-generic template returns `NoCandidates` (ordinary dispatch already resolves it), exactly as if no template had ever been built for it.

**Still scoped short of generic *inherent*-impl methods.** `Registry::inherent_method` is already a direct, unambiguous lookup (no algebra-style candidate search needed — see "Inherent impls" above), structurally closer to the top-level-`fn` case than the algebra one — a smaller follow-up, not attempted this increment; nothing here reuses the algebra-matching machinery for it yet. `--dump-monomorphized` still renders inherent impls as bare markers.

**Call sites inside a specialization's own body show the mangled callee name** (`identity<i32>(x)`, not the ambiguous bare `identity(x)`) — added after direct feedback that seeing the un-mangled name made the output look like generics hadn't actually been eliminated. `dump.rs`'s `fmt_expr_typed`/`fmt_expr_list_typed`/`fmt_block_inline_typed` (mutually recursive, several call sites) each gained a `call_names: &HashMap<NodeId, String>` parameter — consulted only in the `Call` arm, overriding the literal callee path when a resolved mangled name exists for that specific node; `dump_block`'s own existing signature was kept exactly as-is (a thin wrapper passing an empty map) so every pre-existing `--dump-inference-pass` caller needed zero changes.

**This surfaced a real bug during testing, worth recording.** Every instantiation of the same generic `fn` shares the *same* body and therefore the *same* `NodeId`s (see the "no AST cloning" note above) — a self-recursive call site's `NodeId` is identical across `fibonacci<i32>` and `fibonacci<i64>`, needing to resolve to `"fibonacci<i32>"` in one specialization's own rendering and `"fibonacci<i64>"` in the other's. A first version kept one *shared*, global `NodeId -> mangled name` map across every specialization — whichever instantiation was processed *last* silently overwrote the other's own recursive-call resolution, so `fibonacci<i64>`'s own body rendered its recursive call as `fibonacci<i32>(...)`. Fixed by scoping `call_names` *per specialization* (a field on `Specialization`, built fresh during that one instantiation's own processing), exactly mirroring how `node_types` was already correctly scoped per-specialization from the start. A separate, always-safe *global* map (`seed_call_names`) still covers calls made from non-generic ("seed") functions like `main`, which are never re-processed under a different instantiation and so have nothing to collide over.

## What's still explicitly not done

Kept visible rather than smoothed over, matching how every other gap in this project has been tracked:

- **Mutability checking beyond gating generalization.** The environment is types only — nothing here checks that a plain (non-`mut`) `let` is never illegally reassigned; `mutable` is consulted only to decide whether to generalize.
- **Monomorphization for `impl` methods.** `monomorphize.rs` closes this for top-level `fn`s (a real worklist pass — self-, mutual-, and transitive-instantiation-aware — producing one fully concrete specialization per instantiation actually reached from a concrete entry point, `--dump-monomorphized`), but generic `algebra`/inherent-impl methods still have no equivalent: neither has a real, reusable `Scheme` the way a top-level `fn` does (each call site re-instantiates fresh via `impl_mapping`, dispatch-style), so the same worklist algorithm doesn't apply to them directly — a separate, larger follow-up.
- **An inherent method's real inferred return type reaching an *external* caller when unannotated.** Self- and mutual recursion *within* one impl block are both resolved now (`Infer::infer_inherent_impl_block`); a different function calling an unannotated inherent method still only sees the placeholder, since nothing propagates a block's own inferred results across impl-block boundaries. No notion of a method's own generalized, reusable `Scheme` the way a top-level `fn` has, either — each call site still re-instantiates fresh via `impl_mapping`, dispatch-style. See "`impl` methods: algebra dispatch is unaffected, inherent methods now share a block-level pass" above.
- **A self-recursive `let`-bound lambda** (`let g = fn(n) { g(n) };`) still isn't resolved — a lambda has no name to publish a placeholder under until it's already bound. Only top-level `fn`s (and, now, a self-recursive inherent method calling itself via `.method()`) get this treatment.
- **Calling a lambda *literal* directly** (`(fn(a, b) { a + b })(1, 2)`) isn't representable — `Call`'s callee is a `Path`, not an arbitrary expression (see `grammar.pest`'s `lambda_expr` note). Only a named binding holding a lambda can be called.
- **The circular-primitive-impl problem** (`impl TestAlg<i32> { fn add(x, y) { x + y } }`, genuinely circular at the operational level, no base case) isn't caught anywhere — not a type error, so type inference alone can't catch it; needs a dedicated static check, not built yet.
- **Const-generic algebra parameters** (`algebra Foo<const N: i32>`) are ignored when instantiating a declared *algebra* signature — only `GenericParam::Type` gets a fresh variable there; a `GenericParam::Const` mapping isn't attempted for an algebra's own generics (an ordinary `struct`'s or `impl`'s own const-generics, by contrast, are real — see "Generic structs" above; this gap is specifically about an *algebra declaration's* own const parameters).
- **A scheme's own constraint set isn't checked for satisfiability at generalization time**, only when something actually instantiates it. A mutually-recursive group whose members' literals disagree on shape (`Int t` *and* `Float t` on the same quantified `t`) generalizes without complaint if nothing ever calls into it — the impossible requirement only surfaces at the first real instantiation. Matches how dead code isn't otherwise checked for soundness here in general, but worth naming as its own gap rather than assuming it's covered by the `Int`/`Float` work above.
- **Complex literals** (`3+4i`) alone still return an explicit `<complex-not-yet-inferred>` placeholder — everything else that used to be in this bucket (field access, method calls, indexing, array literals, `while`/`for`, array *types*) now has real inference; see their own sections above.
- **Overlap checking is shape-only, not bound-satisfiability-aware.** `check_no_overlapping_impls` rejects two impls whose target *patterns* could structurally coincide, without asking whether their respective bounds (`T: Float` vs. `T: Ord2`) could ever really be satisfied by one shared concrete type — deliberately conservative (false positives possible in principle, never false negatives), not attempted otherwise since deciding real bound-satisfiability in general is a much harder problem than pattern matching.
- **Constant folding for a computed expression that's still abstract when written, only concrete later** (`[T; N+M]`, where `N`/`M` are const generics not yet pinned at declaration time). `const_eval.rs`/`const_value_from_expr` fold pure-literal arithmetic and bare const-generic references today; a *symbolic* deferred expression — re-evaluated once its own operands eventually resolve, at instantiation or monomorphization time — would need `Ty` itself to carry a small expression shape, not just a resolved `Const` leaf or an unresolved `Var`. See "Constant folding" above for exactly what's covered and why the deferred case is a separate, larger effort.
- **Indexed/field assignment (`arr[i] = v`, `s.field = v`) has no mutability check either**, same pre-existing gap the first bullet above already names for a bare `name = value` — `mutable` still only ever gates generalization.
