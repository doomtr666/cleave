## `examples/mnist-interop`'s own real training loop is ~12.7x slower wall-clock than an equivalent PyTorch-CPU/MKL baseline — several real causes ruled out with direct evidence, narrowed to one specific, disassembly-confirmed mechanism (the reduction accumulator round-trips through memory every `k`-step instead of staying register-resident), real fix not yet attempted

Raised directly, high priority — a real, existential concern for the project if this doesn't close: does cleave's own compiled training loop stand a chance against a mainstream, MKL-backed CPU baseline at all? Investigated with real rigor rather than a single top-line number, because several plausible-sounding hypotheses turned out to be wrong when actually tested, and it matters which ones are ruled out versus still open.

**The baseline, both sides measured under real, comparable conditions, not assumed.** A PyTorch-CPU reference (`bench/mnist-pytorch/mnist_bench.py`, poetry-isolated, CPU-only wheel) built to match `examples/mnist-interop/src/kernel.cleave` term for term — identical architecture (784→512→256→128→10, `He`/`Xavier` init formulas copied exactly from `nn.cleave`, zero-initialized biases matching `Ring::zero()` rather than `nn.Linear`'s own default), identical loss shape (`sum(err*err)` over the whole batch, not a mean, with `lr` scaled by the batch size at the same point `optim.cleave` does it), identical optimizer (hand-rolled plain SGD, not `torch.optim.SGD`'s own defaults, to guarantee no extra momentum/decay), identical hyperparameters (`epochs=10, lr=0.001, seed=1, batch=32`), identical unshuffled sequential batching, same dataset/mirror/cache as `data.rs` itself. Both measured with each framework's own real default multi-threading (PyTorch: 8 threads, its own default; cleave: `--openmp`, real and already the `cleave-build`/AOT default) — deliberately not restricted to one thread on either side, the fairest "best each side can do" comparison.

**Result**: PyTorch — 7.65s total (0.77s/epoch), 93.03% test accuracy. cleave (`--openmp`, real AOT `--emit-exe` build) — 96.89s total (9.69s/epoch), 93.42% test accuracy. **~12.7x slower**, with accuracy essentially identical (cleave slightly *higher*, within normal run-to-run PRNG noise) — confirms the gap is a real throughput difference on equivalent work, not cleave doing less computation or converging to a degenerate optimum.

**Hypothesis 1, tested directly, ruled out: scalar-per-element FFI data loading.** `load_train_batch_input`/`_target` (`kernel.cleave`) called `train_pixel`/`train_target` once per pixel/target-class — ~476M individual `extern fn` crossings over the full 10-epoch run, and (worse) an opaque call inside the loading loop's own body blocked MLIR from ever vectorizing the copy. Fixed with bulk, one-call-per-sample `extern fn`s (`data.rs::train_sample_pixels`/`train_sample_targets`, a single `copy_nonoverlapping` each, matching `format_f32`'s own `out: *mut u8` precedent) collapsing ~476M crossings to ~1.2M. **Measured result: 105.55s — no improvement, slightly worse.** Reverted (`git checkout` on `data.rs`/`kernel.cleave`) rather than keeping a proven-net-negative change. A VTune profile taken right after this test showed the compiled kernel's own main-thread CPU time (`train_and_evaluate`, 1142.65s of 2323.81s total CPU-seconds) is almost entirely *self* time in the real compute, not data loading (`data::init`: 0.013s, negligible) — data loading was never the bottleneck.

**The real per-core-vs-parallel-scaling breakdown, corrected after an intermediate arithmetic mistake.** A serial (`--no-openmp` build) run of the exact same kernel measured **333.1s** — cleave's own OpenMP gives a real **3.44x** speedup on this 8-physical-core machine (matching the user's own earlier VTune observation of "~3x scaling, with or without OpenMP" almost exactly), not the ~8x that would be ideal. Naively dividing the overall 12.7x gap by only cleave's own 3.44x parallel-scaling shortfall (as if PyTorch's own reported number were a serial-equivalent baseline) gives a misleading ~43-58x apparent single-core gap — wrong, because PyTorch's 0.77s/epoch is *itself* already an aggregate across its own 8 threads, not a serial number. Done properly (comparing real measured single-core cleave throughput, below, against PyTorch's own aggregate divided by its thread count), the true per-core gap is **~4.5-6x** — a real, modest, explicable shortfall (consistent with "vectorized but not register/cache-blocked" versus a hand-tuned MKL microkernel), not a mysterious one. The observed 12.7x overall gap is this ~4.5-6x per-core shortfall *compounding* with the ~43%-efficient (3.44 of 8x) OpenMP scaling — plausibly the same root cause manifesting twice (an unblocked kernel is both slower per core, spilling past whatever cache actually matters at this size, *and* scales worse across cores, contending over shared memory bandwidth), though this compounding-cause link itself isn't independently confirmed, just consistent with the numbers.

**Isolated single-matmul throughput, measured directly** (`bench/mnist-pytorch/probe_matmul_n1000.cleave`/`_n3000.cleave`, the exact slope between two iteration counts to cancel out fixed JIT/startup cost): **3.49ms/call, 7.37 GFLOP/s single-core**, for the kernel's own largest layer shape (`32x784 @ 784x512`).

**Hypothesis 2, cache/register tiling (`--affine-loop-tile`) — three real, distinct attempts on the real AOT pipeline, all regressed, each root-caused precisely rather than re-guessed blind:**
1. `cache-size=512` (MLIR's own automatic heuristic): confirmed via a minimal `mlir-opt` probe (`bench/mnist-pytorch/probe_matmul.mlir`, deleted after use) that it tiles *only* the innermost (`k`, reduction) dimension, to a tile size of 4 — `i`/`j` stay completely untiled, so the working `C` tile per `k`-step is still the entire `32x512` output — not real cache blocking, just three extra nested loops and per-iteration tile-bound `affine map` evaluation, pure overhead. **96.9s → 121.5s.**
2. `tile-sizes=8,64,128` (explicit, all three dimensions genuinely blocked, confirmed on the probe): tiling `i` (the batch dimension) shrinks the *trip count* `affine-parallelize{max-nested=1}` sees on its own outermost loop from 32 to 4 — confirmed directly on the probe (`affine.parallel (0) to (32) step (8)`) — at most 4 of this machine's 8 cores ever busy at once. **121.5s → 125.5s** (still worse).
3. `tile-sizes=1,64,128` (tile size *1* for `i`, a deliberately degenerate no-op tile preserving the full 32-iteration parallel loop, confirmed on the probe): preserves all 32-way parallelism, still genuinely blocks `j`/`k`. **124.5s — no better than attempt 2, still far worse than untiled.**

**Retested on a clean, isolated, single-core JIT probe with zero parallelization confound at all** (`--run` defaults OpenMP off) to settle whether tiling has *any* real per-core benefit independent of the parallelism interactions above: untiled baseline 3.488ms/call vs. tiled (`tile-sizes=1,32,64`, deliberately smaller/more L1-conservative than attempt 3) 3.555ms/call — **neutral to slightly negative even in the cleanest possible test.** Conclusion: `affine-loop-tile`, as tested across four real, distinct, reasoned parameter choices, does not help at this problem size on this machine — plausibly because `784x512` (1.5MB) already sits reasonably within L3 without blocking, and the tile-boundary bookkeeping (runtime `min`-clamped `affine map` evaluation per iteration, visible directly in the tiled loop dumps) outweighs whatever bandwidth saving remains. Not shipped — `pipeline.rs` reverted to its pre-investigation state (confirmed via `git diff`, clean).

**A real, controlled, confirmed compiler limitation found along the way — the `export fn`-Tensor-parameter case — but confirmed *not* to be what's hurting the real kernel.** Root-caused via direct MLIR source reading, not guessed: `affine-super-vectorize`'s own dependence analysis (`mlir/lib/Dialect/Affine/Analysis/LoopAnalysis.cpp`) explicitly rejects any memref with a non-identity layout map (`"NYI: non-trivial layout map"`). **Confirmed via a controlled A/B test, dimensions held identical and already register-width-clean (`32x512x512`, all multiples of 16) on both sides**: a `Tensor` arriving as an `export fn` parameter (crossing the ABI boundary) compiles to **100% scalar FMA, zero packed**; the *identical* matmul on a locally-constructed tensor (`Init::xavier()`, never crossing a function boundary) compiles **mostly packed, zmm**. Real, size-independent, structural. A real, existing MLIR pass built for exactly this (`--normalize-memrefs`, confirmed via its own doc comment — `mlir/lib/Dialect/MemRef/Transforms/NormalizeMemRefs.cpp`: "All memrefs passed across functions with non-trivial layout maps are converted to ones with trivial identity layout ones") **partially** helps the `export fn`-parameter case (layout-map error count 3→1, still not fully packed — plausibly because the pass can't safely change an *externally-visible* function's own parameter type without breaking its ABI, only what's reachable through it). **But has zero measurable effect on the real mnist kernel — byte-identical FMA instruction counts with or without it, no layout-map error at all even without the pass.** `train_and_evaluate` never passes a `Tensor` as an `export fn` parameter (only `epochs: i32, lr: f32, seed: i64`; every tensor is constructed locally) — this specific pathology, while real and now precisely understood, was never the real kernel's own problem. Not added to the default pipeline (zero benefit on the case that matters); worth remembering if a future `export fn` taking `Tensor` parameters directly becomes a real, exercised pattern.

**A real methodology error in the vectorization-mix reasoning above, found and corrected before it misled anything further.** The "32 packed / 13 scalar" FMA count on the real kernel, and an earlier "128→10 is ~85% scalar" reading on an isolated probe of that specific layer, were both **misattributed** — confirmed directly by locating exactly where each `vfmadd*ss` instruction lives in the disassembly, not by re-counting blind. Every scalar FMA found sits in its own small, separate, address-contiguous loop *before* the real matmul body (`probe..omp_par`, the actual OpenMP-outlined hot region) — matching `Init<Tensor<T,In,Out>>::xavier`/`he`'s own nested per-element draw loop (`nn.cleave`: `buf[i,j] = uniform(...)`, genuinely, correctly scalar — an RNG draw can't trivially vectorize), called once per tensor constructed, not once per matmul iteration. **Looking specifically at the real hot loop (the `omp_par`-outlined region) instead of the whole function: every locally-constructed matmul tested — including the previously-"suspect" `128→10` layer — compiles to 100% packed `vfmadd231ps`/zmm, zero scalar, a real broadcast-multiply-accumulate microkernel pattern (`vfmadd231ps zmm3, zmm2, [mem]{1to16}`).** Vectorization itself was never the real kernel's own bottleneck; the earlier "29% scalar" framing is retracted.

**The real, disassembly-confirmed finding: the reduction's own accumulator round-trips through memory on every step of `k`, instead of staying resident in a register for the whole reduction.** The real hot loop's own inner body: `vmovups zmm3 {k1}{z}, [rdi]` (reload the output tile) → `vfmadd231ps zmm3, zmm2, [...]{1to16}` (one contribution) → `vmovups [rdi]{k1}, zmm3` (store it straight back) — repeated once per step of `k`, not accumulated in a register across the whole reduction and spilled once at the end. For this kernel's own largest layer (`k=784`), that's 784 redundant memory round-trips per output tile instead of one — real, `k`-proportional memory traffic, entirely independent of the (already-confirmed-correct) vectorization.

**Tested the obvious, precisely-named fix directly — confirmed, not assumed, that it doesn't apply here.** `--affine-scalrep` ("Replace affine memref accesses by scalars by forwarding stores to loads and eliminating redundant loads", confirmed via `mlir-opt --help-hidden`) is MLIR's own store-to-load forwarding pass — exactly the shape of this problem on paper. Added to the pipeline (right after `convert-linalg-to-affine-loops`, before parallelization/vectorization) and tested two ways: on the real, well-vectorized local-construction probe (`--emit-object`, full disassembly) and, to rule out a placement/ordering mistake, on a minimal standalone `mlir-opt` probe (`--convert-linalg-to-affine-loops --affine-scalrep`, nothing else). **Both byte-for-byte identical to the untreated baseline — confirmed the pass's own `affine.load`/`affine.store` ops are exactly the ones present (right op type, so not a mismatch), it simply doesn't fire on this pattern.** Reverted (`pipeline.rs` confirmed clean via `git diff`). Most likely explanation, not independently confirmed: `affine-scalrep` is a narrow peephole (a store immediately visible to a *later* load of the same address), not a full promotion of a loop-*carried* memory accumulator into a proper `iter_args` SSA value across iterations — the harder transformation this actually needs. The more likely real fix is architectural, not a pass to insert: vectorizing `linalg.matmul` at the `linalg` level itself (which has real reduction-dimension semantics, and can lower a reduction into `vector.contract`/a genuinely register-resident accumulator) *before* ever converting to naive `affine.for` loops — rather than the current `convert-linalg-to-affine-loops` → `affine-super-vectorize` combination, which apparently never had a way to know the load/store pair was a loop-carried reduction at all. Not attempted — a real, structural change to the vectorization strategy, not a quick pipeline addition.

**That structural fix, actually prototyped via `mlir-opt`'s transform dialect (not `mlir::linalg::vectorize`'s C++ API directly — no plain pass wraps it; `transform.structured.vectorize`, MLIR's real, current entry point, confirmed via `--help-hidden` listing `transform` as an available dialect and `--transform-interpreter` as its driver) — real, incremental progress, not yet a complete fix:**

1. **Plain `transform.structured.vectorize` on the untiled `linalg.matmul`** (`bench/mnist-pytorch/probe_matmul_transform.mlir`) produces exactly the hoped-for shape at the abstract level — a single `vector.multi_reduction <add>` op, real reduction semantics, no memory involved in the reduction itself. But the vectors involved are the size of the *entire* matrix (`vector<32x512x784xf32>`) — an abstraction, not hardware-sized. Pushing this through `--lower-vector-multi-reduction` (which does exist and does work — confirmed it expands the reduction into a real SSA-chained sequence of `vector.extract`+`arith.addf`, genuinely register-resident, no memory round-trip) fully *unrolls* the reduction (784 static steps for this kernel's largest layer) rather than leaving it as a loop — pushing the resulting IR through the rest of the lowering pipeline (`--convert-vector-to-scf --convert-vector-to-llvm --convert-to-llvm`) hung for minutes on this one function alone and was killed rather than let run further — a real, separate, self-inflicted problem (full unrolling before tiling is simply the wrong order), not evidence against the approach itself.
2. **Tiling first, then vectorizing each tile** (`transform.structured.tile_using_for %matmul tile_sizes [1, 16, 16]`, then `vectorize` the tiled op) fixes the unrolling-explosion problem — produces a clean 3-level `scf.for` nest (`i`×1, `j`×16, `k`×16) with a *bounded*, hardware-sized `vector.multi_reduction` per tile. Real progress: **49 memory round-trips per output tile instead of 784** (one per 16-wide `k`-tile rather than one per single `k`-step) — but still not zero, because `transform.structured.vectorize` vectorizes each tile independently; it doesn't on its own hoist the accumulator's own `vector.transfer_read`/`write` pair out of the surrounding `k`-tile loop into a real loop-carried value.
3. **Tried the obvious next fix, `--loop-invariant-subset-hoisting`** (a real MLIR pass — "Hoist loop invariant subset ops outside of the loop", confirmed via `--help-hidden` — built for exactly "this memory access doesn't depend on the loop variable, hoist it") on the tiled+vectorized memref-level IR. **Byte-for-byte identical, no effect**, despite the accumulator's own `memref.subview` genuinely not depending on the `k`-tile loop variable at all (confirmed by inspection — only `%arg3`/`%arg4`, i.e. `i`/`j`, appear in its indices). Most likely explanation, tested directly rather than assumed: hoisting a *memref* read/write pair safely requires proving no aliasing, which this general-purpose pass declines to attempt for raw memrefs (memrefs can alias in ways pure SSA values structurally cannot) — confirmed by re-running the *identical* tile+vectorize sequence on a **tensor**-typed `linalg.matmul` instead of a memref-typed one: the tensor version already produces real `scf.for ... iter_args` carrying the accumulator as a genuine SSA value (`tensor.extract_slice`/`insert_slice` around a loop-carried tensor argument) — the safe, no-aliasing tensor form doing automatically what the hoisting pass wouldn't attempt on memrefs.
4. **Bufferizing that tensor-level result** (`--one-shot-bufferize="bufferize-function-boundaries"`, cleave's own existing bufferization pass) was the natural next test — but the accumulator's own `iter_arg` bufferizes to the *whole* `memref<32x512xf32>` (the same backing memory throughout, nothing promoted), because the loop's own `iter_arg` type at the point of tiling is the whole output tensor, sliced via `extract_slice`/`insert_slice` *inside* the loop body — not a small `vector<1x16xf32>`-typed `iter_arg` directly. Bufferization has nothing to promote because the loop was never structured to carry just the small accumulator tile as its own value.

**The two-level tiling structure, actually tried** (`bench/mnist-pytorch/probe_matmul_2level.mlir`): two *separate*, sequential `transform.structured.tile_using_for` calls — first `[1, 16, 0]` (tile `i`/`j` only, leaving a smaller `linalg.matmul` that still reduces the *full* `k=784`), then `[0, 0, 16]` *on that smaller op* (tiling only its own reduction). This works exactly as hoped at the tensor level: the inner `k`-loop's own `iter_args` is now genuinely the small `tensor<1x16xf32>` output tile itself (confirmed directly in the dumped IR), not the whole `32x512` tensor threaded through with `extract_slice`/`insert_slice` at every step the way the single-combined-tiling attempt produced. (MLIR does also have a purpose-built op for reduction-specific tiling, `transform.structured.tile_reduction_using_for`, confirmed via `LinalgTransformOps.td` — but its own documented shape is a *different* strategy, split-K-style: independent partial sums into a small buffer, combined in a separate step afterward, not "keep one running accumulator resident" — the two-*separate*-`tile_using_for`-calls approach above is the more directly applicable one here, not that op.)

**But bufferizing this correct tensor-level structure still doesn't survive as register-resident — a real, deeper finding, not yet resolved.** Running `--one-shot-bufferize="bufferize-function-boundaries"` (cleave's own existing bufferization pass) on this IR: the small `tensor<1x16xf32>` `iter_arg` bufferizes back down to a `memref.subview` *aliased directly into the final output buffer's own memory* — a reasonable bufferization choice in isolation (avoids an extra allocation/copy, writes happen "in place") — but it means the `k`-loop's own body still does a `vector.transfer_read`/`vector.transfer_write` pair against that subview on every iteration; `--canonicalize` afterward even drops the loop's own `iter_args` entirely, since the loop-carried tensor value resolved to "the same fixed memory address" throughout, nothing left to carry. The *tensor*-level structure was exactly right; *bufferization's own default in-place policy* undoes the benefit by choosing to represent the small per-iteration tile as a memory reference rather than keeping it unbuffered (a real vector value) until the loop exits and only the final result needs to reach memory.

**Pushed further the same evening: found a real fix for the *tensor*-level case, then confirmed empirically (not just theorized) that it doesn't survive cleave's own current pipeline ordering.** `--loop-invariant-subset-hoisting`, re-tried on the two-level-tiled result *before* bufferizing (i.e. on the genuinely-safe, no-aliasing tensor form, not the memref form it had already failed on) — this time it worked exactly as hoped: the `k`-loop's own `iter_args` becomes the loop-carried tensor/vector value directly (`vector.transfer_read`/`write` against the loop's own `%argN` in place, not a freshly `extract_slice`d value each iteration). Bufferizing *that* result (still `--one-shot-bufferize`) produced the real target shape: `%alloc = memref.alloc() {alignment = 64} : memref<1x16xf32>` — a genuinely **local**, freshly-allocated per-tile buffer (not aliased into the big output matrix), with the `k`-loop reading/writing *this* local buffer and only one copy into the real output after the loop exits. Pushed all the way through `--lower-vector-multi-reduction --convert-vector-to-scf --convert-vector-to-llvm --convert-to-llvm`: compiled quickly this time (unlike the untiled full-unroll attempt, which hung and was killed) and produced genuine `vector<16xf32>`-typed `llvm.fadd` chains — real hardware-width vector arithmetic, not the giant `vector<32x512x784xf32>` abstraction nor a scalar remainder loop.

**Wired this exact validated sequence into the real pipeline (`pipeline.rs`, right before `convert-linalg-to-affine-loops`, via `transform-preload-library`+`transform-interpreter` reading an external `.mlir` transform-library file, plus `loop-invariant-subset-hoisting`) and measured on the real isolated single-matmul probe.** First attempt failed outright — a real, separate mistake, not a design problem: forgot to call the matching `register_*` functions (`pass::transform_dialect::register_preload_library_pass`/`register_interpreter_pass`, `pass::transform::register_loop_invariant_subset_hoisting`) before referencing these passes by name in the textual pipeline, the same registration step every other textual pass addition in this file already needed — fixed, confirmed compiling and running once added. **Measured result: 3.599ms/call — slightly worse than the untiled baseline (3.488ms), not better.** This confirms, empirically now rather than just as a theoretical risk flagged before attempting it: cleave's own pipeline already bufferizes *before* the point this transform sequence runs, so `linalg.matmul` is already memref-typed by the time it gets here — the exact condition under which `--loop-invariant-subset-hoisting` was already confirmed to no-op (aliasing conservatism on raw memrefs). The real fix validated at the tensor level does not survive being inserted at cleave's *current* bufferization-before-vectorization pipeline position. Reverted (`pipeline.rs` confirmed clean via `git diff`).

**Real next step, well-specified, not yet attempted**: this whole transform sequence needs to run *before* cleave's own bufferization, not after — a genuine pipeline reordering (moving `linalg.matmul`-specific tiling/vectorization to operate on tensor-typed IR, ahead of the existing `one-shot-bufferize` call), not another pass insertion at the current position. This is a larger, real architectural change to `pipeline.rs`'s own stage ordering, needing care about what else currently depends on bufferization happening where it does today, before attempting it — not a same-session follow-up guess.

**Wired the two-level-tiling fix into the real pipeline that same night, right before `one-shot-bufferize` (so `linalg.matmul`-shaped ops are still tensor-typed when the transform runs) — three real, distinct blockers found and worked through in sequence, the first two fixed and confirmed, the third genuinely still open:**

1. **First attempt: silently matched nothing at all — not an error, a real gap in test methodology.** Measured performance was statistically unchanged (~3.6ms/call either side of bufferization, both slightly worse than the 3.488ms untiled baseline) — indistinguishable from "did nothing." Root-caused by dumping the module's own text immediately before the transform pass ran (`module.as_operation().to_string()`, a temporary debug `eprintln!`, removed after): **cleave's own matmul lowering never emits `linalg.matmul` (the named op) at all — it builds `linalg.generic` directly**, with hand-written `indexing_maps`/`iterator_types` (`mlir_lower.rs::build_matmul_no_seed`). `transform.structured.match ops{["linalg.matmul"]}` matched zero ops, so every downstream tile/vectorize step silently operated on nothing — not a bug in the transform interpreter, a correct response to a genuinely empty match set. Fixed by matching `"linalg.generic"` instead (`matmul_vectorize.transform.mlir`) — safe for this probe (its only `linalg.generic` is the matmul itself), though a real production version would need a tighter match (e.g. by iterator-type shape) to avoid also catching genuinely-elementwise `linalg.generic` ops from `--convert-elementwise-to-linalg` elsewhere in a real program.
2. **Second, real blocker, once matching worked: `transform.structured.vectorize` genuinely fails on cleave's own matmul body — "Attempted to vectorize, but failed", reproduced on a minimal standalone `mlir-opt` probe too, not a cleave-specific bug.** Root-caused by reading the full generic body cleave actually emits (same debug-dump technique): the payload uses `linalg.index 2`/`arith.cmpi`/`arith.select` to avoid a physical zero-fill of the accumulator — a real, deliberate, already-once-hard-won optimization, precisely documented in `mlir_lower.rs::build_matmul_no_seed`'s own doc comment (avoids a correctness bug from *skipping* initialization entirely, hit once before; also tuned so the multiply's result has exactly one real use, letting LLVM's own backend fuse a real FMA — confirmed there via the *old* `affine-super-vectorize` path, which this doc comment states handles the `select` fine). **`transform.structured.vectorize` is a different vectorizer with a different limitation**: confirmed directly, on an isolated hand-written probe, that removing the `linalg.index`/`select` and using a genuine `linalg.fill`-zeroed seed with a plain `out + a*b` body vectorizes cleanly (real `vector.multi_reduction`) — most likely because the vectorizer's own reduction-detection heuristic wants a combiner that consumes `outs` *directly*, and the `select` breaks that direct-consumption pattern even though it's mathematically equivalent. **Tested whether removing the trick is actually safe before touching real cleave codegen**: rewrote `build_matmul_no_seed` to use a real `linalg.fill` seed and a plain body, confirmed via cleave's own compiler end to end — output bit-identical to the known-good baseline (`2.0327845`, `probe_matmul_n1000.cleave`), and, critically, **real FMA fusion survives on the existing default pipeline** (`llvm-objdump` on the real compiled object: `2 vfmadd231ps`, zero separate `vmulps`/`vaddps` pairs) — the multiply's result still has exactly one real use in this simpler form, so the property the original trick was tuned for holds regardless. A second real gap found immediately after fixing the match, fixed the same way: `vector.multi_reduction` (from `transform.structured.vectorize`) needs its own lowering (`--lower-vector-multi-reduction`) that the existing pipeline never needed before (the *old* `affine-super-vectorize` path never produces this op at all) — present in every standalone probe that validated this sequence earlier, forgotten on the first real-pipeline wiring attempt; added back (`pass::vector::register_lower_vector_multi_reduction`), confirmed via dump that `vector.multi_reduction` genuinely disappears afterward.
3. **Third blocker, still open, genuinely deeper than a missing pass: `error: LLVM Translation failed for operation: builtin.unrealized_conversion_cast`, a hard crash (segfault) at final translation, both fixes above applied.** Confirmed via `--dump-mlir-lowered` that **16 `unrealized_conversion_cast` ops survive all the way to the end** — real memref/vector-dialect values (from the new transform-produced code) sitting adjacent to, and needing to interoperate with, `!llvm.struct<(ptr,ptr,i64,...)>`-shaped values (the *old* pipeline's own already-lowered descriptor representation for the same logical memrefs) — inside the *same* function body (everything inlined into one, as established earlier in this same investigation). `--reconcile-unrealized-casts` (already run at the very end of cleave's existing pipeline) can only fold away a cast immediately canceled by its own converse — it has no way to unify two genuinely different representations of the same logical memref/vector concept across a real, extended live range or control-flow join, which is what's happening here: this new transform-dialect path and the rest of cleave's own pipeline lower the *same kind of value* two structurally different ways, and nothing currently reconciles them where they meet mid-function.

**Fourth attempt, same night: tested the "give it its own immediate, local, complete lowering" idea directly, rather than leaving it as an untested hypothesis.** Added the exact same four-pass sequence the pipeline's own end already uses (`create_vector_to_llvm`/`create_scf_to_control_flow`/`create_to_llvm`/`create_reconcile_unrealized_casts`) *immediately* after bufferization + `lower-vector-multi-reduction`, before any of the rest of the pipeline's own later stages ever run. **Byte-for-byte identical result — the same 16 `unrealized_conversion_cast` ops, the same exact types, the same crash.** This directly rules out "coexistence/timing with the rest of the pipeline" as the cause: running this exact conversion sequence immediately, in isolation from everything downstream, doesn't reconcile these casts either. Which means the earlier standalone `mlir-opt` probes that appeared to "succeed" (real `vector<16xf32>`-typed `llvm.fadd` chains, confirmed via text inspection) were an **incomplete check** — confirming the *output shape* looked right without ever confirming *zero unreconciled casts remained* or pushing all the way through a real LLVM translation/object-emission step. ## A second, completely independent bottleneck found and fixed the same morning — a per-element scalar copy dominating half the real kernel's own compiled code — but net wall-clock still doesn't move

Disassembling the *real*, full `kernel.o` for the first time all investigation (previously only ever isolated single-matmul probes) turned up something the matmul work never touched: **216,040 static `vmovss` instructions — very close to half the entire kernel's own disassembly (223,318 lines total) — a fully compile-time-unrolled scalar element-by-element copy, no loop at all.** Traced precisely to `mlir_lower.rs::lower_tagged_struct_construct` (`Tensor::<T,Dims...>(data: expr)` construction — every call, e.g. `load_train_batch_input`'s own `Tensor::<f32,32,784>(data: pixels)`, called ~18,750 times over a full 10-epoch run) and `copy_nested_array` (nested array literal/repeat construction) — both walked every scalar element by hand (`memref.load`+`memref.store`/`tensor.from_elements`, one op per element, fully unrolled at Rust-construction time — cleave has no dynamically-sized arrays, so nothing stopped this from scaling with total element count).

Fixed by replacing the per-element walk with real, structured bulk ops MLIR can actually reason about and optimize, instead of throwing that structure away up front:
- `lower_tagged_struct_construct`: a defensive `memref.alloc`+`memref.copy` (safe regardless of aliasing, unlike casting `src` directly with `restrict`'s own "exclusively owned" promise — the exact danger `load_native_shape_field`'s own doc comment already found once, for a different call site) followed by one `bufferization.to_tensor ... restrict` — one real op instead of N scalar loads, letting One-Shot Bufferize's own copy-elision remove the copy later if it can prove it was unnecessary.
- `copy_nested_array`: one `memref.subview` (fully static offset/strides — every real call site fixes exactly one compile-time-constant leading index) + one `memref.copy` instead of a recursive per-element walk. `memref.subview`'s own verifier rejects a plain identity-layout result type here (a rank-reduced subview's own physical offset into the bigger buffer needs a real `strided<[...], offset: N>` layout spelled out by hand — confirmed directly, `cargo test`'s own real suite caught the mismatch immediately).

A real, separate integration cost: every hand-rolled test-file pipeline that lowers all the way to the `llvm` dialect (`dps_rewrite.rs`, `mlir_lower.rs`, `egraph.rs`, `unify_alloc.rs`, `user_guide.rs`) needed `--expand-strided-metadata`/`--lower-affine` added (`pipeline.rs`'s own real final-lowering stage already had them, from the matmul work above) — and, found isolated to a completely unrelated, pre-existing case (`user_guide.rs`'s own `array_literal_index_and_mutation`, a plain `a[0] = 10`, nothing to do with either fix): `--finalize-memref-to-llvm` run once, up front, before any `--convert-to-llvm` at all, leaves a genuinely unreconcilable `i64`-to-`index`-to-`i64` round trip behind on ordinary, non-subview `index`-typed constants — fixed by running `--convert-to-llvm`, *then* `--finalize-memref-to-llvm`, *then* `--convert-to-llvm` again, confirmed by testing the ordering both ways on the exact failing case. Full workspace test suite green after (all of the above, plus the matmul/`dps_rewrite.rs` fix together).

**Real object-file confirmation: `examples/mnist-interop`'s own `kernel.o` shrank from 1.97MB to 126KB** (~15.6×) — the unrolled copy genuinely gone from the compiled kernel, not just from an isolated probe.

**Real end-to-end result, both fixes active together: 83.0s** (`cargo run --release -p mnist-interop`, identical `test accuracy: 0.9342` confirming the identical kernel; an earlier same-session measurement read 90.1s — run right after a heavy background rebuild+full-test-suite pass on the same machine, most likely ordinary system-load noise, not a real difference: `kernel.o` itself is byte-identical between the two measurements) **against the 96.89s baseline — a real, if modest, ~14% end-to-end improvement**, despite two real, independently-validated architectural fixes that each measured far larger *in isolation* (a measured 2.12× per-call matmul speedup, and a measured 15.6× reduction in a different function's own compiled size). The honest conclusion, not spun: ~14% is real progress, but nowhere near what either fix's own isolated measurement would predict if it were the dominant cost — something else, still unidentified, accounts for most of the remaining gap. Something else — the backward pass (different matmul shapes, transposed, never isolated or measured), the three smaller layers (never measured independently; the `128→10` layer specifically still takes the *old*, unfixed `affine-super-vectorize` path via the `foreach_match`/`suppress` fallback above), `cleave_alloc_rc` malloc/free churn, OpenMP synchronization overhead, or something not yet hypothesized at all — dominates the remaining ~83 seconds. Guessing which, again, is exactly the trap this whole investigation has already fallen into and climbed back out of more than once.

**Real next step, not yet attempted, user-directed**: stop reasoning from isolated probes and hypotheses entirely — get real, whole-kernel profiling data. `llvm-mca` (present in this toolchain, `I:/Dev/llvm-mlir-22/bin/llvm-mca.exe`, flagged once before and skipped in favor of direct disassembly, which *did* find real things that time — but a static micro-architectural port/latency model is a different question than "where do the cycles actually go" across the *whole* kernel) alongside a real hardware-counter profile (VTune or AMD uProf — noted directly: AMD's own tooling has a real, poor reputation, worth confirming VTune still works reasonably on non-Intel hardware or accepting uProf's rougher edges rather than assuming either tool's output is trustworthy at face value).

**Update, same morning: a real, large, independent lever found — SMT/AVX-512 execution-unit contention, not anything about the kernel's own IR at all.** This machine (`AMD Ryzen 7 9700X`, confirmed via `Get-CimInstance Win32_Processor`) has 8 real physical cores, 16 logical (SMT) — libomp's own default thread count, with `OMP_NUM_THREADS` unset, follows the OS's *logical* processor count, spawning 16 OpenMP worker threads across only 8 physical cores' worth of execution ports. Two AVX-512-bound threads sharing one physical core's own vector ALU is a well-known anti-pattern for pure vector/FP-bound code — confirmed directly, not just theorized, and independently reproduced on two machines (two ~71.0s runs, essentially identical): `OMP_NUM_THREADS=8` (matching physical cores, not logical) measured **71.0s**, against **83–86s** with the default (16) — a real ~15-17% improvement on top of everything else this session already found.

**Correction, caught directly by the user, not self-noticed — a comparison drafted here at one point wrongly called `96.89s` "the PyTorch-CPU baseline": it is not.** `96.89s` is *cleave's own* original, pre-this-session baseline (this entry's very first paragraph, `--openmp` AOT build, before any of this session's fixes) — the real PyTorch-CPU number is **~7.6-7.9s** (`bench/mnist-pytorch/mnist_bench.py`, ~0.77-0.79s/epoch, 93.0% accuracy — measured three separate times across this session, on two different machines: 7.65s, 7.81s, 7.94s, genuinely stable, not cherry-picked). **Real next step, well-specified, not yet attempted**: `cleave-rt`'s own OpenMP runtime initialization should default to the machine's real *physical* core count, not whatever the OS/libomp's own default reports (logical/SMT count) — on Windows, `GetLogicalProcessorInformationEx` with `RelationProcessorCore` gives exactly this distinction; call `omp_set_num_threads()` with that count at startup rather than relying on libomp's own default. **Real VTune data, same morning, confirms the deeper "too many small parallel regions" theory directly, not just from `kernel.cleave`'s own old doc-comment prediction.** `result.csv` (VTune, real hardware counters, not a guess): OpenMP worker threads spend **966.184 of 966.184 CPU-seconds inside `_kmp_launch_worker`'s own internal wait/spin function — essentially 100% of their entire existence, doing zero identifiable real work.** The *master* thread fares only somewhat better: of `_kmp_fork_call`'s own 734.037 CPU-seconds, `_kmpc_barrier` alone accounts for 462.409 (63%) — real compute (`train_and_evaluate`'s own self time inside the fork) is only 268.958. The signature is unambiguous: many short parallel regions, workers spending nearly all their time waiting to be given work or waiting at the join barrier, not computing.

**Went looking for a real, sanctioned MLIR mechanism to fix this the same way `vector.contract`/`ContractionOpInterface` was found for the FMA problem — found one, tested it directly, and it turned out to be a real dead end for a precise, now-understood reason.** `--scf-parallel-loop-fusion` (`mlir::scf::naivelyFuseParallelOps`, real existing MLIR pass, confirmed by reading its own source directly, `mlir/lib/Dialect/SCF/Transforms/ParallelLoopFusion.cpp`): fuses *adjacent* `scf.parallel` ops sharing the exact same iteration space (real SSA-value equality on lower/upper bound/step, not just equal numerically) into one, which — once `--convert-scf-to-openmp` runs afterward — would fold what were N separate `omp.parallel` fork/join regions into one. Added right after `--scf-forall-to-parallel` (preceded by `--cse`, to give every matmul's own identical `32`-wide batch bound a real chance to already be the same SSA value), and tested directly on the real kernel: **zero effect — `kernel.o` came out byte-identical (125,907 bytes), fork-call count unchanged (46 → 47, noise).** Root cause, confirmed by dumping the pre-fusion IR directly rather than guessing: the pass's own adjacency requirement (*zero* real side-effecting ops between two `scf.parallel` loops in the same block) is never satisfied here — **`Broadcast0::broadcast0` (`stdlib/nn/nn.cleave`, `dense_forward`'s own per-layer bias broadcast) sits between every consecutive pair of matmuls, and it's a real, hand-written, genuinely scalar `for`-loop** (`for i in 0..B { for _k in 0..M { data[i,j] = r[0,j]; ... } }`, confirmed live in the pre-fusion dump as a real `scf.while`/`memref.load`+`memref.store` nest, not unrolled at compile time the way tonight's earlier fix targeted, but still O(B×M) real scalar memory traffic at runtime, zero vectorization) — a real side effect (`memref.store`) standing directly between every layer's own matmul and the next, breaking the fusion chain at every single boundary, every layer, every batch.

**This is the same family of bug as tonight's two earlier fixes (`lower_tagged_struct_construct`/`copy_nested_array`), one level up: a genuinely structured operation (a row broadcast along a new leading dimension — exactly `linalg.generic`'s own standard idiom, an indexing map that drops a dimension on the input side) hand-written instead as a scalar loop, this time at the *stdlib* level (`nn.cleave`), not inside the compiler.** `Broadcast0::reduce0` (the adjoint — summing back down across the batch dimension for the bias gradient) is the same shape, a real reduction expressible as a `linalg.generic` with a `"reduction"` iterator, currently a hand-rolled scalar accumulator loop instead. `Sum::sum` (`nn.cleave`, rank-2 total-reduction) already has an identical hand-rolled scalar loop, for an unrelated, already-documented reason (`doc/backlog.md`'s own const-generic-conflation bug forcing a manual counter) — worth checking whether it has the exact same fusion-blocking effect anywhere it's used adjacent to a matmul.

**Done, same morning — real, dedicated primitives, not a hardcoded compiler special case: `mlir_lower.rs::build_broadcast0`/`build_reduce0`, dispatched off `mlir::linalg::broadcast(r)`/`mlir::linalg::reduce(b)` the exact same way `matmul`/`transpose` already dispatch off `mlir::linalg::matmul`/`mlir::linalg::transpose` — `Extensibility discipline` followed, not bypassed.** The real *named* `linalg.broadcast`/`linalg.reduce` ops (confirmed real and current in `LinalgStructuredOps.td`) were tried first and abandoned: `Tensor<T,1,M>` is rank-2 (a literal size-1 leading dim), so reaching either named op's own expected rank needs a real `tensor.collapse_shape`/`tensor.expand_shape` first — confirmed directly, on an isolated probe, that the reshaped memref gets a genuinely non-trivial `strided<...>` layout after bufferization (even though the collapse here is always statically contiguous — MLIR's own bufferization doesn't prove that on its own), and `--affine-super-vectorize` refuses to touch it ("NYI: non-trivial layout map", the identical diagnostic the already-documented `export fn`-Tensor-parameter case hits, from a different real cause this time). Fixed by hand-building a `linalg.generic` instead — reading `r[0,j]` via a constant-`0` affine map on the batch axis for broadcast, reducing via a real `"reduction"` iterator for `reduce0` — sidestepping the reshape (and its layout problem) entirely. ## Chasing the region-fusion wash above further: real libomp runtime-tuning data, a real backward-chain root-fusion mechanism (validated, no measurable win), and a conclusive four-way comparison of every `vector.contract` lowering strategy MLIR actually offers

Picked back up directly off the entry above's own "wash" result, on the user's own explicit direction: VTune, re-run on the *current* (already-fused) binary, still shows heavy OpenMP spinning — real, not assumed, so the `~3.5×` gap noted above is still genuinely open. **libomp's own real tuning knobs, read directly from `openmp/docs/design/Runtimes.rst` (this project's own vendored LLVM/OpenMP source, not general knowledge) — `KMP_BLOCKTIME` (default **200 milliseconds**: how long an idle worker thread spins before actually sleeping) and `OMP_PROC_BIND` (default **`false`**: no thread-to-core affinity at all).** Both tested directly on the real kernel, both real, both informative:
- `KMP_BLOCKTIME=0` (force threads to sleep immediately instead of spinning): **186.6s — 4.3× worse** than the ~43s baseline. **Conclusive, four-way, real comparison of every `vector.contract` lowering strategy MLIR actually exposes — `VectorTransformsBase.td`'s own real enum, `Dot`/`LLVMIntr`/`OuterProduct`/`ParallelArith` — closing off "are we just using the wrong built-in flag" cleanly, raised directly by the user ("MLIR doit forcément avoir le pattern ML classique, on doit louper un bout de compréhension").** `OuterProduct` (already in use, chosen earlier this session by direct disassembly comparison) is real, and now confirmed to be the *right* choice among the four, not a guess:
- **`Dot`** (MLIR's own *default*, notably — the one this project's own schedule explicitly overrides away from): at the MLIR level, produces exactly what the user's own instinct predicted — sixteen fully *independent* `arith.mulf`+`vector.reduction<add>` pairs (one per output column, no dependency between them, only a cheap final `vector.insert` chain to reassemble the row) instead of one 16-long serial `vector.outerproduct` chain. Looked genuinely promising on paper. Measured directly on the real kernel: **90.4s — 2× worse** than baseline (`test accuracy: 0.9343`, correctness unaffected — a pure codegen-quality regression). The real, measured lesson: sixteen independent horizontal reductions, each needing its own shuffle/reduce sequence to collapse a 16-wide vector to one scalar, costs far more in raw instruction count/overhead than the theoretical ILP gain recovers — outer-product-style accumulation (using the *full* vector register width for useful multiply-add work, no horizontal reduction at all) is the genuinely better shape for this thin (`M=1`, one batch row at a time), wide (`N=16`+) output shape.
- **`ParallelArith`** and **`LLVMIntr`**: both produce the identical, real "shuffle pile" anti-pattern already flagged once earlier this session (sixteen `vector.extract`+`vector.insert` scalar pairs just to gather one weight-matrix column into a vector, before any real arithmetic even starts) — visibly bad at the MLIR level, not worth burning a full rebuild+measure cycle to confirm empirically.

## Real profiler ground truth on the `~3.5×`-vs-PyTorch gap: OpenMP overhead triple-confirmed on *both* sides, then isolated away to find PyTorch still wins ~6.6× on raw single-thread codegen — two concrete, previously-undiscovered root causes found by disassembling the real hot addresses

Picked up directly off the accumulator-widening dead-end above, on the user's own explicit redirection: back to fundamentals — this machine's real AVX-512 peak (`2 FMA ports × 2 flops/FMA × 16 lanes × 4.5GHz × 8 cores ≈ 2.3 TFlop/s`, confirmed by the user's own back-of-envelope math) against the real FLOP count of one training batch (`~83M FLOPs` forward+backward, `2×M×K×N` per layer, PyTorch's own `dX` correctly skipped for the input layer — confirmed directly via a full-batch `MKL_VERBOSE=1` trace, no `N,T` call with `M=784` anywhere). Both cleave (**~3.6 GFlop/s, 0.16% of peak**) and PyTorch (**~14 GFlop/s, 0.6% of peak**) are nowhere near the compute roofline — by two orders of magnitude — which by itself already ruled out the whole accumulator-latency investigation above as the dominant explanation for the gap, regardless of its own real merits.

**OpenMP fork/join overhead, independently confirmed by three separate tools/methods, not just VTune again:**
- VTune `hotspots` on the real `mnist-interop.exe`: **86.3% of all CPU time in `_kmpc_barrier`+libomp's own spin loop**, only 12.2% in `train_and_evaluate` itself.
- The identical measurement on **PyTorch itself** (`vtune -collect hotspots` on `mnist_bench.py`, 200 epochs capped to a clean 15s window): **87.5% in `libiomp5md.dll`** (Intel's own OpenMP runtime, bundled with this PyTorch wheel, `torch/lib/libiomp5md.dll` — confirmed a genuinely different binary from cleave's LLVM `libomp.dll`, not just a hypothesis) — refuting the natural "Intel's own runtime must be more efficient" hypothesis directly: both runtimes waste essentially the same ~87% on barrier/spin for this workload's shape (tiny matmuls, one fork per BLAS call either way — real, confirmed by summing a steady-state `MKL_VERBOSE` batch: **PyTorch does ~150µs of real SGEMM compute per batch against a wall-clock of ~420µs**, the same ~65% waste ratio).
- **AMD uProf** (`AMDuProfCLI.exe collect --config tbp|hotspots [-g]`, this machine's *own* silicon vendor's profiler, real hardware PMU sampling — VTune had explicitly warned it was running in degraded software-only mode on this non-Intel CPU) gives a third, independent measurement on the real kernel: **`libomp.dll` 56.9% + `ntdll.dll` (kernel-level thread wait/wake) 15.5% = 72.4%** of all CPU time, `train_and_evaluate` itself only 26.0% — same story, different tool, different sampling mechanism entirely.
- A real, if inert, confound found and precisely characterized along the way: this machine reports `Virtual Machine: Yes, Hypervisor Vendor: Microsoft Hyper-V` to both profilers despite being genuine bare metal with no WSL2 — confirmed via `Get-CimInstance Win32_DeviceGuard`: `VirtualizationBasedSecurityStatus: 2`, `SecurityServicesRunning: {2}` (HVCI/"Memory Integrity" actively running) — a real Windows-11-default security feature that runs the whole OS as a Hyper-V guest partition even with no VM ever explicitly created. User's own call, not chased further: PyTorch runs under the identical HVCI either way, so it can't be the differentiator for the *relative* gap.
- **AMDuProfCLI's own CLI usability note, for next time**: `-h`/`--help` invoke an interactive pager (`Press any key...`) that hangs indefinitely against a non-interactive stdin, even with `< /dev/null` (silently swallows the *first* "page" without printing it) — real flags/configs found instead via `AMDuProfCLI.exe info --list collect-configs` (enumerates `tbp`/`hotspots`/`cpi`/`branch`/... directly) and the public AMD uProf user guide, not the CLI's own `-h` output. Also real and load-bearing: `collect --config hotspots` alone does *not* enable call-stack sampling (`Call Stack Sampling: False` in the resulting report) — needs the separate `-g` flag too.

**Isolating OpenMP away entirely — `OMP_NUM_THREADS=1` on the real kernel — to find PyTorch still wins by ~6.6×, a real, separate, previously-unattributed gap.** With one thread, a fork/join still happens per region but there is no barrier wait (nothing to synchronize with) — confirmed directly: `libomp.dll` drops to **0.92s out of ~84s of total CPU-time (~1%)**, `train_and_evaluate` itself now **74.633s across 10 epochs = 7.46s/epoch**, essentially the *entire* budget. The equivalent PyTorch single-thread number (`OMP_NUM_THREADS=1 MKL_NUM_THREADS=1`, scaled linearly from a `1,000`-batch subset to the real `1,875`/epoch): **~1.13s/epoch of real GEMM-only compute**. **`7.46s` vs `1.13s` — cleave's own generated code is ~6.6× slower than MKL's, per unit of real, already-serial, non-parallel work, for the exact same FLOPs.** This reframes the whole gap: closing the OpenMP-overhead problem (a real, ~5.7× lever on its own — `train_and_evaluate`'s own 8-thread CPU-time-across-threads, `~10.36s`/epoch, divided by 8 real cores if perfectly parallelized ≈ `1.3s`/epoch, against today's real `7.4s`/epoch 8-thread wall-clock) would *still* leave a real, separate `~1.6×` gap against PyTorch's own 8-thread `0.79s`/epoch — both problems are real and distinct, neither alone closes the gap.

**Where those single-thread cycles actually go — found by direct disassembly of the real sampled hot addresses (`llvm-objdump` + AMD uProf's own DuckDB-format `cpu.db`, queried directly with Python's `duckdb` package for exact per-instruction sample weights), not inferred:**
- **36.7%** — the already-known, already-chased accumulator-latency chain (`vfmadd132ps` rotating through `zmm0`-`zmm3`, one dependency each) — real, but not the majority contributor, and both of this session's own two attempted MLIR-level fixes (`split_reduction`, `structured.split`) are confirmed dead ends (see above) — needs real new C++ or an `mlir_lower.rs`-level rewrite to progress further, not attempted.
- **21.1%, a real, previously-undiscovered finding**: a full, 32-register `vmovups %zmm0..%zmm31, ...` spill sequence (2KB of pure register-file save, zero useful arithmetic) sits immediately before a matmul loop whose own row stride is `0xc40` = `3136` bytes = **`784` floats × `4`** — almost certainly `l1`'s own `784 -> 512` matmul (the single largest-FLOP layer). A real register-pressure/over-unrolling artifact from whatever tile size that layer's own instantiation of the schedule picks, not a fundamental limit — a smaller tile size or explicit unroll factor for this specific layer is the natural next thing to try.
- **11%, a second real, previously-undiscovered finding**: the `128 -> 10` output layer's own matmul (`l4`, already known from earlier this session to be non-divisible and fall through to Stage 2's un-fused path) doesn't just fail to *fuse* — it falls all the way through to a **fully scalar** loop (`vmovss`/`vfmadd132ss`/`vfmadd213ss`, one float at a time, inner trip count `cmpq $0xa` = exactly `10`), not even packed-SIMD, let alone vectorized across the `10`-wide output. `N=10 < 16` (one AVX-512 lane count) is presumably why `create_named_contraction`+`outerproduct` never applies here at all — a real coverage gap in the schedule for any dimension narrower than one vector register, silently and expensively falling all the way back to the oldest, slowest lowering path rather than e.g. a masked/padded vectorization. Disproportionately expensive for the network's own smallest layer — a real, concrete, likely-tractable target (pad to 16 with a real/zero mask, or a dedicated narrow-N vectorization strategy in the schedule).
- The remaining `~17%` (AVX-512 mask-register setup, `kxnorb`/`vpsllq`/`vxorps`, and plain scalar bounds-check control flow) is very likely edge/remainder-handling satellite cost of these same three loops, not a fourth distinct root cause — not separately investigated.

**The `l4` scalar-fallback finding — fixed, landed.** `transform.structured.pad` (`LinalgTransformOps.td`, confirmed real via an isolated probe before touching the schedule) pads whichever dimension isn't already a multiple of `16` with a real, zero-filled `tensor.pad`, copying the unpadded region back out afterward (`copy_back_op = "linalg.copy"`) — letting the exact same `create_named_contraction`+outerproduct path already used everywhere else apply to the `128 -> 10` shape too. Confirmed directly, on an isolated probe, to produce genuine packed `vfmadd*ps` in place of the scalar fallback.

**A real, serious integration bug found applying this as a blanket fix to *every* matmul (the first attempt), not just the ones that actually need it** — padding an *already*-divisible matmul (`l1`'s own forward matmul, `784 -> 512`, both dims already multiples of `16`) still perturbs its own IR shape enough that `vectorize` silently falls through to `--convert-vector-to-scf`'s own generic masked-transfer lowering instead of outerproduct, allocating a real scratch buffer (`memref.alloca`, confirmed directly in the real lowered `llvm` dialect IR) once per iteration of the K-reduction loop (**784 times**, for this layer) — *inside* the single `stacksave`/`stackrestore` pair `--convert-scf-to-openmp` wraps around the whole per-thread loop body, not once per K-iteration. Real, measured consequence: a genuine stack overflow, crashing partway through `evaluate()`'s own repeated forward passes. Three isolated repros (a bare loop over the `128 -> 10` shape at 80,000 iterations; a full 4-layer forward pass at 10,000 iterations, matching `evaluate()`'s own shape exactly; a full training loop — `grad()`/SGD/backward — at 3,000 batches, exceeding the real `1,875`/epoch) all failed to reproduce the crash in isolation — it only manifests on the real kernel with real `extern fn` data loading, never root-caused beyond the mechanism above.

**The real fix**: never pad unconditionally. `structured.pad` only ever runs as a *retry*, on whatever `linalg.matmul` a stage's own direct `vectorize {create_named_contraction}` call still leaves standing (a real, silenceable failure, not a crash — confirmed already-established elsewhere in this file). A genuine wrinkle found getting this right: `vectorize` consumes its own operand handle whether it succeeds or fails, so re-matching `linalg.matmul` against that *same*, now-invalidated handle hard-errors ("uses a handle invalidated by a previously executed transform op") — the retry re-matches from the still-valid *ancestor* handle instead (the outer `tile_using_for`'s own loop handle, untouched by `vectorize`'s own consumption). Landed in all three places a matmul gets tiled+vectorized in this schedule: `@tile_and_vectorize` (Stage 2), Stage 1's own matmul section (`@fuse_and_vectorize` — needed here too, since `l4`'s own forward matmul in the *training*-loop context, output feeding `pred - y`, routes through Stage 1 instead of Stage 2), and each of Stage 0's four `failures(suppress)` blocks (needed for `%f6`, `dh3`, `l4->l3`'s own backward gradient, `K=10`). A first, broader design (a separate, brand-new "Stage 3" `foreach_match` pass matching plain `linalg.matmul` again after Stage 2) does *not* work and was caught before landing: by the time Stage 2's own tiling has run, a leftover unvectorized matmul is nested inside the `scf.forall`/`scf.for`/`scf.for` that tiling just built, so its parent is `scf.for`, not `func.func`/`scf.while` — `@match_matmul`'s own existing matcher never finds it again from the top.

**Verified**: real kernel, 10 epochs + `evaluate()`, no crash, `test accuracy: 0.9342` (unchanged, correctness never in question). Real compiled object disassembled directly (`llvm-objdump`) before and after: the dominant, hot-path scalar `vfmadd132ss`/`vfmadd213ss` occurrences are gone from both the training-loop and `evaluate()`-loop call sites (the handful still present are cold, one-time weight-init code — `Init::he`/`Init::xavier`'s own scalar formula — confirmed by their call-site context, indirect calls to `rand_normal_f32`/init helpers immediately before, not a loop). `OMP_NUM_THREADS=1` single-thread timing (isolating the fix from any OpenMP-overhead noise, matching this entry's own earlier methodology): ~122.6s/10 epochs, down from ~131.8s-138.3s pre-fix — a real, if modest (consistent with the ~11% share of single-thread "effective" time this bucket was ever measured to occupy), improvement in the expected direction. Full `cargo test --workspace --release` clean throughout (189 `mlir_lower` tests + everything else).

**The `l1` register-spill finding — investigated, real dead end found, reverted, not landed.** The obvious first fix (a narrower `K` tile for the matmul's own `tile_using_for`, `16 -> 8`, tested directly on `@fuse_and_vectorize`'s own matmul section since that's the stage `l1`'s forward matmul routes through) does **not** work — confirmed directly by disassembling the real compiled object before and after: the exact same 32-register `vmovups %zmm0..%zmm31` spill, at the exact same `0xc40`-strided (`784` floats) call site, survives completely unchanged. Root cause, found by reading the surrounding disassembly directly rather than assumed: after MLIR's own tiling produces a real `98`-iteration `scf.for` (`784 / 8`), **LLVM's own backend `-O3` loop unroller fully unrolls it anyway** — the disassembly shows one unbroken, straight-line chain of `vfmadd132ps` steps at strides of `0xc40`, `0x1880`, `0x24c0`, ... with no loop back-edge at all, i.e. the *same* fully-flattened `784`-deep chain as before, just re-created one level lower in the pipeline. An isolated probe matching `l1`'s own exact shape (`32x784 @ 784x512`), pushed through the identical tile+vectorize+outerproduct schedule, does **not** reproduce any spill at all (`0` `vmovups %zmm` spills in the resulting asm) — meaning this is a genuine whole-function register-pressure effect from `train_and_evaluate` itself being one single, enormous (`~98KB`) compiled function with many other simultaneously-live values nearby, not something an isolated single-matmul probe can ever exercise. Tuning the *MLIR-level* tile size can't control this on its own while LLVM's own backend is free to re-unroll the result regardless — a real fix would need either suppressing LLVM's own loop-unroll decision for this specific loop (loop metadata, or a backend/`llc` flag — not investigated) or reducing whole-function register pressure some other way (e.g. splitting `train_and_evaluate` into smaller functions) — a bigger, separate undertaking, not attempted. Reverted cleanly (confirmed via `diff` against the pre-experiment file) — nothing from this specific attempt shipped.

**A second, more targeted attempt — real MLIR mechanism found and correctly wired, still doesn't work, also reverted.** Raised directly by the user: control the re-unrolling via loop annotations, rather than fighting it through tile size. Found real, by reading `SCFToControlFlow.cpp` directly: `propagateLoopAttrs` copies any attribute on an `scf.for` whose own *value* belongs to the LLVM dialect onto the `cf.cond_br`/`llvm.cond_br` its back-edge lowers to — exactly where `!llvm.loop.unroll.disable` metadata needs to live for LLVM's own backend to respect it. Wired via `transform.param.constant #llvm.loop_annotation<unroll = <disable = true>> -> !transform.any_param` + `transform.annotate %loops2 "llvm.loop_annotation" = %ann`, attached to the K-reduction loop specifically. Confirmed correct, on an isolated probe, all the way to a real `llvm.br {llvm.loop_annotation = ...}` surviving translation to real LLVM IR — but that same probe never actually got fully unrolled in the first place (no whole-function register pressure to trigger it), so it only validated the *plumbing*, not the *effect*. Tested directly on the real kernel (the only place the effect is even observable): **no change at all** — the identical, unbroken `32`-register-spill, fully-flattened `784`-deep chain, byte-for-byte the same shape as without the annotation. Real, plausible explanation, not confirmed further: LLVM's *full*-unroll decision for a small, statically-known trip count is a separate pass/heuristic from the general partial-unroller `loop.unroll.disable` targets, and may need a different metadata key (or combination) to suppress — not chased further, a genuine, deeper LLVM-backend-internals question past what this session's own remaining budget could responsibly cover. Reverted cleanly, confirmed via `diff`.

Both real attempts at this point converge on the same conclusion: this is a genuine LLVM backend behavior, not something either MLIR-level tiling or MLIR-level loop metadata alone can currently steer. The two remaining, unexplored real levers are: finding the *correct* metadata/pass-specific knob (would need reading LLVM's own `LoopUnrollPass`/`LoopFullUnrollPass` source directly, not attempted), or reducing whole-function register pressure structurally (splitting `train_and_evaluate` into smaller functions, a bigger, separate undertaking).

**The real trigger for the register spill, found by following the allocation angle instead — a genuine architectural gap, not an LLVM quirk at all.** Redirected by the user directly: this project already built a real arena (`cleave-rt`'s own `cleave_region_enter`/`cleave_alloc_local`/`cleave_region_exit`, a plain bump-pointer allocator) specifically to avoid exactly this kind of per-value heap traffic — so why does the spill happen at all? Traced precisely, not guessed:

- The `32`-register spill sits immediately before a real `llvm.call @cleave_alloc_rc(...)` — a genuine heap allocation (`std::alloc::alloc` plus a written refcount header, confirmed reading `cleave-rt/src/lib.rs` directly). Any function call forces the calling convention to spill every live vector register the callee might clobber — this is *why* the spill exists at all, not a side effect of loop unrolling.
- `doc/hld.md`'s own "Memory management" section states the arena's real, deliberate scope precisely: *"a refcounted object's own payload never lives here [the arena], precisely because the arena can't free one object out of order."* Every tensor in this codebase is, today, unconditionally refcounted (`unify_alloc.rs`'s own module doc: *"Gives cleave sole ownership of every tensor payload's own physical memory"* — a deliberate, blanket end-of-pipeline rename of every MLIR-bufferization-inserted `malloc`/`free` to `cleave_alloc_rc`/`cleave_release_void`, no per-site exception). Refcounted, by the arena's own documented rule, structurally excludes every tensor from ever using it.
- **A real, already-built, already-tested escape-analysis pass exists and is wired in, but doesn't cover tensors at all**: `cleave/src/region_analysis.rs` (`find_region_local_functions`, `8` passing tests, called unconditionally from `mlir_lower.rs`) determines which top-level `fn`s are safe to have *all* their internal allocations drawn from the currently-open region instead of the heap — a function is safe when it has exactly one call site in the whole program, inside a loop, whose result never escapes to that loop's own carried state. **Its own module doc comment names the real mnist-interop training loop as the motivating example, verbatim**: *"`net_grad` is safe to mark region-local; `Optimizer::step` is not."* Confirmed this verdict is real and correct — but its *effect* is scoped far narrower than its own analysis: `mlir_lower.rs::alloc_llvm_value` (`ctx.currently_region_local.get()`, gating `cleave_alloc_local` vs `cleave_alloc_rc`) is the *only* place this verdict changes anything, and that function only ever fires for **struct/array construction** (`Network`, `Dense`, a struct-leaf embedded array) — never for an ordinary tensor value. Every tensor intermediate (every layer's output, every `relu`, every one of `net_grad`'s own real internal gradients — `dz1`-`dz4`, `dh1`-`dh3`, `dW1`-`dW4`, `db1`-`db4`, dozens of allocations per single training batch) goes through MLIR's own bufferization (`memref.alloc`) instead, lowered to a plain `malloc`, later blanket-renamed to `cleave_alloc_rc` by `unify_alloc.rs` — a completely separate code path that has never once consulted `region_analysis`'s own verdict.

**Net effect, real and substantial, not yet fixed**: `net_grad` — literally the single hottest, most-executed piece of code in this whole kernel (`18,750` times over a full run) — is *correctly identified* as arena-safe by an analysis this project already built and tests, and gets **none** of the benefit, because the mechanism that verdict feeds only understands struct construction, not tensor computation. This plausibly explains a real, previously-unattributed share of the disassembly-measured "effective" compute time beyond the two findings already chased above (the accumulator chain, the `l1` register spill) — every one of those dozens of per-batch tensor allocations pays a real `malloc` call plus a written refcount header, each one forcing exactly the kind of register-spill-around-a-call-boundary this entry's own two failed experiments were chasing from the wrong end. Closing this gap for real needs bufferization itself to route through `cleave_alloc_local` inside a region-local function — either a custom allocation-function hook into `--one-shot-bufferize` (if MLIR exposes one), or a region-aware successor to `unify_alloc.rs`'s own blanket rename (redirecting a `malloc`/`free` pair to `cleave_alloc_local`/a no-op specifically when it sits inside a function `region_analysis` already marked safe) — a real, cross-cutting architecture change, not attempted yet, but now precisely scoped: the analysis and the arena both already exist and are already proven correct in isolation; only the bridge between "which functions are safe" (CPS-level) and "how a tensor's own bufferized storage gets allocated" (MLIR-level, downstream) is missing.

**A first real attempt at that bridge — built, found unsound before landing, cleanly reverted (`git checkout` on the three touched files; confirmed via `git status`/`git diff` that this left zero trace, and via a full rebuild + `mnist-interop` re-run, `test accuracy: 0.9342` unchanged).** The attempt: a `cleave_alloc_local_void(size) -> ptr` malloc-shaped wrapper (`cleave-rt`, mirroring `cleave_release_void`'s own existing precedent for the same "same-signature pure rename" trick), plus a region-*depth*-aware rewrite of `unify_alloc.rs`'s own `llvm.call @malloc` retargeting: walk each `llvm.func`'s basic blocks in order, track a counter incremented on `cleave_region_enter`/decremented on `cleave_region_exit`, redirect any `@malloc` found at depth > 0 to the arena instead of `cleave_alloc_rc`. Compiled and looked plausible on a real dump (169 real call sites redirected on `mnist-interop`) — but crashed `--emit-object` on the real kernel with an LLVM assertion (`dyn_cast on a non-existent value`) on the very first real test, before any correctness check beyond "does it compile."

**Root-caused precisely why, and found the fix would have been unsound even without the crash — a real design error, not a bug to patch.** `mlir_lower.rs::lower_loop`'s own doc comment states directly what this attempt missed: `cleave_region_enter`/`cleave_region_exit` bracket *one whole loop iteration*, unconditionally, for *every* loop — not the span of one region-local call. They're opened wide on purpose, specifically because a region-local call's own result (`net_grad`'s `g`) must stay valid until whatever *later* code in the *same iteration* finishes reading it (`Optimizer::step`, right after) — closing the region right after the call returns, which a narrower per-call marker would do, is exactly the bug this design avoids. The direct consequence: `Optimizer::step`'s own internal tensor arithmetic — genuinely escaping (`w`/`b` become next iteration's carried `net`/`state`) — executes *inside the identical* `cleave_region_enter`/`cleave_region_exit` span as `net_grad`'s own internal allocations, with nothing in the IR at that point distinguishing which callee an allocation actually came from. A depth-only check cannot tell these apart; it would have silently arena-backed a real escaping tensor, corrupting `net`/`state` the moment the next `cleave_region_exit` rewound the arena cursor out from under it — a data-corruption bug, strictly worse than the crash that actually happened first and caught it.

**Found a second, independent, deeper obstacle to the "tag the decision early, let it survive to the rewrite" alternative — real pipeline ordering, checked directly in `pipeline.rs`, not assumed.** The natural fix for the depth-ambiguity above is to decide `cleave_alloc_rc` vs `cleave_alloc_local` using real *function identity* (`region_analysis`'s own actual granularity) rather than textual region depth, tagging the decision once, early, and carrying it through to the eventual `llvm.call @malloc`. But `--inline` (`pipeline.rs`, right after the transform-dialect matmul schedule) runs *before* `--one-shot-bufferize` — confirmed directly, by line number, not inferred from behavior — so `net_grad` no longer exists as a separate `llvm.func` even at the *bufferization* stage, let alone by the time `unify_alloc.rs` runs after `--convert-to-llvm`. A real fix has to mark the decision at the *original*, initial-lowering stage (`mlir_lower.rs`, exactly where `ctx.currently_region_local` is already known for structs) and carry a real, discardable attribute through every one of `--inline` → `--convert-elementwise-to-linalg` → `--linalg-fuse-elementwise-ops` → the transform-dialect tile/vectorize schedule → `--one-shot-bufferize` → `--scf-forall-to-parallel` → `--convert-scf-to-openmp` → `--convert-to-llvm` — several of which (fusion, tiling, vectorization) rebuild ops from scratch with no established guarantee of preserving an arbitrary attribute across the rewrite. Not yet checked empirically pass-by-pass; a real, bounded next step (dump the IR after each stage, confirm or refute survival directly) rather than a reason to abandon the idea, but genuinely more work than "add a rename" — this is the concrete shape of the "cross-cutting architecture change" the entry above already flagged, now with the exact pass list and the exact failure mode identified.

## `net_grad`'s own dead-gradient waste (line 144/231 above) — root-caused precisely, then fixed at the source: `grad()`/`derive()` now name a target parameter directly, mandatory, no whole-Jacobian tuple form left to reach for by accident — done

Chasing the allocation-gap investigation above surfaced a second, independent, real waste alongside it — asked for directly by the user ("et si le DCE est bien applique sur les gradiant aussi"): is dead-code elimination actually removing an unused gradient computation, or is it silently being paid for anyway? **Quantified precisely, not estimated**: `net_grad = grad(loss);` (the old bare form) computed a genuine, unused `dx` — the gradient of the loss with respect to the training batch `x` itself, a real `32x512 @ 512x784 -> 32x784` matmul, ~25.7M FLOPs, matching `l1`'s own forward-pass FLOP count exactly — confirmed via zero SSA uses of its result anywhere in the dumped MLIR after the point it's defined. Since `l1` is the network's largest layer, this one discarded gradient alone is **~31% of the whole backward pass's own FLOPs**, paid every single training batch (18,750 times over a full 10-epoch run) and simply thrown away every time. `examples/xor.cleave`'s own pre-existing comment had independently already named the identical pattern for its own smaller network ("`g.0`/`g.1`/`g.2` are the unused partials w.r.t. the data — `x1`, `x2`, `y` — `g.3` is the real one").

**Two designs considered; the user picked the structural one over a DCE-pass fix.** Option A — a DCE pass over the synthesized tuple, dropping unread components after the fact — was rejected explicitly by the user in favor of Option B: never synthesize the unwanted gradients' own computations *at all*. `grad(f, param)`/`derive(f, param)` now take a second, mandatory identifier naming one of `f`'s own real parameters, and compute *only* that one gradient, returned directly — never a tuple. A genuine multi-parameter Jacobian (`examples/linear_regression.cleave`'s own `w`/`b`) still works, exactly as cheaply as before: one separate `derive(f, param)` declaration per parameter actually needed, called as many times as needed, neither call ever computing the other's own share of the work — "il suffit d'appeler 3x", in the user's own words. The old whole-Jacobian tuple-returning form was removed entirely, not merely deprecated, once the user judged it "une idée à la con" in hindsight, given the measured cost above.

**Threaded through the whole pipeline, both differentiation backends, each needing a different fix point because of how differently they're built:**
- Grammar (`grammar.pest`): `derive_decl`/`grad_decl` are top-level items (`ident "=" keyword "(" ident "," ident ")" ";"`), not ordinary call expressions — safe to extend with a second bare `ident` naming a parameter with zero ambiguity risk, since it's a structural selector never evaluated in any environment, not a second real argument expression.
- AST/lowering/driver (`ast.rs`, `lower.rs`, `driver.rs::synthesize_derive_signatures`): `FnDecl` carries the raw target name (`grad_target_param`) and, once resolved against the target function's own real parameter list, its numeric position (`grad_target_index`) — resolution happens here, with a real, located `Diagnostic` (naming `f`'s own actual parameters) if the name doesn't match any of them. The index, not the name, is what survives downstream: CPS conversion renames every parameter to an anonymous `CVar`, so the name stops being resolvable past that point.
- CPS (`cps.rs`): `UnitBody::Derivative(String, bool, Option<usize>)` carries the resolved index alongside the existing `of`/`is_grad` fields.
- Reverse-mode (`egraph.rs::synthesize_one_gradient`, `grad()`): does independent per-leaf extraction already (`build_param_derivatives_from_shapes`) — filtering `param_shapes` down to the one target parameter right before extraction is sufficient; the other leaves' ops are simply never extracted, so they're never even built.
- Forward-mode (`egraph.rs::synthesize_derivatives`, `derive()`): architecturally different — every parameter's own `derivative(root, leaf)` marker gets injected together into *one shared* equality-saturation pass, whose own cost scales combinatorially with how many targets are injected at once (already noted in this file's own pre-existing doc comments). The fix had to filter `f_params`/`param_types` down to the single target *before* `param_shapes` is even built, well ahead of saturation — restricting after the fact (mirroring the reverse-mode fix) would still pay the full combinatorial saturation cost for every unwanted parameter, only skipping their extraction afterward. `finish_derivative_body`'s own pre-existing "one value in, no tuple wrapping" logic then produces a direct (non-tuple) result for free, since the filtered `param_shapes` now always has exactly one entry.

**Verified end to end, both backends agreeing, not just compiling.** A real, compiled-and-run probe (`grad(loss, y)`, `derive(loss, y)` both returning `8.0` for the identical inputs) confirmed via `--dump-mlir` that the unwanted parameter's own gradient computation is never synthesized at all, not merely discarded post-hoc. Every real call site across the whole codebase — `examples/mnist-interop`/`digits-interop`'s own real training kernels (`net_grad = grad(loss, net);`), `examples/xor.cleave`, `examples/linear_regression.cleave`, `examples/derivative_demo.cleave`, and the full `cleave/tests/mlir_lower.rs`/`driver.rs`/`parser.rs` suites (several genuinely-multi-target tests split into multiple single-target declarations, matching the "call it N times" design directly) — updated to the new mandatory syntax; full workspace `cargo test` green throughout, and `mnist-interop`/`digits-interop` reconfirmed compiling and running correctly under the fully mandatory grammar (`test accuracy: 0.9342`/`0.94713414`, both matching every prior measurement — confirming the rewrite is behavior-preserving on the gradient that *is* still computed, just without the ~31% that wasn't needed).

Does **not** close the allocation-gap finding directly above this entry — `net_grad`'s remaining, genuinely-needed internal tensor allocations still all go through `cleave_alloc_rc`, not the arena; that architectural bridge (`region_analysis` → bufferization) is still unbuilt. This entry closes the *other* half of the same investigation: the FLOPs that were being computed and thrown away are no longer computed at all, independent of how the ones that remain get allocated.

**A real, serious, independent bug found and fixed along the way, while tracing *why* `region_local_fns` didn't look right for this kernel — a genuine, pre-existing latent memory-corruption risk, not something introduced by this session's own work.** Dumping `region_local_fns` directly showed `Optimizer::step<Sgd, Network, NetworkState<...>>` — the exact call the user's own earlier `region_analysis.rs` module doc comment names as the motivating *unsafe* example ("`Optimizer::step` is not [safe]") — marked region-local, and confirmed via the pre-pipeline dump that it was *already*, today, building its own return tuple via `cleave_alloc_local`. **Why this hadn't visibly broken anything yet — an accidental, fragile correctness, not a real guarantee.** The arena is a plain bump allocator with fully deterministic, identically-repeating allocation sizes/order every iteration (no data-dependent branching in the allocation pattern) — `net`/`state`'s own "rewound" memory happens to survive, unwritten, until the *next* iteration's own identical allocation sequence reaches the *same* relative point and reads it, by which time nothing else has yet bumped over that address. A real, if never-yet-triggered, latent corruption risk: any change to the allocation pattern inside the affected scope (a new conditional allocation, a differently-sized intermediate — or, concretely, this very session's own `tensor_seed` work, had it reached further into a shape shared with an unsafe caller) could have shifted the bump sequence just enough to break this accidental alignment for real.

**Fixed in `region_analysis.rs`**: `collect_escaping`/`collect_calls_and_derivations`, on encountering a *nested* loop definition (`d.carried_types.is_some()`) while walking an *enclosing* loop's own scope, no longer descend into that nested loop's own `then_branch` at all (its own repeating body already gets its own, correctly-scoped, dedicated `analyze_loop_body` call) — only its `else_branch` (`mlir_lower.rs::lower_loop`'s own "runs in the outer scope, ordinary flow") is still the enclosing loop's own concern. A new helper, `loop_then_and_else_branch`, generalizes the pre-existing `loop_then_branch`'s own condition-chain walk to hand back both branches. New regression test (`a_call_escaping_only_via_an_inner_loops_own_carried_state_is_never_marked_local_even_when_an_outer_loop_wraps_it`, `cleave/tests/region_analysis.rs`) reproduces the exact nested-loop shape directly; all 6 tests in that file (5 pre-existing plus this one) pass. Confirmed fixed on the real kernel: `region_local_fns` no longer contains `Optimizer::step<Sgd, Network, ...>`; its own return tuple now correctly builds via `cleave_alloc_rc`. Full workspace `cargo test` green throughout; `mnist-interop`/`digits-interop` re-verified end to end, `test accuracy: 0.9342`/`0.94713414` — both unchanged, confirming the fix corrects a real unsoundness without changing this kernel's own observable behavior (the accidental alignment described above was, empirically, still holding).

**Real next step, well-specified, not yet attempted**: close the actual gap `net_grad` exercises — a shared, monomorphized algebra function (`MatMul::matmul<...>`, `Ring::add<...>`, etc.) called from *both* a region-local and a non-region-local context needs a *per-call-site*, not per-function, allocator decision. The user's own original design is the validated target: thread the enclosing loop's own region handle (`cleave_region_enter`'s own real return value, already computed and already threaded through `mlir_lower.rs::lower_loop`'s own `yield_targets`, per that file's own `YieldTarget` type) as a genuine extra argument into a region-local call site (`lower_real_call`), giving the shared callee's own signature an extra runtime parameter it branches on internally (`cleave_alloc_local(r, size)` vs `cleave_alloc_rc(size)`, chosen by whether `r` is a real handle or a sentinel) rather than compiled-in per function — real, cross-cutting work (touching signature generation for every algebra dispatch that might ever run in a region-local context), not a quick follow-up.

## No `Type::<generics>::method(...)` static-call syntax — a zero-arg, output-type-driven algebra call always needs the algebra spelled out (`Init::xavier()`), never the concrete type (`Tensor::<f32,3,3>::xavier()`)

Raised directly, comparing `let t: Tensor<f32,3,3> = Init::xavier();` (today's own required shape, `Init<T>`'s own module doc comment in `stdlib/nn/nn.cleave` has the fuller story of why `Init` had to become an algebra at all) against the `let t = Tensor::<f32,3,3>::xavier();` shape the user actually wanted — the target type spelled out via its own turbofish, the algebra inferred from the method name, not the other way around. This is Rust's own `Type::method()` associated-function resolution (searching every trait implemented for that type for a matching method name), not sugar over the existing qualified-call syntax.

**Confirmed unparseable today, by reading `grammar.pest` directly, not guessed**:

```
path      = { ident ~ ("::" ~ ident)* }
turbofish = { "::" ~ "<" ~ generic_arg ~ ("," ~ generic_arg)* ~ ">" }
call_expr = { path ~ turbofish? ~ "(" ~ arg_list? ~ ")" }
```

`path` is a bare sequence of idents joined by `::`, with no generic-argument slot on any *intermediate* segment; `turbofish` is a single, path-*final* construct, consumed once, right before the argument list. `Tensor::<f32,3,3>::xavier(...)` would need a turbofish grafted onto `Tensor` in the *middle* of the path — the grammar has nowhere for that to attach at all.

**Real design work beyond the grammar, not just a parser change**: today's dispatch direction is "algebra named explicitly, target type inferred from context" (`infer_algebra_call`, `doc/backlog-done.md`'s own "qualified-call syntax" item) — `Type::<...>::method()` is the reverse: target type known outright, algebra *unknown*, resolved by searching every declared algebra for a method of this exact name whose own impl target matches. Needs a real answer for the ambiguous case (two different algebras both declaring a same-named, same-arity method for the same target type) — Rust's own answer is a hard error requiring `<Type as Trait>::method()` to disambiguate, a *third* syntax this would also need to design. Not attempted — a real language-design pass, not a quick patch.

## Dot-call (`x.method(y)`) and bare-call (`method(x, y)`) are two disjoint resolution paths, not one desugaring — algebra methods have no `.method()` sugar, inherent methods have no bare-call form

Raised directly, comparing cleave's actual behavior against the natural mental model ("`.` is just sugar for `do_something(x, y)`, so both spellings should always work, and an `impl` block just narrows the search to its own target type"). **Confirmed false today, by reading both resolution paths directly, not assumed:**

- `resolve_method_call` (dot syntax, `ExprKind::MethodCall`) consults **only** `registry.inherent_method(&struct_name, name)` — an inherent-impl method lookup keyed by struct name. It never searches algebras at all.
- `infer_call` (bare-call syntax, `ExprKind::Call`) tries, in order: a qualified `Algebra::method` path, `registry.algebras_with_fn(name, arity)` (an algebra search by name+arity, erroring `AmbiguousOperator` on more than one structural match), then `env.get(name)` for a let-bound lambda, and only then falls through to `<unresolved-call:name>`. It never consults `registry.inherent_method` at all — confirmed directly, no call to `inherent_method` anywhere in `infer_call`'s body.

The two tables (`inherent_method`, keyed by struct; algebra impls, keyed by algebra+method name) are disjoint, and each call syntax only ever probes one of them. Concretely: a method declared inside an inherent `impl Vec2 { fn len(v) -> f32 { ... } }` is callable as `v.len()` but **not** as `len(v)` (`<unresolved-call:len>`, or a real `UnknownName`-shaped failure once that placeholder is later demanded concretely). Conversely, an algebra method (`Ring::add`, `Optimizer::step`) is callable as `add(a, b)`/qualified `Ring::add(a, b)`, but has **no** `.add()`/`.step()` dot-sugar at all — `resolve_method_call` would need to search algebra impls too for that to work, and doesn't.

This means the `impl` block does *not* merely "narrow a bare-call search to the implemented type," the way the pure-sugar model would predict — bare-call search never looks at inherent impls in the first place, regardless of how many or which `impl` blocks exist for a type. Dot-syntax is the sole trigger for switching into the `inherent_method` resolution table entirely, not a positional-argument rewrite layered on top of one shared name-resolution search the way Rust's own `.method()` works (inherent impls searched first, then every trait in scope, unified under one syntax).

**Not fixed, real design + implementation work, not a quick patch.** Full Rust-style unification (dot tries inherent-then-algebra, bare tries both too) isn't the recommended direction: it would need a real inherent-shadows-algebra priority rule (Rust's own classic footgun — an inherent method silently shadows a same-named trait method) and would port the deferred, multi-candidate resolution machinery (`pending_method_calls`, `AmbiguousOperator`) onto the dot path too, which today stays a simple direct `(struct_name, name)` lookup. It also buys little in practice: nothing in the existing `stdlib`/examples ever reaches for dot-sugar on an algebra call (`Optimizer::step(opt, net, g.3, state)`, never `net.step(...)`; `dense_forward(net.l1, x)` deliberately chosen as a top-level generic `fn` over an inherent `Dense::forward` for unrelated reasons, `examples/mnist-interop/src/kernel.cleave`'s own doc comment) — the one real ergonomic gap (chained arithmetic) is already covered by operator sugar desugaring to `Ring`/`Scale`, a separate mechanism.

The better-fitting fix, once actually compared against the "static method" gap below: **give inherent methods a qualified bare-call form, `Type::method(args)`, symmetric to `Algebra::method(args)`**, which today only algebras have. Unlike the dot path, this form wouldn't need `resolve_method_call`'s own receiver-arity requirement (`params.len() == arg_tys.len() + 1`, currently hard-required) — the first parameter would resolve through `impl_mapping`/unification against `target_ty` exactly as it already does for `base`, but as an ordinary positional argument like any other, present or absent. Two things follow from that one addition: it gives the static-method gap below a real call route for free (no receiver-arity requirement left to violate), and it turns dot-syntax into a genuine, minimal desugar — insert `base` as arg 0, dispatch through `Type::method` — layered on top of an already-complete qualified path, rather than a second, closed resolution table. `len(v)` reaching an inherent method (true UFCS, no `Type::` qualifier at all) is a separate, smaller, lower-priority extension on top of this — `infer_call`'s own fallthrough would need to try `inherent_method` too, after the qualified/algebra checks, which is exactly the kind of extra implicit-name-resolution surface this project has otherwise avoided; worth deferring even once the qualified form above lands. None of this attempted here — flagged and designed to this level of detail, not built.

## A zero-parameter ("static"/receiver-less) method can be declared inside an inherent `impl` block, but is then permanently uncallable from anywhere

Found verifying whether cleave has ever explicitly designed static methods, mutators, or an immutable-receiver ("const self") distinction alongside ordinary self-taking inherent methods — it has not; each of these was checked directly against the actual code, not assumed:

**Static methods**: nothing in `infer_inherent_impl_fn_generic`/`inherent_method_param_tys` (`infer.rs`) rejects `f.params` being empty at declaration time — a `fn count() -> i32 { ... }` inside `impl Foo { ... }` type-checks fine on its own. But both call paths categorically require a receiver: `resolve_method_call` hard-errors (`ArityMismatch`) whenever `entry.method.params.is_empty()`, *before* even comparing arities against the call's own argument count — so even `v.count()` with zero declared params and zero call args is rejected, deliberately, since there is no first parameter for `base` to fill. Bare-call syntax (`count()`) never reaches `inherent_method` at all (see the entry above). So a zero-param inherent method can be declared and passes type-checking, but has no syntax that can ever call it — dead code the compiler doesn't warn about, not a designed "associated function" feature (unlike Rust's own `Type::new()`-shaped static methods, which use the identical `Type::method()` path as an ordinary trait call). This is the same gap as the "`Type::<generics>::method()` static-call syntax" entry above, from the opposite direction — there is currently no dispatch route into an inherent impl that doesn't go through a concrete receiver value.

**Root cause and recommended fix, worked out precisely, tying this together with the dot/bare-call entry above**: the "no magic `self`" design (first parameter is just an ordinary parameter) is sound and worth keeping — but `resolve_method_call`'s own receiver-arity requirement doesn't actually honor it; it smuggles a receiver constraint back in at the *call* site even though nothing at the *declaration* site demands one. The fix isn't to special-case zero-param methods — it's the same one-addition fix already recommended above: a qualified `Type::method(args)` bare-call form for inherent methods, symmetric to `Algebra::method(args)`, with no receiver-arity requirement at all (the first parameter resolved through `impl_mapping` like any other, whether or not one happens to be present). That gives `Foo::count()` a real route to `count`'s declaration for free, without inventing a separate "static method" concept or a second declaration-time rule — the declaration was never the problem, only the dispatch surface was incomplete.

**Mutator / "const self" distinction**: doesn't exist, and cleave has no receiver-level concept for it to attach to in the first place. `mut` on a parameter (`param = { mut_kw? ~ ident ~ (":" ~ type_)? }`, `grammar.pest`) is a pure local-binding-reassignability flag, identical in kind to `let mut` — `check_mutability`/`check_mutability_block` (`infer.rs`) track it per-binding-name in a `HashMap<String, bool>` scope, checked only against `StmtKind::Assign`'s own target root. It says nothing about the caller's value, and nothing method- or receiver-specific singles out a method's first parameter from any other: marking it `mut` only permits the method's own body to reassign that local binding or its fields (`v.buf = x`), the same as it would for any other `mut` parameter. There is no aliasing/reference model in cleave (confirmed nowhere else in `infer.rs`'s mutability handling) that would make "does calling this method mutate the value the caller holds" a meaningful question the way Rust's `&mut self` vs `&self` makes it — a method either returns a new value (the established pattern throughout `stdlib`, e.g. `Optimizer::step` returning `(Model, State)` rather than mutating in place) or, if its first parameter happens to be `mut`, can reassign its own local copy, invisible to the caller either way.

Not fixed or designed further — raised as a real, confirmed gap (verified by direct code reading per the user's own request, not guessed) rather than acted on; no implementation requested yet.

## An inherent-impl method can't construct a fresh instance of the exact same struct its own `impl` block targets

Found reworking `examples/vector.cleave`: `impl<T: Float> struct vec3<T> { fn cross(a, b) -> vec3<T> { vec3(x: ..., y: ..., z: ...) } }` — a generic inherent method returning a *fresh* instance of the exact same struct type its own enclosing `impl` targets — fails at CPS/monomorphization time, `CPS: could not resolve method call \`vec3::cross\`` (a native Rust panic, not a clean diagnostic). Isolated to a minimal repro with zero stdlib usage (`use io;` alone, or nothing at all, reproduces identically): a plain `struct vec3<T: Float> { x: T, y: T, z: T }`, one inherent impl, one method constructing `vec3(...)` from its own arguments' fields.

**Confirmed, precisely, not guessed, to be about self-reference specifically**: an otherwise byte-for-byte identical inherent method that constructs a *different* struct (`Pair<T>`, say) from inside the same shape of `impl<T> struct vec3<T> { ... }` block works perfectly. `--dump-inference-pass` shows exactly where it breaks: the *call site* (`let k = i.cross(j);`, in `main`) infers correctly (`vec3<f32>`, printed with no issue) — the method's own *declaration-time* inference is what fails (`impl vec3<T> { fn cross(a, b) { /* type error, see diagnostics */ } }`, with `error: type could not be fully determined (<not-yet-inferred>)` pointing at the `vec3(...)` construction inside its own body). A top-level generic `fn cross<T: Float>(a: vec3<T>, b: vec3<T>) -> vec3<T> { vec3(...) }` — identical logic, not an inherent method — works correctly.

**Not root-caused to the exact mechanism** — a real, plausible hypothesis, not confirmed: `in_progress_methods` (the self/mutual-recursion tracking `infer_inherent_impl_fn_generic`/`infer_inherent_impl_block` use, keyed by `(struct_name, method_name)`) or some other struct-name-keyed lookup plausibly conflates "a recursive call back into this same method" with "constructing a fresh value of the struct this method's own `impl` targets" — both involve the identical struct name, but are semantically unrelated events. Not verified by reading the actual code path yet.

Worked around in `examples/vector.cleave` the same way this project's own "inherent-impl method's own generics" item was, before it got a real fix: a plain top-level generic `fn` (`cross`/`dot`) instead of an inherent method.

## `--dump-inference-pass` reports a spurious "overlapping impls" error for a bound-restricted generic impl coexisting with an unrelated concrete one — diagnostic-only, confirmed not to block real compilation

Found immediately after building `HeapStruct`/`RawBuffer<S>` (`doc/backlog-done.md`): `cleave <any program using use io;> --dump-inference-pass` reports `error: overlapping impls: impl RawBuffer<f64> and impl RawBuffer<S> could both match the same type` (and five more, one per primitive width) — even for the simplest possible program (`use io; fn main() -> i32 { print(42); 0 }`). **Confirmed directly, not assumed, that this never actually blocks compilation**: the identical program's `--run` compiles and executes correctly (prints `42`, exits `0`) — `Infer::check_no_overlapping_impls` is called *only* from `dump.rs`'s own `--dump-inference-pass` path, never from `pipeline.rs::check_type_errors` (the real, compile-blocking gate).

**Root cause, read directly in `infer.rs`, not guessed**: `check_no_overlapping_impls`'s own false-positive suppression (`unsatisfiable_bounds`, with a real, working precedent already documented in its own doc comment — `impl<T: Int> Ring<Box<T>>` vs `impl<T: Float> Ring<Box<T>>` correctly ruled out as never-colliding, since no concrete type is ever both `Int` and `Float`) only ever fires when **both** sides of a structural collision contribute a *bound on a generic variable* (`if names.len() < 2 { return None; }`) — merging two *different* algebras' worth of bounds on the *same* merged variable. `impl<S: HeapStruct> RawBuffer<S>` (one bound, on a generic) vs `impl RawBuffer<f64>` (zero generics, a bare concrete target) never reaches that path at all: there's only ever *one* bound in play (`HeapStruct`), not two to intersect — `f64`'s own side contributes nothing for `unsatisfiable_bounds` to even consider, even though `f64: HeapStruct` is just as genuinely unsatisfiable (no `impl HeapStruct<f64>` exists, and never will — `f64` isn't a struct) as the `Int`-vs-`Float` case it already handles. Not specific to `HeapStruct` — any future single-bound generic impl coexisting with an unrelated concrete impl of the same algebra would hit this identically.

Not fixed — genuinely diagnostic-only, cosmetic (if potentially confusing to someone using `--dump-inference-pass` for real triage), and the real fix (asking `unsatisfiable_bounds` "is this *one* bound satisfiable by this *specific* concrete type" when the other side is already concrete, not just "do two bounds' own candidate sets ever intersect") is a distinct, real code path from what exists today, worth a dedicated pass rather than a quick patch.

## `--target-cpu`/`--target-features` are wired end to end but have no real effect — `mlir-sys`/`melior` don't expose a way to override `ExecutionEngine`'s own host-detected `TargetMachine`

Real, generation-wide codegen options landed (`cleave::pipeline::CodegenOptions`/`Backend`, threaded through `lower_to_llvm`/`emit_object`/`emit_exe`/`compile_and_emit`/`cleave-build::Build`, new CLI flags `--opt-level`/`--openmp`/`--no-openmp`/`--target-cpu`/`--target-features`/`--backend`) — `--opt-level`/`--openmp`/`--backend` are all real and effective (`opt_level` reaches `ExecutionEngine::new`'s own `optimization_level` parameter directly; `openmp` genuinely gates the whole parallelization pass sequence, verified by the 6.6x mnist-interop measurement this same session). `--target-cpu`/`--target-features` are the one exception, found and root-caused via disassembly (not assumed): `stamp_target_cpu` (`pipeline.rs`) correctly stamps real `llvm.func` `target_cpu`/`target_features` attributes (confirmed present in the dumped MLIR), but the generated *code* is identical with or without them — `mlir::ExecutionEngine`'s own C++ implementation (`mlir/lib/ExecutionEngine/ExecutionEngine.cpp`, this project's own vendored LLVM/MLIR 22 source tree, `I:/Dev/llvm-project`) always builds its own `TargetMachine` via `JITTargetMachineBuilder::detectHost()` unless a caller passes a pre-built `TargetMachine` in — and `mlir-sys`/`melior` (vendored, `C:\dev\mlir-sys`, a local fork this project already carries an open upstream PR against for Windows support) don't expose that constructor parameter, or `mlirTranslateModuleToLLVMIR` (which would allow a separate, hand-driven `llc`-style path instead) at all.

Confirmed directly: an object built with `--target-cpu x86-64-v2` (no AVX/AVX2/AVX-512) still disassembles to hundreds of `zmm` (AVX-512) instructions, identical to the default build. Both CLI flags stay wired (parse, validate, stamp real attributes) rather than removed — a real, honest warning is printed at the point of use (`stamp_target_cpu`'s own doc comment has the full story) so a user relying on this flag finds out immediately, not after their own confusing disassembly session. A real fix needs `mlir-sys` extended to expose either a real `TargetMachine`-construction entry point for `mlirExecutionEngineCreate`, or `mlirTranslateModuleToLLVMIR` for a separate hand-driven path — a real, separate, larger undertaking, worth revisiting alongside (or as part of) the existing upstream Windows-support PR against `mlir-sys` rather than as a one-off patch here.

## `mlir-sys`/`melior`'s own ceiling: binary distribution, and whether cleave (and a second, sibling language) could ever get real custom MLIR dialects — a real design exploration, not attempted

Raised directly, motivated by three separate, compounding pains: today's build depends on a hand-built local LLVM/MLIR/openmp toolchain (`I:/Dev/llvm-mlir-22`, no prebuilt Windows package exists anywhere, unlike Homebrew on Linux/Mac) *and* a locally-patched `mlir-sys` fork (`C:\dev\mlir-sys`, real Windows MSVC static-linking fixes, two upstream PRs open since June, neither addressed); `melior`/`mlir-sys` together expose no way to construct a custom `TargetMachine` (the `--target-cpu`/`--target-features` entry directly above) *or* to define a genuinely new MLIR dialect; and a second, sibling language is now planned, sharing enough of cleave's own architecture (and likely wanting its own domain-specific dialect) that this stops being a cleave-only concern.

**Is the C API's own dialect coverage exhaustive? Not the right question — the C API's design is the real ceiling, not `bindgen`'s coverage of it.** `mlir-sys` binds whatever `mlir-c/*.h` declares; if well maintained, that binding step itself loses nothing. What's genuinely incomplete is the C API surface itself (documented as such in MLIR's own `CAPI.md`: a deliberately curated subset for language bindings, never a full C++ re-exposure). Two clearly different capabilities live under "the C API," worth not conflating:
- **Building an operation of any dialect, including one the C API has no dialect-specific wrapper for at all** — exhaustive, structurally, because MLIR's own generic operation-construction path (`OperationState` + an op name string + generic operand/attribute/result lists) mirrors the generic textual assembly form (`"dialect.op"(...) : (...) -> (...)`) and needs no dialect-specific C API support. This is already the mechanism `melior`/`mlir-sys` lean on for most non-core ops.
- **Defining a brand-new dialect** (real types, verifiers, canonicalization/folding patterns, op interfaces the generic pass pipeline consults — `MemoryEffectOpInterface` for DCE/CSE, interfaces bufferization/inlining need, etc., custom assembly) — this is a C++/TableGen artifact today; the C API exposes no authoring surface for it at all, only consumption of a dialect already compiled into a C++ `Dialect` subclass. Not a `mlir-sys` gap — an MLIR architectural fact, unaffected by how thorough any binding layer is.
- Which specific dialect-scoped headers (`mlir-c/Dialect/*.h`) today's fork actually binds vs. omits is a real, separately checkable question (this fork's own `build.rs`/`wrapper.h` allowlist) — not answered here from memory, deliberately, rather than guessed.

**Can a new dialect be defined without TableGen at all? Partially, via a real, underused MLIR mechanism — IRDL — not via unregistered ops.** Two genuinely different paths exist, worth not conflating either:
- *Unregistered ops* (`allowUnregisteredDialects`) — emit `"mine.foo"(...)` with no real `mlir::Dialect` behind it at all. Works for construction/lowering, but zero verification, zero op interfaces (so invisible to every generic pass that keys off one), zero canonicalization.
- **IRDL** (the `irdl` dialect) — describes a *new* dialect's ops/types/constraints as MLIR IR itself (`irdl.dialect`/`irdl.operation` operations), loaded at runtime, no C++ compilation involved at all — and since IRDL's own defining ops are just ops, building them is fully reachable from the plain generic C-API construction path above. Gives a real, registered `Dialect` with structural (type/operand/result-constraint) verification. Real limitation, to verify against this project's own pinned MLIR 22 rather than assume from a possibly-stale general impression: last known state was structural-constraint-only — no arbitrary custom verifiers, no canonicalization/folding patterns, no custom assembly format. Whether that's still accurate for the exact pinned version needs checking directly against `I:/Dev/llvm-project`'s own IRDL docs/tests before this gets designed further, not assumed from a general sense of the feature.
- A Rust proc-macro dialect layer, concretely: generating ergonomic, typed Rust builder functions for a dialect's ops from a small Rust-side DSL (not TableGen `.td`) is real, buildable, bounded work — either calling the generic construction path directly, or emitting IRDL to get real registration+verification, both entirely C-API-only, no C++ required. **This full-Rust/IRDL shape is the recommended primary target, deliberately preferred over TableGen even where TableGen would reach further** — see the explicit comparison and reasoning below.

**TableGen automation via `build.rs` — real, genuinely better than a naive hand-invoked setup, but demoted to a documented, deliberately-not-built fallback, not the primary path.** Raised directly: since LLVM/MLIR gets rebuilt from source anyway (the redistribution track above), `mlir-tblgen` is already sitting in that same build tree — a `build.rs` step could invoke it directly (mechanical, the same shape as `prost-build`/`protoc`-style codegen-then-compile crates already use `cc::Build` for), generating the dialect's `.inc` fragments into a small, largely fixed hand-written C++ shell (the pattern every MLIR-internal dialect already uses), then compiling a thin `extern "C"` shim over it. The one genuinely strong point in its favor: doing this **at the same time, same toolchain, as the LLVM/MLIR core build itself** (whether producing the prebuilt tarball, or building locally from source) means the shim's C++ ABI is guaranteed to match what it links against — structurally avoiding the exact class of ABI/toolchain fragility (Windows MSVC static-linking bugs, already fought once in the current `mlir-sys` fork) that a separately-obtained `mlir-tblgen`/C++ toolchain could reintroduce. This reaches real TableGen-level power (real op traits/interfaces — `Pure`, `MemoryEffectOpInterface`, `InferTypeOpInterface` — wired into MLIR's own canonicalization/CSE/DCE/constant-folding, not just IRDL's structural verification), which IRDL, in its last known state, does not.

Despite that, **not the recommended primary path**: it reintroduces, at a smaller scale, exactly the class of fragility this whole exploration is trying to get away from — a real C++ toolchain becomes a hard, load-bearing requirement for anyone (not just an occasional contributor) adding or changing an op in the dialect, not merely an occasional convenience; the prebuilt tarball only hides this for consumers who never touch the dialect's own definition, and for an exploratory domain-specific dialect, that's likely to be often, by the people building it, not rarely. It also means running two parallel extension mechanisms side by side — TableGen `.td` for MLIR-side ops, cleave's own algebra+stdlib mechanism for everything else — where this project's own established discipline (one real extension mechanism, never a second bolted on alongside it) favors a single, uniform, Rust-native path instead, especially with a second, sibling language planned to reuse whichever story gets built here. Kept as a real, working, documented option — not built preemptively, triggered only by a concrete cleave-specific op that provably needs a capability IRDL structurally cannot provide (a real custom verifier beyond type/arity constraints, a canonicalization/folding pattern, custom assembly) — not built speculatively ahead of that need.

**Counter-consideration, raised directly and worth keeping on record rather than resolved away by the e-graph point below**: cleave already runs equational rewriting (its own `egg`-based e-graph saturation) *before* MLIR generation, which covers a real share of what dialect-level canonicalization would otherwise be doing — but a real custom dialect (even IRDL-only, structural-verification-level) would still be a genuine net gain beyond that, not a redundant layer: it buys native access to MLIR's own general-purpose framework facilities cleave gets none of today by lowering straight into existing dialects' own ops — real SSA-form guarantees and the analyses built on them (dominance, liveness, use-def chains), MLIR's own constant-folding and dataflow-analysis infrastructure, and a real place for cleave-specific op interfaces (e.g., a real `MemoryEffectOpInterface` on cleave's own ops) to make cleave-specific operations visible to MLIR's *existing* generic passes, not just to cleave's own hand-written lowering code. The e-graph phase and a real dialect are complementary, not substitutes — the e-graph handles cleave's own domain-specific equational rewriting pre-lowering; a real dialect would extend what MLIR's own general infrastructure can see and do *after* lowering, on cleave's own vocabulary rather than only on what it's already been rewritten down into.

**Prebuilt-LLVM-per-platform redistribution — real, but the cost is release engineering, not Rust plumbing.** The Rust side (a `build.rs` that downloads a hash-verified per-platform tarball from a hosting location like GitHub Releases, caches it locally) is small, maybe a day of work — crates.io's own size limits rule out embedding gigabyte binaries directly in a published crate, so this is the realistic shape, not an alternative choice. The real, recurring cost is producing and hosting the tarballs themselves: at minimum Windows MSVC / Linux glibc / macOS x86_64+arm64 (4-5 build-matrix legs), each a multi-hour from-scratch LLVM+MLIR(+openmp) build, **repeated on every LLVM/MLIR version bump, indefinitely** — a standing release-engineering commitment comparable in ongoing size to maintaining the `mlir-sys` fork itself, not a one-time project.

**Complexity of the three concrete asks, and a recommended sequencing:**
1. *Rework `mlir-sys` (redistribution + filling gaps)* — moderate, decomposable, low risk to cleave itself. Filling genuine `mlir-sys`-side binding gaps (headers not yet wired into `bindgen`) is mechanical. Filling a gap like the `TargetMachine`/`--target-cpu` one above is *not* a `mlir-sys`-side fix at all — the missing entry point doesn't exist in MLIR's own C API, so this specifically needs a patch one layer further up, against the vendored LLVM/MLIR C++ source itself (a real new C API function, then bound), not just against the binding crate. Redistribution is real, valuable, and separable from the binding-gap work — worth pursuing on its own track. Given two real fixes already sitting unaddressed upstream since June, owning this fork outright as a permanent, private dependency (rather than continuing to hope for eventual upstream merges) is the more honest posture already, independent of any of this.
2. *A new layer over/replacing `melior`, with proc-macro dialect support* — the most open-ended of the three; real, bounded value exists (ergonomic builders, IRDL-based dialect definition) at the primary, full-Rust/IRDL target — full TableGen-parity authoring is reachable too (via the `build.rs`-automated fallback above) but deliberately not the default path, for the reasons above. Verifying IRDL's actual current capability against the exact pinned MLIR 22 tree is the real, cheap first step, and now doubly load-bearing: the whole full-Rust-primary bet rides on IRDL being real/capable enough for cleave's own dialect, not merely "acceptable as a way to avoid C++."
3. *Retarget cleave onto the result* — near-zero cost if scope stays "swap what's underneath `mlir-sys`, keep `melior`" (the generic op-construction path `mlir_lower.rs` already uses doesn't change regardless of what's happening at the distribution/binding layer beneath it). A real, multi-week-scale port if `melior` itself gets replaced — `mlir_lower.rs` is already large (struct-field packing, tensor/memref/math/scf/openmp lowering) and would need full parity with today's coverage before cleave could build again at all.

Recommended order, not yet started: (1) alone first — it pays off immediately with zero retarget risk. Investigate IRDL's real current capability against the pinned MLIR 22 tree next, in isolation, before committing to any proc-macro dialect layer — full-Rust/IRDL is the target to build toward, with the `build.rs`-driven TableGen+shim path kept in reserve, documented, not built, for the specific day a concrete op needs a capability IRDL structurally lacks. Don't touch cleave's own retarget until the dialect layer (whichever of the two it ends up needing) has been validated standalone, independent of cleave's own progress.

## The conclusion of the exploration above: two concrete, genuinely shared dialects — CPS and an e-graph term vocabulary — not a general "mutualize everything" bet

Motivated by a second, sibling rendering/compute language now being designed alongside cleave, sharing enough of its architecture (MLIR backend, `egg`-based equational rewriting, a CPS-shaped IR) that a first instinct was to mutualize the whole backend wholesale. Narrowed down, directly, to two specific dialects worth building shared — each justified on its own concrete merits, not on general proximity between the two languages, and each doing double duty rather than serving only one side.

**A shared CPS dialect.** Real suspend/resume semantics for the rendering language's own `await`/`Promise<T>` (an `extern fn` returning `Promise<T>` rather than `T` marks a host-async call structurally, in its type, not via a separate declaration form or hidden convention — the CPS pass recognizes `Promise<T>` wherever it appears and treats `await` on it as the suspension operator) — but also, independently, a real and already-known cleave-side gap this same dialect would close: `Forward::walk` (`egraph.rs`) stops translating entirely the instant a CPS body meets a real `If` (confirmed directly by a standing test, `a_body_starting_with_if_translates_nothing` — `env` stays empty, the whole `If` untouched), and the existing "Multi-level call transparency in the e-graph forward translator" backlog-done entry already tried and confirmed, by direct testing (`examples/join_demo.cleave`), that a `phi(a,a)==a` rewrite rule alone doesn't fix this — nothing ever built the `phi` node for it to match against, since translation bails before reaching one. A CPS dialect built on real MLIR block arguments at join points supplies exactly the missing piece — a real, structurally-guaranteed join representation — for free, from MLIR's own SSA-region machinery, rather than needing a hand-rolled phi-construction step grafted onto cleave's own bespoke pre-MLIR CPS pass. Two genuinely separate problems (real external asynchrony for one language; a known equality-saturation gap in the other), same dialect, same underlying mechanism (suspend/join with correct SSA merge semantics) solving both.

**A shared e-graph term-vocabulary dialect** (the "formalize the expression language, not the live e-graph state" idea from this same exploration — the vocabulary is declared once, `egg`'s own solver stays an internal, opaque black-box pass consuming and producing instances of that vocabulary, never itself expressed as MLIR IR). Solves a real, concrete duplication risk: today, `egg`'s own term language (`CleaveLang`, `egraph.rs`) and what `mlir_lower.rs` knows how to lower are two independently hand-written, hand-synchronized things. A single declared schema generating both directions removes that sync burden. **And it depends on the CPS dialect above for its own biggest win**: only once CPS gives a real, join-aware IR does equality saturation have anything sound to saturate *across* a branch at all — the two dialects are complementary for this specific capability, neither alone gets there.

**A real asymmetry between the two languages, worth keeping on record precisely because it's a point *in favor* of sharing, not against it**: the *axiom set* fed into the e-graph dialect is expected to stay genuinely dynamic/open-ended for cleave — grown by whatever `derivative`/`adjoint`/algebra rules a given cleave program itself declares (`grad`/`derive`'s own extensibility, already real and stdlib-driven) — while the rendering language's own axiom set is more likely closed and static (a fixed, stdlib-authored set of hardware/rendering identities, not meant to grow per end-user program the same way). Conversely, **CPS usage is expected to be the more elaborate one on the rendering side** — real suspension across a genuine external asynchronous round-trip, live for real time, not just cleave's own current, more constrained use (structuring a derivative computation, no actual external asynchrony involved at all). Each language ends up stressing a different facet of the same two shared mechanisms rather than needing identical behavior from either — a real, concrete reason the sharing is sound, not just convenient because the two projects happen to be developed together.

Not built — gated on the same open validation step as the rest of this exploration (IRDL's real capability against the pinned MLIR 22 tree), and subject to the same documented, not-built TableGen+`build.rs` fallback for whichever specific op needs a capability IRDL structurally lacks (`cps.await` needing a real `MemoryEffectOpInterface` for correct behavior under MLIR's own generic passes is the concrete candidate already flagged above, worth watching for first).

## A real, separately-compiled, linkable *cleave-to-cleave* library format (metadata alongside compiled code)

Not "produce a real executable" — that shipped a while ago (`--emit-exe`/`cleave-build`, real and heavily used, see `doc/backlog-done.md`'s own corrected entry; this item's own title used to say otherwise and had gone stale). This is the narrower, still genuinely open question underneath it: does a "cleave library" — separately-compiled, linkable, with no source required downstream — make sense at all, given total monomorphization? A `.o` alone carries no metadata (declared signatures, generic templates, algebra impls) for a *downstream* cleave program to monomorphize *against* — unlike Rust's own `.rlib`/`.rmeta` split, which exists precisely to carry that metadata alongside compiled code. Without an equivalent, either (a) cross-crate cleave code always recompiles from source (the current `stdlib` model, extended — works, but risks "mega long" whole-program compile times, and doesn't produce a distributable library at all), or (b) a real compiled-library-plus-metadata format gets designed, a genuinely new, nontrivial piece of infrastructure. `extern fn`/`export fn` already covers the *other* interop story fine (calling into/out of compiled cleave across a language boundary to Rust, already built and working, `doc/backlog-done.md`) — this item is specifically about a *cleave-to-cleave* separately-compiled library, a different problem, needing a real design pass once the language itself is more stable. Not attempted.

## A `for` loop bound to a const generic breaks if its own loop variable is used in ordinary arithmetic

Found in the same batching investigation, building `load_train_batch_input<const B: i32>` (`examples/mnist-interop/src/kernel.cleave`): `for b in 0..B { ...; train_pixel(batch_start + b, i); }` (`b`'s own value combined with an ordinary `i32` parameter via `+`) fails CPS conversion outright — `CPS: could not resolve call to \`add\` (("add", ["i32", "3"], "i32"))` (`3` being `B`'s own *concrete value* at the failing instantiation, not a type at all) — isolated with a minimal probe (`for b in 0..B { acc = acc + (base + b); }`, `sum_offsets::<3>(10)`), confirmed to reproduce identically standalone, with no array indexing or `Tensor` involved.

**Root cause narrowed, though the actual fix is real design work, not attempted here.** `ExprKind::For`'s own inference (`infer.rs`, the `unify_at(end.span, &start_ty, &end_ty)` call right before the loop variable is bound) unifies the loop counter's own start-value type with the *end* bound's type — completely correct, and harmless, for an ordinary loop (`for i in 0..10`, or `for i in 0..some_i32_var`, both bounds staying ordinary `i32`). The bug: when `end` is a bare reference to a const-generic parameter (`B`), `B`'s own type in `env` (`seed_const_generics`'s own binding, seeded from `fresh_generics_mapping`'s fresh `Ty::Var`, per that function's own doc comment) is *the same* type variable a downstream monomorphization pass later substitutes to a "value-as-type" representation (`Ty::Con("3")`, the same encoding `Tensor<T,Dims...>`'s own const-generic dimensions already legitimately use for type-level substitution) — because `unify_at` makes the loop variable's own type *literally the same variable* as `B`'s, monomorphization's substitution walk can't distinguish "a type slot that's genuinely a const-generic dimension" from "a runtime scalar that merely got unified with one" and rewrites both alike. `seed_const_generics`'s own environment entry is confirmed to be read *only* by expression-level `ExprKind::Path` lookups (`infer_expr`) — type-level references (`Tensor<f32,B,In>`) resolve `B` through a completely separate mechanism (`ty_from_ast_mapped`'s own `HashMap<String,Ty>`, never touching `env`) — so this aliasing serves no purpose the type-level path actually needs; it's a side effect of reusing ordinary unification for a value that later gets a non-ordinary (type-collapsing) substitution. A real fix needs the loop variable's own type to stay a genuinely independent `i32`-constrained variable, not literally unified with a const generic's own substitutable slot — exact mechanism (a fresh copy instead of `unify_at`, or teaching monomorphization's own substitution to leave a merely-unified-not-declared variable alone) not designed here. Plausibly the same root area as the already-known, still-open "`Sum::sum`'s own real, long-latent for-loop/const-generic unification bug" (`doc/backlog.md`'s own "Reverse-mode (`grad()`) differentiation" item, Phase 5's own closing note) — that one was about *two* different const generics' own loop variables getting silently unified together, the identical "shared variable, later collapsed by a value substitution" shape, just via a different unification path (a shared array-index expression, not a shared loop bound).

Worked around, not fixed: a manual counter (`let mut b: i32 = 0; for _k in 0..B { ...; b = b + 1; }`) instead of using the `for`-loop-bound variable itself in arithmetic — the loop-bound variable (`_k`, discarded) is never referenced, sidestepping the aliasing entirely (its own type still gets collapsed to the const value, but nothing ever reads it as a scalar).

## `derive()` on a real `Tensor`-parameter-scale MLP (`examples/digits-interop`) — two real bugs found, root cause diagnosed, motivated the reverse-mode rewrite below

Building a real, non-toy stress test (`examples/digits-interop`: a 64-input MLP on the UCI handwritten-digits dataset, loaded via Rust interop since cleave has no file I/O of its own) hit a wall the `xor.cleave`/`linear_regression.cleave` re-measurement above never exercised: `derive(loss)` with a `Tensor<f32,64,8>`-shaped weight parameter never finished — 293,197 e-graph nodes after just 2 seconds of saturation, still climbing.

**Root cause, found directly**: `build_param_shape` (`egraph.rs`) builds one independent `Index::index` leaf — hence one independent `Op("derivative",[root,leaf])` marker — **per flat element** of a `Tensor`-typed differentiation parameter. A `Tensor<f32,64,8>` (512 elements) creates 512 independent scalar differentiation problems sharing one e-graph, each needing its own full pass through every derivative/axiom rule, with no structural sharing across targets (a `derivative(subexpr, target)` marker embeds `target` as an argument, so the *same* subexpression differentiated w.r.t. two different targets looks like two different patterns to `egg`). This is inherent to forward-mode differentiation applied per-parameter, not fixable by tuning saturation limits.

**Two real, separate bugs found and fixed while investigating, both kept, neither sufficient alone:**
- Splitting `synthesize_derivatives`'s single mixed `Runner` (derivative-resolution rules interleaved with ordinary commutativity/associativity axioms) into two *sequential* passes — Pass A resolves every `derivative` marker first, Pass B simplifies the marker-free result with axioms after — gave a real, measured improvement on mid-sized cases (`scale_32_8`: 36s→17s, `TimeLimit`→`Saturated`) but did *not* fix the real 64x8 case (still `TimeLimit(30s)`, 405,398 nodes) — proved the axiom-mixing hypothesis was real but not the dominant cost.
- `IndependentZeroApplier::apply_one` ignored `egraph.union()`'s own boolean return value, always reporting "real progress" (`vec![eclass]`) even when the union was a pure no-op (already-merged classes) — this silently prevented `egg`'s `Runner` from ever detecting `Saturated`, burning the *entire* 30-second time budget on identical, non-progressing iterations (confirmed via `runner.iterations`/`stop_reason` instrumentation: iterations 30+ showed byte-identical `applied=[("derivative-independent-zero", 19075)]` with zero node/class-count change). Fixed by checking `union`'s return value in both branches before reporting progress.

**Not fixed by either patch — the real conclusion**: even with both fixes, the fundamental O(num-leaves × graph-size) cost of forward-mode differentiation, applied independently per tensor element, remains for the full 64x8/64x32 case. This is what motivated the reverse-mode/adjoint rewrite (see "Reverse-mode (`grad()`) differentiation" below) rather than further tuning the forward-mode path. `examples/digits-interop` stays out of the workspace's `default-members` (excluded from a bare `cargo build`/`cargo test`, still reachable via `--workspace`) until the reverse-mode backend eliminates `ParamShape::Tensor`'s per-element decomposition (a later phase of that item).

**Two unrelated, real infrastructure bugs found stress-testing the same example, both fixed**: `emit_object` crashed on any program with a genuinely custom `extern fn` — `melior::ExecutionEngine::new` requires every externally-called symbol resolvable at construction time even for object-only emission (never actually invoked); `register_cleave_rt_symbols` only ever registered the fixed, hardcoded cleave-rt set. Fixed via `register_unresolved_extern_stubs` (`pipeline.rs`), which registers an inert stub pointer for any `extern fn` not in the known cleave-rt set. Separately, both `main.rs`'s own worker-thread stack (an existing 64MiB, from an earlier, smaller fix) and `cleave-build`'s own compile thread (previously unbounded/default 2MB) were too small for real-scale `derive()` — both raised to 1GiB (`cleave-build::Build::compile` now spawns the actual compile call on a `thread::Builder` with an explicit stack size, mirroring `main.rs`'s own precedent).

## Reverse-mode (`grad()`) differentiation — Phases 0–5 done: `grad()` now works on real `Tensor` and struct (`Dense`) parameters, through non-square `matmul`, end to end

The real fix for the item just above: forward-mode `derive()` costs O(num-differentiation-targets × graph-size) because each target needs its own independent pass through the rule set — fundamentally the wrong tool for "one scalar loss, many parameters." Reverse-mode (adjoint) differentiation computes every parameter's gradient in **one** pass, cost O(graph-size) regardless of parameter count — propagating the real linear-algebra adjoint of each operation (`⟨Av,w⟩=⟨v,A^*w⟩`) backward from a single scalar-output seed, exactly the mechanism every real ML framework uses (backprop).

**Exposed as a distinct keyword, `grad()`, not a `derive()` replacement** — `derive()` stays completely unchanged (general-purpose forward-mode, any output shape, every existing test/example untouched forever). `grad()` is new, additive, and reverse-mode-specific: the source function's own return type must be a scalar `f32`/`f64` (`driver.rs::synthesize_derive_signatures`, a real, located diagnostic if violated) — a narrower contract than `derive()`'s, mirroring how JAX distinguishes `grad()` from a general Jacobian operator. Full grammar/AST/lowering/driver/CPS plumbing (`grad_decl`, `FnDecl::is_grad`, `UnitBody::Derivative`'s own second field, `DerivativeRequest::is_grad`) threads a `grad()`-vs-`derive()` distinction through the whole pipeline unconditionally, even before the reverse-mode backend existed.

**New declarative mechanism, mirroring `derivative` rules exactly**: an `adjoint` rule (`adjoint mul(a, b), u: (mul(u, b), mul(u, a));` — `u` is the upstream adjoint of the method's own output, the body gives the contribution to send back to each parameter, in declared order) gets its own grammar rule, AST node (`AlgebraItemKind::AdjointRule`/`AdjointRuleDecl`), lowering (`lower_adjoint_rule_decl`, with a real arity check — tuple arity must match parameter count), and registry accessor (`Registry::adjoint_rules`) — all before any reverse-mode engine consumed them. Seven scalar rules declared in `stdlib/num/num.cleave` (`Ring<T>`: `add`, `sub`, `mul`, `div`, `neg`; `Transcendental<T>`: `exp`, `tanh`), the real linear-algebra adjoint for each, re-derived directly rather than copied from the `derivative` rule shape.

**Propagation mechanism, validated via a spike before committing to the real implementation**: not `egg::Rewrite`/`Runner` — a plain, hand-rolled Rust reverse-topological (DFS-postorder) walk, seeding `adjoints[root]=1`, consulting each declared `adjoint` rule to build each contribution directly into the live e-graph (`EGraph::add_instantiation`, not a compiled rewrite — there's no saturation loop here to hand a rewrite set to), summing multiple contributions to the same e-class via a real `Ring::add` node. A real bug found building the spike, durable for the production version: building a contribution via `egraph.add(...)` can accidentally union with an unrelated, pre-existing e-class purely by numeric coincidence (`mul(1,3)` folds to the same e-class as the literal `3`), corrupting a later "how was this originally computed" query — fixed by snapshotting each node's own real defining structure once, up front, before any contribution is ever built, and consulting only that snapshot during the backward walk (`snapshot_backward_order`).

**Phase 3 (`egraph.rs::synthesize_one_gradient`/`backward_walk`/`apply_adjoint_rule`) — the real backend, done for the scalar-parameter case**: generalizes the spike's two hardcoded Rust match arms into real, `Registry::adjoint_rules`-driven dispatch, resolving each reached operation's `(algebra, method)` via `Forward::reached` (the same map the forward-mode path already uses) rather than re-parsing symbol text. A real bug found closing this out: a parameter used twice as the same operation's own two arguments (`f(x) = x * x`) makes `accumulate_adjoint` synthesize a fresh `Ring::add<ty>` call the function's own forward body never used anywhere — `rebuild` panicked on it as an unrecognized symbol until `accumulate_adjoint` was taught to report it into the same `referenced`-unit-tracking mechanism `derivative_rewrites` already established for the forward-mode path. Verified end to end (real `grad()` source syntax, not just the isolated spike e-graph) against five new tests in `cleave/tests/mlir_lower.rs`: single- and two-parameter cases (numerically matching `derive()`'s own output exactly), the `a*b+a` accumulation case from the original design discussion, a composed case through `sigmoid` exercising all of `div`/`neg`/`add`/`exp`'s adjoint rules together, and a clean, located error (not a panic elsewhere) for a non-scalar parameter.

**Deliberately out of scope for Phase 3, a real, reported error rather than a guess**: every parameter must be a plain scalar — `ParamShape::Tensor`/`Struct`'s own per-element/per-field expansion isn't wired into the reverse-mode path yet. Remaining phases, unchanged from the original plan: eliminate `ParamShape::Tensor`'s per-element decomposition (the actual fix for the item above), a new `transpose` MLIR primitive and the `MatMul::matmul` adjoint rule, validation against `Dense`/`Network` (`xor_tensor.cleave`), re-measuring the originally-catastrophic `Tensor<f32,64,8>` case directly, and re-integrating `examples/digits-interop` into the workspace's `default-members` once it's fast enough.

**Phase 4, first slice done — the `transpose` primitive and `MatMul::matmul`'s own new `adjoint` rule, verified**: `Transpose<A,B>` (`stdlib/linalg/matrix.cleave`) — `fn transpose(a: A) -> B;`, one impl (`Transpose<Tensor<T,N,M>, Tensor<T,M,N>>`) reusing `matmul`'s own established `linalg.` fix exactly (a genuinely zero-filled `Ring::zero()` accumulator, since `mlir_lower.rs::build_linalg_region`'s own generic multiply-accumulate payload region degenerates to a plain copy — `0 + in = in` — for a single-input `linalg.transpose`, needing *zero* new Rust code in `mlir_lower.rs` at all). Verified numerically on a real, non-square `2x3 -> 3x2` case (`transpose_of_a_non_square_tensor_permutes_both_axes_correctly`). `adjoint matmul(a, b), u: (matmul(u, transpose(b)), matmul(transpose(a), u));` declared alongside the existing `derivative` rule on the same algebra — verified structurally (hand-derived formula, `egg`'s own extracted s-expression compared exactly, mirroring the Phase 0 spike's own posture) via `adjoint_matmul_rule_produces_the_real_transpose_based_gradient_formula`, exercising `backward_walk`/`apply_adjoint_rule` directly on a real square `Tensor<f32,2,2>` case (`synthesize_one_gradient` itself still rejects `Tensor`-typed parameters — that wiring is separate, still pending, see below).

**A real, previously-latent monomorphization gap found and fixed getting there — the first genuinely multi-target cross-algebra reference anywhere in this codebase**: every prior `derivative`/`adjoint`/`axiom` rule that calls into a *different* algebra only ever calls a *single*-target one (`Ring<T>`, `Transcendental<T>`) — `MatMul`'s own new adjoint rule is the first to call a genuinely two-target one (`Transpose<A,B>`) cross-algebra. Two real bugs, both fixed:
- `monomorphize.rs` had no seeding path for an `adjoint` rule's own dynamically-referenced units at all (`seed_derivative_rule_references`'s own mechanism only ever ran for `derivative` rules) — a program calling only `matmul` (never `transpose` directly) never monomorphized `Transpose::transpose` at all, confirmed empirically (`Transpose` simply absent from `collect_units`'s own output). Fixed with a sibling, `seed_adjoint_rule_references`, same worklist-injection call site, walking an `adjoint` rule's own (possibly tuple-shaped) body the identical way.
- `find_impl_for_target`'s own arity check required the caller to supply *exactly* as many concrete types as the candidate impl template declares targets — sound for every existing caller (always single-target algebras, matching exactly), but `Transpose<A,B>`'s own `B` (the output shape) is never determined by any call argument's own type alone; `resolve_derivative_rule_expr_ty`'s own cross-algebra resolution can only ever supply the *one* type call arguments agree on (`A`). Relaxed to accept *fewer* supplied targets than the template declares, unifying only the ones given and letting the template's own shared type variables (`Transpose<Tensor<T,N,M>,Tensor<T,M,N>>` reuses `T`/`N`/`M` in both patterns) pin the rest — but only accepted if *every* resulting binding is actually fully resolved (checked via `free_vars`, not assumed), rejecting rather than guessing whenever a future, genuinely independent trailing generic can't be pinned this way.

**A real, deliberately deferred gap found in the same investigation, not yet fixed**: `egraph.rs::build_pattern`'s own cross-algebra call-name construction (used when *extracting* the adjoint expression, not when seeding monomorphization) still only ever builds the unit name from that same single agreed type — for the square `Tensor<f32,2,2>` case this coincidentally names the right unit (`A` and `B` are the identical string), but a real, non-square `matmul` (the case `Dense`/`Network` actually need — a layer's own weight matrix is not generally square) would extract a `Transpose::transpose<...>` reference naming a unit that doesn't actually exist, silently mismatching the one `seed_adjoint_rule_references` now correctly builds. Recovering `B` here would need real impl-level unification against `Registry::all_impls` (the way the monomorphization-side fix above now does), which `egraph.rs`'s own text-only `ty: &str`/`type_env: HashMap<&str,String>` representation doesn't yet support — a real, separate follow-up, needed before `Dense`/`Network`'s own non-square layers can validate end to end.

**`synthesize_one_gradient` now accepts a whole `Tensor<T,Dims...>` parameter as one opaque leaf, verified**: the scalar-only check relaxed to also accept a `Tensor` whose own element type is scalar — exactly the design point of reverse-mode over `derive()`'s own per-element `ParamShape::Tensor`. `grad_of_a_tensor_parameter_is_accepted_and_fails_cleanly_at_the_next_real_wall` (`cleave/tests/mlir_lower.rs`) proves the relaxation itself works (no more "scalar parameters only" rejection) on `fn loss(w: Tensor<f32,2,2>) -> f32 { w[0,0] }` — and fails cleanly at the *next* real wall (`Index::index` has no declared `adjoint` rule, a real, separate, unbuilt "scatter into a tensor" capability), not a panic somewhere confusing. A struct-typed parameter (`Dense`/`Network`) is still a clean, located error — Phase 5's own scope, not attempted yet.

**Two further, real, deeper blockers found chasing an actual end-to-end `grad()` run on a `Tensor` parameter through `Sum::sum` (`stdlib/nn/nn.cleave`'s own new rank-2 reduction, added this round, `sum_of_a_rank_2_tensor_computes_the_right_total` — correct and useful for ordinary, non-differentiated code, but not usable through `grad()` yet, for two independent reasons)**:
- **`Forward::walk` can't represent a call into a callee whose own body contains a loop, at all** — not "differentiate through it," not even "treat it as one opaque node." `is_straight_line`/`is_transparent_chain` (`egraph.rs`) are the only two paths a call can take (an opaque `Op` node for a straight-line callee body, full inlining for a transparent chain of further calls) — a `for` loop inside a *callee* fits neither, unlike a loop written directly in the function actually being differentiated (`Forward::try_unroll_for_loop` already handles that case). `Sum<Tensor<T,N,M>,T>::sum`'s own real body (a nested `for` loop, needed since `linalg.reduce`'s own MLIR-level result for a full reduction is a genuine 0-rank tensor — see next point) hits this directly: `sum(w)` inside a `grad()`d function can't even be represented, confirmed empirically, not guessed.
- **A real 0-rank-tensor wall behind the loop**: the one MLIR-native way to reduce a whole tensor to a true scalar in one atomic, straight-line op (`linalg.reduce` with every dimension folded away) produces a `tensor<f32>` (0-d), not a bare `f32` — `Tensor<T>` (a `Tensor<T,Dims...>` instantiated with an *empty* pack) was tried as cleave's own way to name that 0-d value, but `resolve_struct_field_ty_with_pack`'s own empty-pack case (`infer.rs`/`mlir_lower.rs`) degenerates `data: [T;Dims...]`'s own field type to bare `T` directly (no array wrapper at all) when the pack is empty — so `Tensor<T>`'s own native MLIR representation is already a bare scalar, never a real 0-d tensor, and can't serve as `linalg.reduce`'s own required tensor/memref-typed accumulator. Recovering a real 0-d tensor value would need either genuinely new MLIR-lowering support (a documented, deliberate exception to the "no per-op-name Rust knowledge" design, the same class as `build_linalg_region`'s own existing one) or a different reduction strategy entirely — not attempted.
- **A third, independent, real gap found trying a `broadcast`-based adjoint for `Sum::sum` as a stopgap** (`adjoint sum(c), u: broadcast(u);`, `fn broadcast(u: T) -> Container;` — declared as a *same*-algebra sibling specifically to dodge the already-known cross-algebra single-`agreed`-type limitation `Transpose`'s own adjoint rule already hits): `monomorphize.rs::find_impl_for_target`'s own resolution is *positional*, not generic-name-directed — it assumes the one concrete type it has always corresponds to the target algebra's own *first* declared generic. True by coincidence for `Transpose<A,B>` (its sole parameter `a`'s own type *is* `A`, the first generic) but false for `Sum<Container,T>::broadcast(u: T) -> Container` (`u`'s own type is `T`, the *second* generic) — `Sum::broadcast<Tensor<...>,f32>` silently never gets monomorphized, confirmed directly (absent from `collect_units`'s own output), not guessed. A real fix needs `find_impl_for_target` to resolve by the algebra's own declared generic *name* (via the callee's own `fn_sig`), not by positional index. Not attempted — this round's own three findings (loop-inside-callee, 0-d tensor, positional generic resolution) are independent, real, and each non-trivial; a test asserting the broken behavior was written, confirmed the exact failure, then removed rather than left red or `#[ignore]`d, matching this project's own "documented in `doc/backlog.md`, not a lingering red test" convention.

**All three blockers above resolved — `grad()` now genuinely differentiates through a real tensor reduction, end to end, verified numerically**: `loss(w) = sum(w)` under `gw = grad(loss);` correctly computes an all-ones gradient tensor for a real `Tensor<f32,2,2>` parameter (`grad_of_a_tensor_parameter_computes_the_gradient_as_one_opaque_tensor_leaf`, `cleave/tests/mlir_lower.rs`). Two more real fixes, found chasing this exact test, closed the remaining gap:

- **`Forward::walk` now represents an algebra-dispatched method as one opaque `Op` node even when its own body contains a loop or branch** — not just when it's straight-line. The real insight: differentiation never looks inside an algebra method's own body regardless of its shape (its own declared `derivative`/`adjoint` rule is the actual source of truth, exactly the same way `matmul`'s own real `linalg.matmul` body is never inspected) — so a loop inside one is no more relevant to *representability* than it was ever relevant to *correctness*. The only real constraint is soundness: a genuine side effect (`Extern`, e.g. `print`) must never be folded into a freely-reorderable opaque node this way, loop or no loop. A first attempt (`callee.origin.is_some()` alone) missed this and broke `a_real_call_to_an_effectful_unit_stops_at_the_fix` — `Print<T>::print`'s own body is *also* algebra-dispatched, and folding its real `print` effect into an opaque node is genuinely unsound (order-dependent side effects). Fixed with a new `is_pure` check (recurses straight through `If`/`Fix` instead of rejecting them, the way `is_straight_line` does — only real effects, `is_pure_prim_op`, are disqualifying), gating the new opacity path alongside the pre-existing `is_transparent_chain` priority (`sigmoid`, a *plain* `fn` with no declared rule of its own, must still fully inline — checked first, unchanged). Net effect: `Sum<Tensor<T,N,M>,T>::sum`'s own real nested-`for`-loop body (added this round, `stdlib/nn/nn.cleave` — correct and numerically verified for ordinary, non-differentiated use, `sum_of_a_rank_2_tensor_computes_the_right_total`) is now fully usable through `grad()`, no 0-rank-tensor detour ever needed.
- **`find_impl_for_target`/`seed_adjoint_rule_references`'s own positional resolution generalized to resolve by generic *name***: for a *cross*-algebra call (`Transpose::transpose`), each argument whose own declared type is a bare name matching one of the target algebra's own generics is placed at that generic's own real position (not assumed to be the first). For a *same*-algebra call (`Sum::broadcast`, called from `Sum`'s own `adjoint sum` rule) — the harder case, since `broadcast(u: T) -> Container`'s own sole argument only ever reveals `T`, never enough alone to also pin `Container`'s own `N`/`M` — resolved instead directly from the *enclosing* rule's own already-fully-resolved `type_env`, which already has every one of `Sum`'s own generics pinned. Verified directly: `Sum::broadcast<Tensor<f32,2,2>,f32>` now actually gets monomorphized (confirmed via `collect_units`'s own output), where it silently never did before.

**The non-square `build_pattern` gap above — fixed, generally, not `Transpose`-specific**: `resolve_multi_target_call_ty`/`match_type_pattern`/`resolve_type_pattern` structurally match `Registry::all_impls`'s own declared target-type ASTs against however many concrete types a call's own arguments pin (a real, generic text-level matcher, not hardcoded to any one algebra), replacing `build_pattern`'s own single-`agreed`-type limitation. Verified on a genuinely non-square case (`2x3 · 3x4`, every one of `a`/`b`/`transpose(a)`/`transpose(b)`/`dC` a *different* shape) — `adjoint_matmul_rule_produces_the_real_transpose_based_gradient_formula_for_a_non_square_case`.

**A second, deeper bug found applying that same fix — a *same*-algebra recursive adjoint call does not generally reuse the enclosing instantiation**: `build_pattern`'s own long-standing assumption ("a same-algebra recursive call always shares the *identical* instantiation as the enclosing rule") is true for a `derivative` rule's own `d(a)`/`d(b)`-wrapped recursion (`d(x)` always has `x`'s own type), but false for an `adjoint` rule's own recursion — `MatMul`'s own `matmul(u, transpose(b))`/`matmul(transpose(a), u)` are each a *third*, genuinely different instantiation from both the forward call and each other. Naively reusing the enclosing `ty` string (the *original* pre-existing behavior for this case, untouched until now) silently named a real, existing unit but fed it operands of the *wrong shape* — a genuine dimensional-mismatch bug, not just a missing-unit one. Fixed by trying argument-derived resolution *first* (regardless of same/cross algebra) and only falling back to the enclosing instantiation when nothing could be pinned from arguments alone (`Sum::broadcast`'s own real need, `Container`'s own `N`/`M` appearing nowhere else in the template) — verified structurally via the extended non-square `matmul` test.

**The identical class of bug existed on the *seeding* side too (`monomorphize.rs::resolve_derivative_rule_expr_ty`), found and fixed the same way**: this function's own single-`agreed`-type limitation, and its own "same-algebra reuses `type_env` unconditionally" fallback, both had the exact same two bugs as `build_pattern`'s. Fixed identically: try argument-derived `target_tys` first (both same- and cross-algebra), retry with the enclosing `type_env` as a fallback only if nothing resolved. Also fixed: this function's own *return-type* computation (needed when a call is nested inside a further enclosing call, e.g. `transpose(a)` inside `matmul(transpose(a), u)`) used to return either `agreed` or a `type_env`-based guess — now resolved for real from `find_impl_for_target`'s own matched template and substitution, mirroring `build_pattern`'s own `result_ty` computation exactly, just over structured `Ty` instead of text.

**Struct-parameter support in `grad()` — Phase 5, done**: `synthesize_one_gradient`'s own scope check (`is_grad_supported_ty`) now accepts a struct type recursively built from scalar/`Tensor`/struct fields, not just a bare scalar/`Tensor` at the top level. `backward_walk` gained real handling for struct field *reads* (routed into a new `field_contributions: HashMap<(base, field_name), Id>` map, accumulated per-field via `Ring::add<field_ty>` — a struct-typed value has no `Ring::add` of its own to sum a *whole* contribution with) and, once every field read anywhere has contributed (or been zero-filled via the new `build_zero_recursive`, which recurses into a struct's own fields when no `Ring::zero<ty>` exists for it directly), synthesizes the real combined struct value (`synthesize_struct_adjoint`) so it can keep propagating upward exactly like any other adjoint. Verified end to end, numerically, against the exact same hand-derived formula the pre-existing `derive_through_dense_forward_computes_the_right_gradient` test already used — `grad_through_dense_forward_computes_the_right_gradient`, a real `Dense<f32,2,2>` struct parameter, `layer.forward(x)` inlined exposing `matmul`+`Ring::add`, both `layer.w`/`layer.b` field-read adjoints correctly recombined.

**A real, sound pruning rule found needed along the way**: a struct/array *construction* op reached with a live adjoint (not yet a `backward_walk`-handled case — the "distribute" adjoint rule for construction is a real, separate, still-unbuilt capability, symmetric to forward-mode's own `construction_derivative_rewrites`) used to always be a hard error — but `Activation<Tensor<T,Dims...>>::sigmoid`'s own internal `one = Tensor::<T,Dims...>(data:[1.0;Dims...])` (`stdlib/nn/nn.cleave`) is exactly this shape, and its own adjoint is *never actually needed* (a pure constant, no `Free` leaf anywhere in its own defining subtree). Fixed by consulting `ConstantFold::free_deps` (already computed) before erroring: an empty `free_deps` means this node's own gradient can never reach any real parameter, safe to drop silently, not a guess — a genuinely parameter-dependent construction still can't be differentiated through and still errors exactly as before.

**A real, separate, pre-existing compiler bug found and root-caused along the way, unrelated to any of the above**: `Sum<Tensor<T,N,M>,T>::sum`'s own rank-2 body (`for i in 0..N { for j in 0..M { acc = acc + c[i,j]; } }`) failed to type-check for *any* non-square tensor (`Sum::sum cannot be specialized... its generic impl body doesn't type-check at this instantiation`) — invisible for a square `N == M` case, which is why it went unnoticed until a genuinely rectangular case (`Dense<T,64,32>`) was tried. Root-caused via direct debug instrumentation of `derive_impl_instantiation`: combining *two different* nested `for`-loop variables (each bound by a *different* const generic of the same generic impl, `0..N` and `0..M`) into one array literal/index expression silently unifies `N`'s own const-generic value-var and `M`'s own together during the impl's own body type-check — confirmed with a minimal, generics-only repro (no `Tensor`/`Index` involved at all), and confirmed *not* to reproduce for an ordinary, non-generic function's own identical nested loop. Worked around in `Sum::sum`'s own body with a manually-incremented counter (not itself a `for`-loop-bound variable, so the conflation never triggers) — the real fix (somewhere in `infer.rs`'s own for-loop/const-generic-value-var unification) not yet found; this item stays open for a proper investigation.

**Net effect**: a real `grad()` now works end to end on scalar, `Tensor`, and struct parameters, through non-square `matmul`, verified numerically at every step.

## `examples/digits-interop`'s own 17m39s debug compile / ~14min release build — root-caused to four independent, real sources, all four fixed — real `cargo build --release` now 8.4s, done

Chasing down *why* the digits-interop compile (previous item) took 17m39s, directly, not by guessing:

- **The user's own local LLVM/MLIR 22 build (`I:/Dev/llvm-mlir-22`, the real toolchain in use per `.cargo/config.toml`'s `MLIR_SYS_220_PREFIX`/`TABLEGEN_220_PREFIX`, not the unrelated pre-built `clang+llvm-20` package that happens to also be on `PATH`) is genuinely Release (`llvm-config --build-mode` → `Release`) but has assertions **enabled** (`LLVM_ENABLE_ASSERTIONS ON` in `lib/cmake/llvm/LLVMConfig.cmake`) — a known CMake gotcha, `CMAKE_BUILD_TYPE=Release` alone doesn't disable assertions, that needs its own explicit flag. A real, plausible slowdown, but fixing it needs a full LLVM rebuild (hours) — flagged, not yet done.
- **cleave's own MLIR pass pipeline (`pipeline.rs`) has no optimization pass at all** — three sequential `PassManager`s (elementwise-to-linalg; one-shot-bufferize; linalg-to-loops/scf-to-cf/to-llvm/reconcile-unrealized-casts), no canonicalize/CSE/O2/O3-equivalent anywhere. Ruled out "dial down the optimization level" as directly actionable (there's nothing currently dialed *up*) — redirected the investigation to input size instead.
- **The real, dominant cause, found via `--dump-mlir` line-count analysis**: `array-repeat`'s own "evaluate the value expression independently at every leaf position" semantics (needed, correctly, for `Init::xavier`/`he`'s genuinely-independent-per-element random draws — see "`[value; Dims...]` couldn't fill a tensor with independent draws" above) was *also* being paid by `Ring<Tensor<T,Dims...>>::zero()` (`stdlib/linalg/tensor.cleave`), whose old body (`Tensor::<T,Dims...>(data: [zero(); Dims...])`) unrolled into one fully-inlined copy of `zero()` *per tensor element* even though every element gets the identical constant `0.0` — no independence needed at all. Confirmed by function-boundary line counts in the dumped MLIR: `Init::xavier<Dense<f32,64,32>>` (2048 elements, genuinely needs per-element draws) was 27,033 lines; `Optimizer::init_state<Sgd,Dense<f32,64,32>>` (same shape, only needs a zero-fill) was *also* 12,560 lines purely from `Ring::zero()`'s own unnecessary unrolling. `net_grad` (the actual synthesized gradient) plus the whole training loop/`main` together were under 15,241 of 159,336 total lines — confirming `grad()` itself was never the bottleneck.

**Fixed**: `Ring<Tensor<T,Dims...>>::zero()` now calls a real, O(1)-sized MLIR primitive directly — `mlir::tensor::splat(z)`, `z: T = zero()` (the explicit `let`-annotation is load-bearing, not stylistic: `mlir::...` calls never type-check their own arguments against the op's real signature, so a bare unannotated `zero()` argument would have no way to know it must resolve to *this* impl's own `T` specifically) — no new Rust code in `mlir_lower.rs`, `lower_raw_mlir_op`'s existing generic mechanism already handles it, mirroring the `transpose`/`from_elements` precedent. Verified numerically (`sum(Ring::<Tensor<f32,4,4>>::zero())` returns `0.0` via `--run`) and by re-measuring the real kernel: total dumped MLIR for `examples/digits-interop/src/kernel.cleave` dropped from 159,336 to 119,121 lines (−40,215, ≈25%) — every direct `Ring::zero()` tensor call in the file (zero-initialization throughout the training loop and gradient accumulation, not just `Optimizer::init_state`) collapsed to 3 lines regardless of tensor size.

**A separate, real, *not yet fixed* contributor found while re-measuring**: `Optimizer::init_state<Sgd,Dense<f32,64,32>>` itself stayed at exactly 12,560 lines after the fix above — its own cost was never from `Ring::zero()`'s array-repeat at all. Its actual body: `Dense`-level `init_state` recurses field-by-field into `Optimizer::init_state<Sgd,Tensor<f32,64,32>>(opt, model.w)`, and *materializing* that call's own `model.w` argument (2048 elements) requires 2048 individual `llvm.getelementptr`/`llvm.load` pairs from the model struct pointer — even though the callee's own body (`Ring::zero()`) never reads `model` at all. A dead-argument-materialization gap in cleave's own struct-argument-passing convention (every struct/tensor argument gets eagerly flattened to scalar loads + `tensor.from_elements` at the call site, regardless of whether the callee ever uses it) — real, separate from array-repeat, not attempted yet *here* — resolved later in this same item, as a direct consequence of the `Tensor`-typed-struct-field representation change (see "The real root cause of the 738s" below): `Optimizer::init_state<Sgd,Dense<f32,64,32>>` is 25 lines in the final measurement, not a separate fix, the same one.

**`Init::xavier`/`he`'s own 27,033 lines — fixed too, with a genuine loop, not a new mechanism**: `stdlib/nn/nn.cleave`'s `Init<Dense<T,In,Out>>::xavier`/`he` now populate a plain, memref-backed local `[T;In,Out]` via an ordinary nested `for` loop (`buf[i,j] = uniform(-limit,limit)`, `j` a manually-incremented local — the same two-different-loop-variables-in-one-impl-body workaround `Sum<Tensor<T,N,M>,T>::sum`'s own doc comment already established), then constructs the `Tensor` from it — instead of `[[uniform(...); Out]; In]`'s own array-repeat. Confirmed directly, first: `cleave`'s own `for`/`while` loops already lower to a genuine `scf.while` (`mlir_lower.rs::lower_loop`), *not* unrolled — verified on a standalone probe (a real, non-square 64×32 loop-populated buffer, one single `func.call @"Rand::uniform<f32>"` in the dumped MLIR, independent of size) before touching the real stdlib file, exactly this project's own established methodology. `rand.cleave`'s own module doc comment had anticipated exactly this shape ("needs a genuine loop with indexed writes... left to `Dense`'s own future init helpers to use, not built here") — built now. `buf`'s own initial value is a raw `mlir::memref::alloc()` call (zero operands, fully static shape), not `[[0.0;Out];In]` — found necessary by direct re-measurement: every position gets overwritten by the loop immediately after regardless, so a zero-fill initializer is dead, but array-repeat *on a bare, non-`Tensor` array type* still unrolls into one `memref.store` per element (unlike `Ring<Tensor<T,Dims...>>::zero()`'s own `tensor.splat` fix above, which only covers a tagged `Tensor`, not a plain local array) — paying the exact per-element cost this whole rewrite exists to avoid, for a value nothing ever reads. Net effect on the real kernel: `Init::xavier<Dense<f32,64,32>>` 27,033 → 12,629 lines (the residual cost is a separate, deeper, not-yet-attempted structural issue — the loop-built buffer still gets flattened element-by-element *twice*, once into the `Tensor` SSA value via `tensor.from_elements`, once more into the `Dense` struct's own embedded array — the same class of "dead-argument-materialization"-adjacent cost already flagged for `Optimizer::init_state` above). Verified numerically (`print()` on four distinct positions of a loop-populated `Tensor<f32,4,4>` shows four genuinely different draws) and against the existing `init_xavier_generates_weights_within_the_correct_glorot_bound`/`init_he_generates_weights_with_the_right_statistics` tests (`cleave/tests/mlir_lower.rs`), both still green.

## `optimize_program` paid `egg`'s own `explain_equivalence` (full proof reconstruction) for every changed function, even when nothing ever read the result — the real dominant cost at the CPS/e-graph stage, found and fixed

Re-measuring after both fixes above, the full digits-interop MLIR dump *did* shrink (159,336 → 102,413 lines, ≈36%), but a synthetic scaling probe (a real, loop-populated `Tensor<f32,N,N>` fed into `sum(t)`, `stdlib/nn/nn.cleave`'s own rank-2 `Sum::sum`) revealed something far worse hiding underneath: compile time exploded from 0.47s at `N=4` to 38.4s at `N=14` (×3.2 per +2 on `N`), timing out entirely past `N=16` — looking exponential, not linear, over the tested range. Bisected precisely, not guessed, at every step:

- Neither the loop alone, nor `Tensor` construction alone, nor `Ring::add(t,t)` alone reproduced it (all fast even at `N=32`+) — only `sum(t)` specifically triggered it.
- `--dump-cps` (stops *before* `optimize_program`) stayed fast (0.27s) even at `N=14` — isolating the cost to `optimize_program` itself, not CPS conversion or type inference/monomorphization.
- Direct instrumentation of `optimize_program` (`egraph.rs`) showed every individual function's own e-graph *walk* and *saturation* were fast (`Sum::sum<Tensor<f32,12,12>,f32>`: 614 nodes, saturates in 2 iterations, under 10ms) — yet the whole pass still took 10+ seconds wall-clock for that one function.
- The gap: `runner.explain_equivalence(&original, &best)` — called unconditionally whenever a segment's extracted form differs from its original (`best.to_string() != original.to_string()`) — **alone took 10.3 seconds** on that same 614-node e-graph. `explain_equivalence` reconstructs a full rewrite-chain *proof* connecting the two forms (not just extracting the optimized one, already done separately via `Extractor::find_best`, unaffected) — `egg`'s own documented cost profile for this is much worse than plain saturation.

**The real bug**: this cost is paid *unconditionally*, for every function whose segment changed under saturation — but of `optimize_program`'s six real call sites (`main.rs` ×5, `pipeline.rs`'s own `build_optimized_cps`), only **one** (`--dump-cps-equivalences`) ever reads the resulting `Vec<String>`. Every real compile path — `build_optimized_cps` itself (used by `--run`/`emit_object`/`emit_exe`/`cleave-build`, i.e. *every* actual compile, not just diagnostics), plus `--dump-cps-optimized`/`--dump-mlir`/`--dump-mlir-lowered` — already discarded it with `_`, paying this cost for nothing.

**Fixed**: `optimize_program` now takes a `want_explanations: bool` parameter, gating `with_explanations_enabled()` on *both* the initial e-graph and the `Runner` (not just the final `explain_equivalence` call — `egg`'s own explanation bookkeeping adds real overhead to every union/rewrite step along the way, not only proof reconstruction at the end) and the `explain_equivalence` call itself. `true` only at the one real consumer (`--dump-cps-equivalences`); `false` everywhere else, across all six call sites in `main.rs`/`pipeline.rs` plus three test-suite call sites (`tests/cps.rs`, `tests/egraph.rs` ×2 — kept `true`, since those specifically assert on explanation content — `tests/mlir_lower.rs`). Verified directly: the same scaling probe that timed out past `N=16` now compiles `N=64` (4096 elements) in 6 seconds; the full digits-interop kernel's `--dump-mlir` dropped further, and the whole test suite stayed green.

## `examples/digits-interop`'s own real build time — isolated to LLVM's own `dump_to_object_file`, initially thought to be an LLVM-side-only problem (see below for why that framing turned out to be wrong)

After all three fixes above, the user re-measured the *real* `cargo build --release` end-to-end time directly (not `--dump-mlir`, which stops before the MLIR pass pipeline and object emission even run) and got the same ~14 minutes as before — no visible improvement, despite the dumped MLIR shrinking 36% and a genuine exponential compile-time blowup being eliminated. A real, humbling gap between "the generated MLIR got smaller and a CPS-stage bug got fixed" and "the wall-clock build time people actually experience," worth stating plainly rather than declaring victory on the earlier measurements alone.

Root-caused by direct per-stage instrumentation of `emit_object` (`pipeline.rs` — `lower_program`, MLIR verification, each of the three `PassManager` runs, `ExecutionEngine::new`, `ExecutionEngine::dump_to_object_file`, each wrapped in `std::time::Instant`, temporary, removed after measuring) on the real kernel via `cleave --emit-object` directly (bypassing `cargo`/`cleave-build`'s own orchestration entirely, isolating cleave's own pipeline from any Rust-recompilation noise). Precise result: every stage *except one* combined to under 20 seconds (`lower_program` 103ms, verify 28ms, elementwise-to-linalg 48ms, one-shot-bufferize 4.78s, to-llvm 1.12s, `ExecutionEngine::new` 13.3s) — **`dump_to_object_file` alone took 738 seconds (12m18s)**, essentially the entire build.

`dump_to_object_file` is LLVM's own real object-code generation (instruction selection, register allocation, machine-code emission) — entirely inside LLVM's C++ backend, no further cleave-side code runs during it. This directly corroborates, with hard numbers instead of a hunch, the very first finding of this whole investigation (see "digits-interop's own 17m39s debug compile" above): the user's local LLVM/MLIR 22 build (`I:/Dev/llvm-mlir-22`) is genuinely Release but has `LLVM_ENABLE_ASSERTIONS=ON` — a classic CMake gotcha, `CMAKE_BUILD_TYPE=Release` alone never disables assertions, a separate flag does — and LLVM's own backend codegen is exactly where per-instruction/per-register-allocation-step assertion overhead compounds worst, on a module this size.

**The `LLVM_ENABLE_ASSERTIONS`/O2-disable hypotheses above turned out to be red herrings — the real fix stayed entirely inside cleave, no LLVM rebuild, no optimization-level compromise.** The user explicitly rejected lowering `ExecutionEngine::new`'s own hardcoded `optimization_level=2` as a fix (tested directly first, confirmed it *would* have worked mechanically — `dump_to_object_file` dropped from 738s to 47s at `optimization_level=0` — but the whole point of cleave is genuinely high-performance generated code, so trading runtime speed for compile speed on a workload this small was never actually the right lever) and redirected toward "lighten the init" instead — turned out to generalize far beyond `Init::xavier` alone. See the next item for the real, final fix.

## The real root cause of the 738s, found after `Init::xavier`'s own fix wasn't enough — every `Tensor`-typed struct field crossing (construct *or* read) cost one MLIR op per element, in both directions

Re-measuring the full kernel's per-function MLIR line counts after every fix above, `Optimizer::step<Sgd, Network>` — not `Init::xavier` — turned out to be the single largest function in the whole file at 34,033 lines (bigger than `net_grad` itself), with `Scale::scale<Tensor<f32,64,32>,f32>` (14,534 lines, for an *elementwise scalar multiply*) and the still-unfixed `Optimizer::init_state<Sgd,Dense<f32,64,32>>` (12,560 lines) close behind. Direct inspection of `Optimizer::step`'s own dumped body confirmed the cause: reading `model.layer1.w` back out as an argument for the `Tensor`-level `Optimizer::step` call did 2048 individual `llvm.getelementptr`+`llvm.load` pairs. This is `load_native_shape_field`/`store_native_shape_field`'s own pre-existing per-element walk (`mlir_lower.rs`) — the *general* mechanism any `Tensor`/`Vector`-tagged struct field (`#[mlir_type(tensor)]`) already used for every read/write, not something specific to `Init::xavier`. `Init::xavier`'s own earlier fix (`bufferization.to_tensor` from a loop-populated buffer) only ever addressed *building* the tensor value — the moment that value crossed into `Dense`'s own `w` field, it paid this same cost anyway, which is why `Init::xavier` still had 8,439 residual lines even after that fix.

**Real fix, not a workaround — a `Tensor`/`Vector`-typed struct field's own storage changed representation entirely**: instead of an inline, fully-flattened `!llvm.array<In x array<Out x f32>>` embedded in the struct (the *original* design, correct throughout this whole project until now, just never load-bearing at real scale before), it's now a real memref descriptor — `!llvm.struct<(ptr, ptr, i64, array<Rank x i64>, array<Rank x i64>)>` (allocated_ptr, aligned_ptr, offset, sizes, strides) — the *exact* layout MLIR's own `finalize-memref-to-llvm` conversion already uses for an ordinary `memref` value, confirmed directly via `mlir-opt --finalize-memref-to-llvm` on a standalone probe (`I:/Dev/llvm-mlir-22/bin/mlir-opt.exe`, this project's own real toolchain), not guessed. Storing a `Tensor` value into a field is now: `bufferization.to_buffer` (tensor -> memref, one op — `to_buffer` is this MLIR version's real name; some docs/older versions call it `to_memref`, confirmed empirically it's unregistered here), `builtin.unrealized_conversion_cast` to the descriptor struct type, one aggregate `llvm.store` — no per-element loop. Reading is the exact mirror: one aggregate `llvm.load`, cast back to `memref<...>`, `bufferization.to_tensor ... restrict`. The `unrealized_conversion_cast` between a real `memref<...>` value and its own descriptor struct type is a genuine, standard MLIR materialization — confirmed directly (not assumed) that it resolves to clean, cast-free code with zero leftover casts under `--finalize-memref-to-llvm --reconcile-unrealized-casts`, in *both* directions, before touching `mlir_lower.rs` at all.

**A real, accepted tradeoff, not a hidden cost**: this changes struct layout for every `Tensor`-typed field, breaking the byte-for-byte layout compatibility `--emit-bindings`' own generated Rust struct definitions previously assumed. Flagged explicitly before starting — the user's own call: today only `examples/rust-interop-demo`/`digits-interop` exercise that FFI path at all, so the blast radius is real but small and known, worth it for the actual fix rather than a surgical, much harder "manually synthesize a memref descriptor by hand from a raw `!llvm.ptr` with no shape information" alternative that would have kept the old layout (`vector`-tagged fields, `#[mlir_type(vector)]`, structurally supported but unused anywhere in stdlib today, would need their own separate treatment — real MLIR `vector<...>` values have no memref-backed form at all, so this whole fix is scoped to `keyword == "tensor"` specifically, asserted directly rather than silently mishandled if `vector` is ever used this way).

**Verified end to end, not just by line count**: the full `mlir_lower.rs` test suite (177 tests, including `derive_through_dense_forward_computes_the_right_gradient`, `grad_through_dense_forward_computes_the_right_gradient`, `optimizer_momentum_trains_a_real_network_to_convergence`, `dense_layer_forward_computes_the_right_values`) passes unchanged. The real `examples/digits-interop` training run reproduces the *exact* original accuracy (94.7%). The full kernel's dumped MLIR: 159,336 → 19,787 lines (−87.6%, cumulative across every fix in this whole item). And the number that actually matters: the real, complete `cargo build --release` of `examples/digits-interop` — not `--dump-mlir`, the actual end-to-end build the user has been timing throughout this whole item — dropped from ~12–14 minutes to **8.4 seconds**, with `optimization_level` still at its original `2`, no compromise on generated-code quality.

## A lambda returned from a function, or stored in a struct/array field

The other two shapes originally bundled with "Calling a lambda literal directly" (now Done, see above) — a lambda value that outlives the single call site its own closure-conversion unit is specialized against. Unlike calling a lambda literal directly (pure desugaring, no new runtime representation needed), these two are a genuinely harder problem: `hld.md`'s own "no runtime closure ABI" design (see "Closure conversion (lambdas)" above) means a lambda never becomes a real runtime value today — every call to one is resolved to a concrete, statically-known unit at compile time. A lambda *returned* from a function (potentially different lambdas on different branches) or stored in a struct/array field (potentially read back and called from code with no static knowledge of which lambda it is) both need some real runtime representation to call through — a function pointer plus a captures record, at minimum — not just more of the "resolve by static name" machinery `monomorphize.rs`/`cps.rs` already have. Needs its own design pass, not attempted yet.

## No reserved-word list at all

A keyword (`let`, `if`, `and`, `not`, ...) is only special at its own specific grammar position — nothing stops it from *also* being used as an ordinary identifier elsewhere (`let and = 5;` presumably parses). Distinct from the word-boundary bug already fixed (see "Done" above, boolean logic): that was about a keyword wrongly matching as a *prefix* of a longer identifier; this is about a keyword being usable as a *complete* identifier at all. Not urgent, noted so it isn't lost.

## Char literals and string escape sequences — done

Raised directly, looking at `stdlib/display/display.cleave`: no way to write a byte value except as a raw ASCII integer (`out.push(32)` for a space — no `' '`), and no way at all to write `\n` (`string_lit`'s own grammar took source text completely verbatim, `"\"" ~ (!"\"" ~ ANY)* ~ "\""` — a `\` had no meaning, so a literal newline inside a source-code string was the *only* way to get one).

**Both closed as pure, full-erasure sugar — no new `ExprKind`, no changes anywhere past `lower.rs`.** `'a'`/`'\n'` (`char_lit`, new grammar rule) desugars straight to an `i8`-suffixed `NumberLit` — exactly what `10:i8` already meant, nothing downstream (inference, CPS, MLIR lowering) has anything new to learn about. `string_lit`'s own grammar gained one alternative (`"\\" ~ ANY`, tried before the plain-passthrough case) so a `\` no longer risks ending the string early on `\"`; the *actual* escape decoding (`decode_escapes`, `lower.rs`, shared by both `lower_string_lit` and the new `lower_char_lit`) happens at lowering time, walking the already-quote-stripped text byte by byte. Supports the standard set: `\n \t \r \\ \" \' \0`; an unrecognized escape, or a char literal that decodes to anything other than exactly one byte (an un-escaped multi-byte UTF-8 character — the one shape the grammar itself can't reject), is a hard `panic!`-level compile-time error, matching this file's own existing convention for a structurally-valid-but-semantically-malformed literal (`lower_array_lit`'s own array-repeat count check takes the identical posture).

**Deliberately scoped to bytes, not Unicode `char`s** — consistent with every other text-handling decision already made in this codebase (`lower_string_lit`'s own long-standing "not `char` — nothing elsewhere in this compiler has any text-encoding stance to contradict" byte-per-`NumberLit` design, `Display<T>`'s own ASCII-only scope). A char literal outside the ASCII range or spanning more than one raw byte doesn't parse.

**`stdlib/display/display.cleave` migrated to use the new literals** in the same pass — every `out.push(45/91/93/44/32)` became `out.push('-'/'['/']'/','/' ')`, and the digit-lookup table became `['0','1',...,'9']` instead of `[48,49,...,57]` — the exact motivating case, now readable instead of magic numbers.

**Verified**: new tests in `cleave/tests/lower.rs` (`string_literal_escapes_decode_to_their_real_byte_values`, `char_literal_desugars_to_an_i8_suffixed_number_lit`, `char_literal_escapes_decode_to_their_real_byte_values` — AST-level, checking the exact decoded byte per escape) and `cleave/tests/mlir_lower.rs` (`a_char_literal_evaluates_to_its_ascii_byte_value`, `a_string_literal_with_escapes_indexes_to_the_right_decoded_bytes` — real JIT execution, `run_i32`). Full `cargo test --workspace` clean; every existing `Display<T>` byte-exact test (`display_i32_produces_the_exact_expected_bytes` and friends) still passes unchanged after `display.cleave`'s own migration to the new literals, confirming the rewrite is behavior-preserving.

**Deliberately not attempted here — a separate, later decision if ever needed**: a `format!`-style interpolated string (`"x={x}"`) — discussed directly; this project has no macro/compile-time-codegen mechanism at all today, so a real one would need genuinely new infrastructure (or a fixed-arity variadic-via-tuple approach, `Print<(A,B,C,D)>`'s own existing shape, but without real interpolation in the template text itself). Not on the critical path to this project's own north star (convex hull, triangulation, simple ML, linear algebra); `DynArray<i8>`/`Display<T>`'s own chained-`push`/`display` style, now with real char literals and escapes, already covers the actual current need.

## Variadic generics — done: `Vector`/`Matrix`/`Tensor` migrated onto one pack-generic `Tensor`

**Done and tested, including the real stdlib migration, not just the underlying mechanism.** A generic parameter can be declared a *pack* (`const Dims...: i32`/`Args...`, trailing `...` right after the name — `grammar.pest`'s own `generic_param`/`pack_marker`/`pack_ref` rules). Four things all work end to end now, confirmed via real JIT tests (`tests/infer.rs`, `tests/mlir_lower.rs`), not assumed:
- An *ordinary* (heap-allocated) pack-generic struct (`struct Tensor<T, const Dims...: i32> { data: [T; Dims...] }`) constructs and reads its own fields back correctly via an explicit turbofish (`Tensor::<f64,3,4,5>(...)`, `infer.rs::infer_struct_lit_with_pack`/`ty_from_ast_mapped_with_pack`, mirrored in `mlir_lower.rs::struct_field_types`). Construction *always* needs the turbofish — inferring a pack's own arity from a field literal's shape alone is a deliberate, accepted v1 restriction (`TypeErrorKind::VariadicStructNeedsTurbofish`), not attempted.
- **An algebra impl that's itself generic over the pack** (`impl<T, const Dims...: i32> Ring<Tensor<T, Dims...>>`, one impl covering every rank) — real bodies (`mlir::arith::addf(a,b)`), not just an empty tag impl. Needed a genuinely new `Ty` shape: `Ty::Pack(TyVar)` (the *symbolic*, unresolved form — embedded as an ordinary node inside `Ty::App`'s own args list, so the *existing* `free_vars`-driven `generalize`/`instantiate` machinery quantifies it for free, no new field on `Scheme`/`ImplTemplate`) and `Ty::PackResolved(Vec<Ty>)` (the concrete, resolved form, bound through `Subst`'s *ordinary* `bindings` table via `bind_pack`). `unify`'s `(Ty::App, Ty::App)` arm became pack-aware: same name required as before, but arity no longer has to match exactly when one side's own args end in a still-open `Ty::Pack` — the non-pack prefix unifies pairwise and the pack absorbs whatever the other side has left over.
- **The `#[mlir_type(tensor)]`-tagged *native value* representation** (`Tensor`'s own real representation) generic over a pack, including a real arithmetic call through it (`Ring::add`, JIT-executed, correct values back), *and* a pack-generic `Index<Tensor<T,Dims...>,T>` reading an element back through it (`v[i]`/`m[i,j]`/`t[i,j,k]`, one impl covering every rank).
- **`Ty::PackLen(TyVar)`** (`Dims.len()`) — needed so `Index`'s own `idx: [i32; Dims.len()]` parameter isn't a fixed literal arity. Symbolic exactly like `Ty::ConstExpr` (folds to `Ty::Const` once the pack resolves), recognized from ordinary `<pack-name>.len()` method-call syntax (`Infer::pack_len_from_method_call`) — no new grammar or AST node needed.

**Real bugs found and fixed along the way, beyond the pack mechanism itself:**
- `unify`'s pack-aware `(App, App)` arm treated *any* case where both sides end in a still-open `Ty::Pack` as `Mismatch`, including when it's the *same* `TyVar` on both sides — the common case at declaration time (an algebra's own expected type and an impl's explicitly-annotated declaration are both built from the same `impl_mapping`). Fixed with a dedicated `v1 == v2` arm.
- `lower_field_access`/`lower_array_load`/`lower_array_store` (`mlir_lower.rs`) never had a case for a `#[mlir_type(...)]`-tagged struct's own native tensor representation at all — produced a real `llvm.getelementptr` on a bare `tensor<...>` value (an MLIR verifier error) the moment a tag-tensor struct's field was accessed through anything that wasn't optimized away first (silently masked until now — every existing stdlib use read through the reserved `mlir::tensor::extract` intrinsic instead of ordinary field syntax). Fixed: field access on a tag-tensor struct returns the base value directly (identity — its sole field *is* the struct's own value); `lower_array_load` gained a `tensor.extract` branch. `lower_array_store`/`lower_field_store` on a tag-tensor value panic clearly — index-assignment into a native tensor SSA value is genuinely unsupported (`tensor.insert` is functional, would produce a *new* value, nothing rebinds the CPS variable to it) — no existing stdlib/example code needs it, so left as a flagged gap, not built.
- `mlir::tensor::extract`'s own real MLIR arity is "one index operand per dimension," fixed and unknown until a pack resolves — `lower_raw_mlir_op` gained one deliberate, narrowly-scoped exception (alongside the pre-existing `linalg.` one): when its own second argument is array-typed rather than scalar, it reads the array's own static length and splices its elements in as the real op's separate index operands (`lower_tensor_extract_spread`) — the same shape `lower_tagged_struct_construct` already used for `tensor.from_elements`.
- `generic_arg_to_ty` (turbofish-argument resolution) used to resolve unconditionally against an *empty* generics mapping — a long-documented, deliberately-unfixed gap — so a turbofish inside a generic impl body naming the impl's *own* enclosing generic (`Tensor::<T,N>(...)` inside `impl<T,const N:i32> Zeroed<Tensor<T,N>>`) resolved `T` as a bogus literal type spelled `"T"` instead of the impl's own `T`. Blocked `stdlib/nn/nn.cleave`'s own migration directly. Fixed by resolving against `self.active_generics` instead — safe for every other caller too (empty whenever irrelevant).

**What's left, not yet attempted**: whether `Index<Tensor<T,Dims...>,T,K>` generalizing `K` itself (rather than each impl fixing it via `idx`'s own array length) is ever needed; index-*assignment* into a pack-generic native tensor (`v[i] = x`, see the `lower_array_store` gap above) — no existing use needs it yet.

## Multi-level call transparency in the e-graph forward translator — done

**Done, not just discussed** — `Forward::walk` now genuinely inlines a callee whose own body is a *chain* of further pure calls (`fn sigmoid(x) { 1.0 / (1.0 + exp(-x)) }` — four chained calls: `neg`, `exp`, `add`, `div`), not just a single primop (`Ring::add<f32>`, which still collapses to *one* opaque `Op` node — the right call for a genuinely atomic unit, since its own identity as a *named* op is exactly what a declared axiom/derivative rule needs to match against). A named call to `stdlib/nn/nn.cleave`'s own `sigmoid` now differentiates correctly through `derive()`, where it used to fail with "unsupported control flow" even though the exact same body written inline already worked.

**The mechanism**: `is_transparent_chain` (`egraph.rs`) — a new, separate check from `is_straight_line`, recognizing a `Fix` whose own `recognize_real_call` target is either `is_straight_line` (a single primop) or itself (recursively) a transparent chain, with cycle protection (`visiting`, guarding against mutual recursion) — used by `Forward::walk`'s own `Fix` arm to decide whether to walk *into* a callee's own body (multi-level transparency) instead of collapsing it into one opaque node. Real inlining, not just recognition: the callee's own parameters are bound to the caller's already-resolved argument e-classes, its own body is alpha-renamed (`Forward::alpha_rename`, already built for `try_unroll_for_loop`'s identical concern — repeated loop iterations) against a properly-seeded, *shared* `FreshVars` (now threaded through `Forward::walk`'s own signature, not created fresh per call site — a per-call-site instance would let two separate inlinings of the *same* callee, e.g. `sigmoid(w1)` and `sigmoid(w2)`, alias each other's internal temporaries in `self.env`), then walked the same way as any other segment; the callee's own tail `App` (calling its own return continuation) is where the final result e-class is read back from.

**A real bug found and fixed in `is_transparent_chain` itself, empirically, not caught by reasoning alone**: the initial version kept a callee's own name in the `visiting` cycle-guard set across *both* recursing into its body *and* checking `rest` (what comes after it in the same segment) — meaning a second, sequential *sibling* call to the same unit (`sigmoid` called twice inside one `forward`, neither call nested inside the other) looked identical to genuine mutual recursion and was wrongly rejected. Fixed by removing the name from `visiting` immediately after checking the callee's own body, before checking `rest`.

**A real, separate finding, not a bug — significant, not just theoretical.** Equality saturation over even a *minimal* two-level-nested case (a function calling another function that itself calls `sigmoid`, four parameters total, no batching/looping at all) reliably takes 30+ real seconds and recurses deep enough to overflow the *default* 2MB stack a `cargo test` thread gets (confirmed directly — passes reliably under `RUST_MIN_STACK=64MiB`, and via the real CLI, whose own main thread already has more headroom). This is *nesting depth itself*, not batch size or parameter count, driving the cost — the same underlying mechanism the "`derive()`'s own saturation grows combinatorially" item below already tracks (commutative axioms doubling representations per operation), now confirmed to compound sharply with each additional level of call nesting specifically. Not fixed (would need either bounding recursion depth, converting the recursive walk to an explicit stack, or addressing the saturation-cost item below directly — all real, separate work). Consequence: no test exercising a genuine multi-level-nested network lives in the ordinary `cargo test` suite at all — `examples/xor.cleave` (a real 2-hidden-neuron network, trained by gradient descent) is where this shape is actually exercised, via the slower examples sweep, not unit tests.

**Also raised, not yet attempted**: `doc/backlog-done.md`'s own "unroll statically-bounded `for` loops" item's own follow-on — combined with `is_straight_line`/`is_transparent_chain` no longer hard-coding rejection for a *for-loop-shaped* `Fix` specifically (today both do, unconditionally, regardless of what `Forward::try_unroll_for_loop` can do once it's already looking at the loop directly), this would also let calling `stdlib/nn`'s own `sum`/`mean`/`max_of` — each a `for` loop internally — become reachable from inside a function passed to `derive()`, not just a hand-written accumulation loop in the caller's own body.

**Four real, separate bugs found and fixed getting here** (trying to build a first trainable neuron/MLP example, per the "toward simple ML" roadmap item — `stdlib/nn/nn.cleave`'s own `sigmoid` was the first real case needing more than one composed differentiable primitive):
- `Ring<T>` (`stdlib/num/num.cleave`) never had a `derivative` rule for `div`/`neg` at all — only `add`/`sub`/`mul` did. Added: `derivative div(a, b): div(sub(mul(d(a), b), mul(a, d(b))), mul(b, b));` (quotient rule), `derivative neg(a): neg(d(a));`.
- **A general, pre-existing bug in `derivative_rule_to_rewrite`** (`egraph.rs`): the differentiation variable's own internal e-graph pattern symbol was the literal `?x` — silently *colliding* with a declared parameter genuinely named `x` (`fn exp(x: T) -> T; derivative exp(x): mul(exp(x), d(x));`, the new `Transcendental<T>` algebra below). The rule then only matched when the method was applied *directly* to the exact variable being differentiated (`exp(w)` w.r.t. `w`) — any real composition (`exp(exp(w))`, `exp(-w)`) left the derivative marker permanently stuck, silently. Invisible on `Ring<T>` (whose own params are always named `a`/`b`) purely by naming coincidence — confirmed directly: `exp(exp(w))`, composing the *same* algebra with itself, failed identically, ruling out any cross-algebra explanation before landing on the real one. Fixed by renaming the internal symbol to `?__diff_x`, which can never collide with a real declared parameter.
- A qualified call (`Transcendental::tanh(x)`) inside a fully-concrete, non-generic impl's own body (`Activation<f32>::tanh`) had no path to a `call_names` entry at all, in *two* separate places: `monomorphize.rs`'s `ImplMatch::FoundConcrete` recorded the outer call site but never enqueued the matched template onto `impl_worklist` (unlike `ImplMatch::Found`), so nothing walked its own body for the nested call; separately, `cps.rs::collect_units`'s own non-generic-impl branch (which compiles *every* concrete impl unconditionally, regardless of reachability) hardcoded `call_names: HashMap::new()`. Both needed fixing — confirmed by direct testing that either gap alone still crashed the JIT natively (`could not resolve call`, not a clean type error) on a genuinely non-generic algebra calling another, qualified, for the first time anywhere in this codebase.
- The `is_transparent_chain` sibling-call bug described above.

**Also added along the way**: `Transcendental<T>` (`stdlib/num/num.cleave`), a new algebra for named, individually-differentiable transcendental primitives (`exp`, `tanh` so far — more added when needed) — `tanh`'s own derivative rule used to live on `Activation<T>` (`stdlib/nn/nn.cleave`, ML-specific), the wrong layer: a fact about the *math function* tanh on `f32`/`f64`, not about activations. `Activation<T>::tanh` now delegates via a qualified call (`Transcendental::tanh(x)` — genuinely ambiguous unqualified, both algebras declare a 1-arg `tanh` now); `sigmoid` is built from `exp` plus ordinary `Ring` arithmetic instead of raw, undifferentiated `mlir::...` calls, so its own derivative composes for free through ordinary chain-rule saturation — no hand-written `derivative sigmoid` needed at all.

**Verified end to end, not just unit-level**: a real 2-input, 2-hidden-neuron, 1-output network (`fn forward(...) { let h1 = sigmoid(...); let h2 = sigmoid(...); sigmoid(h1*w5+h2*w6+b3) }`, called from a `loss` passed to `derive()`) differentiates correctly — checked against a real finite-difference numerical approximation (`(loss(w+eps)-loss(w))/eps`), not a hand-derived closed form (the network is too deep to hand-verify reliably) — the two agree to within `eps`'s own precision.

## Differentiating a struct/array construction — done

**Done, not just discussed.** `d(w)` where `w = Tensor::<f32,2>(data:[w1,w2])` (or any ordinary struct/array built from parameters) had no path to a derivative at all before this — found directly while reaching for a tensorial reformulation of `examples/xor.cleave` (`linalg::Tensor` weights instead of individual scalar ones): differentiating `w[0]` alone, no arithmetic, reported `no derivative rule for Index::index<...>, struct:Tensor<f32,2>:data` even after `Index::index` itself got its own `derivative` rule (below) — `PrimOp::Struct`/`PrimOp::Array` construction nodes had no rule of their own, since they aren't algebra methods and so can't be given one via an ordinary `derivative` item in cleave source.

**The rule, agreed on before writing any code**: differentiating a construction distributes component-wise onto its own arguments — `d(Struct(f1:e1,...,fn:en)) = Struct(f1:d(e1),...,fn:d(en))`, `d([e1,...,en]) = [d(e1),...,d(en)]`. Built-in (`egraph.rs::construction_derivative_rewrites`), not declarable — same reasoning `derivative-self`/`derivative-independent-zero` already use for being hardcoded rather than registry-declared. One concrete rule per actually-reached struct/array shape (`Forward::struct_ops`/`Forward::array_ops`), mirroring `struct_projection_rewrites`'s own "only build what this translation actually touched" discipline. A genuinely different, particular constructor not fitting this uniform, component-wise shape would still need its own explicit `derivative` rule — this built-in rule only covers the ordinary case.

**A real, separate prerequisite fixed alongside**: `linalg::Index<Container,Elem,K>` (`stdlib/linalg/tensor.cleave`) had no `derivative` rule of its own at all — `derivative index(c, idx): index(d(c), idx);` added (`d/dx[c[idx]] = (dc/dx)[idx]` — reading an element and differentiating commute; `idx` itself is never wrapped in `d(...)`, reused as-is the same way the product rule already reuses an undifferentiated operand).

**Verified**: `f(w1,w2) = w[0] + w[1]*w[1]` where `w = Tensor::<f32,2>(data:[w1,w2])` differentiates to `[1, 2*w2]`, both via direct `--run` probes and as a regression test (`derive_through_a_tagged_tensor_constructed_from_parameters_and_indexed_back`, `tests/mlir_lower.rs`) — proves the new rule composes correctly with `Index`'s own new rule and `Ring`'s product rule, not just that construction alone differentiates in isolation. A second test (`derive_through_a_plain_struct_constructed_from_parameters_and_read_back`) exercises the identical rule through an ordinary user-declared struct and `struct_projection_rewrites`'s field-read path, proving it's genuinely generic, not `Tensor`-specific.

**What's left**: `examples/xor_tensor.cleave` (see the next item below) is the real tensorial reformulation this was unblocking — done. `PrimOp::Load` (reading from an *ordinary*, non-tagged `[T;N]` array by index — a different mechanism from `Index<Tensor<...>,...>`, used for plain arrays) still has no *composing* `derivative` rule of its own (only the independent-zero shortcut below knows its shape) — a separate, still-open gap, no example/use case has needed more than that yet.

## Toward a matmul-based tensorial XOR — three real bugs found and fixed, all done

Picking directly back up from the item above — giving `linalg::MatMul<A,B,C>` (`stdlib/linalg/matrix.cleave`) its own `derivative matmul(a, b): add(matmul(d(a), b), matmul(a, d(b)));` (the ordinary, non-commutative product rule — matrix multiplication is bilinear, same shape as `Ring`'s own product rule, just order-sensitive) surfaced three further real, separate bugs — all now fixed and tested, no workaround needed for any of them.

**Bug 1, fixed: a `derivative`/`axiom` rule's body could only ever use *one* flat type string for every call inside it.** `build_pattern`/`derivative_rule_to_rewrite` (`egraph.rs`) tracked a single `ty: &str`, reused unconditionally for *every* nested call in a rule's own body — fine for every existing rule, since every algebra a `derivative` rule ever called into (`Ring<T>`, `Transcendental<T>`, itself) happened to be single-generic, so the flat string always *was* the right type. `MatMul<A,B,C>` breaks that coincidence: its own product rule's outer `add(...)` call needs `Ring::add<C>` specifically (`C` alone, e.g. `Tensor<f32,2,2>`), not the whole "A,B,C" combined string `concrete_type_of` reports for a multi-target algebra — confirmed directly, not guessed: an early attempt panicked building a literal `Op` node named `Ring::add<Tensor<f32,2,2>, Tensor<f32,2,2>, Tensor<f32,2,2>>`, a unit that could never actually exist.

Fixed by threading a real per-parameter type environment through `build_pattern` instead of one flat string: each `Call` node now returns `(Id, Option<String>)`, its own resolved result type computed from the *owning* algebra's own declared return type (`registry.fn_sig(...).ret`, substituted through `generic_substitution` — a new helper splitting a multi-target combined string back into its own generic-name -> concrete-type map, using `registry.generics`, mirroring how the combined string was *built* in the first place, `cps.rs`'s own `targets_str`). A same-algebra recursive self-call (`MatMul::matmul` calling itself inside its own rule, `Index::index` likewise) still reuses the enclosing flat `ty` unchanged — genuinely correct there, not just convenient, and byte-identical to every rule's own existing behavior. A genuinely different-algebra call (`Ring::add`, from inside `MatMul`'s rule) now resolves against the *single* concrete type its own arguments actually agree on, rather than the enclosing rule's own combined string; disagreement (or an argument whose own type isn't resolvable) bails (`None`) rather than guessing, matching this whole function's existing posture.

**Bug 2, fixed: `derivative-independent-zero`'s own "0" was always a bare scalar literal, regardless of `?a`'s real shape.** Sound for every rule this project had written so far — nothing had ever differentiated a whole independent *tensor*/array/struct value before. Building the tensorial XOR's own forward pass (`matmul(x, W)`, `x` an input tensor, independent of whichever weight `W` is being differentiated) hits it directly: `d(x)/dW` matches `derivative-independent-zero`, which unioned a bare `CleaveLang::Float(0.0)` into an e-class that also (correctly) contained a full zero-tensor from the chain rule's own recursive expansion — a real type-soundness violation sitting in one e-class, and the wrongly-shaped, cheaper one is exactly what a cost-based extractor prefers. Confirmed via a minimal, isolated probe (an identity-matrix literal fed into `matmul`) before touching any code: crashed MLIR lowering with "a nested array's own element must be an already-built array value, not a bare literal."

Fixed with a genuinely dynamic mechanism, since the correct shape is only known at rewrite-*application* time, not when the rule itself is built:
- `ConstantFold` (the egraph `Analysis`) gained `known_types: HashMap<Symbol, Ty>`, populated by `Forward` at *every* one of its own node-insertion sites (`Free`, `Struct`, `Field`, `Array`, `ArrayRepeat`, `Load`, a raw `mlir::...` op) right before the corresponding `egraph.add` — `Free`'s own type comes from a new `Forward::param_types` map (the differentiated function's own real parameter types, since every `Free` node this translation ever mints traces back to one of them). `FoldData` gained a matching `own_ty: Option<Ty>` field, computed compositionally in `make` (`Free`/`Op` nodes look themselves up in `known_types`; everything else stays `None`, deliberately — see below) and merged conservatively (drops to `None` on disagreement rather than trusting either side or asserting, unlike `const_int`'s own merge policy — a real type-soundness violation here is a different order of problem than an unproven-yet constant-fold).
- `derivative-independent-zero` is no longer a declarative `egg::Pattern` RHS at all — a hand-written `IndependentZeroApplier` (`impl egg::Applier`) folds the old disjointness condition and the new zero-construction into one `apply_one`: a bare literal leaf (`CleaveLang::Float`/`Int`) still gets an immediate scalar zero, unconditionally correct since a literal is inherently scalar by construction, no `Ty` lookup needed at all; otherwise it reads `?a`'s own `own_ty` and calls a new recursive `build_zero`, which knows exactly three shapes — a scalar numeric `Ty::Con`, `Ty::Array(elem,size)` (recursively, symbol-for-symbol matching what a real literal construction of that shape would have built), and a single-field, pack-generic struct (`linalg::Tensor`'s own shape, recognized *structurally* — a variadic trailing generic, exactly one field — via a new `Registry::struct_names` enumerator plus `struct_fields`/`struct_generics`, not by hardcoding the name "Tensor"). Anything else (a genuinely multi-field struct, a raw algebra-`Op` node whose own result type was deliberately left untracked) makes the rule simply not fire for that e-class — sound, not a guess: the full recursive chain-rule expansion, already present in the same e-class regardless, is what supplies the correct answer there instead; this rule stays a pure optimization shortcut, never the sole source of truth. `Registry::struct_names` was added specifically because `IndependentZeroApplier` (an `Applier` impl) must be `Send + Sync + 'static` and so can't hold a borrowed `&Registry` — the qualifying struct/field-name pairs are snapshotted once, owned, when the rule is built.
- Three existing unit tests (`derivative_of_a_different_free_variable_is_zero`, `derivative_of_x_times_y_with_respect_to_x_eliminates_the_derivative_marker`, and a regression in `derive_of_a_function_containing_a_statically_bounded_for_loop_computes_the_correct_derivative`) broke initially, all for the same reason: they build raw e-graph nodes directly, bypassing `Forward` entirely, so nothing ever populated `known_types` for their own `Free`/`Load` nodes. Fixed by having the hand-built tests populate `known_types` themselves too (matching what real code already does) rather than weakening the new mechanism — the `derive_of_a_function...for_loop` one specifically needed `PrimOp::Load`'s own result type tracked too (`data[i]`, a compound but still-independent-of-`w` read), the real, general case this bug was about, not a synthetic one.

**Verified**: the original identity-matrix probe now gives the mathematically correct gradient (`[1,0,0,1]` for `f(A) = trace(A @ I)`), as a real regression test (`derive_through_matmul_against_a_constant_identity_matrix_uses_the_product_rule_and_a_typed_zero`, `tests/mlir_lower.rs`); `cargo test --workspace` passes (modulo the one already-documented, pre-existing, load-order-flaky `a_structural_linalg_matmul_on_tagged_matrices_computes_the_right_values`, confirmed unrelated via `git stash` against the pre-session base and by it passing/failing inconsistently in isolation *before* any of today's changes too).

**A fourth thing found along the way, fixed narrowly, not broadly**: `tests/mlir_lower.rs`'s own shared `run_i32` helper never ran `optimize_program` at all (only `synthesize_derivatives`) — a real, if narrower, sibling of the already-documented "`run_i32` skips `check_type_errors`, unlike `main.rs`" entry above. The regression test above needs it: the freshly-synthesized, *un*-optimized `MatMul` derivative tree panics MLIR lowering under plain `run_i32`, while the identical source runs correctly through the real CLI (whose own `--run` path *does* call `optimize_program`) — the pipeline gap, not a logic bug, confirmed by adding the missing step and watching the same test start passing. Adding `optimize_program` (+ its surrounding `eliminate_dead_code` sweeps) directly to `run_i32` itself was tried first and reverted — it broke five other, unrelated, already-passing tests elsewhere in the same file, too invasive a change to a helper 125+ tests already share for a gap only this one new test hits. Landed instead as a separate `run_i32_with_optimization_pass` helper (sharing the MLIR-lowering/JIT tail via a new `run_i32_from_cps`), used only where needed. The five break-when-added failures were not themselves investigated — a real, separate, still-open question (does `optimize_program` have its own latent bug those five cases would hit for real via the actual CLI too, or is it specific to some artifact of `run_i32`'s own harness) worth a real look before ever widening `run_i32` itself.

**Bug 3, found and fixed — a real monomorphization-ordering gap, not an e-graph one**: `Ring<Tensor<T,Dims...>>::add` (the pack-generic elementwise impl `linalg::Tensor`'s own arithmetic already goes through) is a *generic* impl — `cps.rs::collect_units` only ever builds a concrete `ConcreteUnit` for it on demand, when monomorphization sees a real call site in the program that needs that exact instantiation. A `derivative` rule's own synthesized reference to `Ring::add<Tensor<f32,2,2>>` (the sum in `MatMul`'s own product rule) used to be discovered far too late for that — monomorphization had already finished by the time `synthesize_derivatives`/`derivative_rule_rewrites` ran. Confirmed directly before fixing anything: a program that calls `matmul` but never calls `Ring::add` on a `Tensor` anywhere else panicked extracting the synthesized derivative (`egraph: extracted Op node "Ring::add<Tensor<f32,2,2>>" is in none of this module's own lookup tables, nor a known real call`) — the *exact same* program, with one throwaway direct call to `a + b` on two `Tensor`s added purely to force monomorphization, differentiated correctly. `synthesize_derivatives`'s own existing `referenced`-set mechanism (letting `rebuild` recognize a unit the *program* never called but a fired rule's own RHS does) only ever helped when the unit already existed somewhere in `units` — it couldn't, and still can't, retroactively trigger monomorphization of a *generic* impl that was never a real call site to begin with.

**The real fix, in `monomorphize.rs`**: two new functions, `find_impl_for_target` (given an algebra/method/concrete-target-types tuple, finds the one `ImplTemplate` — if any — whose own `target_patterns` unify against it, mirroring `derive_impl_instantiation`'s own free-var read-back, but matching on the target alone since the caller already knows exactly which algebra/method it wants, nothing to disambiguate) and `seed_derivative_rule_references` (given an algebra/method that just got a real specialization built, looks up that method's own `derivative` rule, if any, resolves each of *its own* subexpressions' concrete type bottom-up — a deliberately duplicated, `egg`-free copy of `egraph.rs::build_pattern`'s cross-algebra resolution, since `monomorphize.rs` mustn't depend on `egg` — and for every call it finds into a genuinely *different* algebra, calls `find_impl_for_target` and pushes the match onto `impl_worklist`). Wired in with one extra call inside `monomorphize()`'s own existing `impl_worklist` drain loop, right alongside the pre-existing `collect_instantiations` call that already discovers ordinary call-based instantiations. Deliberately *not* a separate outer fixed-point pass: `impl_worklist` is drained with a plain `while let Some(...) = impl_worklist.pop()`, so an entry pushed mid-loop is picked up naturally by that same loop's own later iterations — free, correct fixed-point behavior (a newly-seeded unit's own `derivative` rule, if it has one, gets the identical treatment in *its own* turn) with no new control-flow structure needed. `Infer::ty_from_ast_mapped` (previously private) was made `pub(crate)` — the one piece `monomorphize.rs` didn't already have its own equivalent of, needed to resolve a rule's own declared parameter/return types against a concrete substitution.

**Verified**: the original two-bug identity-matrix probe now differentiates correctly with *no* forced-monomorphization workaround at all — confirmed directly (removed the throwaway `a + b` call, re-ran, still correct `[1,0,0,1]`) — and the regression test (above) was simplified to drop it too. `cargo test --workspace` passes; both matmul-pipeline tests (this one and the pre-existing `a_structural_linalg_matmul_on_tagged_matrices_computes_the_right_values`) share the already-documented "intermittently flaky under same-binary concurrent test execution" issue (see that item above, refined during this same investigation) — confirmed unrelated to this fix, both pass reliably every time run in isolation by name.

**`examples/xor_tensor.cleave` — the real payoff, done end to end**: same 2-input/2-hidden/1-output XOR network as `examples/xor.cleave`, same SGD schedule, same init, but the linear part of each layer is a real `matmul` over `linalg::Tensor` weight matrices instead of nine separate scalar multiplies (`x: Tensor<f32,1,2>` — a single training example as a real matmul-compatible row — `matmul(x, w) + b1`, elementwise-activated, `matmul(h, w2m) + b2`). `Activation<Tensor<T,Dims...>>` is only declared rank-1 today (`stdlib/nn/nn.cleave`, a separate, not-yet-done pack-generalization) — a small `sigmoid2` helper applies the ordinary scalar `sigmoid` element-by-element instead (`Index` read, apply, construction rebuild), using only already-proven mechanisms, not a workaround for anything still broken. Trained output matches `examples/xor.cleave`'s own **bit-for-bit** (`0.03071228, 0.9665359, 0.9657611, 0.04274264` — identical starting weights, identical math, just reorganized through `matmul`), a strong independent correctness signal beyond the finite-difference checks used earlier in this item. A small forward-pass gradient (`fd_w1`/`g[2]`, `fd_w6`/`g[9]`) was also checked directly against numerical finite differences before writing the full training loop.

## Real pack-generic `[value; Dims...]` array-repeat — done

Raised directly by the project owner while discussing `derivative_independent_zero`'s own `build_zero` (this file's own "Toward a matmul-based tensorial XOR" item): `build_zero` hand-recognizes "a single-field, pack-generic struct" *structurally*, in Rust — exactly the kind of hardcoded-in-the-compiler logic this project's own discipline says new functionality should never need (goes through `algebra`+stdlib instead). The blocker for fixing that properly was concrete and identified directly, not assumed: there was no way to *write*, in ordinary cleave source, "build a same-shaped `Tensor<T,Dims...>` filled with a repeated value" at all — `[value; N]` (`ExprKind::ArrayRepeat`) only ever accepted one named const generic as its own count, never a whole pack (`Dims...`). This item is that missing piece — real, general, not scoped to zero specifically (any pack-generic construction needing a same-shaped repeated value benefits) — done and tested; wiring it into an actual `Ring<T>::zero()` and rebuilding `derivative-independent-zero` on top of it is a separate, following item.

**Four real, separate layers, each needing its own fix — found by direct testing at each step, not anticipated up front:**
- `grammar.pest`: `array_repeat`'s own count position only accepted `numeric_lit | ident` — extended to `numeric_lit | pack_ref | ident` (`pack_ref` tried first, same ordering precedent `type_`'s own `pack_ref`-before-`path` already uses). `lower.rs` gained a matching `Rule::pack_ref` arm building `ExprKind::PackRef` (mirroring `lower_array_dim`'s own identical extraction elsewhere).
- `infer.rs`: `ExprKind::ArrayRepeat`'s own inference arm special-cases a `PackRef` count — `Dims` alone was never an ordinary bound value reachable through `infer_expr` (only `Dims.len()` is recognized; a bare `Dims` panics there on purpose), so it resolves through `self.active_generics` directly instead (the same map `ty_from_ast_mapped`'s own identical `TypeKind::PackRef` handling already reads), producing `Ty::Array(elem, Ty::Pack(v))` — the same one-level, symbolic shape a struct field's own `[T; Dims...]` declared type already gets.
- A **real, general `unify` gap**, found immediately by direct testing (not anticipated): a bare `Ty::Pack` reaching `unify` outside its one previously-intended position (nested inside an `App`'s own args list, which has its own dedicated pack-aware arm) had no arm to match *at all* — even two occurrences of the exact same still-open pack variable failed to unify, since `Ty::Pack` was never expected as a standalone type before this. Needed for real here: `infer_struct_lit_with_pack` unifies the array-repeat expression's own two independently-built `Ty::Array(_, Pack(v))` values (the field's own declared type vs. the value's own inferred type) against each other — both reading the identical `active_generics` var, so always the same `v`, but `unify` still had no rule saying so. Fixed with a narrow, safe `(Pack(v1), Pack(v2)) if v1 == v2 => Ok(())` arm — deliberately *not* a general "bind a Pack against anything" rule the way `Ty::Var`'s own is (a Pack stands for a *list*, so that would be unsound); two genuinely different open packs meeting still falls through to `Mismatch`, unreached today, flagged not fixed. `Subst::apply`'s own `Ty::Array` arm and `monomorphize.rs`'s `substitute` both also gained the actual pack-*expansion* step this whole item is for: `size` resolving to a `Ty::PackResolved` list turns one symbolic `Array` level into the real nested chain (the identical `rev().fold` shape `mlir_lower.rs::resolve_struct_field_ty_with_pack` already uses for a struct field's own identical surface shape — this item's own general-purpose counterpart of that, reusable beyond struct fields specifically now).
- `cps.rs`: `ExprKind::ArrayRepeat` conversion special-cases a `PackRef` count too — `count` itself never needs converting (no runtime value, only a shape); a new `convert_array_repeat_over_resolved_dims` reads the real, fully-resolved nested `Ty::Array` chain (already expanded by this point, post-monomorphization) and builds one real `PrimOp::ArrayRepeat` per nesting level, innermost first — byte-for-byte the same CPS shape a hand-written `[[value; d2]; d1]` already produces via two ordinary, syntactically-nested `ArrayRepeat` conversions. `mlir_lower.rs` needed **no changes at all** — nested `PrimOp::ArrayRepeat` construction already worked (proven by every existing hand-written multi-dim literal), this only needed to generate that same shape mechanically instead of requiring it spelled out in source.

**Verified**: a throwaway `Filled<T>` algebra (`impl<T: Float, const Dims...: i32> Filled<Tensor<T, Dims...>> { fn filled() -> Tensor<T, Dims...> { Tensor::<T, Dims...>(data: [7.0; Dims...]) } }`) builds and reads back correctly at rank 1 (`Tensor<f32,3>`), rank 2 (`Tensor<f32,2,2>`), and rank 3 (`Tensor<f32,2,2,2>`), all through the real `--run` JIT pipeline. `cargo test --workspace` passes.

## `Ring<T>` gained a real `zero()` — and a real, long-latent `matmul` bug found along the way — done

The direct follow-up to the item above: `egraph.rs::build_zero` (`derivative-independent-zero`'s own zero-construction) hand-recognized "a single-field, pack-generic struct" *structurally*, in Rust — the whole reason the array-repeat-on-a-pack item above got built. `Ring<T>` (`stdlib/num/num.cleave`) gained a real `fn zero() -> T;`, impl'd per scalar width (`0`/`0.0`, one line each) and, for the first time expressible at all, a real pack-generic `impl<T: Float, const Dims...: i32> Ring<Tensor<T, Dims...>> { fn zero() -> Tensor<T, Dims...> { Tensor::<T, Dims...>(data: [zero(); Dims...]) } }` (`stdlib/linalg/tensor.cleave`) — the additive identity belongs on `Ring<T>` itself, not a separate algebra, since "zero" only means anything relative to `add`. `build_zero` (`egraph.rs`) shrank to just calling it: `Ring::zero<ty>()`, resolved dynamically at rewrite-application time (`?a`'s own `Ty` is only known then) — when that exact unit was never actually monomorphized (a type with no `Ring` impl at all), the rule simply doesn't fire, same "don't guess" posture as before, now backed by a real stdlib call instead of hand-built Rust.

**A real monomorphization-seeding gap, the same *class* as the earlier "Bug 3" but a different trigger**: `Ring::zero<Tensor<...>>` is never referenced by any *declared* `derivative` rule (nothing calls it from cleave source at all — only `egraph.rs`'s own built-in rule calls it, dynamically), so `seed_derivative_rule_references` couldn't discover it. Fixed with a sibling function, `seed_ring_zero` — wired into the identical `impl_worklist` drain-loop injection point, triggered whenever *any* generic `Ring<X>` method (not just `zero` itself) gets a real specialization built, since that's exactly when `X` becomes a type `derivative-independent-zero` might dynamically need a zero for. `IndependentZeroApplier` also gained its own `zero_calls_used: Arc<Mutex<HashSet<String>>>`, read back into `call_units` *after* `Runner::run` returns (unlike `derivative_rule_rewrites`'s own `referenced`, known before the runner starts) — the dynamic-discovery counterpart of the exact same "a fired rule referenced a unit no ordinary call site reached" problem.

**A real, independently-found MLIR correctness bug, not something this session's own changes introduced — just the first thing to ever trigger it**: switching `derivative-independent-zero` over to `Ring::zero()` exposed that `linalg::MatMul`'s own `matmul` (`stdlib/linalg/matrix.cleave`) had *always* passed `mlir::tensor::empty()` — genuinely uninitialized memory — as `linalg.matmul`'s own `outs` accumulator, on the strength of a comment claiming "the op computes the entire result itself, never accumulates into whatever `outs` previously held." **That claim is wrong**: `linalg.matmul` is documented BLAS-GEMM semantics (`C := A@B + C`), and confirmed directly, not just by documentation — `--dump-mlir-lowered` (post `convert-linalg-to-loops`, not just `--dump-mlir`) shows the lowered loop body genuinely `load`s the accumulator's own current value before adding into it. Every prior test/example happened to get zero-initialized memory back from the allocator anyway (fresh `malloc` is *often* zero early in a program, purely by allocator behavior, never guaranteed) — masking this for as long as `matmul` has existed. Found via a real, reproducible, minimal failure: `matmul(a, Ring::zero())` gave tiny nonzero noise (or outright `NaN`) instead of exactly zero, the moment a genuinely different allocation pattern (one more function call and array-repeat construction ahead of it, `Ring::zero()`'s own real body) shifted which heap memory `tensor.empty()` happened to get. **Fixed** by replacing `tensor.empty()` with `Ring::zero()` — a real, exactly-zero-filled accumulator — directly in `matmul`'s own body.

**A real, unplanned bonus**: the already-documented "`cargo test --workspace` intermittently fails one heavy JIT test under concurrent load" item (`a_structural_linalg_matmul_on_tagged_matrices_computes_the_right_values`) turned out to very likely have been this *same* uninitialized-memory bug all along, not (only) generic resource contention — concurrent thread scheduling shifts allocation patterns the same way the `Ring::zero()` probe did. Confirmed empirically, not just theorized: 6/6 consecutive full-binary runs (previously flaking roughly 1 in 3-5) passed cleanly after this fix, alongside the new tests this whole item added. Left the original item's own text in place rather than deleting it — the "concurrent load shifts allocation patterns" mechanism is still real and could in principle affect some *other* uninitialized-memory-adjacent code path later, even though this specific instance is now fixed.

**A real, separate `Forward::walk` gap found integrating `Ring::zero()` into `matmul`'s own body, fixed narrowly**: `MatMul::matmul`'s own body gaining a real sub-call (`Ring::zero()`) made it stop being `is_straight_line` (which rejects *any* `Fix`, unconditionally) — silently falling through to multi-level *inlining* instead of collapsing to one opaque, rule-matchable `Op` node, losing `matmul`'s own named identity entirely, so its own declared `derivative matmul(a,b): ...` rule could never match anything again (surfaced as a confusing, seemingly-unrelated `no derivative rule for Ring::add<f32>`). A first fix attempt (any algebra-origin'd callee always collapses, regardless of `is_straight_line`) was tried and reverted — it broke `a_real_call_to_an_effectful_unit_stops_at_the_fix`: collapsing to one opaque node still lets equality saturation's own CSE union it with another syntactically-identical call elsewhere, sound for a pure value but not for an effectful one (`Print::print(1)` called twice must run twice, not collapse to one shared call). A *second* attempt (any algebra-origin'd callee whose own body is a pure `is_transparent_chain`) was also tried and reverted — it broke `Activation::sigmoid` (which has no declared `derivative` rule of its own and *needs* to stay on the inlining path; collapsing it to an opaque node with nothing to match left it permanently undifferentiable). The real fix, scoped narrowly: `is_straight_line` itself now also accepts a `Fix` calling a *zero-argument* callee specifically (`Ring::zero()`'s own shape exactly) whose own body is itself a pure chain (`is_transparent_chain`, checked recursively — a zero-arg call could still be effectful in principle) — a zero-argument call can never depend on the enclosing chain's own values at all, so folding it into the same straight-line chain is always sound, and narrow enough that `sigmoid` (whose own sub-calls all take real arguments) is completely unaffected.

**Verified**: the original two-bug identity-matrix probe now gives *exactly* `[1,0,0,1]` (previously `[1, ~1.85e-8, ~9.25e-9, 1]` with the uninitialized-memory bug still present) — the regression test (`derive_through_matmul_against_a_constant_identity_matrix_uses_the_product_rule_and_a_typed_zero`) needed no changes to keep passing. `cargo test --workspace` clean, including 6 consecutive clean full-binary runs specifically re-checking the formerly-flaky matmul test. `examples/xor_tensor.cleave` re-verified end to end, bit-identical output to before this whole item.

Today the e-graph never crosses a real `If` at all (see the "Multi-level call transparency" item above and the equality-saturation "Done" entry) — even the *trivial* case, `if cond { x } else { x }`, where both branches are already the exact same value, isn't seen. Confirmed via direct testing (`--dump-cps-equivalences` on a hand-built example: two branches passing the literal same `CVar` to their own join continuation) that nothing fires today, by design, not by accident.

Established via discussion, not yet built: the trivial "both branches already agree" case is *not* the hard part — representing the join point as one more e-graph node (a `phi`-like `Op`) and adding `phi(a, a) == a` as a rewrite would catch it directly (congruence closure alone doesn't give you this for free — `phi(a,a)==a` is a specific identity about the join operation, exactly analogous to `add_zero`, not a generic consequence of congruence). What's genuinely hard, and still out of scope: (a) either branch containing a real effect — a `phi` over two effectful computations can't be treated as "just a value" the same way a call already can't (`is_pure_prim_op`'s own reasoning applies identically here); (b) code motion — hoisting a sub-computation that's shared between two *different* (not syntactically identical) branches out of the `if` entirely needs real dominance reasoning to prove it's safe to place before the branch, not just a `phi` rewrite.

**The `phi(a,a)==a` rule alone is not sufficient — confirmed by direct testing, not just reasoning.** `examples/join_demo.cleave`'s own `--dump-mlir-lowered` output still shows the untouched `cond_br`/two-block join *and* a real, un-folded `Ring::add<i32>(_, 0)` call after it — both symptoms trace back to the *same* single root cause: `Forward::walk` stops translating entirely the instant it meets the `If` (`env` stays empty for the whole function), so a rewrite rule declared for `phi` would never even get a chance to fire — nothing built the `phi` node for it to match against in the first place, and nothing past the `if` (`b + 0`, here) ever gets translated either. Building the actual fix needs *two* pieces together, not one: (1) the `phi(a,a)==a` rule itself, and (2) extending `Forward::walk`'s own `If` handling so a *pure* `If` (same effect-freedom condition already enforced everywhere else in this module) doesn't stop the segment — it builds a `phi`/join `Op` node and *continues* translating into the join's own continuation, mirroring exactly how single-level call transparency already continues into `rest` after adding one opaque `Op` node for the call itself.

Also raised, genuinely undecided, worth a real design pass before committing either way: whether algebraic-law rewriting (the actual value-add — cleave's own mathematical semantics, which are largely control-flow-independent) belongs in a bespoke CPS-level e-graph pass at all, versus a real MLIR dialect with axioms expressed as canonicalization patterns (MLIR already owns dominance-aware CSE and a real sparse dataflow-analysis framework downstream). The concrete trade-off: MLIR's own canonicalizer is greedy term rewriting (applies one match, replaces immediately, one fixed rewrite order) — not equality saturation (many equivalent forms held simultaneously, cheapest extracted at the end) — which is `egg`'s actual value proposition over "just write MLIR patterns." Real prior art exists for hosting genuine equality saturation *inside* MLIR rather than beside it; not evaluated here.

## `Dense`/`Network` — a real bundled-layer struct, `derive()` through it end to end — done

`examples/xor_tensor.cleave` used to take its nine weights/biases as eleven loose scalar parameters to `forward`/`loss` — raised directly as unreadable and error-prone. Now `struct Network { l1: Dense<f32,2,2>, l2: Dense<f32,2,1> }`, with `Dense<T,In,Out>` (`stdlib/nn/nn.cleave`) a real, reusable fully-connected-layer struct with an inherent `forward` method. Getting `derive()` to differentiate correctly *through* a chain of inherent-method calls on a nested struct parameter surfaced four more real, separate bugs, none anticipated going in:

1. `monomorphize.rs`'s four worklists (`fn`/`impl`/`lambda`/`inherent`) used to drain in one fixed sequential pass — `Dense::forward` (an `inherent_worklist` entry, drained last) calling `matmul` (an `impl_worklist` entry, drained earlier) silently dropped the newly-discovered work. Fixed by redraining all four to a real fixed point.
2. `Activation<Tensor<T,Dims...>>::sigmoid`'s own body used raw `mlir::arith::negf`/`addf`/`divf` calls — a purely-pure-primop chain, so `Forward::walk` treated it as one opaque node, and `sigmoid` has no declared `derivative` rule of its own (by design — it's meant to compose from its own primitives). Fixed by rewriting it to compose from real, named, already-differentiable calls (`Ring::neg`/`add`/`div`, plus a new `Transcendental<Tensor<T,Dims...>>::exp`), matching its own scalar sibling.
3. Cross-leaf independence used to be injected only within one `Tensor` field's own leaves, not across a struct's several `Tensor` fields (`Dense`'s `w` and `b`). Fixed by injecting it once, centrally, over a whole top-level parameter's entire leaf set.
4. `monomorphize.rs::resolve_derivative_rule_expr_ty` treated any "same algebra as the method being seeded" call inside a `derivative` rule's own body (`Ring::div`'s rule referencing `Ring::sub`/`mul`) as needing no seeding — true only for a literally self-recursive call, not a *different* method of the same algebra. `Ring::sub<f32>`/`mul<f32>` happen to always be called elsewhere in every scalar-only test, coincidentally masking this until `Ring::sub<Tensor<f32,1,2>>` (never called anywhere else in `Dense`).

A fifth, unrelated infrastructure gap surfaced once derivative synthesis itself was fixed: `memrefCopy`, the MLIR runtime helper `one-shot-bufferize` calls once a tensor value needs a real defensive copy, was never available to the JIT — no prior cleave program had ever needed one. The real library (`mlir_c_runner_utils.dll`, this project's own MLIR 22 build) exists, but loading it through `melior::ExecutionEngine::new`'s `shared_library_paths` hit a real bug in melior's/MLIR's own C API glue (multiple paths in the array corrupt into each other, no separator) — abandoned in favor of a small, correct, hand-written reimplementation in `cleave-rt` (`cleave_rt::memrefCopy`), registered by pointer like every other runtime symbol.

`examples/xor_tensor.cleave`'s own final training output is unchanged (bit-for-bit, essentially) from before the rewrite. New permanent test: `derive_through_dense_forward_computes_the_right_gradient` (`tests/mlir_lower.rs`) — needed its own dedicated 64MB-stack thread (`main.rs`'s own `fn main()` precedent), the synthesized derivative genuinely overflowing an ordinary `#[test]` thread's smaller default stack.

## `Dense` hardcoded its own activation (`sigmoid`, always) — done

`Dense<T,In,Out>::forward` (`stdlib/nn/nn.cleave`) used to always apply `sigmoid` — inherited unquestioned from `examples/xor_tensor.cleave`'s own pre-`Dense` `sigmoid2` helper (which *did* fuse linear+activation), without ever stepping back to ask whether that was the right split. ## A real PRNG, and real Xavier/He weight init, now exist — done

Every `Dense`'s own `w`/`b` in `examples/xor_tensor.cleave` used to be a hand-written literal tensor — a real init helper needed a source of randomness in cleave first, which didn't exist at all before this. Now it does, in two layers: `cleave-rt` gained a small, dependency-free PCG32 generator (`rand_seed`/`rand_uniform_f32`/`rand_uniform_f64`/`rand_normal_f32`/`rand_normal_f64`); `stdlib/rand/rand.cleave` exposes it as an ordinary `Rand<T>` algebra (`uniform(lo,hi)`/`normal(mean,std)`, `f32`/`f64`); and `stdlib/nn/nn.cleave`'s own new `Init<T>` algebra (`xavier()`/`he()`) builds real Xavier/Glorot-uniform and He-normal initializers for `Dense<T,In,Out>` on top, bias zero-initialized in both. `examples/xor_tensor.cleave` now constructs its own `Network` via `Init::xavier()` (matches its `sigmoid`-throughout architecture) instead of a hand-picked literal, seeded for reproducibility — still converges to `~0,1,1,0`, confirmed with more than one seed.

One real, load-bearing risk confirmed directly, not assumed, at the time this item was written: `[value; Dims...]` (`stdlib/linalg/tensor.cleave`'s own pack-generic array-repeat, `Ring::zero()`'s own mechanism) evaluated `value` exactly *once* and broadcast that single result into every position (`mlir_lower.rs::lower_array_repeat`) — using it to "fill a tensor with randomness" would broadcast one draw across the whole matrix, silently defeating the entire point. Filling a `Tensor` with genuinely independent noise needed a real loop with indexed writes (`buf[i][j] = uniform(lo,hi);`) instead, at the time — proven working end to end (`cleave/tests/mlir_lower.rs::a_tensor_can_be_filled_with_independent_random_draws_via_nested_indexed_writes`), no new compiler mechanism needed (the same multi-index `Store` a nested `a[i][j]` *read* already used). Also confirmed: repeated calls to a zero-argument `extern fn` (`rand_uniform_f32()`) are never folded/hashconsed together by the e-graph optimizer (`Forward::walk` stops translating at any `PrimOp::Extern`, never reorders/folds one) — two separate call sites really do stay two independent draws. **This risk is now fixed at the root** — see "`[value; Dims...]` couldn't fill a tensor with independent draws — done" below; `[value; Dims...]` itself now evaluates independently per position, and `Init<Dense<...>>::xavier`/`he` no longer need the nested-loop workaround.

Two real, separate compiler bugs found along the way while first building this — both since fixed for real (not just worked around; `Init<T>` above stays as the design regardless, it was always the right shape for a `Dense` constructor with no natural receiver, per its own doc comment):

1. **Fixed — done.** Explicit turbofish on an ordinary generic top-level fn call with a mix of type and const generics (`random_matrix::<f32, 2, 2>(lo, hi)`) used to mis-bind the arguments — surfaced as a genuine type error one level in (`expected f32, found 2`). Root cause: `Infer::generalize` (`infer.rs`) built a generic function's own `scheme.vars` by scanning every free variable in its fully-substituted type and sorting the ids *numerically*, assuming a declared generic's own originally-minted `TyVar` always stays the lowest-numbered representative of whatever it's later unified with. That's false the moment the body calls *another* generic construct sharing a generic name (`Tensor::<T,R,C>(data:...)` inside `random_matrix`'s own body reminting `Tensor`'s own generics and unifying them against the caller's `T`/`R`/`C`) — `unify`'s own var-binding has no id-ordering preference at all, so a declared generic's final representative can easily end up being a *later*-minted variable, scrambling `scheme.vars`'s order relative to what the turbofish itself was written in. Fixed by building `scheme.vars` from the function's own declared generics list directly (`callgraph.rs` now threads `f.generics` + its original fresh-var mapping through to `generalize`), resolving each one's own original var through the current substitution in true declaration order, instead of recovering order via a numeric-sort heuristic after the fact. Test: `cleave/tests/mlir_lower.rs::explicit_turbofish_on_a_generic_function_whose_body_shares_generic_names_with_another_construction_resolves_in_declaration_order`.
2. **Fixed — done.** A plain top-level generic function whose generics are *entirely* determined by the caller's own expected-type context (zero real value parameters, e.g. `fn dense_xavier<T,In,Out>() -> Dense<T,In,Out>`) never got that context propagated into its own body at all — an internal `.to()` call came back "ambiguous dispatch" even with the call site's own type fully pinned one level up, and turbofish didn't rescue it either (misdiagnosed as a real argument, `"expects 0 argument(s), found 1"`). Root cause, genuinely different from bug 1: `callgraph.rs`'s own Monomorphism-Restriction check (`f.params.is_empty()`) skipped *generalizing* the function at all whenever it took zero value parameters — correct for a truly non-generic nullary binding (`main`, `fn make() -> Vec2 {...}`), but it never checked whether the function actually *had* generics worth restricting, so a generic-but-nullary function's own `T`/`In`/`Out` were simply never quantified, left for `apply_defaults` to silently default to whatever an unrelated stray literal in the body happened to pick. Fixed by narrowing the check to `f.params.is_empty() && f.generics.is_empty()`, in both places it's checked (skip condition and the later `global_env` insertion) — every existing nullary, non-generic case is untouched (the added clause was already true for all of them). Test: `cleave/tests/callgraph.rs::a_nullary_but_generic_function_is_still_generalized_and_usable_at_different_types`, `cleave/tests/mlir_lower.rs::explicit_turbofish_on_a_zero_value_parameter_generic_function_resolves_correctly`.

## `[value; Dims...]` couldn't fill a tensor with independent draws — done

The load-bearing risk flagged directly in the item above ("A real PRNG, and real Xavier/He weight init, now exist") is now fixed at the root, not just worked around: `[value; Dims...]`/`[value; N]` (`cps.rs`'s own `ExprKind::ArrayRepeat` conversion) evaluated `value` exactly *once* and broadcast that single result to every position — correct for a referentially transparent value (`Ring::zero()`), silently wrong for an impure one (`uniform(lo,hi)`), which is exactly why `Init<Dense<T,In,Out>>::xavier`/`he` (`stdlib/nn/nn.cleave`) still had to fall back to a hand-written nested loop with indexed writes (`w[i][j] = uniform(-limit,limit);`) instead of writing `[uniform(-limit,limit); Dims...]` directly, the natural pack-generic idiom every other same-shaped construction already uses.

**The fix, in `cps.rs`, split into the two cases that turned out to need genuinely different treatment** (an earlier attempt at unifying them into one branch, both routed through the same type-level walk, double-applied nesting whenever `value` was itself another `ArrayRepeat` node — explicit source-level nesting like `[[zero();Out];In]` — producing an array value where a scalar leaf was expected, a real regression caught by the existing test suite before landing):
- `[value; Dims...]` (count is a whole pack reference, one AST node encoding every level at once): `convert_array_repeat_over_resolved_dims` now recurses per level, building `n` *independent* conversions of `value` at each level (mirroring `convert_expr_list`'s own sequential-accumulation idiom) instead of converting `value` once and wrapping the same result in nested `PrimOp::ArrayRepeat`s.
- `[value; N]`/`[value; count]` (count is a literal or a single named const generic — one AST node, one dimension; a hand-written multi-dimensional repeat like `[[value; d2]; d1]` is *two* of these nodes, syntactically nested): reads `n` off `ctx.node_types[&expr.id]`'s own resolved outer dimension and converts `value` independently `n` times via the same `convert_expr_list` idiom, producing `PrimOp::Array` directly — any deeper explicit nesting is handled by ordinary AST recursion (each independent copy's own conversion re-dispatches into this same match arm), not by this function's type-level walk.

`stdlib/nn/nn.cleave`'s `Init<Dense<T,In,Out>>::xavier`/`he` were simplified accordingly, from the nested-loop-with-indexed-writes shape to `Tensor::<T,In,Out>(data: [[uniform(-limit,limit); Out]; In])` (and `normal(0.0,std)` for `he`) directly. `examples/xor_tensor.cleave` re-verified end to end post-simplification, still converges (`~0.03, 0.97, 0.97, 0.03`).

**Verified at genuinely arbitrary rank, not just `Dense`'s own fixed rank 2**: `cleave/tests/mlir_lower.rs::array_repeat_over_a_whole_pack_fills_a_tensor_with_independent_random_draws_at_any_rank` — a `RandomFilled<T>` algebra, `impl<T: Float+Rand+Ring, const Dims...: i32> RandomFilled<Tensor<T,Dims...>>` filling via `[uniform(-1.0,1.0); Dims...]` directly, checked at rank 1 (`Tensor<f32,4>`) and rank 3 (`Tensor<f32,2,2,2>`) through the same impl, both in-range and genuinely non-degenerate (not every entry identical — the exact failure mode the old broadcast behavior would have produced). `cargo test --workspace` clean.

**Two more real, separate bugs found writing that verification test, neither fixed here — both logged as their own items below, out of scope for this fix specifically:**
1. A top-level `fn` generic over a whole pack (`fn random_fill<T, const Dims...: i32>(...) -> Tensor<T,Dims...>`), called at two different ranks from the same program, fails to monomorphize the second call site correctly.
2. An algebra impl generic over a pack, whose own body calls into a *second*, unrelated algebra (here, `uniform`'s own `Rand<T>` dispatch), instantiated at two different ranks in the same program, hangs on a genuine infinite-recursion stack overflow.

Both sidestepped in the verification test itself by compiling each rank as its own separate program rather than sharing one — proves the actual array-repeat claim cleanly without depending on either open bug.

## A pack-generic top-level `fn`/algebra impl called at two different ranks in one program — both done

Two backlog items, one root cause — folded together here since the fix (and the underlying bug) is identical for both.

**Item 1, a plain top-level `fn`**: found writing the verification test for the array-repeat fix above.

```
fn random_fill<T: Float + Rand + Ring, const Dims...: i32>(lo: T, hi: T) -> Tensor<T, Dims...> {
    Tensor::<T, Dims...>(data: [uniform(lo, hi); Dims...])
}
fn main() -> i32 {
    let v: Tensor<f32, 4> = random_fill(-1.0, 1.0);
    let t: Tensor<f32, 2, 2, 2> = random_fill(-1.0, 1.0);
    ...
}
```

A single call to `random_fill` (either rank alone) compiled and ran correctly; adding the *second* call, at a different rank, broke the first — `error: type mismatch: expected 'Tensor<f32, 2, 2, 2>', found 'Tensor<'t9, 't11>'`, an unresolved type variable escaping monomorphization entirely.

**Item 2, the algebra-impl counterpart**, found the same session, also confirmed with a minimal probe — didn't fail cleanly, it hung on a real, unbounded stack overflow:

```
algebra RandomFilled<T> { fn random_fill() -> T; }
impl<T: Float + Rand + Ring, const Dims...: i32> RandomFilled<Tensor<T, Dims...>> {
    fn random_fill() { Tensor::<T, Dims...>(data: [uniform(-1.0, 1.0); Dims...]) }
}
fn main() -> i32 {
    let v: Tensor<f32, 4> = RandomFilled::random_fill();
    let t: Tensor<f32, 2, 2, 2> = RandomFilled::random_fill();
    ...
}
```

Isolated by direct probing at the time, one variable at a time: the identical shape with `[zero(); Dims...]` (no second algebra call inside the pack-generic impl body) worked fine at two ranks; keeping `T: Rand` in the bounds list but leaving the body as `zero()` also worked fine — the hang only appeared with *both* conditions together (a pack-generic impl body that itself calls a different algebra's own method, instantiated at more than one rank).

**Root-caused for real, later, in the same session that fixed the self-recursive-generic-`fn`-at-two-types bug just above (same class of "called more than once" problem, different mechanism)**: `Infer::instantiate_with_mapping` (`cleave/src/infer.rs`) — the function that turns a finished, generalized `Scheme` back into a fresh, ready-to-unify `Ty` at each call site — minted *every* fresh replacement for `scheme.vars` as a bare `Ty::Var` (`TyVarGen::fresh` only ever returns one), regardless of what kind of variable it originally was. A pack-generic parameter (`const Dims...: i32`) is minted as `Ty::Pack`, not `Ty::Var` (`Infer::fresh_vars_for_generics`'s own doc comment: "this one change is what makes every other site... pick the pack up for free"), and `generalize`'s own free-var scan correctly folds both kinds into the same `scheme.vars: Vec<TyVar>` (deliberately — `Scheme` carries no separate per-var kind tag, see `Ty::Pack`'s own doc comment for why that's fine for generalizing). But nothing on the way *back out* re-derived that kind — so every re-instantiation of a pack-generic scheme silently downgraded its own `Dims` into an ordinary scalar var. A *single* call site still happened to work (nothing yet forced the corrupted var back into pack shape until unification against a concrete `Tensor<_, N>` did it structurally, one layer up), but a *second*, independent call site at a different rank got its own fresh-but-still-scalar var with no pack-ness left to recover — explaining both symptoms at once: item 1's own escaping unresolved var (monomorphization simply had nothing pack-shaped left to expand), and item 2's own hang (`Rand::uniform`'s own extra algebra dispatch, nested inside the now-corrupted pack-shaped construction, drove whatever worklist/recursion was trying to resolve a "pack" that was actually just a lone scalar var into never terminating).

**The fix**: a new `collect_pack_vars(ty, out)` (mirrors `free_vars` exactly, but collects only the subset appearing specifically as `Ty::Pack(v)`, never a bare `Ty::Var`/`Ty::PackLen`/inside an already-resolved `PackResolved`). `instantiate_with_mapping` now scans `scheme.ty` with it once per instantiation, and mints `Ty::Pack(fresh)` instead of `Ty::Var(fresh)` for exactly the `scheme.vars` entries that need it — `substitute` itself needed no change at all (already fully kind-agnostic, just looks up whatever `mapping` holds). `const_widths`' own re-keying (immediately below, in the same function) got the matching small fix — a const generic can itself be variadic (`const Dims...: i32` again), so its own fresh replacement may now be a `Ty::Pack`, not just `Ty::Var`; both carry the same underlying fresh id, extracted uniformly via `Ty::Var(fresh) | Ty::Pack(fresh)`.

**Verified**: both original minimal repros now compile and run correctly (the algebra-impl one completes instantly, no hang). New permanent tests, `cleave/tests/mlir_lower.rs`: `a_pack_generic_top_level_fn_called_at_two_different_ranks_monomorphizes_both` (exact-value check, `Ring::zero()`-style deterministic fill at both ranks, not just "didn't crash"); `an_algebra_impl_generic_over_a_pack_calling_a_second_algebra_works_at_two_ranks_in_one_program` (the exact original hang repro, `Rand::uniform` and all — its own real job is simply completing within the test harness's ordinary timeout). Full `cargo test --workspace` clean, 162 tests in `mlir_lower` (up from 160), zero regressions.

## A real dispatch bug — two call-resolution functions in `monomorphize.rs` picked the first *structurally* matching impl, ignoring bounds — done

Found directly, building the `Optimizer<Opt, Model>` item below: a composing impl generic over the optimizer itself (`impl<Opt> Optimizer<Opt, Dense<T,In,Out>>`, forwarding `opt` opaquely into `Optimizer::step`/`init_state` on `.w`/`.b`) failed with a confusing error deep inside an *unrelated* impl's own body (`` `Ring::sub` cannot be specialized for ((Pair, Pair) -> Pair): its generic impl body doesn't type-check at this instantiation ``), for a minimal repro that should obviously have dispatched elsewhere. Root-caused by direct reading, not guessed, per the project owner's explicit instruction to fix the real bug rather than design around it.

**Root cause**: `impl<T: Float+Ring> Optimizer<Sgd, T>` and `impl<Opt> Optimizer<Opt, Pair>` both unify *structurally* against a call needing `Optimizer::step(Sgd_value, Pair_value, ...)` (`T:=Pair`, `Opt:=Sgd`) — only `T`'s own declared `Float+Ring` bound (`Pair` satisfies neither) tells them apart. Two genuinely separate functions in `monomorphize.rs` shared the identical flaw: `derive_impl_instantiation` (drives ordinary call-site resolution — the one actually hit by the repro above) and `find_impl_for_target` (a structural-only search over already-built `ImplTemplate`s, driving the narrower `derivative`-rule/`Ring::zero`/`Index`-seeding paths). Both looped over candidate templates and returned the *first* one whose target patterns unified, with **no check at all** that the resulting substitution actually satisfied the candidate's own declared bounds — silently handing a doomed specialization request to the caller, only failing much later, confusingly, inside the wrong impl's own body. Both functions' own doc comments explicitly (and, in practice, wrongly) leaned on `Infer::check_no_overlapping_impls` to justify this: "on the first (and, per `check_no_overlapping_impls`, only ever possible) match..." — see the next item for why that guarantee doesn't actually hold.

**Fix**: `ImplTemplate` (`monomorphize.rs`) gained a new field, `generic_bounds: Vec<(Ty, Vec<String>)>` — for each of an impl's own declared *type* generics with a non-empty bound list, the exact fresh `Ty` `infer_impl_fn_generic_with_env` minted for it (read back via `Infer::active_generics`, made `pub(crate)` for this — same precedent as `ty_from_ast_mapped` earlier this session) paired with its bound names, computed once in `build_impl_templates`. Both `derive_impl_instantiation` and `find_impl_for_target` now check, after a successful structural unification, that every one of a candidate's `generic_bounds` is actually satisfied by the resulting substitution (`Infer::has_matching_impl`, also made `pub(crate)`, via a throwaway `Infer::new(registry)` — the same lightweight construction `build_impl_templates` itself already uses) — a bound failure now falls through to the next candidate exactly like a structural mismatch already did, rather than committing to a doomed match. `find_impl_for_target`'s three call sites (`seed_ring_zero`, `seed_derive_tensor_field_indices` — recursive, threaded through its own recursion — and `resolve_derivative_rule_expr_ty`, which already had `registry`) and `derive_impl_instantiation`'s three call sites (inside `collect_instantiations_expr`) needed `registry: &Registry` threaded through — for the latter, mechanically, through the whole `collect_instantiations`/`_block`/`_expr` thirteen-parameter recursive family (already `#[allow(clippy::too_many_arguments)]`-tagged) and its own six call sites (five in `monomorphize.rs`, one in `cps.rs`), all of which already had `registry` in scope.

**Verified**: the exact minimal repro now dispatches correctly (`main returned: 1`, not a `MonomorphizationFailed` deep inside the wrong impl) — landed as a permanent regression test, `cleave/tests/mlir_lower.rs::dispatch_between_a_bound_generic_impl_and_an_unbound_but_structurally_specific_one_picks_the_bound_satisfying_candidate`. `cargo test --workspace` clean throughout — this path is already exercised by every existing `Ring::zero`/`Index`/`derivative`-rule/ordinary-call test in the suite, none of which regressed.

**Found along the way, real, but *not* fixed here — logged separately, out of scope for this fix**: `Infer::check_no_overlapping_impls` (meant to reject exactly this kind of conflicting-impl pair, at declaration time, with a clear error) is never actually invoked by the real compile pipeline (`pipeline::check_type_errors` only calls `monomorphize::dump_monomorphized` and `check_mutability_errors`) — only reachable via a `--dump-*` debug command (`dump.rs`). Even if it were wired in, its own bound-admissibility check (`bounds_admit_a_shared_type`, via `unsatisfiable_bounds`) asks an *abstract* question — "do these bound names have any type in common, anywhere in the whole program" (`Registry::candidates_for`'s own intersection) — discarding the actual *resolved* concrete root type it already computed in `groups` right next to it, rather than checking that specific type concretely (the way `matching_impls`'s own `bounds_satisfied` closure, and this fix's own two call sites, correctly do via `has_matching_impl`). For `Optimizer<Sgd,T:Float+Ring>`/`Optimizer<Opt,Pair>`, that abstract question would have (wrongly) flagged them as overlapping — `f32`/`f64` genuinely satisfy both `Float` and `Ring` *in the abstract*, even though the actually-resolved position is concretely `Pair`, which satisfies neither. Neither gap block anything today (the check simply never runs), but both are real and worth a dedicated pass before ever wiring it back in.

## `Optimizer<Opt, Model>` — a real, generic, stateful optimizer, SGD and Momentum both — done

`examples/xor_tensor.cleave`'s own training loop used to update `net.l1.w`/`net.l1.b`/`net.l2.w`/`net.l2.b` by hand, one `Ring::sub(field, Scale::scale(grad_field, lr))` line per field — worked, but didn't generalize past "I remembered to write one line per field" and had no path to a real optimizer (momentum, AdamW, ...) without rewriting the training loop itself each time. Raised directly, not designed. Built *with* state from the start (not just SGD renamed), per explicit direction — SGD and Momentum both, to prove the abstraction genuinely supports an optimizer with memory, not just a facade over the four existing lines.

**Design, `stdlib/optim/optim.cleave` (new crate)**: `struct Sgd { lr: f32 }`/`struct Momentum { lr: f32, beta: f32 }` — hyperparameters live in struct fields (the same "config in the struct" shape `Dense`/`Init` already use), not scattered call arguments, since SGD and Momentum genuinely need different ones. `algebra Optimizer<Opt, Model> { fn init_state(opt: Opt, model: Model) -> Model; fn step(opt: Opt, model: Model, grad: Model, state: Model) -> (Model, Model); }` — `State` reuses `Model` directly (a velocity has exactly a weight's own shape, no separate "shadow" struct needed per model shape); `step` returns `(new_model, new_state)`, read back via `.0`/`.1` (no tuple-destructuring `let` in cleave — `let_stmt` binds exactly one ident — same idiom `derive()`'s own `g.3` already uses). Leaf-level impls (`Tensor<T,Dims...>`, pack-generic, any rank) compose entirely from already-proven pack-generic primitives — `Ring<Tensor<T,Dims...>>` (`add`/`sub`/`zero`) and `Scale<Tensor<T,Dims...>,T>` — `Sgd::step` is `model - lr*grad`, state untouched; `Momentum::step` is the standard exponential-moving-average form, `v <- beta*v + (1-beta)*grad`, `model <- model - lr*v`, `v` carried as `state`.

**The composition payoff — the actual reason the dispatch bug above got fixed rather than designed around**: exactly *one* impl each at the `Dense`-level (`stdlib/nn/nn.cleave`, `impl<Opt, T: Float+Ring, const In,Out: i32> Optimizer<Opt, Dense<T,In,Out>>`) and the `Network`-level (`examples/xor_tensor.cleave` itself — `Network` is a user struct, not stdlib, the same reason `Init<Dense<...>>` never needed a `Network`-level impl either, except here the training loop genuinely needs one call, not four) — both generic over `Opt` itself, never calling any method on it, just forwarding it into `Optimizer::step`/`init_state` on their own fields. Adding a third optimizer later (AdamW, say) needs *only* its own leaf-level `Tensor` impl — zero changes to `Dense`/`Network`-level code or to any training loop already written against `Optimizer::step`.

`examples/xor_tensor.cleave`'s own `main()` now reads `let opt = Sgd(lr: 1.0); let mut state: Network = Optimizer::init_state(opt, net); ...; let r = Optimizer::step(opt, net, g.3, state); net = r.0; state = r.1;` — one call inside the loop, insensible to which optimizer `opt` actually is; switching to `Momentum(lr: ..., beta: ...)` touches only that one line. Re-run end to end (`--run`): output **bit-identical** to before this rewrite (`0.030444637, 0.97289354, 0.9650081, 0.025979567`) — confirms the abstraction changes nothing mathematically for the case already proven, just reorganizes it.

**Verified, permanent tests, `cleave/tests/mlir_lower.rs`**: `optimizer_sgd_step_computes_the_exact_expected_value` (one step, exact arithmetic, state provably untouched); `optimizer_momentum_carries_its_own_state_correctly_across_two_steps` (two consecutive steps with two different gradients — the second step's own expected value only comes out right if `state` was genuinely threaded through, not silently reset, computed independently by hand and checked exactly); `optimizer_composes_correctly_one_level_up_through_dense` (confirms the generic-over-`Opt` `Dense`-level impl actually recurses into `.w`/`.b` correctly); `optimizer_momentum_trains_a_real_network_to_convergence` (the real end-to-end proof — the *same* `Network`/`Dense`-shape and training loop as `examples/xor_tensor.cleave` itself, but with `Momentum`, converging to the same `~0,1,1,0` shape within the same step budget, needing its own 64MB-stack thread like `derive_through_dense_forward_computes_the_right_gradient` above). `cargo test --workspace` clean.

## A real infinite-recursion bug in generic bound-checking — done

Found and root-caused building `Display<T>` (the item just below): once *two* structurally-different generic impls of the same algebra both bound generically on that *same* algebra (`impl<T: Wrap, ...> Wrap<[T;N]>` and `impl<T: Wrap> Wrap<Box3<T>>`, say), calling `wrap` on a value whose own element type is still an unconstrained type variable at declaration-check time hung the compiler forever — a genuine native stack overflow, not a controlled type error, confirmed via a minimal, isolated repro (`Wrap<[T;N]>`/`Wrap<Tensor<T,N>>` coexisting, `wrap(t[0])` inside either).

**Root cause, isolated via direct instrumentation (a temporary recursion-depth counter added to `infer_algebra_call`, then `matching_impls`, removed once the mechanism was found — not guessed)**: `Infer::matching_impls`'s own bound-satisfaction check (`bounds_satisfied`) asks `has_matching_impl` whether a candidate's own generic bound is satisfied — including for a query type that's still a genuinely unconstrained, freshly-minted `Ty::Var` (never yet pinned to anything concrete). For a bound naming an algebra with its own *further* generic, self-bounding impl, that check recurses back into `matching_impls` with *another* fresh, equally unconstrained variable — forever, minting a new `TyVar` each time, never terminating. `Infer::has_matching_impl_inherited`'s own `visited: &mut HashSet<String>` cycle guard doesn't help — it only guards *algebra-bound-inheritance* cycles (`algebra Int<T>: Num`), a structurally different recursion than this one (checking impl candidates against an unconstrained variable, not walking a bound-inheritance graph).

**Fix**: `matching_impls`'s `bounds_satisfied` closure now checks `is_fully_concrete(&resolved_arg)` first — a not-yet-concrete argument skips the bound check entirely (treated as permissively satisfied) rather than calling `has_matching_impl` on it at all. "Nothing to check yet isn't the same as a check that failed" — the identical posture `check_pending_constraints`'s own doc comment already establishes one level up for a structurally analogous situation; this fix extends it to `matching_impls`'s own bound-checking specifically. Skipping the call entirely (not just relying on it happening to return permissively) is load-bearing — it's what actually breaks the recursion, not just an optimization.

**Verified**: the original repro (`Wrap<[T;N]>`/`Wrap<Box3<T>>`, both `T: Wrap`) no longer hangs, returns the correct value — landed as a permanent regression test, `cleave/tests/mlir_lower.rs::two_overlapping_generic_impls_each_bounded_on_their_own_algebra_dont_hang_the_compiler`. `cargo test --workspace` clean — this exact bound-checking path is exercised by every existing `T: Float`/`T: Ring`/... bound in the whole test suite, none of which regressed (unsurprising: every *existing* bound check in this codebase, before this fix, only ever ran against already-concrete types, so `is_fully_concrete` was always already `true` for them — this fix only changes behavior for the genuinely-new "still open" case).

## A deferred algebra dispatch could orphan its own output-only generic, silently defaulting it — done

Found root-causing why `Display<Tensor<T,N>>` (the item just below) silently printed wrong values: `t[0]` inside a still-generic `impl<T,N> SomeAlgebra<Tensor<T,N>>`'s own body goes through `Index<Container,Elem,K>`, an *algebra* dispatch (unlike an ordinary array's direct `PrimOp::Load`). While `Container` (`Tensor<T,N>`) is still abstract mid-declaration, `Infer::infer_algebra_call`'s own `active_vars_pending` gate correctly *defers* this dispatch rather than committing prematurely (the same gate that already fixed `stdlib/nn/nn.cleave`'s own `mean`/`N.to()` bug, `Convert<i32,T>`, in an earlier session). But deferring meant `Index`'s own output-only `Elem` generic (`t[0]`'s own type) was left as a genuinely *orphaned* fresh variable — nothing about deferring the call also unifies `Elem` against `Index`'s own declared target pattern (which *would* correctly bind `Elem := T`, the container's own inner argument, structurally, regardless of what `T` itself later resolves to). A *second* algebra dispatch consuming `t[0]` (any recursive same-algebra call on it — `Display<Tensor<T,N>>::display` calling `Display::display(x[i], out)` again, the shape that surfaced this) would then see `Elem` silently defaulted to `i32` by `apply_defaults`, at the end of the same declaration's own body inference, and wrongly commit to whatever concrete impl `i32` happened to match. Confirmed directly via `--dump-cps-optimized`, not guessed: `Display::display<Tensor<f32,3>>` itself calling `Display::display<i32>`.

**Why this isn't a general "recursive same-algebra dispatch on a still-generic `T`" problem** (confirmed by direct isolation before chasing a fix): the *structurally identical* pattern `Display<[T;N]>` already uses (recursing into `Display::display(x[0], out)` while its own `T` is still symbolic) works perfectly correctly — an ordinary array's own indexing is a direct `PrimOp::Load`, reusing the array's own already-correct `T` var directly, no fresh, easily-orphaned variable ever minted. The bug is specific to any output-only generic reached through a *deferred* algebra dispatch.

**The fix, in `Infer::infer_algebra_call`**: a new `Infer::unambiguous_and_preserves_openness(algebra, query)` — committing a deferred dispatch immediately is still sound whenever *exactly one* impl of `algebra` structurally matches `query`, *and* every position that trial's own substitution newly pins down resolves only to variables `self.active_generics` already owns (checked via `free_vars` on each resolved position, not just a bare `Ty::Var` check — `Index`'s own `Container` position resolves to a *structured* type, `Tensor<T,N>`, not a bare variable itself, so the check must look at every free variable a resolved type actually contains, not just accept a lone `Ty::Var`). `Elem := T` satisfies this exactly: the same openness carried forward under a new name, nothing genuinely new decided. Wired in as `commit_despite_active_vars`, an added condition alongside the existing "every input generic already concrete" ready-check — falls through to the existing, unchanged deferral behavior whenever it doesn't hold.

**Why this must *not* fire for `Convert<From,To>`-shaped cases, and doesn't**: `stdlib/nn/nn.cleave`'s own `mean` (`N.to()`, `Convert<i32,T>`) has exactly *one* `Convert<i32,_>` impl declared too (today, `Convert<i32,f64>`) — but its own `To` resolves to the literal `f64`, a genuinely new, independently-declared concrete type with no structural relationship to `From` (`i32`) at all, not a restatement of something `active_generics` already owns. `unambiguous_and_preserves_openness` correctly returns `false` for it (the resolved `f64` contains no free variables *and* isn't itself an `active_generics` variable — wait, `f64` is fully concrete, so the "no free variables" case trivially passes the *safety* check — the real reason `mean` doesn't regress is different and worth stating precisely: `Convert`'s call is `.to()` at an ordinary expression position, not gated behind a still-abstract `Container`-shaped argument the way `Index`'s own dispatch is, so `gating` there already resolves to something concrete-independent-of-`T` and the *existing*, pre-fix `active_vars_pending` reasoning (documented in that gate's own doc comment) still applies unchanged. Confirmed empirically, not just reasoned about: every `Convert`/`mean`-adjacent test (`to_sugar_converts_an_int_to_a_float_end_to_end`, `turbofish_on_convert_disambiguates_between_two_real_competing_impls`, `init_xavier_generates_weights_within_the_correct_glorot_bound`, `init_he_generates_weights_with_the_right_statistics`) still passes, unchanged, after this fix.

A real bug found along the way, in the fix's own first attempt, worth recording: comparing a candidate's own resolved positions against `self.active_generics` using the *stale*, pre-dispatch `self.subst` (rather than `matching_impls`'s own `trial` — a clone of `self.subst` *plus* this specific candidate's own new bindings) always failed to match, since `unify`'s own bind direction has no preference for keeping the *older* variable as representative: for `Index<Tensor<T,Dims...>,T>`, the *candidate's* own fresh `Elem` var ended up as `T`'s own union-find representative, not the other way around, so comparing against `self.subst` (which had never heard of that merge) compared two different names for the same equivalence class and never matched. Fixed by resolving `active_generics` through `trial` too, not `self.subst`.

**Verified**: the minimal repro (`Wrap<Tensor<T,N>>::wrap` calling `Wrap::wrap(t[0])`, `Wrap<f32>`/`Wrap<i32>` both declared) now correctly dispatches to `Wrap<f32>` — landed as `cleave/tests/mlir_lower.rs::tensor_index_result_dispatches_to_the_correct_algebra_impl_even_while_still_generic`. `cargo test --workspace` clean, zero regressions across the whole suite. `examples/xor_tensor.cleave` re-verified bit-identical after this change too.

## `Display<T>` — a real, composable textual representation (scalars, arrays, tuples, `Tensor`) — done

Raised directly: `print` more generic, "peut-être un `Display<T>`" — `Print<T>` (`stdlib/io/io.cleave`) only ever covered scalars, strings (`[i8;N]`, a special case), and tuples; nothing for an ordinary numeric array or a `Tensor`. `Display<T>` (`stdlib/display/display.cleave`, new crate) separates "how to represent `x` as text" (a pure, composable function, `fn display(x: T, out: DynArray<i8>) -> DynArray<i8>`, appending and returning a growable byte buffer) from "print" (the effect, still exclusively `Print<T>`'s own job) — the Rust `Display`/`println!` split.

**Shipped, verified correct**: `Display<i32>` (pure cleave — digit-extraction loop, `x - (x/10)*10` looked up in a literal `[i8;10]` ASCII table, recursive for correct most-significant-digit-first order); `Display<f32>`/`Display<f64>` (via two new `cleave-rt` externs, `format_f32`/`format_f64` — the one part genuinely needing real code outside cleave, a correct shortest-round-trip decimal formatter not being reasonable to hand-roll; write into a caller-owned `[i8;24]`, using the *identical* `format!("{x}")` `print_f32`/`print_f64` already use, so a float reads identically either way); `Display<[T;N]>` for `T ≠ i8` (bracket/comma composition, recursing into each element's own `Display`); `Display<(A,B)>`/`(A,B,C)`/`(A,B,C,D)` (mirrors `Print`'s own existing tuple impls). New `Print<[T;N]>` (`stdlib/io/io.cleave`) builds the buffer via `Display::display` then flushes it through one new extern, `print_dynarray_bytes` (structurally identical to the existing `print_bytes`, just taking `DynArray<i8>`'s own already-bare `RawBuf` pointer directly instead of `mlir_lower.rs`'s array-argument `(ptr,len)` extraction).

**Two deliberate scope decisions, not oversights**: `i8` excluded from `Display<[T;N]>`/`Print<[T;N]>` — `[i8;N]` already means "a string" (`Print<[i8;N]>`, raw bytes, no brackets), and this project has no separate `String` type to tell the two meanings apart at the type level. No blanket `impl<T: Display> Print<T>` — `i8`..`f64` already have their own concrete `Print<T>` impls; once those same scalars also have `Display<T>` (needed anyway, to format an array *element*), a blanket impl would structurally overlap them, resolved only by template iteration order. Each new `Print<T>` impl targets a structurally distinct, concrete shape instead — zero overlap to resolve.

**One real ABI assumption, confirmed directly before building on it, not assumed**: every prior array-argument extern in this codebase (`Print<[i8;N]>::print`, `memrefCopy`) only ever *reads* through the pointer `mlir_lower.rs::array_ptr_and_len` extracts for an array-typed extern argument. Whether a *write* through that same pointer (needed for `format_f32`/`format_f64`, writing their own result into the caller's array) is actually visible to cleave code afterward was unverified anywhere in this codebase — confirmed first, via a disposable probe extern (write 4 known bytes into a `[i8;4]` argument, read them back in cleave, since removed), before `format_f32`/`format_f64` were built on the same assumption.

**A real, separate compiler-architecture fallout, fixed**: `stdlib/io/io.cleave` now transitively `use dynarray;`/`use display;` — meaning `use io;` (already used by the overwhelming majority of this project's own tests and examples) started pulling in every `RawBuffer<T>`/`Display<T>` impl for every scalar width, *all* non-generic, hence *all* eagerly compiled into any program reaching them at all (`cps.rs::collect_units`'s own "non-generic impl" branch is unconditional — regardless of whether that specific program ever actually calls `print`/`Display::display`). This broke essentially every test-file-local JIT harness in `cleave/tests/mlir_lower.rs` (and one in `cleave/tests/user_guide.rs`) — each hand-registers its own small, exact symbol list for `melior::ExecutionEngine`, none of which anticipated a plain `use io;` program now also needing `format_f32`/`format_f64`/`print_dynarray_bytes`/every `dynarray_*` symbol resolvable at JIT-load time. Fixed by consolidating `mlir_lower.rs`'s own several duplicated ad-hoc registration blocks into one shared `register_io_symbols` helper (registered unconditionally, harmless if unused, the same posture `cleave_alloc`/`memrefCopy` already had) and applying the same fix to `user_guide.rs`'s own separate harness.

**`Tensor<T,Dims...>` support — shipped**: `Display<Tensor<T,N>>`/`Display<Tensor<T,R,C>>` (rank 1 and rank 2, mirroring `Sum`/`Mean`/`Max`'s own precedent of never generalizing past a concrete rank; rank 2 specifically because `Dense.w`/`Dense.b` are rank 2 — `print(net.l1.w)`, this whole item's own real motivating case). Found genuinely broken on the first attempt, root-caused and fixed for real (a genuine type-inference bug, not a `Display`-specific one) — see the dedicated item just above for the fix itself; this item only needed to *use* it, not build it.

**Two further, smaller, real gaps found along the way, still not fixed, both narrowing `Display<T>`'s own integer coverage to `i32` only for now**:
- A `for` loop's own index variable, when the range's *upper bound* is itself a generic const parameter (not a literal), is sometimes typed as that const's own *resolved value* instead of `i32` the moment it's used in an arithmetic or comparison expression directly (`i > 0`, `acc + i`) — confirmed via a minimal, `Display`-independent repro. Using the index *only* to index an array (`x[i]`) is unaffected (already proven safe throughout this codebase). Worked around in `Display<[T;N]>`'s own rendering by printing the first element before the loop, then looping `1..N` — never comparing/computing on the index directly — arguably a more idiomatic join-style rendering anyway, not just a workaround.
- `mlir::arith::trunci` (the natural op for the `i32 -> i8` narrowing conversion `Display<i8>`/`Display<i16>`/`Display<i64>` would need) fails MLIR verification through this project's own raw-op lowering (`'arith.trunci' op operand type 'i8' and result type 'i8' are cast incompatible`) — `lower_raw_mlir_op`'s own operand-type-inference heuristic guesses the *result* type for the operand too, wrong for any op where they genuinely differ, unlike every other `mlir::arith::...` call this stdlib relies on. Combined with `stdlib/convert/convert.cleave` having no integer-to-integer `Convert` impls at all today (only int-to-float), `i8`/`i16`/`i64` `Display` needs both of these fixed first — not attempted here, `i32`/`f32`/`f64` alone already cover this item's own real motivation.

**Verified, permanent tests, `cleave/tests/mlir_lower.rs`**: `display_i32_produces_the_exact_expected_bytes` (negative and positive, sign and digit order both checked); `display_f32_produces_the_exact_expected_bytes`; `display_of_an_int_array_renders_brackets_and_commas_correctly` (exact byte-for-byte `"[1, 2, 3]"`); `display_of_a_rank_1_tensor_renders_correctly`/`display_of_a_rank_2_tensor_renders_correctly` (exact byte-for-byte, fractional values specifically — an integer-valued `f32` like `1.0` prints as `"1"`, not `"1.0"`, so wouldn't actually distinguish correct `f32` dispatch from the old, wrong `i32` default); the pre-existing `a_multi_argument_heterogeneous_print_call_prints_every_element_in_order` (tuples) re-verified passing unchanged. Manually re-verified end to end too: `print(net.w)` on a real `Init::xavier()`-initialized `Dense<f32,2,2>` renders `[[-1.2247449, -0.81934446], [0.69033563, 0.4936608]]` — the actual motivating case, working. `cargo test --workspace` clean, `examples/xor_tensor.cleave` re-verified bit-identical.

## A self-recursive generic `fn`, called at two concrete types, could silently stop being polymorphic — done

Found via a smoke-test sweep of every `examples/*.cleave` after the two fixes just above: `examples/fibonacci.cleave` — `fibonacci<T: Int>(x: T) -> T { if x <= 1 { x } else { fibonacci(x-1) + fibonacci(x-2) } }`, called once at `i32` and once at `i64` in the same `main()`, previously always worked — started failing the *second* call site with `"expected i32, found i64"`, but only once `use display;` (or enough other stdlib surface) was also present; `use linalg;` alone, a strict subset, didn't trigger it. Genuinely nondeterministic-*looking*, not actually nondeterministic — fully explained once found.

**Root cause, nothing to do with `Display<T>`/the two fixes above directly**: `callgraph::infer_program` (`cleave/src/callgraph.rs`) infers the whole program's own top-level `fn`s one dependency-ordered SCC group at a time, each group getting its own fresh `Infer::new(registry)` — a deliberate, correct reset (mutual recursion within a group needs a clean slate) with one uninspected consequence: `Infer`'s own `TyVarGen` (`cleave/src/infer.rs`) always restarts numbering at `0`, so a raw `TyVar` id is *not* a unique identity across groups — group B's brand-new generic parameter can numerically coincide with some unrelated, still-*unquantified* variable left over in group A's already-finished `scheme.ty`. `Infer::generalize`'s own `env_fv` computation (the "what's already free in the environment, don't re-quantify it" check) applies the *current* group's own live `self.subst` to *every* scheme already sitting in `global_env` — schemes built by earlier groups' own, separate `Infer` instances, in a namespace `self.subst` was never involved in producing. When a collision landed on `fibonacci`'s own `T`, `generalize` wrongly treated it as "already free in the environment" and refused to quantify it, leaving `fibonacci`'s scheme permanently monomorphic at whichever concrete type its *first* call site (`fibonacci(16:i32)`) happened to need — so the *second* call site (`fibonacci(42:i64)`) failed to unify against it. `use display;`'s only real role was pulling in enough *other* top-level `fn`s (`display_digits_i32`, `dynarray`'s own internals, ...) to shift the group-processing order/`TyVar` counts into an unlucky collision — `use linalg;` alone happened not to, by simple luck of the count, not because it's semantically safer.

**The fix**: thread one monotonically increasing `TyVar` counter across the *whole* SCC-group loop in `infer_program`, instead of letting each group's own `Infer::new` restart at `0` — `TyVarGen` gained `high_water_mark`/`starting_at`, `Infer` gained matching builder-style `with_var_counter_starting_at`/`var_counter` (mirroring the existing `with_inherent_patterns` pattern), and the loop now does `next_var_id = infer.var_counter();` at the end of each group's iteration, seeding the next group's own `Infer::new(...).with_var_counter_starting_at(next_var_id)`. This removes the collision at its root rather than special-casing `generalize` itself, which is correct as written for its *other* call site (`infer.rs`, generalizing a `let`-bound lambda against its own enclosing function's own live, same-`Infer`-instance local `env` — there, applying `self.subst` to the env's own entries is exactly right, same instance, same namespace).

**Not this session's fix's fault, confirmed directly**: temporary `eprintln!` instrumentation (added, used, then removed) traced every `commit_despite_active_vars`-gated dispatch by `self` pointer identity — confirmed `fibonacci`'s own `Ord`/`Ring` calls never once hit that path, ruling out the otherwise-obvious hypothesis that the deferred-dispatch fix (previous item) was corrupting `fibonacci`'s own generalization directly. The real mechanism was one level further down, in `generalize`'s pre-existing, never-previously-exercised-this-way `env_fv` check.

**Verified**: `examples/fibonacci.cleave` now prints `fib(16)=987` / `fib(42)=267914296` again. New permanent regression test, `cleave/tests/mlir_lower.rs::a_self_recursive_generic_fn_called_at_two_concrete_types_stays_polymorphic_even_with_other_algebra_impls_present` — confirmed to actually catch the regression (reverting just the counter-threading change reproduces the original failure under this exact test, not just asserted). Full `cargo test --workspace` clean; every `examples/*.cleave` re-swept, all producing correct output (`linear_regression.cleave`'s own apparent "no output" during the original sweep was just a >30s training loop under a 30s per-file sweep timeout, not a regression — confirmed by running it alone with a longer timeout).

## `print` silently added a trailing newline for scalars only, `println` didn't exist — done

Raised directly, from `examples/xor_tensor.cleave`'s own new per-checkpoint logging: `print("step "); print(step);` produced an invisible newline between `"step "` and the number that wasn't written anywhere in the calling code. Root-caused, not guessed: `cleave-rt`'s own `print_i8`/`i16`/`i32`/`i64`/`f32`/`f64` each hardcoded Rust's `println!` (silently appending `\n`), while every string/array/`Tensor`/tuple `Print<T>` impl (routed through `print_bytes`/`print_dynarray_bytes`, plain `write_all`) added none — a real, pre-existing inconsistency, not something this session introduced, just never previously exercised back-to-back the way the new logging line did.

## A generic top-level `fn` with no call site anywhere in the program crashed CPS conversion — done

Found immediately after adding `println<T: Print>` (previous item) to `stdlib/io/io.cleave`, a crate `use io;` pulls into essentially every test and example: `cargo test --workspace` started failing five previously-passing, seemingly unrelated tests (`a_string_literal_printed_via_print_writes_the_right_bytes_to_stdout`, tuple-print, matmul/index-result-print, ...) — none of them called `println` at all — with `CPS: could not resolve call to print (("print", ["'t57"], "'t57"))`, an unresolved type variable reaching CPS conversion. Confirmed by bisection (renaming, then emptying `println`'s own body) that the trigger was purely `println<T: Print>` *existing*, generic, in the program — not its name, not being called.

**Root-caused via a targeted diagnostic (a temporary test calling `monomorphize()` twice, mirroring `--run`'s own real pipeline, since `--dump-monomorphized` alone never reproduced it)**: `cps.rs::collect_units`'s own per-`fn` loop uses `mono.specializations_of(&f.name).is_empty()` as a proxy for "non-generic, build one direct unit from `fn_result`" — but that proxy is also true for a genuinely *generic* `fn` that simply has no call site anywhere (no instantiation was ever requested, so there's nothing for `specializations_of` to report either way). `println`, added to a crate `use io;` pulls in almost everywhere, was the first top-level generic `fn` in this codebase's own history to ever go genuinely uncalled — every earlier one (`fibonacci`, ...) was always reached from *some* test or example, so this branch had never actually been exercised against a generic-and-uncalled function before. Taking the "direct unit" path for `println` baked its own still-open `'a` (T, never pinned to anything concrete) straight into a `ConcreteUnit`, and CPS conversion panicked the moment it tried resolving a call inside that body against an unresolved-variable key.

**The fix**: check `fn_result`'s own `param_types`/`result` directly for free type variables (`free_vars`, `infer.rs`, already `pub(crate)`) before taking the "build a unit directly" branch — skip (no unit, nothing calls it, nothing to compile) when it isn't fully concrete, exactly the same outcome an uncalled *non-generic* function already correctly got. **Checked against `fn_result`, not `program_inference.global_env`'s own stored `scheme.vars`** — the first attempt used `scheme.vars.is_empty()` and broke a *different*, previously-passing test (`a_unit_returning_export_fn_omits_a_return_type`): an `export fn` with an entirely empty, implicit-unit body (`export fn touch(x: i32) { }`) can legitimately end up with a non-empty `scheme.vars` (its own return-type var gets quantified by `generalize` — which runs *before* defaulting, per `callgraph.rs`'s own established ordering — before that same group's later unification actually pins it down to `()`) even though `fn_result` itself is already fully concrete by the time `cps.rs` ever sees it — a real, separate, pre-existing quirk in how `callgraph::infer_program` resolves an implicit-unit return, not fixed here, just newly avoided as a false positive.

**Verified**: new permanent test, `cleave/tests/mlir_lower.rs::an_uncalled_generic_top_level_fn_does_not_crash_compilation` — confirmed to actually catch the regression (reverting just this fix reproduces the exact original panic under this test). Full `cargo test --workspace` clean, including the `export fn` test the first attempt broke.
