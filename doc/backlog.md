## OpenMP parallelizes at far too fine a grain — the real, current axis; direction is coarser-grained tasking (`omp.task`/an explicit `spawn`/`sync` primitive), not further micro-fusion within today's model

VTune (software sampling; this machine is AMD, no hardware-event sampling available), `mnist-interop`, post-pool-allocator baseline. At 1 thread the kernel is genuinely compute-bound (`train_and_evaluate` 86%, `memcpy` 6%, allocator ~2%). At 4 threads (the empirical throughput peak — see the sweep below) it flips: **libomp spin-wait + `__kmpc_barrier` eat ~82% of CPU time, real compute is ~6%.** VTune's own diagnostic: *"CPU time spent on parallel work arrangement can be a result of too fine-grain parallelism. Try parallelizing outer loops rather than inner loops."* Confirmed, not a guess: `--convert-scf-to-openmp` forks a parallel region and hits a barrier around individual small ops *inside* the per-batch inner loop — on the order of millions of fork/join+barrier round-trips over a real 10-epoch run, each doing microseconds of work on batch-32 MLP layers. The pool-allocator spinlock was checked and ruled out as the cause (buried in `[Others]` at <5%).

| threads | elapsed (10 epochs, `0.9342` every time) | speedup vs 1T |
|--------:|--------:|--------------:|
| 1 (`CLEAVE_NO_OPENMP=1`) | ~18.8 s | 1.00× |
| 2 | 13.3 s | 1.43× |
| 4 | **12.1 s** | 1.56× |
| 8 | 18.0 s | 1.05× |
| 16 | 28.4 s | 0.66× |

**This is the real OpenMP-efficiency gap vs. PyTorch** (whose persistent threadpool dispatches coarse tasks) — not allocation, not `memcpy`. Fixing it means parallelizing an outer loop (the batch loop, or a tile band spanning many rows) once per region instead of the innermost `linalg` op, and/or keeping a worker pool alive across regions rather than paying fork/join per region. Re-run the sweep + both VTune profiles above after any such change.

**A new, not-yet-root-caused lead from the first real VTune session run against the per-file debug info above**: `Ord::lt` no longer shows up in the profile at all (the wrong-file-attribution bug is fixed), but `train_and_evaluate` now shows **578 indirect calls** (`call r13`, `call r14`, `call rsi`, ...) in its own disassembly, and `net_grad`'s own compute doesn't correlate cleanly to any one line the way `matmul`/`Ord::lt` do — despite `--inline` supposedly running to a fixed point. 578 real indirect call sites inside a function that's meant to be one fully-inlined blob is a real anomaly, not expected noise: either `--inline` is stopping short somewhere (plausible culprit — a generic/algebra dispatch recursing through a shape `--inline`'s own cost model or recursion-depth limit declines to unfold), or these are a structurally different kind of call (an OpenMP-outlined `..omp_par.N` region invoked through a `__kmpc_fork_call` function-pointer argument, which *would* legitimately be indirect and *would* explain why VTune can't attribute the work inside it back to `net_grad` by name). Not distinguished yet — the concrete next step is reading the real disassembly at one of those 578 call sites directly (what's in the register, is it a stable per-build symbol or a runtime-computed address) before guessing further. `memrefCopy` also now reads ~10% of CPU in this same profile, a real, separate data point worth carrying into whatever measurement follows the granularity fix above.

**Direction, agreed but not yet designed**: an explicit, Cilk/Go-style `spawn`/`sync` primitive, backed by MLIR's real `omp.task`/`omp.taskwait` (a genuine work-stealing model, architecturally distinct from the fork-join-team model cleave uses today, and able to spawn continuously *inside one already-open parallel region* rather than paying a fresh team fork per unit of work) — deliberately chosen over trying to auto-discover/cost-model where to fuse regions (tried, see below, too hard to generalize). Three real design questions need answers before any code: closure capture (`spawn { ... }`'s body needs its free variables — depends on the still-open lambda-capture gap below); a concurrency-safety story (cleave has no ownership/borrow discipline today — two spawned tasks writing the same buffer is a real, currently-unguarded race class); and where this sits relative to the extensibility discipline (a real core-language addition, not an `algebra`+`mlir::`-stdlib extension).

Two real bugs surfaced by this same investigation are prioritized separately, right below — pulled out rather than left as an aside here.

Extensive earlier tuning inside the *old*, fine-grained-parallelism model — region/fork-join fusion (built, worked, measured as a regression, reverted), a per-shape static thread-count lever (never attempted), a `vector.contract`-lowering-strategy comparison (concluded: already optimal), a batch-size bug and an MLIR crash blocking weight/bias-gradient region fusion — is now superseded by the diagnosis above and kept only in `backlog-done.md`; none of it is worth resuming before the granularity fix itself.

## A real double-release crash in `mnist-interop`'s own real training run — root cause fully characterized, real progress landed, genuinely open until a *general* fix is found

This is the current "robustness" slot, by the same alternating agreement as the OpenMP-granularity "quality" entry above. Long-running investigation; superseded several earlier, narrower framings of "the" root cause along the way (each real, each fixed, each turning out not to be the whole story) — see `backlog-done.md` for the two `refcount.rs`-only bugs (`state`/Sgd aliasing through composed calls, `Resolved::Local`) fully landed and closed out of this entry once confirmed.

**The real, whole-program root cause, found after the CPS-level bugs above stopped explaining new crashes**: two *independent* systems both believe they own a tensor's physical memory, with no coordination between them.
- MLIR's own `--ownership-based-buffer-deallocation` tracks any value with genuine `memref.alloc()` provenance and inserts a `memref.dealloc` (wrapped in its own `scf.if`, often simplified to a literal `%true`) once its own liveness analysis proves the value dead.
- `refcount.rs` treats *every* bare `Tensor` value as `is_rc` (`is_bare_tensor_ty`, `cleave-rt`'s size-class pool commit) and inserts an explicit `cleave_retain`/`cleave_release` whenever CPS-level bookkeeping needs to protect or finally dispose of one — necessary for values that only ever get released via this mechanism (below), but blind to whether that same physical memory is *also* bufferization's responsibility.

When a bare `Tensor` value both (a) survives with a real, un-eliminated `memref.alloc()` (not fused away by One-Shot Bufferize, not redirected to `cleave_alloc_rc` directly the way `dps_rewrite.rs` already does for struct-field writes) and (b) gets an explicit `cleave_release` from `refcount.rs` (typically because it's read/reused more than once, e.g. a value used in both a forward and a matching backward computation), both systems free it — cleave's own release wins the race in practice, so bufferization's own (`unify_alloc.rs`-renamed) `cleave_release_void` finds the block already parked. Root-caused down to the exact two call sites in the real kernel's own post-buffer-deallocation MLIR (`CLEAVE_DUMP_POST_DEALLOC`), not guessed — confirmed instances found and fixed, in order: `load_train_batch_input`/`load_train_batch_target`'s own batch tensors (`x`/`y`, `mlir::memref::alloc()` + fill loop), then each of the network's own 4 layers' training-batch (32-row) activations in turn (identical padded-by-one-AVX-512-vector size signature each time — fixing layer 1's own crash simply revealed layer 2's, then 3's, then 4's).

**Two whole-system alternatives tried and rejected, both measured, neither assumed:**
1. **Make cleave the sole owner of all non-stack memory** (skip `--ownership-based-buffer-deallocation` entirely, let `refcount.rs` cover everything) — **12.7GB resident after 10 seconds**. `refcount.rs` does not track the release of most free-standing intermediate tensor arithmetic today; `unify_alloc.rs`'s own "free-standing tensor arithmetic is left entirely to bufferization" is load-bearing fact, not just an aspiration, for the large majority of tensor values in this kernel.
2. **Make MLIR the sole owner, disengage `refcount.rs` for bare tensors** (`is_rc` without `|| is_bare_tensor_ty(...)`) — reintroduces, precisely and immediately, the already-fixed `Scale::scale` leak: exactly one existing test fails, `a_bare_tensor_returned_from_a_call_and_consumed_only_as_a_borrowed_argument_is_released` (`cleave/tests/refcount.rs`). Confirms both mechanisms cover real, disjoint needs — the actual bug is only their *partial overlap*, not either one being wrong to exist.

**The fix that is landed: `cleave/src/compensate_refcounts.rs::suppress_bufferization_owned_releases`** — a new pass, run right after `--ownership-based-buffer-deallocation` (before `--convert-to-llvm`, unlike its sibling `compensate_merged_refcounts` in the same file — pointer identity for a `cleave_release`'s own operand and a lowered `memref.dealloc`'s own operand never converge into one shared SSA value even by the end of the pipeline, confirmed empirically, `CLEAVE_TRACE_SUPPRESS`: 227 "owned" sites, 173 `release_void` sites, zero matches when tried at the end). For a `memref.dealloc %m` found to have a real, same-*effective*-scope `cleave_retain`/`cleave_release` on the identical `%m` (`effective_block` walks up through any number of `scf.if` ownership-check wrappers first — the dealloc's own *direct* block is never the release's block even for a textbook-adjacent, same straight-line case, found by direct testing), redirects the dealloc's own operand to a freshly inserted, throwaway `memref.alloc()` instead — a pure operand edit, never an erase (erasing a real `memref.dealloc`/`memref.alloc` in this pipeline is separately confirmed to corrupt state that only crashes later, at module teardown).

**Currently gated to a specific, individually-validated shape list, not yet a fully general criterion — this is the real remaining gap.** Two general (no per-shape special-casing) criteria were tried and both leaked on the real kernel, watched under close memory monitoring both times:
- Plain "any release surplus" (`releases > retains`, no locality) — the very first version, **~22GB in ~2 epochs**.
- "Real surplus *and* real release in the identical effective scope" (`same_scope_release && owned.contains(&target)`, no shape restriction) — **~3.6GB in 3-6 seconds**, even after excluding the weight-gradient-shaped candidates on top (which was the leading hypothesis for the false-positive class and turned out wrong, or at least incomplete).
- The root problem, understood but not yet solved: a plain, singly-constructed, singly-consumed tensor (a weight gradient computed once and fed into one `Scale::scale` call) legitimately nets to exactly `releases == retains + 1` — the *identical* CPS-level signature a genuinely double-owned value has. Neither the surplus count nor same-scope locality, alone or combined, has yet distinguished them; whatever the real discriminator is (something about *which* `memref.dealloc`'s own `scf.if` condition was truly simplified to `%true` vs. genuinely data-dependent — `dealloc_helper`'s own multi-candidate ownership-selection shape, seen in the real kernel's own post-deallocation MLIR but not yet investigated as the discriminator — is the leading untested idea) is the right next thing to chase, not another shape added to the safe list.

**What is landed, safe, and confirmed (`CLEAVE_DEBUG_POOL=1`, careful memory monitoring, no leak observed) — the shape list `suppress_bufferization_owned_releases` currently ships with:** `memref<32x512xf32>`, `memref<32x256xf32>`, `memref<32x128xf32>`, `memref<32x10xf32>` (the 4 layers' own training-batch activations), `memref<32x784xf32>`/`memref<1x784xf32>` (`x`/`load_test_input`'s own batch tensors). `cargo test -p cleave --release` green throughout. `examples/mnist-interop` no longer crashes on any of these — reaches meaningfully further into a real training run than at any earlier point in this investigation.

**A fourth, distinct crash surfaces once the above is fixed — not yet diagnosed**: `data_size=104` (26 `f32` elements, or a small aggregate — not yet resolved which), attributed to `kernel.cleave:218:1` (`train_and_evaluate`'s own opening line — network/optimizer-state *construction* time, not a per-batch pattern at all, so likely a different mechanism than the activation-tensor class above; possibly closer to `compensate_merged_refcounts`'s own CSE-merge shape than the bufferization-ownership one). Not investigated yet.

**Working method, worth keeping for the next session** (all still accurate): `lldb` (`clang+llvm-20.1.0` distribution on `PATH` — not the `llvm-mlir-22` one this project compiles with, which ships no debugger) debugs an AOT-compiled cleave binary directly, batch-mode via `lldb -b -s script.txt program.exe`. `breakpoint set --name cleave_alloc_rc --condition "$rcx == <size>"` finds every call site allocating an exact byte count (Win64 ABI, first arg in `%rcx`) — the single fastest way to identify *which* construction a `CLEAVE_DEBUG_POOL`-reported `data_size` belongs to. `CLEAVE_DUMP_POST_DEALLOC=<path>` (`pipeline.rs`) dumps the module right after buffer-deallocation, memref-level, before `--convert-to-llvm` turns everything opaque — the only place `memref.dealloc`/its own `scf.if` wrapper/`dealloc_helper` calls are still directly readable. `CLEAVE_TRACE_SUPPRESS=1` prints every `suppress_bufferization_owned_releases` candidate (shape, surplus, scope match) for exactly this kind of investigation. `cdb`/WinDbg cannot launch any child process at all from within this tool's own sandbox (confirmed on a trivial `cmd.exe /c echo hi`) — don't retry it. **Always monitor real memory footprint directly** (`Get-Process mnist-interop | Select WorkingSet64`, polled every few seconds) before trusting any change to this pass — both real leaks this session were fast (seconds, not minutes) and would have been caught by a first poll within 10 seconds.

## `net_grad`'s own remaining internal tensor allocations still all go through `cleave_alloc_rc`, never the region/arena allocator

Even when a call would otherwise qualify as region-local, a shared, monomorphized algebra function (`MatMul::matmul<...>`, `Ring::add<...>`) called from both region-local and non-region-local contexts in the same program never gets promoted, because `region_analysis.rs` has no per-call-site view, only a whole-function one. Well-scoped, not yet attempted: teach the bridge to reason per call site rather than per function.

## Generalize `matmul(a, transpose(b))` → `matmul_transpose_b(a, b)` (and the `_a` symmetric case) into a real e-graph rewrite, not just the backward-mode adjoint's own hand-wired special case

Raised directly by the user. `MatMulTransposeA`/`MatMulTransposeB` (`stdlib/linalg/matrix.cleave`) already exist as real algebras backed by real MLIR intrinsics (`mlir::linalg::matmul_transpose_a`/`_b`, whose `indexing_maps` read an operand "as if transposed" via stride arithmetic alone — no `linalg.transpose` gather/scatter, a real, already-confirmed cost eliminated entirely for this shape, see `backlog-done.md`) — but the *only* thing that ever routes through them today is `MatMul`'s own hand-written `adjoint` rule (`adjoint matmul(a, b), u: (matmul_transpose_b(u, b), matmul_transpose_a(a, u));`), reached exclusively from reverse-mode `grad()` synthesis. Any *forward-mode* code — user code, or stdlib code — that directly writes `matmul(a, transpose(b))` gets the real, materialized `linalg.transpose` today, with none of the same saving.

**Why this isn't just "write the axiom"**: `axiom_to_rewrite` (`egraph.rs`) builds an ordinary `axiom`'s rewrite pattern from a *single* flat `HashMap<param, ty>` — its own doc comment states directly, "no cross-algebra resolution attempted." `matmul(a, transpose(b)) == matmul_transpose_b(a, b)` needs three *different* algebras' own generics reconciled at once (`MatMul<A,B,C>`, `Transpose<B,B2>`, `MatMulTransposeB<A,B2,C>`) — structurally the same multi-target-algebra problem `derivative`/`adjoint` rules already solve via `derivative_rule_type_env` (used today for exactly this pair, just in the adjoint direction), not something a plain `axiom` can express as things stand. The real, well-scoped work is extending the axiom-rewrite path to reuse `derivative_rule_type_env`'s own multi-algebra resolution (or adding a distinct, narrower rewrite-rule kind for this cross-algebra-fusion shape) — not a new MLIR-side mechanism; the intrinsics and their real cost savings already exist and are already proven.

Also worth deciding, not yet designed: `matmul(transpose(a), transpose(b))` has no existing intrinsic at all (only `_a`/`_b`, never both) — whether that's worth a real `MatMulTransposeAB`/`indexing_maps` variant, or better rewritten as `transpose(matmul(b, a))` (one transpose instead of two, but now a real materialized one) is an open question, not just a missing case to fill in mechanically.

## Language/compiler-level bugs, found and precisely scoped, not yet fixed

- **`DynArray::push` never gets a protecting retain**, and **a top-level function's own parameters are invisible to `retain_targets`** (`refcount.rs`) — pushing an existing struct into a `DynArray`, or embedding a borrowed struct-typed *parameter* (not a `let`-local) into any container, inserts no retain at all; the caller's own later release then frees memory the container still points at. Confirmed present in the real kernel exactly once (`Sum::broadcast`'s own `u: f32` parameter — harmless, `f32` isn't refcounted) — real and general, but P1 not P0 on that basis. A general fix for the parameter-invisibility bug likely also fixes the `DynArray::push` case, since `push`'s own pattern is exactly "borrowed parameter embedded into a container."
- **A `for` loop bound to a const generic, if its own loop variable is used in ordinary arithmetic, breaks CPS conversion.** Root cause narrowed: the loop variable's type gets unified (via `infer.rs::unify_at`) with the *same* type variable a later monomorphization pass substitutes to a "value-as-type" representation — collapsing a genuine runtime scalar and a const-generic dimension onto one slot. The real fix needs the loop variable to stay an independently-substitutable `i32`, not literally the same variable as the bound. Worked around today with a manual counter. Plausibly the identical root cause behind `Sum<Tensor<T,N,M>>::sum`'s own rank-2 body failing to type-check for any non-square tensor (two different const generics' own loop variables getting silently unified together via a shared array-index expression) — also worked around, not fixed.
- **`cargo test` intermittently fails a couple of heavy-JIT-pipeline tests under concurrent load** — not a logic bug (passes every time run alone, and via the real CLI). Two distinct causes found: real resource contention running several heavy MLIR-lowering tests in one binary concurrently, and a real build-ordering race in `tests/pipeline.rs`'s exe-emission tests (they need `cleave_rt.lib`'s unhashed copy, only materialized once some workspace member finishes building it as a real Cargo dependency). Workaround for both: rerun the specific failing test binary alone.
- **A struct's embedded, non-`Tensor`-tagged array field (`[T;N]` declared directly on a struct) always still heap-boxes the whole struct** — the one remaining unimplemented half of the light-struct design (tensor-tagged fields are done, see `backlog-done.md`). No known instance in real workloads today.

## No `Type::<generics>::method(...)` static-call syntax — a zero-arg, output-type-driven algebra call always needs the algebra spelled out (`Init::xavier()`), never the concrete type (`Tensor::<f32,3,3>::xavier()`)

Confirmed unparseable by the grammar as-is (`turbofish` is a single, path-final construct — no slot on an intermediate path segment). Real design work beyond the grammar: today's dispatch is "algebra named, type inferred"; this is the reverse ("type named, algebra resolved by searching every declared algebra for a matching method name"), and needs a real answer for the ambiguous case (two algebras, same method name, same target) — Rust's own answer is a `<Type as Trait>::method()` disambiguator, a third syntax this would also need. Not attempted.

## A lambda returned from a function, or stored in a struct/array field, has no runtime representation

Calling a lambda literal directly is done (pure desugaring). This is harder: cleave's own "no runtime closure ABI" design means a lambda is never a real runtime value — every call is resolved to a statically-known unit at compile time. A lambda that outlives its own call site (returned, or read back from a field) needs a real representation to call through (a function pointer + captures record, at minimum), not just more static-name resolution. Needs its own design pass. Directly relevant to the `spawn`/`sync` primitive above, which needs closure capture to exist first.

## No reserved-word list — a keyword is only special at its own grammar position, so `let and = 5;` presumably parses

Not urgent, noted so it isn't lost.

## `--dump-inference-pass` reports a spurious "overlapping impls" error for a bound-restricted generic impl coexisting with an unrelated concrete one

Diagnostic-only — confirmed directly that it never blocks real compilation (`check_no_overlapping_impls` is only ever called from the `--dump-inference-pass` path, never from the real compile-blocking gate). Root cause: `unsatisfiable_bounds`'s own false-positive suppression only fires when *both* sides of a collision contribute a bound on a generic — a single-bound generic impl (`impl<S: HeapStruct> RawBuffer<S>`) coexisting with an unrelated concrete impl (`impl RawBuffer<f64>`) never reaches it. Not fixed — cosmetic, and the real fix (asking "is this one bound satisfiable by this one concrete type" rather than "do two bounds' candidate sets intersect") is a distinct code path worth a dedicated pass.

## `cleave/mlir/matmul_vectorize.transform.mlir` is read from a real filesystem path at runtime — breaks for a `cleave` binary shipped without its own source tree alongside it

Not urgent. The path itself is already correct on any machine that builds cleave from a full source checkout (`env!("CARGO_MANIFEST_DIR")`, resolved at compile time) — this is only about a *distributed* `cleave`/`cleave-build` binary, copied somewhere without `cleave/mlir/` next to it. `--convert-to-llvm`'s own `transform-preload-library` pass option wants a real path, not in-memory text, so the fix needs either a "parse a transform library from a string buffer" C-API entry point (not checked for) or writing an embedded copy out to a real temp file once at first use. Programs *compiled by* cleave never need this file at their own runtime — only `cleave`/`cleave-build` itself does, at the moment it compiles a program containing a matmul.

## `--target-cpu`/`--target-features` are wired end to end but have no real effect

`mlir::ExecutionEngine`'s own C++ implementation always builds its own `TargetMachine` via `JITTargetMachineBuilder::detectHost()`, and `mlir-sys`/`melior` (the vendored fork) expose no way to override it. Confirmed directly: an object built with `--target-cpu x86-64-v2` still disassembles to `zmm` (AVX-512) instructions, identical to the default build. Both flags stay wired (parse, validate, stamp real `llvm.func` attributes) with a real warning printed at the point of use, rather than removed. A real fix needs `mlir-sys` extended with a real `TargetMachine`-construction entry point or `mlirTranslateModuleToLLVMIR` — worth doing alongside the existing upstream Windows-support PRs against that fork rather than as a one-off.

## `mlir-sys`/`melior`'s own ceiling: no path to binary redistribution, and no way to define a real custom MLIR dialect — a real design exploration, not attempted

Three compounding pains: today's build needs a hand-built local LLVM/MLIR/openmp toolchain with no prebuilt package on any platform, `mlir-sys`/`melior` expose no way to construct a custom `TargetMachine` (above) or define a new dialect, and a second, sibling language is now planned, sharing enough architecture to want its own domain-specific dialect too.

**Recommended path, not yet started**: (1) rework `mlir-sys` for redistribution (a `build.rs` that downloads a hash-verified prebuilt tarball per platform — real, bounded Rust-side work; the recurring cost is release engineering, rebuilding 4-5 platform tarballs on every LLVM/MLIR bump, not code) — pays off immediately, zero retarget risk, do first. (2) Investigate IRDL's real current capability against the pinned MLIR 22 tree next — describes a new dialect's ops/types/constraints as MLIR IR itself, loaded at runtime, no C++/TableGen required, reachable entirely through the generic C-API construction path `mlir_lower.rs` already uses; last known limitation is structural-constraint-only verification (no custom verifiers/canonicalization/assembly). A `build.rs`-driven TableGen+C++-shim fallback is real and reaches full parity, but deliberately kept in reserve, not built, for the specific day IRDL structurally can't do something needed — it reintroduces a hard C++ toolchain dependency this whole exploration is trying to get away from, and a second extension mechanism alongside cleave's own algebra+stdlib one. (3) Retarget cleave onto the result — near-zero cost if `melior` itself doesn't change, a real multi-week port if it does.

Two concrete shared dialects for the sibling language are the target once IRDL is validated: a **CPS dialect** (real MLIR block-argument join points — also closes cleave's own known gap that `Forward::walk` bails out entirely the moment it meets a real `If`, since nothing today builds a join node for a `phi(a,a)==a` rule to match against) and an **e-graph term-vocabulary dialect** (one declared schema generating both `egg`'s term language and `mlir_lower.rs`'s lowering, removing today's hand-synchronized duplication) — the latter depends on the former for anything to saturate *across* a branch at all. Not built.

## A real, separately-compiled, linkable *cleave-to-cleave* library format

Distinct from `--emit-exe`/`export fn` (real, shipped, used for Rust interop). A `.o` alone carries no metadata (signatures, generic templates, algebra impls) for a downstream cleave program to monomorphize against — unlike Rust's `.rlib`/`.rmeta` split. Without an equivalent, cross-crate cleave code always recompiles from source (today's `stdlib` model, works but risks long whole-program builds) rather than linking a real distributable library. Needs a real design pass once the language is more stable. Not attempted.
