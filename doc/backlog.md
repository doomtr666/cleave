# Backlog

*Ordered — top to bottom is the order we work through it. Not a wishlist: each entry is a real, confirmed gap (found by testing or by direct inspection), not a guess about what might be missing.*

## Done

### Real MLIR lowering, end to end (`cleave/src/mlir_lower.rs`)

CPS-form code lowers to real MLIR and JIT-executes (`--dump-mlir`, `--run`) — not just a dump. Covers: a function's own `return`; `if`/`else` as `scf.if`, with a join carrying **any** number of positions (the `if`'s own value, plus one per outer variable either branch reassigns — not just a single value, see "real bugs" below); `while`/`for` as `scf.while`, carrying loop state correctly *per position* (a loop carrying an `i32` counter and an `f32` accumulator at once needs each materialized against its own type, not one shared guess); a real call to another top-level `fn` as `func.call`; an `extern fn` call as `func.call` against a `private` declaration.

**The generic MLIR intrinsic mechanism** — `doc/hld.md`'s own "one generic 'emit this named MLIR op' primitive" thesis, actually built: a reserved `mlir::dialect::op(...)` call (e.g. `mlir::arith::addi(a, b)`), recognized *structurally* by its path's first segment (not algebra-dispatched), lowers via one generic `OperationBuilder`-based builder — zero per-op-name Rust knowledge. Named call-arguments (`predicate: "2 : i64"`) carry a static MLIR attribute's raw text. Replaces the earlier `#[mlir(...)]`-attribute mechanism entirely (deleted, along with `PrimOp::Intrinsic`/`UnitBody::Intrinsic`). `#[mlir_type("...")]` on an algebra `impl` does the same one level up, for *type* lowering (`ty_to_mlir` looks a cleave type name up in a map built from every tagged impl, parses the declared MLIR type text — no per-type-name Rust match left beyond `bool`, a genuine structural special case matching `infer.rs`'s own treatment of it).

**Arrays** — literal/nested-literal (`[[1,2],[3,4]]`)/`[value; N]` construction, and multi-index read/write at any depth (`a[i,j]`, collapsed into one op by `cps.rs`'s own `collect_index_chain`), in **two** representations depending on where the array lives: a standalone array is a self-describing `memref`; an array reached through a struct field (below) is an opaque `!llvm.ptr` into that struct's own storage (a `memref` can't be an `!llvm.struct` field at all — confirmed empirically, MLIR's verifier rejects it, "operand #1 must be primitive LLVM type"), addressed via `llvm.getelementptr` instead.

**Structs** — heap-allocated (a real call to `cleave_alloc`, a new `cleave-rt` function backed by `std::alloc::alloc`, deliberately leaked — no ownership/`drop` story exists yet) reference values, not `!llvm.struct`-typed SSA values built via `undef`+`insertvalue`/`extractvalue`: found necessary by direct testing — a struct returned from one function and read by its caller came back reading garbage once its storage lived in the *constructing* function's own stack frame (`llvm.alloca`, tried first, doesn't survive a return). Field access/mutation (`s.x`, `s.x = v`) go through `llvm.getelementptr` + `llvm.load`/`llvm.store` against this same heap pointer. Works for generic structs (both type and const generics, e.g. `Matrix<T, const R, const C>`) and for array-typed fields (embedded *inline* as `!llvm.array`, not a `memref` — addressed via one combined GEP walking through the struct *and* the array together).

Verified end-to-end via real JIT execution, not just verification: `examples/matmul.cleave` (a generic `MatMul` algebra, triple-nested loops, struct-of-arrays, real generic dispatch — numerically verified against hand-computed expected values, not just "didn't crash") and `examples/complex.cleave` (a generic `Complex<T>` struct dispatched through `Ring`).

**Real bugs found and fixed along the way, all by direct testing, none hypothetical:**
- A `()`-returning top-level function (`fn main() { ... }`, no `->` clause) had no MLIR representation at all — `ty_to_mlir` panicked on the unit type. Fixed: zero MLIR results (not "one result of nothing"), and `CVal::Unit` filtered out of a `return`'s own materialized values rather than reaching `lower_cval` (which doesn't support it) — the same filter later reused for `scf.yield`'s own values (see the `if`-join bug below).
- `f32`/`f64`/`bool` literal `CVal`s weren't handled in `lower_cval` at all (only `CVal::Int`) — the first program using a bare float/bool literal anywhere but a comparison hit a clean but blocking panic.
- `lower_loop`'s own "before"/"after" region environments started **empty**, not inherited from the enclosing scope — a loop body referencing *any* outer, non-carried variable (an enclosing function's own parameter, chief among them a struct reference) was invisible inside the loop, panicking "unbound CPS variable." Fixed by cloning the outer `env` into each region's own environment before overlaying the loop's own carried params.
- `lower_loop` materialized every carried value's own *initial* literal against one shared expected type (the enclosing function's own return type) — silently wrong the moment a loop carries more than one type, or a type different from the function's own result. Masked by every earlier loop test (each only ever carried one type, always equal to the function's own return type) until a loop carrying an `i32` counter *and* an `f32` accumulator at once surfaced it as a native MLIR/LLVM assertion crash, not even a clean panic. Fixed properly, not patched around: `CFunDef` gained a `carried_types: Option<Vec<Ty>>` field, populated in `cps.rs` (`mutated_free_vars`/`mutated_free_vars_expr` now also thread `ctx` and return each mutated name's own concrete type, read off its assignment target's own `ctx.node_types` entry) so `mlir_lower.rs` never has to guess.
- **`lower_if` only ever supported a single-parameter join** (the `if`'s own value) — an `if`/`else` whose branches *also* reassigned an outer variable panicked outright, and this bit often in practice: an `if` nested inside a loop body, updating some outer flag/accumulator, is a completely ordinary pattern (confirmed broken by direct testing before the fix, e.g. `if i == 3 { saw_three = 1; }` inside a `while`). `lower_loop` itself needed no equivalent fix — it already iterated `loop_def.params` generically, whatever count `cps.rs` found. Fixed by generalizing `lower_if` to `CFunDef::carried_types` the same way `lower_loop` already used it (join value first, then one `Ty` per reassigned outer variable, `cps.rs`'s own `ExprKind::If` handling populates it), plus a further wrinkle: a *unit-typed* join position (a bodyless-`else`/statement-position `if`'s own discarded value) carries no real MLIR value at all — filtered out of `scf.if`'s own declared results and out of `scf.yield`'s own values entirely (`is_unit_ty`), never bound in `env`, matching `PrimOp::Store`'s own "bound result is unit and never read" convention.

### Boolean logic (`and`/`or`/`xor`/`implies`/`not`)

`stdlib/logic/logic.cleave` — `algebra Logic<T> { and, or, xor, implies, not }`, `impl Logic<bool>` with real bodies (`mlir::arith::andi/ori/xori`, `implies` as `not(a) or b`, `not` as `a xor true` — `arith` has no dedicated `not`/`negi`, confirmed directly against melior's own dialect module). In the prelude alongside `num` — `if a and b { ... }` just works, no `use` needed. The grammar/desugaring for all five already existed (`and`/`or`/`xor`/`implies` as binary keywords, plus `not` newly added as a second unary prefix operator alongside `-`) — this was purely the missing stdlib `impl`, the same gap `Ring`/`Ord` had before real arithmetic landed.

**A real parser bug found and fixed while adding `not`:** a bare-word keyword literal (`"not"`, and — checked, also true of the pre-existing `"and"`/`"or"`/`"xor"`/`"implies"`) matches as a *prefix* of a longer identifier too (`not_a` parsed as the keyword `not` applied to a bogus `_a`), silently truncating the intended variable name. Fixed with a word-boundary lookahead (`"not" ~ !XID_CONTINUE`) — which itself needed the whole rule marked atomic (`@{...}`), since Pest's own implicit whitespace-skipping otherwise runs *before* the lookahead too, checking the character after any following whitespace instead of the one right after the keyword (`and 3` would wrongly fail the guard: a digit *is* itself a valid `XID_CONTINUE` character). `grammar.pest`'s `unary_op`/`logical_op`/`implies_op` all carry this now.

Also fixed in the same pass: `Ring<T>` gained `neg` (`mlir::arith::subi(0, a)` for integers — `arith` has no dedicated `negi` either — `mlir::arith::negf(a)` for floats), closing the previous "unary minus never resolves" gap.

### extern fn / cleave-rt / print

`extern fn name(...) -> ...;` declares and calls a foreign C-ABI symbol — no ABI string (`extern "C"`, an earlier draft) needed, the declared signature already says everything else. Backed by a small Rust crate, `cleave-rt`, exposing plain `extern "C" fn` symbols registered with the JIT `ExecutionEngine` by real function pointer (not resolved by dynamic symbol name — sidesteps Windows/MSVC CRT-symbol-visibility questions a raw libc binding would hit). `extern(symbol) fn name(...)` is the override for when several algebra-impl methods share one cleave-level name (`print`) but each needs a distinct real symbol (`print_i32`/`print_i64`/...) — `stdlib/io/io.cleave`'s `Print<T>` is the working end-to-end example, one `impl` per numeric width, `use io;` (not prelude, unlike `num`/`logic`).

### Real stdlib arithmetic, backed by `mlir::...` calls

`stdlib/num/num.cleave`: `Ring<T>` (`add`/`sub`/`mul`/`neg`) and `Ord<T>` (`lt`/`le`/`gt`/`ge`/`eq`/`neq`), each with a real body — one direct `mlir::arith::*` call — per numeric width (`i8`/`i16`/`i32`/`i64`/`f32`/`f64`). No stub bodies left. `num` is in the prelude (no explicit `use` needed); `io` is not.

### Field-mutation assignment (`s.x = v`)

A struct is a stable reference, mutated in place — same choice as arrays (below), same reasoning: identity never changes across a branch/loop, only the one field's own storage, nothing to thread as extra carried state. `cps.rs` converts it to a single `PrimOp::FieldStore` (mirrors `PrimOp::Store`'s own "real effect, bound result unit, never read" shape); `mlir_lower.rs` lowers it through the exact same `llvm.getelementptr` field-addressing struct construction/read already use, factored into one shared `store_field` helper.

### CPS conversion — Stages 1-5

Turns a monomorphized, fully-concrete `MonomorphizedProgram` into continuation-passing form (`cleave/src/cps.rs`, `--dump-cps`; tests in `cleave/tests/cps.rs`). See the module's own doc comment for the full design (classical CPS, syntax-directed over the structured AST, primitive-vs-real-call distinction).

- **Stage 1 — straight-line code.** Literals, variables, plain `let`, field access, struct construction, calls — both a reserved `mlir::...` intrinsic as a straight-line `LetPrim` (Appel's PRIMOP) and real/recursive callees as a synthesized continuation + tail `App` (Appel's APP).
- **Stage 2 — `if`/`else`.** Both arms tail-call one synthesized join continuation rather than each inlining `k` separately, which would duplicate "what happens after" combinatorially under nesting.
- **Stage 3 — `while`/`for`.** Loop-carried state via a self-recursive continuation (`for`'s own index; `while` carries nothing extra by itself at this stage).
- **Stage 4 — `let mut`/plain (bare-name) assignment.** Mutation *across* a branch/loop is the real work: `mutated_free_vars`/`mutated_free_vars_expr` (a static, shadowing-aware AST walk, no dominance-frontier/φ-node construction needed) find every enclosing-scope name a branch/loop body might reassign — and, since the MLIR-lowering carried-types bug above, each one's own concrete type too — threaded as extra parameters on the join/loop continuation alongside its own value. Continuations carry `(CVal, &CEnv)` throughout for this reason (state-passing-style CPS).
- **Stage 5 — arrays.** Construction (`ArrayLit`/`ArrayRepeat`, including nested `[[0.0; K]; N]`), and reads/writes at *any* depth (`a[i,j]`/`a[i][j]` — indistinguishable after lowering, and semantically identical in this language: a multi-dim array's own type is always `Array(Array(T,C),R)`). `collect_index_chain` collapses a whole run of nested `Index` nodes into *one* combined, multi-index `Load`/effectful `Store` up front rather than chaining single-index ops — required for a *write* specifically (an intermediate single-index `Load` of "the row", written into separately, would only be correct if `Load` aliased the original storage instead of copying it out — a representation choice never actually made) and reused for reads too, for consistency. `Store` is a real effect, not a functional update: HPC rules out copying a whole array per element write, and a stable array *reference* sidesteps Stage 4's own mutation-threading entirely — identity never changes across a branch/loop, only contents, nothing to carry.

Verified end-to-end on `examples/matmul.cleave`, the project's own canonical target — triple-nested loops, `a.values[i,k]`/`result.values[i,j]`, all converting and (now) actually executing correctly.

**Two real bugs found and fixed along the way, both by direct testing:**
- **A `for` loop whose own bound names a const generic** (`for i in 0..N`) broke `resolve_synthetic_binop`. Root cause: `infer.rs`'s `ExprKind::For` unifies `start`'s own type variable with `end`'s (here, `N`'s own `const_widths`-tracked one); once monomorphized, the loop index's own declared *width* could come back as `N`'s own resolved *value* (`Ty::Const`) instead of an ordinary `Ty::Con`. Worked around locally in `cps.rs` rather than fixed at the root (see the `Ty::Const`/`Ty::Con` item below): falls back to `i32` — the same default `apply_defaults` itself would have chosen had its own `const_widths` guard not deliberately deferred it, and correct precisely because nothing else ever pins the counter to a more specific width without going through an ordinary `Ty::Con` directly (never hitting this fallback in that case).
- **Nested/chained indexed assignment** (`result.values[i,j] = sum`) initially panicked — an overly conservative single-level-only guard, since a 2D field access desugars to exactly this shape. Fixed by the `collect_index_chain` multi-index collapsing described above, not by relaxing the guard blindly.

### Closure conversion (lambdas), backed by total monomorphization — no runtime closure ABI

`hld.md`'s own architecture, actually built: a lambda never becomes a runtime value at all. **Stage A** — a `let`-bound lambda gets extracted into its own fresh unit; since `ExprKind::Lambda` is a syntactic value, it's generalized by `infer.rs` exactly like a top-level generic `fn` (real Hindley-Milner let-polymorphism) — a new `Infer::lambda_schemes`/`ProgramInference::lambda_schemes` side-table (keyed by the lambda's own `NodeId`) carries its `Scheme` past inference, and `monomorphize.rs`'s worklist specializes it once per concrete instantiation actually reached, the identical "reverse-unify against a call site's own concrete `node_types`" mechanism a generic `fn` already used, just keyed by `NodeId` instead of name. Free variables (`cps.rs::lambda_free_vars`, a shadowing-aware walk recursing into nested lambda bodies too) become explicit *leading parameters* on the generated unit — structural captures, not a boxed environment record — snapshotted from `env` at the lambda's own `let` (by value, not by reference: a later `let mut` reassignment of a captured variable doesn't affect an already-built closure, verified by a dedicated test). Calling a lambda-bound name resolves through a new `CVal::Closure { captures }` living entirely inside `CEnv` during conversion — never written into the final `CExpr`/`CFunDef` tree `mlir_lower.rs` sees.

**Stage B** — a higher-order call (`apply(inc, 5)`, `apply`'s own `f: (i32) -> i32` parameter fully concrete, no ordinary type variable anywhere in it) needed a second, genuinely new kind of specialization: `cps.rs::build_higher_order_specializations` detects a call whose argument is a `Path` naming a known callable (lambda-bound, resolved via `monomorphize.rs`'s own extended argument-position scanning — a callable passed as a bare *value* never becomes a `Call` node of its own, so the ordinary per-`Call` detection alone would never see it — or a bare top-level `fn`), and builds one specialized copy of the callee per distinct `(callee, resolved callable)` combination reached, erasing the function-typed parameter from its own signature entirely and redirecting every call to it, inside the callee's own body, straight to the resolved callable's own unit (`ConcreteUnit::baked_closures`/`higher_order_args`, reusing `call_names`'s own per-instantiation shape). The *original*, unspecialized callee is never itself converted — a `Ty::Fn`-typed parameter has no runtime representation to call it through in the first place, so `convert_program` skips any such unit outright.

Verified end-to-end via real JIT execution: a captured-variable lambda, a `let`-bound generic lambda instantiated at two types from two call sites, `apply(inc, 5)`, two distinct callables passed to the same higher-order callee from two different call sites (proving separate, not shared, specializations), and `doc/user_guide.md`'s own higher-order-functions example (previously caveated "type-checks but can't run yet" — caveat removed, now verified). A bare lambda *literal* passed directly as an argument (no prior `let`) still panics cleanly via `convert_expr`'s own catch-all — deliberately out of scope for this pass. Self-recursive `let`-bound lambdas and calling a lambda literal directly (see "Done" above) are no longer blocked on this either, both landing later in the same session — a lambda *returned* from a function, or stored in a struct/array field, is still open (see items below), a genuinely harder problem needing a real runtime closure representation, not just more desugaring.

**A real bug found by direct testing, not hypothetical:** the first working version of Stage B still converted the *original*, unspecialized callee unit (`apply`) as an ordinary top-level function alongside its specializations — its own body's call to the now-erased parameter has no resolution at all (nothing ever gives `resolve_call` a `call_names` entry for it, since only a Stage-B-built specialization gets one), so it panicked immediately the moment `convert_program` reached it, even though nothing could ever actually call it. Fixed by skipping any unit with a `Ty::Fn`-typed parameter of its own outright — it's unreachable by construction, since nothing in the language can produce a runtime value of function type to call it with.

### `div`/`mod`/`rem`, and bitwise ops (`bitand`/`bitor`/`bitxor`/`bitnot`/`shl`/`shr`)

`Ring<T>` gained `div` (`mlir::arith::divsi`/`divf`, one-line-per-width, the same pattern `neg` already followed) — `/` was already a grammar-level operator desugaring to `div`, just missing its own stdlib impl. `mod`/`rem` and the six bitwise ops are deliberately **named functions, not operators** (`doc/grammar.md`'s own explicit, pre-existing design call — no precedence level burned on rarely-used-in-HPC bitwise ops, sidesteps the classic C `&`/`|` vs. `==` trap entirely) — a new `Rem<T>` algebra (`rem`: `arith.remsi` directly, truncated, sign follows the dividend; `mod`: no single dedicated MLIR op, computed from `remsi` plus a floored correction when its own sign disagrees with the divisor's) and a new `Bitwise<T>` algebra, both integer-width-only (`i8`/`i16`/`i32`/`i64`).

**A real bug found by direct testing, not hypothetical:** `bitnot`'s first version wrote `mlir::arith::xori(a, -1)` inline — an `mlir::...` call's own arguments don't cross-unify with each other (no real declared signature to unify against), so the bare `-1` independently defaulted to `i32` regardless of `a`'s own width, mismatching for every `Bitwise<T>` impl but `i32` itself (`arith.xori op requires the same type for all operands and results`, MLIR verification failure, for `i8`/`i16`/`i64` specifically — `i32` accidentally happened to match, so a narrower test would have missed it). Fixed with an explicit `let all_bits: i8 = -1;` intermediate per width — same idiom `Logic::implies` already established for exactly this class of problem.

**A second real bug, found only once these landed in the prelude:** `num`/`logic` are unconditionally loaded into *every* compiled program (no dead-code elimination exists yet — see the open item below), so `Rem::mod`'s own `if`/`else` body means `scf.if` is now present in every module regardless of whether the program's own source ever writes an `if` — three existing tests building their own minimal, hand-rolled MLIR pass pipeline (`create_to_llvm` alone, no `create_scf_to_control_flow`) broke the moment `mod` landed, since `scf.if` has no direct LLVM translation. Fixed by adding the missing pass to all three, matching `run_i32`'s own already-correct pipeline — not by reworking `mod`'s own body to avoid `if` just to dodge the issue.

### Equality saturation over straight-line CPS segments, driven by `axiom` (`cleave/src/egraph.rs`)

`doc/hld.md`'s own long-standing thesis — an e-graph (`egg = "0.11.0"`) turning a user-declared `algebra ... { axiom ... }` into a real `egg::Rewrite`, operating on already-monomorphized CPS, not the AST — actually built. `registry.rs` used to discard every axiom outright (`AlgebraItemKind::Axiom(_) => None`); now retained (`AlgebraEntry::axioms`, `Registry::axioms`).

**Scope, deliberately**: one e-graph per *straight-line* CPS segment (never crosses a real `If`/loop/recursive call, "no binders" — `hld.md`'s own open-risk list already flagged full CPS-continuation e-graphs as a research frontier, not attempted here). `CleaveLang` reuses **one** bare-data `Op(Symbol, Vec<Id>)` variant for every operation kind (an algebra-dispatched call, a raw `mlir::...` op, a struct construction, a field read), distinguished only by a symbol-text convention — `define_language!` allows at most one data field per variant, and two same-shaped bare variants are ambiguous to parse (the *first*-declared one always wins), both confirmed empirically against `egg`'s own macro source, not its (partly stale) docs.

**The forward translator** (`Forward::walk`) recognizes two shapes transparently, continuing to build the *same* e-graph through them rather than stopping: a raw `mlir::...` call (already a flat `LetPrim`) and — the single most novel piece — `emit_call`'s own real-call shape (`Fix{defs:[k], body:App(unit, args)}`) *when the callee's own body is straight-line and pure* (`is_straight_line`/`is_pure_prim_op`, an allowlist over `PrimOp` — `RawMlirOp`/`Field`/`Struct`/`Array`/`ArrayRepeat`/`Load`, never `FieldStore`/`Store`/`Extern`), treating the *whole call* as one opaque node (single-level transparency only — descending into the callee's own body is a natural, not-yet-built follow-up, see below). Ordinary arithmetic (`a+b`) does **not** compile to a flat `LetPrim` chain — it's a real call to `Ring::add<i32>` — so this transparency is what makes anything reach the e-graph at all. Struct construction/field-read are translated the identical way once discovered they're just as pure (see the "real bugs" list below for why this needed a prerequisite fix first). Copy-propagation and CSE fall out for free from ordinary hashconsing/environment lookup (a `LetPrim`-bound `CVar`'s later references reuse its own e-class `Id` directly) — not a separate analysis.

An `axiom` becomes **one concrete `Rewrite` per reached concrete instantiation** (never one generic rule): `Op`'s own discriminant is a concrete unit name (`"Ring::add<i32>"`), never an abstract one, so a generically-declared axiom is substituted into a `Rewrite` per `(algebra, concrete type)` pair actually present in the segment being optimized — the same "monomorphize once per instantiation" discipline everything else in this codebase already follows. Patterns are built programmatically (`PatternAst`/`ENodeOrVar`), never parsed from text — the same ambiguity class already hit twice building `CleaveLang` itself. `hld.md`'s stated v1 trust model: an axiom is trusted as declared over its whole generic algebra, no per-impl soundness gate.

Saturates via `egg::Runner`, extracts via `Extractor::new(_, AstSize)`, and a backward translator (`rebuild`/`rebuild_segment`, mechanical inverse of the forward one, memoized — see below) splices the result back in place of the original segment, patching the untouched "boundary" tail's own reference to the segment's final value. `cleave/src/main.rs`'s `--dump-cps-optimized` (the optimized CPS) and `--dump-cps-equivalences` (`explain_equivalence`'s own flat proof string per changed function) inspect it directly; `--run`/`--dump-mlir` apply it by default now too (initially staged as visibility-only, deliberately, before being wired in — see the follow-up entry below).

`Array`/`ArrayRepeat`/`Load` translate the identical way `Struct`/`Field` do (construction/read are pure — the same "a stable reference sidesteps mutation-threading, only `Store`/`FieldStore` are real effects" reasoning `cps.rs`'s own CPS-conversion entry already gives for arrays) — `is_pure_prim_op` had already anticipated this when it landed (see above), this just fills in `Forward::walk`'s own direct translation and `rebuild`'s own reconstruction. The backward translator's own lookup tables were bundled into one `OpTables` struct at this point (8 distinct tables — `raw_ops`/`struct_ops`/`field_ops`/`array_ops`/`array_repeat_ops`/`load_ops`/`call_units`/`free_vars` — past the point where growing `rebuild`/`rebuild_args`'s own positional-parameter list further stayed reasonable).

**A built-in, non-`axiom` rewrite**: `struct_projection_rewrites` — "reading a field straight back out of the struct that just set it" (`field(struct(a0,...,aN), field_i) -> a_i`), definitionally true for every struct the same way constant folding is definitionally true for every `+`, generated from `Forward`'s own `struct_ops`/`field_ops` tables, not from `registry.axioms`.

**Real axioms now shipped** in `stdlib/num/num.cleave`'s `Ring<T>`: `add_commutative`, `mul_commutative`, `add_zero`, and `add_sub_assoc` (`sub(add(a,b),c) == add(a, sub(b,c))`) — the last one specifically chosen to *compose* with the others plus `ConstantFold` rather than encode a bespoke cancellation rule: `10 + x - 10` needs commutativity (regroup `add(10,x)` to `add(x,10)`) *then* associativity (regroup `sub(add(x,10),10)` to `add(x, sub(10,10))`) *then* constant folding (`sub(10,10) -> 0`, only possible once the two `10`s are actually siblings) *then* `add_zero` — four independent, already-present mechanisms composing via ordinary equality saturation, no fifth rule needed. Verified live via `--dump-cps-equivalences` on a real, compiled example.

**Real bugs found and fixed along the way, all by direct testing, none hypothetical:**
- `RecExpr`'s derived `PartialEq` compares raw internal node-index layout, not the semantic tree — two `RecExpr`s printing identically via `Display` can still compare unequal (`id_to_expr` and `Extractor::find_best` each build their own independent internal node list). "Did anything change" is compared by `Display` text now, never the derived `PartialEq`.
- The "original" (pre-rewrite) form for `explain_equivalence`/the change-comparison must be captured from the e-graph *before* `Runner::run` — captured *after* (tried first) reads back an arbitrary member of the now-merged equivalence class, silently defeating the comparison (a `Bitwise::bitnot` segment that never even touches `Ring::add` was showing up as "changed").
- `Runner::with_egraph(...)` *replaces* the runner's own `egraph` field wholesale — calling it before `.with_explanations_enabled()` (which mutates the *current* egraph in place) silently discards the flag; order matters specifically because of that replace-vs-mutate asymmetry between the two builder methods.
- `is_straight_line` only checked for `Fix`/`If` absence, never a `LetPrim`'s own `op` — a callee shaped `LetPrim{op: Extern{..}} -> App` (exactly `Print<T>::print`'s own real body) was judged straight-line, meaning the moment translation could reach a `print` call, `Forward::walk` would've folded it into one opaque, freely-reorderable node — genuinely unsound (an observable, order-dependent effect). Fixed as an *allowlist* over known-pure `PrimOp`s (`is_pure_prim_op`), not a denylist, so a future `PrimOp` variant defaults to "not straight-line" (missed optimization) rather than silently becoming unsoundly reorderable.
- `rebuild` had no memoization — `Extractor::find_best`'s own `RecExpr` legitimately DAG-shares one `Id` between multiple parents once two constructions hashcons together, but the recursive backward walk rebuilt a shared `Id` once *per parent*, with a different fresh `CVar` each time (e.g. two separate `cleave_alloc` calls at runtime for what should be one allocation). Fixed with a `RefCell<HashMap<Id, CVal>>` memo (`RefCell`, not `&mut`, because every continuation in this module is `&dyn Fn`, not `FnMut`) — which itself hit a classic Rust trap: `if let Some(v) = memo.borrow().get(&id) { return k(v.clone()); }` keeps the `Ref` guard alive through the *whole `if let` body* (since `v` borrows from it), so `k`'s own recursive `memo.borrow_mut()` elsewhere panicked ("already borrowed") the moment the memoized path was actually taken. Fixed by cloning out of the borrow (`let cached = memo.borrow().get(&id).cloned();`) before ever calling `k`.
- `optimize_program`'s own root-var detection (`segment_root_var`) originally only recognized the boundary being exactly `App{args:[Var(v)]}` (a whole function body reaching its own final `return`) — meaning a function whose interesting segment is followed by *more* code (e.g. a `print` call, correctly excluded per the bug above) was skipped entirely, even with real algebraic redundancy in the untouched prefix. Generalized to "the one segment-bound var the boundary actually references, if there's exactly one" — which is *also* what closes a real struct-aliasing question (`PrimOp::FieldStore`'s own doc comment: "a struct is a stable reference," and `alloc_struct` really does heap-allocate, never freed, so two hashconsed-together constructions could differ in identity if a boundary held live references to *both* and mutated one) — "exactly one referenced segment var" forecloses that outright, no separate guard needed.
- `const_eval::eval_binop` (reused by `ConstantFold`) only ever implemented `"add"`/`"mul"` — inherited from its original job (const-generic array-size arithmetic, `[T; N+M]`, which historically never needed subtraction). This silently defeated the `add_sub_assoc` composition above: `sub(10,10)` sat in its own un-folded e-class even with both operands literal, since `eval_binop("sub", ...)` simply returned `None`. Fixed with a one-line `wrapping_sub` addition (the module's own doc comment had already anticipated this exact gap). Two existing tests (`const_eval.rs`, `infer.rs`) had used `"sub"`/`4-3` as their own example of "a still-unrecognized operator" — updated to `"div"`/`4/3` instead, now genuinely still unrecognized.

**Verified end to end via real JIT execution** (`cleave/tests/egraph.rs`, `examples/axiom_demo.cleave`): a real axiom folds a genuine call away entirely, the naive and optimized CPS forms are observably different, and both still execute to the identical runtime value — including the full `add_commutative` → `add_sub_assoc` → constant-fold → `add_zero` chain on `10 + x - 10`, not just a single-rule case.

**Explicitly not attempted here, real follow-ups, not oversights** — see the backlog items below: multi-level call transparency (inlining *into* a pure callee's own body, not just treating the call as one opaque node), representing an `If`/join point as an e-graph node at all (even the "both branches already agree" case needs this), and `CVal::Float` in the e-graph (bare `f64` has neither `Ord` nor `Hash`, both required by `define_language!`'s derives — would need `ordered-float` or an equivalent wrapper).

### Dead-code elimination for unused stdlib specializations

`cps::eliminate_dead_code(CpsProgram) -> CpsProgram` — a plain worklist reachability walk starting from `"main"`, following every `CVal::Label` reference (`App`'s own callee, a real call's own continuation argument, ...) recursively, then dropping every `CTopLevelFn` never reached. Works off already-resolved CPS references only, never re-derives call resolution from the AST — a real call's own callee name is already unambiguous by the time CPS exists (`emit_call`'s own `App{func: Label(name), ..}` shape), matching this module's own "everything past monomorphization is already concrete" discipline throughout, the same reasoning the equality-saturation entry above already leans on. A `Fix`-local continuation's own label (`"k$0"`) gets swept into the reachable set too along the way — harmless, `"::"`/`"<...>"` (a real unit's own naming convention) and `"$"`-delimited (a local continuation's own) never collide.

Wired into every one of `main.rs`'s pipeline blocks that calls `convert_program` (`--dump-cps`, `--dump-cps-optimized`, `--dump-cps-equivalences`, `--dump-mlir`, `--dump-mlir-lowered`, `--run`), right after `convert_program` and before `optimize_program` (fewer functions for the e-graph pass to bother with, and a cleaner `--dump-cps-equivalences` signal — no explanations from code nobody reached). Confirmed via direct measurement: `examples/fib.cleave`'s own `--dump-cps` output dropped from 105 functions to 5. Verified against every `examples/*.cleave` file's own `--run` output staying numerically identical before/after.

**A new CLI flag alongside this**, `--dump-mlir-lowered`: mirrors `--dump-mlir`, but runs the identical pass pipeline `--run` itself uses (`create_scf_to_control_flow` then `create_to_llvm`) before printing, rather than after (and instead of JIT-invoking) — shows the `llvm.*`-dialect MLIR actually handed to the `ExecutionEngine`, not the pre-conversion mixed-dialect form `--dump-mlir` shows. Real textual LLVM IR (`.ll` syntax) stays out of reach: `melior`/`mlir-sys`, as vendored, don't expose `mlirTranslateModuleToLLVMIR` at all — would need a raw FFI binding added directly against the C API, not attempted here.

### Inherent-impl methods reach CPS/MLIR

`v.magnitude_sq()` (dot-call syntax) type-checked (`infer.rs`'s own dispatch through `registry.inherent_method`) but panicked at CPS conversion — `cps.rs::collect_units` had no `ItemKind::InherentImpl` arm at all, and `convert_expr` had no `ExprKind::MethodCall` arm either. Both non-generic (`impl struct Vec2 { ... }`, one shared `Infer` instance per impl block via `infer_inherent_impl_block` — real mutual recursion between sibling methods for free, the same discipline `callgraph::infer_program` already applies to a mutually-recursive top-level `fn` group) and generic (`impl<T> struct Boxed<T> { ... }`) impls now reach CPS/MLIR and JIT-execute.

The generic case needed its own worklist in `monomorphize.rs` — a new `InherentTemplate`/`build_inherent_templates`/`derive_inherent_instantiation` triple, structurally close to `ImplTemplate`'s own but one level simpler: `Registry::inherent_method`'s own guarantee (at most one method of a given name per struct) means a `MethodCall` site needs no structural candidate *search* the way an algebra call does — `base`'s own already-resolved concrete type names the struct directly, so it's a plain `(struct_name, method_name)` lookup among `InherentTemplate`s, then the *same* reverse-unification (`unify` the template's own generic `(param_patterns) -> ret_pattern` against the call's own concrete one) every other worklist here already uses. Method-call resolution itself (`cps.rs::resolve_method_call`) is its own small, separate namespace from `resolve_call`'s three tiers, for the identical "no ambiguity to resolve" reason — either a `call_names` override (generic case) or the bare `struct::method` unit name directly (non-generic case, mirroring a non-generic top-level `fn`).

Explicitly **not** in scope for this pass, unrelated gaps: a bare-name call to an inherent method (`magnitude_sq(v)`, as opposed to `v.magnitude_sq()`) still doesn't resolve — inherent methods have no bare-name call form of their own, a separate, pre-existing namespace question; and an unannotated inherent method's return type still isn't usable from outside its own impl block (see the item below, unaffected by this landing).

### String literals + `print` of one string (`[i8; N]`, no new representation)

A string is a plain `[i8; N]` array — full erasure at `lower.rs` time, no new `ast.rs`/`infer.rs`/`cps.rs` representation at all: `"hi"` becomes an ordinary `ExprKind::ArrayLit` of `i8`-suffixed `NumberLit`s (one per UTF-8 byte), structurally indistinguishable from a hand-written `[104, 105]` from that point on. `grammar.pest`'s `string_lit` token already existed (used only inside `mlir_attr`'s own value position) — just added to `literal`'s own alternatives. Deliberately *not* a new `{ptr, len}` value type, and *not* dependent on the "opaque/foreign-pointer type" item below (an earlier assumption, superseded) — reuses cleave's already-built, already-verified array machinery entirely. Multi-argument/heterogeneous `print` (`print("x =", x, "y =", y)`) was raised and deliberately split out — see "Tuples as a language feature" below.

`impl<const N: i32> Print<[i8; N]> { extern(print_bytes) fn print(x: [i8; N]) -> [i8; N]; }` in `stdlib/io/io.cleave` — one generic impl, monomorphized once per distinct string length actually reached, the same discipline every other generic construct here already gets. `cleave-rt` gained `print_bytes(ptr, len)`, writing the raw bytes straight to stdout.

**Three real, previously-unexercised gaps, all found by direct testing, none guessed at in advance:**
- **The extern/array ABI boundary.** `mlir_lower.rs::ensure_extern_declared`/`PrimOp::Extern`'s own call-argument lowering used to pass a `Ty::Array` argument as an ordinary `memref` — but MLIR's default `convert-to-llvm` conversion (the only pass this pipeline runs; melior exposes no bare-pointer-calling-convention option on it) turns a `memref` crossing any `func.call` boundary into a descriptor *struct*, passed by value, not a bare pointer. No hand-written `cleave-rt` extern fn could match that layout — confirmed by a hard `STATUS_ACCESS_VIOLATION` crash before the fix, not a clean panic. Fixed with a new `array_ptr_and_len` (`mlir_lower.rs`): `memref.extract_aligned_pointer_as_index` + `arith.index_cast` + `llvm.inttoptr` (the first two ops have real melior bindings already used elsewhere in this file for array indexing; `llvm.inttoptr` needed a raw `OperationBuilder` build, the same pattern `llvm.ptrtoint` already used) extracts a bare `!llvm.ptr`, paired with the array's own total element count as a compile-time-constant `i64` — both `ensure_extern_declared`'s own declared signature and the real call site now agree on `(!llvm.ptr, i64)` for any `Ty::Array` parameter, scoped generically over element type, not just `i8`. An array-typed *return* (`Print<[i8;N]>::print(x) -> x`, identity) needed its own reconciliation too: the real `print_bytes` symbol returns a plain `i64`, discarded — the cleave-level result reuses whichever argument was already that same array, not a reconstruction attempt (impossible anyway, a `memref` can't be conjured from a scalar).
- **A generic algebra impl whose method is bodyless (`extern`) was unconditionally skipped while building monomorphization templates** (`monomorphize.rs::build_impl_templates`) — a deliberate, previously-correct check ("no body, nothing to substitute a specialization's concrete types into"), but the first-ever *generic and extern-backed* impl in this codebase (`Print<[i8;N]>` — every prior generic impl had a real body; every prior bodyless impl was non-generic) needed a template anyway: the concrete `N` a call site reaches is exactly what `call_names`/the instantiation worklist exist to record, independent of whether there's a cleave-level body to type-check. Fixed by simply not skipping — the existing `unwrap_or(Block::default())` a few lines down already handled an absent body gracefully, for any impl shape.
- **`cps.rs::collect_units`'s own generic-impl branch unconditionally wrapped every specialization as `UnitBody::Real`**, even once a template correctly existed for a bodyless method — silently building a unit with a trivially empty body instead of a real extern call. Fixed to branch on `f.body` the same way the non-generic-impl and top-level-`fn` branches already do (`Some` → `UnitBody::Real`, `None` → `UnitBody::Extern`).

Verified end to end via real JIT execution (`cleave/tests/mlir_lower.rs::a_string_literal_printed_via_print_writes_the_right_bytes_to_stdout`): `print("hi")` genuinely writes `hi` to stdout during a real `ExecutionEngine::invoke_packed` call, not just "compiles and verifies" — plus a dedicated, isolated ABI-proof test (`an_array_argument_crosses_an_extern_call_boundary_correctly`) that exercises the pointer/length extraction alone, with a real numeric assertion, before string support was ever built on top of it.

### A struct field whose own type is another struct — verified, works correctly

The former "Nested struct-as-field, unverified" item — `ty_to_llvm_field_type`'s own fallback (an opaque `!llvm.ptr`, identical reference treatment to every other struct value) needed no changes at all: `Triangle { a: Point, b: Point, c: Point }` constructs, reads (`t.a.x`), and mutates (`t.a.x = ...`) correctly through two levels of field access, each nested field independently addressable (not aliased), verified via real JIT execution (`cleave/tests/mlir_lower.rs::a_struct_field_whose_own_type_is_another_struct_computes_the_right_value`, `..._nested_struct_fields_own_field_mutation_...`). No fix needed — closes that half of the old item cleanly.

The other half — an *array* whose own elements are structs (`[Point; N]`, standalone or as a struct's own field) — used to be a real, confirmed-broken gap; now fixed, see the next entry.

### Array of struct elements (`[Point; N]`, standalone or as a struct's own field)

Used to be a hard native MLIR crash, not a missing feature: `array_memref_type` built `MemRefType::new(ty_to_mlir(ctx, leaf_ty), &dims, None, None)` unconditionally for *every* standalone array, regardless of element type — for a struct-typed leaf, `ty_to_mlir` returns an opaque `!llvm.ptr`, and MLIR's own `memref` machinery rejects that at *type construction* with a hard native assertion (`invalid memref element type`, a `STATUS_STACK_BUFFER_OVERRUN` abort — not a clean panic, not even a clean MLIR verification failure).

**The fix, as anticipated during planning — a struct-leaf array now gets the same dual representation a struct's own array-typed field already had**: `array_leaf_is_struct` (new) checks an array's own flattened *leaf* element, mirroring `ty_to_mlir`'s pre-existing primitive-vs-struct distinction one level down; `ty_to_mlir`'s `Ty::Array` arm picks `memref` (primitive/nested-array leaf, unchanged) or a real heap allocation shaped as an inline `!llvm.array` (struct leaf, new) accordingly. `alloc_struct`/`struct_size_bytes` — both already fully generic over *any* LLVM type, despite their struct-specific names (their own only caller, until now) — were renamed to `alloc_llvm_value`/`llvm_type_size_bytes` and reused verbatim for the array case, no new allocator needed. `lower_array_construct`/`lower_array_repeat` grew a struct-leaf branch: allocate via `alloc_llvm_value`, fill via one `llvm.getelementptr`+`llvm.store` per element, mirroring `lower_struct_construct`'s own per-field GEP+store loop exactly. `copy_memref_into_llvm_field` (renamed `copy_array_into_llvm_field`) generalized its own previously-unconditional `memref.load` to dispatch on `src.r#type().is_mem_ref()` — the exact same runtime dispatch `lower_array_load`/`lower_array_store` already used — adding a GEP+`llvm.load` branch for a struct-leaf source, needed when a struct's own array-typed field is filled from an already-built standalone struct-leaf array.

Scoped deliberately to a single-dimension struct-leaf array only (`[Point; N]`) — a struct-leaf array nested inside another array (`[[Point; 2]; 3]`) panics clearly rather than being silently mishandled, real but rarer, not attempted.

A significant de-risking finding from planning, confirmed correct during implementation: the *consuming* side of a pointer-backed array (GEP+load/store) already existed and worked, since a struct's own array-typed field, once accessed via `lower_field_access`, already handed back exactly this shape — so this fix was genuinely "also *produce* the already-consumed representation from a fresh standalone construction," not "invent a new representation." No real, previously-unanticipated bugs surfaced during implementation (unlike the string-support or equality-saturation entries above) — the plan's own predicted shape matched what actually compiled and ran on the first pass through each stage.

Verified end to end via real JIT execution, the two tests written *before* the fix (confirmed crashing, `#[ignore]`d until now) un-ignored and passing: `cleave/tests/mlir_lower.rs::an_array_of_structs_computes_the_right_value` (standalone, `[Point; 3]`), `..._a_struct_field_whose_own_type_is_an_array_of_structs_computes_the_right_value` (`struct Path { pts: [Point; 2] }`, exercising the struct-leaf-source generalization above). Full `cargo test --workspace` green, 0 ignored; every `examples/*.cleave` file's own `--run` output re-checked, no regressions.

### A `()`-returning function called from another function, not just the program's own entry point

Found via `examples/vector.cleave`'s own `print_vec` helper (a small `()`-returning function called from `main` — an entirely ordinary pattern, not a contrived one): `lower_top_level_fn`'s own unit-return handling (see "Real MLIR lowering" above) already declared a `()`-returning callee with *zero* MLIR results, uniformly, for every top-level fn — never actually scoped to `main` alone, despite the old wording of this item. The real gap was one level up: `lower_real_call`'s own call site unconditionally requested exactly one result (`&[result_mlir_ty]`) regardless of the callee's own return type, mismatching a unit-returning callee's zero-result declaration. Not a clean panic as this item used to predict — a real MLIR verifier failure instead, `'func.call' op incorrect number of results for callee` (`ty_to_mlir` has no special case for `()` at all, so `Ty::Con("()")` silently fell through to the generic-struct arm and became `!llvm.ptr`, requesting a phantom result).

`emit_call` (`cps.rs`) always synthesizes a `result_var` for a real call regardless of the callee's own return type — unlike `PrimOp::Store`'s dedicated "bound result is unit, never read" convention, a real call has no per-callee special case at the CPS level. Handled at the MLIR-lowering boundary instead: `lower_real_call` now branches on `is_unit_ty(result_ty)`, building zero call results and never binding `result_var` into `env` when unit — nothing downstream can look it up anyway (nothing in the language can do anything with a unit value besides discard it).

Verified via a new regression test, `cleave/tests/mlir_lower.rs::a_unit_returning_function_can_be_called_from_another_function` (confirmed failing verification before the fix, passing after), plus the full workspace suite and example sweep staying green throughout.

A narrower related gap, not attempted here — see the open item below: a `()`-returning function declared `extern`.

### Duck-typed fallback for an unannotated generic parameter's own field access

Found via `examples/vector.cleave`'s own `print_vec(v) { print(v.x); ... }`: an unannotated top-level generic parameter can never have its fields resolved by cleave's ordinary Hindley-Milner inference, because field access is *nominal* (needs a concretely-named struct) and HM checks a generic fn's body exactly once, symbolically, with `v`'s type as a fully unconstrained `Ty::Var`. `FieldAccess` on an unconstrained `Ty::Var` defers to a `Ty::Con("<not-yet-inferred>")` sentinel (`infer.rs`'s own `is_placeholder`) rather than erroring — and since this sentinel is a `Ty::Con`, not a `Ty::Var`, `monomorphize.rs`'s existing "substitute concrete types into the one already-computed generic `node_types` map" mechanism (its own module doc comment, "No AST cloning needed") can never repair it at any later call site. The result used to be a confusing, wrongly-attributed error deep inside `Print::print`'s own specialization attempt, rather than any diagnostic pointing at `print_vec` itself.

**Precisely not "how HM is supposed to work" — corrected explicitly during design discussion, worth keeping on record**: HM's own defining feature is the opposite (principal types: checked once, sound for every instantiation, no re-verification ever needed). What actually got built is a second, distinct mechanism — C++-templates-style, duck-typed, checked separately per concrete call site — that *coexists* with HM rather than replacing it, and deliberately triggers **only** as a fallback: `monomorphize.rs::detect_duck_typed_fns` scans every generic top-level fn's own already-computed `node_types` for placeholder residue anywhere in the body (not just the exposed signature); a fn found there gets routed through a real, separate re-inference per concrete call site (`Infer::infer_fn_with_concrete_params`, a sibling of the existing `infer_fn`, differing only in sourcing `param_types` from the call site's own already-concrete argument types instead of `fresh_fn_shape`'s fresh `Ty::Var`s) instead of the ordinary substitution path. Every other generic function — the overwhelming majority — keeps today's exact behavior, performance, and declaration-time error timing, completely unchanged; `callgraph.rs`'s own single HM pass is untouched.

Also corrected during the same discussion: generic **algebra-impl methods** don't already have some per-call-site verification mechanism `print_vec` was missing out on — `build_impl_templates` also only ever type-checks an impl body once, generically. They simply never hit this bug because an algebra method's signature is always fully, explicitly declared by the `algebra` itself — never an inferred/unannotated parameter. Scoped to top-level `fn`s only; extending the identical mechanism to generic impls/inherent methods is a natural, structurally near-identical follow-up, not attempted here.

On a genuine failure (the concrete call site's own argument type really doesn't have the accessed field), the real inner `TypeError` from the fresh re-inference is surfaced directly via a new `TypeErrorKind::GenericFnInstantiationFailed { name, tys, inner }` — strictly more precise than the pre-existing `MonomorphizationFailed` (a blind "no impl candidate unified", no inner detail available, the only thing available to the *substitution* path), since a real inference pass genuinely ran and has a real span pointing at the actual offending expression.

**A real, precise scope boundary, found by direct testing, worth recording so it isn't mistaken for a bug later**: this only fixes a placeholder that stays *buried* somewhere that doesn't block the function's own exposed signature from being clean (print_vec's real shape: the field access feeds a `void`/statement-position call, never the function's own return value). Field access used *directly* as a generic fn's own return value (`fn get_x(v) { v.x }`, called as `get_x(pt)` where the result feeds something expecting a concrete type) still fails earlier, at ordinary declaration-time unification — `get_x`'s own exposed result type is the placeholder itself, and unifying that against a caller's own concrete expectation (e.g. an enclosing `-> i32`) is a real, separate mismatch this fallback never gets a chance to intercept, confirmed via direct testing (`type mismatch: expected \`i32\`, found \`<not-yet-inferred>\``). Fixing that shape too would mean deferring return-type unification itself for a placeholder-tainted callee — a materially bigger, more invasive change than the deliberately narrow, low-blast-radius fallback built here.

Verified via two new tests in `cleave/tests/monomorphize.rs` (`an_unannotated_generic_params_own_field_access_resolves_via_the_duck_typed_fallback`, `a_duck_typed_fallback_specialization_that_genuinely_fails_reports_the_real_inner_error`), the full workspace test suite staying green, and `examples/vector.cleave` itself now running end to end via `--run` (prints `2`, `4`, `6` — `vr`'s own `x`/`y`/`z` fields, correctly resolved).

### A bare-literal `let` binding could silently leave an unresolved type variable, panicking deep in CPS

A real, serious soundness gap, found via `examples/test_loup.cleave` (`let a = 16; let b = 4; let c = a + b; print(c);`) — worse than an ordinary type error: inference reported **no error at all**, and the program crashed with a raw Rust panic much later, in CPS conversion (`CPS: could not resolve call to \`add\` (("add", ["'t4", "'t4"], "'t4"))`), not a clean diagnostic.

Root cause, confirmed precisely by direct testing (isolating `let mut` — never generalized — as a working control case): `let a = 16;` is a *syntactic value* (`is_syntactic_value`), so it got real HM let-generalization, exactly like `let f = fn(x) { x };` legitimately does. But a bare number literal's own defaulting eligibility (`pending_defaults`, consulted by `apply_defaults`) is registered **once**, at the literal itself, tied to *that one* type variable — generalizing the `let` means every later reference to `a` (inside `a + b`) instantiates its own **fresh, independent** variable (`instantiate`), which was never registered in `pending_defaults` in the first place (nothing re-runs literal inference at a use site). Meanwhile the *original* binding-site variable gets correctly skipped by `apply_defaults`, precisely because it's quantified (`Infer::quantified`'s own guard, there to protect a genuinely generic scheme from being wrongly defaulted). Neither variable ever gets defaulted. If nothing *else* later happens to pin that fresh use-site variable to something concrete (an explicit return-type annotation coincidentally masked this in some shapes — `fn main() -> i32 { ...; c }` — via ordinary return-type unification, not defaulting at all), the variable survives, untouched, all the way past type-checking succeeding, into CPS conversion, which assumes everything is already concrete by then.

Confirmed this has nothing to do with `print` specifically (an earlier hypothesis, ruled out by testing): an entirely unused `let c = a + b;`, with no `print`/no `io` involved at all, panics identically — the real condition is just "nothing else happens to concretely unify this particular fresh instantiation."

**Fixed at the root, not patched around**: `is_syntactic_value` no longer includes `NumberLit`/`ImaginaryLit` — a bare-literal `let` binding now binds monomorphically (`Scheme::mono`), exactly like `let mut` already did, so every later reference shares the *same* variable `pending_defaults` already tracks correctly. `BoolLit`/`Path`/`Lambda` are unaffected and keep real let-generalization (`BoolLit`'s own type is already fully concrete, nothing to generalize; `Path`/`Lambda` generalization doesn't depend on `pending_defaults` at all). Deliberately narrower than it sounds: a *function* whose body merely contains a bare literal (`fn add_one(x) { x + 1 }`) still generalizes correctly, `Num` constraint riding along — that's the function's own whole-signature scheme (`callgraph.rs`), an entirely different generalization site from a `let`-bound *value* directly aliasing a literal's own variable.

Verified via a new test, `cleave/tests/infer.rs::a_let_bound_literals_own_use_site_still_defaults_correctly` (confirmed panicking-equivalent — a real `Ty::Var` left in `node_types` — before the fix, clean after), plus `cleave/tests/dump.rs`'s own pre-existing `dumps_let_and_tail_statements_with_their_own_types` updated to reflect the corrected rendering (`let x = 1:i32` at both the binding and its use, no longer two different variables shown as `'a` then `i32`) and a new `a_let_bound_lambda_still_shows_a_still_open_type_variable_at_its_own_definition` added alongside it to keep covering the still-legitimate lambda-generalization case the old test's own example no longer exercised. Full `cargo test --workspace` green, every `examples/*.cleave` file's own `--run` output re-checked, no regressions.

### Two real hygiene gaps in the compiled output, both found by direct inspection of `examples/axiom_demo.cleave`

**1. Dead-code elimination ran only once, *before* equality saturation, missing anything the axioms themselves made unreachable.** `helper(x: i32) -> i32 { let y = 10; 10 + x - y }` fully reduces to `x` via `add_commutative`/`add_sub_assoc`/constant-fold/`add_zero` — but `main.rs`'s own pipeline ran `eliminate_dead_code` only once, *before* `egraph::optimize_program`, so it had no way to know `Ring::add<i32>`/`Ring::sub<i32>` were about to lose their only real callers. Confirmed directly: both survived in `--dump-cps-optimized`'s own output despite `helper`'s optimized body no longer calling either. Fixed by running `eliminate_dead_code` a second time, after `optimize_program`, in every pipeline block that calls it (`--dump-cps-optimized`, `--dump-mlir`, `--dump-mlir-lowered`, `--run` — `--dump-cps-equivalences` doesn't need it, since it never uses the optimized program's own body, only the explanations `optimize_program` already produced before any second sweep could run). `eliminate_dead_code` itself needed no changes at all — already a pure, cheap, idempotent worklist pass, safe to run twice.

**2. Every top-level fn got MLIR's `llvm.emit_c_interface` attribute (and its own extra `_mlir_ciface_<name>` wrapper function), not just `main`.** `lower_top_level_fn` attached it unconditionally to every function it lowered. The *only* function this project ever invokes via `ExecutionEngine::invoke_packed` is `main` — confirmed directly, every call site (`main.rs`'s own `--run`, every test) hardcodes the literal string `"main"` — and an ordinary internal call already goes through a plain `llvm.call @name`, which never needs the C-interface wrapper at all. This used to double the function count in every compiled module for zero functional benefit. Fixed by scoping the attribute to `f.def.name == "main"` alone. `doc/hld.md`'s own "Interop and deployment model" section already sketches the real, not-yet-implemented mechanism for exposing an *arbitrary* cleave function to an external host (`extern fn` on a cleave-side definition, not a separate `export` keyword) — this fix doesn't build that, it just stops the *unconditional* export nobody asked for; the real opt-in mechanism is a natural follow-up once/if a host program actually needs to call into compiled cleave code directly.

Verified via two new tests — `cleave/tests/cps.rs::dead_code_elimination_after_optimization_drops_specializations_the_axioms_folded_away` and `cleave/tests/mlir_lower.rs::only_main_gets_the_c_interface_export_attribute` — plus the full workspace test suite and example sweep staying green throughout.

### A `()`-returning `extern fn`

`PrimOp::Extern`'s own lowering (`mlir_lower.rs`) used to declare/call unconditionally with `ty_to_mlir(ctx, ty)` — no real case for `()` at all (falls through to the generic-struct fallback, `!llvm.ptr`), so `extern fn touch(x: i32);` (no `->` clause) declared and called against a bogus one-pointer-result signature that the real C symbol underneath doesn't actually have. Confirmed by direct testing this is a real, structural ABI mismatch (the dumped MLIR showed `func.func private @touch_i32(i32) -> !llvm.ptr` against a genuinely `void`-returning Rust fn) — just not one that happened to crash on its own in the simplest case, since nothing downstream ever read the bogus result value.

Fixed the same way `lower_real_call`/`lower_top_level_fn` already handle a unit-returning top-level fn (see above): `ensure_extern_declared` now takes `results: &[Type<'c>]` (a slice, not a single `Type`) so it can declare zero results; `PrimOp::Extern`'s own lowering arm branches on `is_unit_ty(ty)` alongside its existing array-return branch, requesting zero call results and never binding the `LetPrim`'s own `var` into `env` when unit — matching `PrimOp::Store`'s "bound result is unit, never read" convention. `cleave-rt` gained `touch_i32(x: i32)` (genuinely `void`-returning, `#[extern "C"]`), a real ABI-proof fixture — every other `extern fn` in the stdlib returns a real value, so this shape had never been exercised at all before.

Verified via a new test, `cleave/tests/mlir_lower.rs::a_unit_returning_extern_fn_can_be_called_correctly` — both a structural assertion on the dumped MLIR (zero results, not a bogus `!llvm.ptr`) and a real JIT-executed call — plus the full workspace test suite and example sweep staying green.

### Mutability checking

`x = v` (or `arr[i] = v`/`s.x = v`) against a plain, non-`mut` `let` binding used to be silently accepted — `mutable` was only ever consulted by `is_syntactic_value`'s own call site to decide whether to generalize, never checked again at an actual assignment.

A purely syntactic fix, deliberately kept separate from `Infer`'s own type-checking machinery entirely — no `Ty`/`Scheme`/`Env` involvement, since mutability doesn't depend on types at all: a new `infer::check_mutability(f: &FnDecl) -> Result<(), TypeError>`, a shadowing-aware static AST walk (mirroring `cps.rs`'s own `mutated_free_vars`/`mutated_free_vars_expr` pair in shape — same recursive `Block`/`If`/`While`/`For`/`Lambda` coverage — but tracking `name -> is_mut` instead of "which outer names get reassigned," and checking every `Assign`, not just the ones needing loop-carrying). An indexed/field assignment target (`arr[i] = v`, `s.x = v`, arbitrarily nested — `s.arr[i].y = v`) resolves to its own *root* binding via a new `assign_target_root` before checking — mutating through a stable reference is still mutating the reference's own binding, matching `cps.rs`'s own "array/struct is a stable reference" design. A function parameter is always immutable (`grammar.pest`'s own `param` rule has no `mut` at all — no way to opt in), seeded as such since it never goes through `StmtKind::Let`. A lambda's own body is recursed into too (unlike `mutated_free_vars_expr`'s own explicit exclusion there, for an unrelated reason specific to CPS's pre-closure-conversion loop-carrying question) — reassigning a captured outer non-`mut` variable from inside a lambda is an ordinary violation, checked the same as anywhere else.

New `TypeErrorKind::AssignToImmutable { name }`. Wired into `main.rs::check_type_errors` (a new `check_mutability_errors`, run once per `fn` body anywhere in the program — top-level `fn`s and every method of every algebra/inherent `impl` — since none of those go through `callgraph::infer_program`'s own whole-program walk uniformly enough to hang this off of instead), alongside the existing `dump_monomorphized`-based type-error check.

Verified via twelve new tests in `cleave/tests/infer.rs` covering: plain reassignment (rejected) vs. `let mut` (accepted), field/index assignment through both (same result), a deeply-nested chain still resolving to its own root, a function parameter, a `for` loop's own index variable, shadowing correctness in both directions (an inner non-`mut` shadow of an outer `mut` binding is still rejected; the outer `mut` binding itself, reassigned through a nested `if` block with no shadowing, is accepted), and a captured variable reassigned from inside a lambda (checked against the *outer* binding's own mutability, correctly, in both directions). Full workspace test suite and example sweep stayed green throughout — no existing test or example relied on assigning to a non-`mut` binding, confirming this was a real, previously-silent gap, not a false-positive risk.

### The `Ty::Const`/`Ty::Con` architectural tension — unified, and a real bug found along the way

A const generic's own value (`const N: T`) flows through *one* shared `Ty::Var`, used both as an ordinary value (`for i in 0..N`) and as a shape slot (`[T; N]`, needing eventual `Ty::Const` resolution) — `Ty::Const`/`Ty::Con` are different `Ty` variants that can't unify with each other directly, so `const_widths: HashMap<TyVar, Ty>` existed as a side-table recording each const generic's own declared width (e.g. `i64`), consulted separately by three independent call sites (`apply_defaults`'s guard, `check_pending_constraints`'s bridge, CPS's own `for`-loop-bound fallback) whenever a variable needed to be recognized as "secretly a const generic in disguise."

**A real, previously-unknown bug was found while investigating, not just the already-flagged fragility.** `const_widths` was keyed by a const generic's own *original* `TyVar`, resolved to its *current* union-find root before every lookup — but `unify`'s own bind direction (`(Ty::Var(v), _) => subst.bind(*v, b)`, checked before the symmetric arm) always binds the *left* operand's var to point at the right one, and `ExprKind::For`'s own `unify_at(end.span, &start_ty, &end_ty)` always unifies `start` before `end`. `for i in 0..N` (`N` as `end`) happens to bind `0`'s own var *to* `N`'s, leaving `N`'s var as the reachable root — correct, but by construction accident, which is exactly why this went unnoticed (every existing example/test uses this direction). `for i in N..5` (`N` as *start*) binds the opposite way: `N`'s own var stops being reachable as a root at all, `const_widths.contains_key` silently misses it, and `apply_defaults` wrongly, permanently defaults the merged variable to a bare `Ty::Con`. Confirmed directly (not just derived): `--dump-inference-pass` on `fn f<const N: i64>() -> i64 { let arr = [0:i64; N]; ...; for i in N..5 { ... }; ... }` showed `arr`'s own declared array type corrupted to the nonsensical `[i64; i32]` — a bare type name sitting in an array's own *size* position, silently losing `N`'s real declared width (`i64`) in favor of `5`'s own generic `i32` default. `generalize`'s own const-width extraction had the identical exposure.

**A simpler-looking fix was considered and ruled out by direct testing first**: binding a const generic's own `env` entry to its declared width type directly (instead of the shared shape-slot var) would break `[0.0; N]` (`ExprKind::ArrayRepeat`) — its own `count_ty = infer_expr(env, count)` becomes the array's own size slot *directly*, so `env["N"]` genuinely must be able to resolve to `Ty::Const`, not just report its own width. The two roles can't be cleanly separated at the `env`-binding level.

**The actual fix**: moved `const_widths` from `Infer` into `Subst` itself, and made `Subst::bind` propagate a const generic's own declared width *forward* on every var-to-var merge — so whichever variable a chain eventually resolves through always carries its own entry, regardless of which direction any given `unify` call happened to bind, or how many merges deep. `Ty`'s own enum stays completely untouched (`Ty::Const`, the *resolved*-value variant, is used correctly and widely elsewhere — `cps.rs`, `dump.rs`, `egraph.rs`, `mlir_lower.rs` — none of it needed to change); the fix is entirely confined to `Subst`'s own internals (`bindings`/`const_widths` as two fields instead of a bare tuple struct, a new `const_width`/`set_const_width` pair of accessors) plus five call sites inside `Infer` switching from its own now-removed `const_widths` field to `self.subst`'s. No other logic changes were needed at `apply_defaults`/`check_pending_constraints`/`generalize` — once `bind` propagates the taint forward, their own existing "resolve then check" / "look up the original var directly" patterns were already correct, just previously reading from a side-table that could silently go stale. CPS's own `for`-loop-bound fallback (`Ty::Const(_) => Ty::Con("i32")`) stays exactly as-is — a genuinely different, later-pipeline-stage situation (`ConstValue` itself carries no width tag to recover once monomorphization has already resolved a const generic to a concrete value), not fixed by this change and not attempted here.

Verified via two new tests in `cleave/tests/infer.rs` (`a_const_generic_named_as_the_start_of_a_for_loop_range_does_not_corrupt_an_unrelated_arrays_own_size`, confirmed failing before the fix via a general "no bare `Ty::Con` ever sits in an array's own size slot" invariant check across `node_types`; `..._the_end_of_a_for_loop_range_still_works`, the regression control for the direction that already worked), the full workspace test suite, and `examples/matmul.cleave` specifically (the project's own canonical const-generic-heavy example, already cited by the old guard's own doc comment as the original motivating case) producing the identical, already-correct result (`42`) before and after.

### An inherent method's inferred return type reaching an external caller

Self/mutual recursion *within* one impl block was already resolved (`infer_inherent_impl_block`); a *different* function calling an unannotated inherent method used to only ever see the `<not-yet-inferred>` placeholder, unconditionally — `ExprKind::MethodCall`'s own dispatch never re-infers or looks up the callee's own body at all (unlike an algebra call, which always has a real declared signature, or a top-level `fn` call, resolved via `global_env`), so an unannotated method's return type had nowhere to come from at another caller's own call site.

**Why this wasn't just "call `infer_inherent_impl_block` from `callgraph::infer_program`"**: both of `infer_inherent_impl_block`'s existing callers (`dump.rs`, `monomorphize.rs`) already pass `global_env` — the *completed* result of `infer_program` — as its own `outer` parameter, which is what lets an inherent method's body legally call an ordinary top-level `fn` today. But `MethodCall`'s own dispatch runs *inside* `infer_program`'s own per-group loop, so whatever publishes inherent-method return types for it to consult must exist *before* `global_env` is complete — a genuine, symmetric mutual dependency between top-level `fn`s and inherent methods, not just missing plumbing.

**The fix**: a new, separate early pass, `callgraph::infer_inherent_impls_early`, runs every inherent impl block through the *existing* `infer_inherent_impl_block` with a deliberately **empty** `outer` env (top-level `fn`s not yet visible to it), publishing each successfully-inferred method's own return type as an `InherentMethodPattern` (`generics_mapping` + `param_patterns` + `ret_pattern`, the same "pattern parameterized by the impl's own generics" shape `monomorphize.rs`'s own `ImplTemplate`/`InherentTemplate` already use one pipeline stage later) keyed by `(struct_name, method_name)`. `callgraph::infer_program` runs this once, up front, and seeds every per-SCC-group `Infer` with the result via a new builder-style `Infer::with_inherent_patterns` (an `Option<&HashMap<...>>` field, `None` by default — every *other* existing `Infer::new` call site, including every test, keeps working completely unchanged). `MethodCall`'s own dispatch now falls back to this map (remapping the pattern's own free vars, named by generic-parameter name, through the call site's own fresh `impl_mapping`) before falling back to the placeholder.

**Gracefully degrades, doesn't regress, the case deliberately not solved**: an inherent method whose own unannotated return type genuinely depends on a top-level `fn` (calling it from inside an impl block processed with an empty `outer` env) simply has no entry in the early pass's own map — `infer_inherent_impl_block` itself already rejects a method whose own final result still contains a placeholder (`check_no_placeholder`, called internally), so it's silently excluded, and an external caller correctly falls back to the ordinary placeholder path, exactly like any other not-yet-resolvable reference throughout this compiler — the method's own *final*, fully-correct type-check still happens unaffected, via the two existing, unchanged call sites that already run after `global_env` is complete.

`infer_inherent_impl_block`'s own return type changed additively (now `(HashMap<String, Ty>, HashMap<String, Result<(Vec<Ty>, Ty), TypeError>>)`, exposing its own previously-discarded `impl_mapping`) — its three existing call sites (`dump.rs`, `monomorphize.rs`, `cps.rs`) and two direct test call sites (`cleave/tests/infer.rs`) all needed a one-line destructuring update, no logic changes.

Verified via three new tests in `cleave/tests/callgraph.rs`: the acceptance case (a non-generic inherent method, unannotated, called from a separate `fn`), a generic inherent impl (proving the `generics_mapping` remap works, not just the trivial non-generic case), and the graceful-degradation control (an inherent method depending on a top-level `fn` — confirmed to *already* correctly defer to a placeholder-shaped error today, and to still do so identically after the fix, not crash or silently produce a wrong type). Full workspace test suite and example sweep stayed green throughout.

### Self-recursive `let`-bound lambda

`let fact = fn(n) { ... fact(n - 1) ... };` — a self-recursive `let`-bound lambda didn't resolve at all, panicking. Two genuinely separate gaps stacked up, one at the type-inference layer, one at CPS/closure-conversion, found and fixed in that order.

**Layer 1 — type inference (`infer.rs`).** `StmtKind::Let`'s handling only inserted `name` into `env` *after* `infer_expr`'d the value — so a lambda's own body couldn't see its own binding name to type-check a self-call against, falling through to `<unresolved-call:fact>`. Fixed the same way `infer_fn_raw` already seeds a top-level `fn`'s own self-reference: a monomorphic placeholder (`Ty::Fn(fresh param vars, fresh ret var)`, classical ML `let rec` restriction — never generalized even when `name`'s own outer binding may be) seeded into a cloned `env` before inferring the lambda's value, then tied back to the real inferred type via `unify_at` afterward (needed for the case where the recursive call's own result is discarded, e.g. `let g = fn(n) { g(n - 1); n };` — otherwise nothing else would ever connect the placeholder's own return var to the body's real result).

**Layer 2 — CPS/closure-conversion, found immediately after, via the same end-to-end CLI repro that always gets run as a final check.** Fixing layer 1 alone just moved the failure: `CPS: could not resolve call to \`fact\`` — because a `let`-bound lambda's own body is converted as a *separate, anonymous* CPS unit, keyed by `NodeId` + concrete instantiation, never by its source-level name. Three independent pieces, all in `monomorphize.rs`/`cps.rs` (no `infer.rs`/`ast.rs`/`callgraph.rs` changes needed):

1. `collect_instantiations_block`'s own `StmtKind::Let` arm inserted `name -> value.id` into its shadowing-aware `scope` only *after* walking the lambda's own body — so a self-call inside that body could never resolve via `scope.get(name)` during that walk. Fixed by moving just the *insert* branch earlier (the *removal* branch, for a non-lambda rebinding, stays after the walk — `let f = f(1);` must still mean "call the outer `f`").
2. Even once discovered, the `lambda_worklist` drain loop — which rebuilds *this specific specialization's own* `call_names` map, the one `cps.rs` actually reads back per-unit — re-walked the lambda's body from a totally empty `scope`, with no way to know its own source name. Fixed by widening `lambda_worklist`'s element type to carry that name along (`(NodeId, Vec<Ty>, String)` — trivially available at both push sites, since each `Lambda` AST node is let-bound exactly once, making that name canonical everywhere `scope` resolves it), and giving `collect_instantiations` a new `initial_scope` parameter the drain loop seeds with `{self_name: lambda_id}` (every other caller passes an empty map, unchanged behavior). The self-call's own re-push onto `lambda_worklist` terminates harmlessly — by the time it's popped, `mono.specializations` already contains its `display` key, same termination shape the existing `fn_worklist`/`impl_worklist` loops already rely on for their own self-recursion.
3. Even once `resolve_call` succeeds, a *captured* self-recursive lambda (one closing over an outer variable) needs those captures re-supplied on the self-call — the callee unit's own leading params are exactly its `capture_count` captured values. The ordinary path for this (`cps.rs`'s `env.get(&name) == Some(CVal::Closure{captures})` fast path) never fires for a self-call, since that binding only ever exists in the *enclosing* scope's own environment, never inside the lambda's own separately-converted unit body (which starts a fresh `env` from just its own params). Fixed in the plain-fallback `Call` arm: when the resolved callee unit has `capture_count > 0`, gather those values from the *current* `env` by name (guaranteed present, since a genuine self-call runs inside a unit whose own leading params are exactly those names) and prepend them before the ordinary arguments.

**A fourth bug, found by direct testing right after the third fix landed, specific to an *unannotated* self-recursive lambda:** an unannotated `fact` is generalized (`is_syntactic_value`) with a genuinely open type variable in its own scheme — so while walking a still-generic copy of its body (during the initial, whole-function "seed scan," reached via the fix to gap 1 above), the self-call's own `node_types` are themselves still type variables. `derive_instantiation` "succeeds" against them anyway (unifying a bare `Ty::Var` against anything always does), producing a bogus, never-reachable degenerate specialization whose own inner calls (`n <= 1`, concretely) then fail to resolve against any real algebra impl. Fixed by requiring a `derive_instantiation`/`derive_value_instantiation` result to be fully concrete (`is_fully_concrete`, checking `infer::free_vars` comes back empty) before ever recording it into `call_names`/`lambda_worklist` — the *real* concrete instantiation is still found separately, from the outer, already-concrete `fact(5)` call site.

Verified via three new end-to-end tests in `cleave/tests/mlir_lower.rs` (real JIT execution via `run_i32`, not just verification): an annotated non-capturing self-recursive lambda (`5! = 120`), the same lambda unannotated (proving the generalized-scheme guard), and a capturing self-recursive lambda (proving the capture-splice fix — confirmed to genuinely exercise it by temporarily reverting the splice and observing an MLIR verification failure, "incorrect number of operands for callee", then restoring it). Full `cargo test --workspace` and `examples/*.cleave --run` sweep stayed green throughout; the original CLI repro re-run directly as the final sanity check.

### Calling a lambda literal directly

`(fn(a, b) { a + b })(1, 2)` — confirmed by direct reading to be a pure grammar/parse-time gap, not a semantic one: `grammar.pest`'s `call_expr` only ever accepted a bare `path` as a call's callee, and `postfix_op` had no "just call whatever's on the left" alternative — a parenthesized lambda literal followed by `(1, 2)` had no grammar production to consume the trailing call args at all.

Everything *downstream* of parsing already fully supported this, confirmed by direct reading: it's structurally identical to a `let`-bound lambda called exactly once — `infer.rs`'s `lambda_schemes` population, `monomorphize.rs`'s lambda-instantiation worklist, and `cps.rs`'s closure conversion all key off the same `StmtKind::Let` shape, hand-written or not. So the fix is pure syntactic sugar at the parser layer: a new `postfix_op` alternative, the bare `call_args` rule (reusing it unchanged — no ambiguity, each of the three `postfix_op` alternatives starts on a distinct token), desugared in `lower.rs`'s `lower_postfix_op` to `{ let <synthetic> = <base>; <synthetic>(<args>) }` (`<iife#N>`, named off the base expression's own globally-unique `NodeId` — collision-free, and `<`/`#`/`>` can never appear in a real `ident`). Deliberately left fully general at the grammar/desugaring level (not restricted to a literal `Lambda` base) rather than adding a new diagnostic path that doesn't exist at this layer — `lower.rs` never fails or reports a semantic diagnostic of its own (see the module's own doc comment, "checked later, not here"); a non-lambda base (a redundant `(some_path)(args)`, say) simply falls through to the *already-existing* "unresolved call" placeholder, since `lambda_schemes` is only ever populated for a `let` whose value is syntactically `ExprKind::Lambda`.

**A real, separate gap found immediately by direct testing once the grammar/desugaring change landed:** `cps.rs`'s `convert_expr` never had a match arm for a standalone `ExprKind::Block` expression at all — only `if`/`while`/`for`/lambda bodies ever reached `convert_block`, each off its own dedicated `Block` field; a `Block` used as an ordinary sub-expression (parseable via `primary`'s own `block` alternative since day one, and exactly the shape this new IIFE desugaring produces) fell straight through to the catch-all `panic!("CPS doesn't support ... yet")`. Fixed with one new arm, `ExprKind::Block(b) => convert_block(b, env, ctx, k)` — `convert_block`'s existing signature already matched `convert_expr`'s exactly, and it already threads its own cloned `env` through the block's statements before handing the tail's value to `k`, the same scoping every other caller of it already relies on.

Verified via three new tests: two end-to-end JIT-execution tests in `cleave/tests/mlir_lower.rs` (the acceptance case, and a direct lambda-literal call composed inside a larger expression — `1 + (fn(x) { x * 2 })(5)` — proving the desugared `Block` works as an ordinary sub-expression, not just alone in tail position) and one parser-level AST-shape test in `cleave/tests/parser.rs`. Full `cargo test --workspace` and `examples/*.cleave --run` sweep stayed green throughout.

### Const-generic algebra parameters

`algebra Sum<T, const N: i32> { fn total(x: [T; N]) -> T; }` — `N` used to be silently dropped whenever the algebra's own declared signature got instantiated, in **three separate places**, all sharing the identical root shape: a hand-rolled `HashMap<String, Ty>` mapping built by hand-matching `GenericParam::Type`/`GenericParam::Const`, with the `Const` arm always producing nothing (`=> None`, or an unconditional `d.generics.is_empty()` gate ignoring the algebra's own generics entirely).

1. **`infer.rs::infer_algebra_call`** — the call-site resolver (`add(a, b)`-style dispatch). Its own generics `mapping` (used to instantiate `param_tys`/`ret_ty` via `ty_from_ast_mapped`) only ever produced an entry for `GenericParam::Type`; `ty_from_ast_mapped`'s own `TypeKind::Array` arm, unable to resolve `N` in `mapping`, fell back to a bare placeholder `Ty::Con("<array-type-not-yet-inferred>")` for the *whole* array type (not just a disconnected size — the element type got discarded too), immediately failing to unify against the call's real, concrete argument. Fixed: replaced the hand-rolled `filter_map` with the existing `fresh_vars_for_generics` (already used identically by `has_matching_impl`'s own speculative probe), which already maps *both* kinds to a fresh var uniformly.
2. **`infer.rs::infer_impl_fn_generic_with_env`** — the impl-body conformance checker (checks an impl method's own body against what the algebra declares for it). Same shape, same bug, its own doc comment even documented the gap directly ("const-generic algebra parameters aren't attempted"). Fixed the same way: the `Const` arm now produces `(name, self.vars.fresh())` instead of `None` — `N` stays a free parameter of the method, pinned later per concrete call site, exactly like an unannotated top-level `fn` parameter.
3. **A third, deeper gap found only by running the fixed signature end-to-end** (`monomorphize.rs`/`cps.rs`): an impl declaring *zero generics of its own* (`impl Sum<i32> { fn total(x) -> i32 { ... } }` — no `<T>` on the `impl` itself) was treated as **fully concrete** by three independent call sites (`monomorphize.rs::build_impl_templates`'s own `is_generic` field, `monomorphize.rs::dump_monomorphized`'s own impl-rendering branch, and `cps.rs::collect_units`'s own impl-unit-building branch) — all gating purely on `d.generics.is_empty()` (the *impl's* own declared generics), never considering that the *algebra* it implements might itself carry a const generic. A "concrete" impl re-infers its own body in total isolation, with no call site to pin `N` down at all — `N` stayed a permanently unresolved type variable, later panicking in `mlir_lower.rs` ("array size must be a resolved constant, got `'t0`") even though `monomorphize.rs`'s own `impl_worklist` had *already* built the correct, fully-substituted specialization — simply never reached, since the "treat as concrete" branch matched first and never consulted it. Fixed at all three sites the same way: `d.generics.is_empty() && !registry.generics(&d.algebra).iter().any(|g| matches!(g, GenericParam::Const { .. }))` — provably correct without needing to run inference speculatively first, since (once an impl's own generics are empty) the *only* possible source of a leftover free variable is exactly this.

Verified via an `infer.rs`-level test (an algebra signature tying a const generic between its param and return type, checked against a deliberately *unannotated* caller so no outer annotation could mask the bug via a different path) and a real end-to-end JIT-execution test in `cleave/tests/mlir_lower.rs` (the exact `Sum<T, const N>` shape above, actually run — this is precisely what surfaced bug 3, never caught by the type-inference-only test alone). Full `cargo test --workspace` and `examples/*.cleave --run` sweep stayed green throughout.

### Explicit turbofish on a const generic, for a plain top-level `fn`

`fn rep<const N: i32>(x: i32) -> i32 { N } fn f() -> i32 { rep::<3>(5) }` rejected the call with `` `rep::<...>` expects 0 argument(s), found 1 ``. **Not a turbofish-arity bug at all**, confirmed by direct testing: `N`, referenced as an ordinary body *value* (`{ N }` — not a type-position use like `[T; N]`, which already worked), shared its own single fresh `Ty::Var` between two different questions — "N's own declared type" (`i32`) and "N's own generic identity" (needed for quantification/monomorphization). Checking `N`'s value against `rep`'s own declared `-> i32` return type *bound* that var directly to `Ty::Con("i32")` via ordinary unification, permanently destroying its identity before `rep`'s own scheme was ever built — `generalize`'s free-var scan of the exposed `Ty::Fn(params, ret)` shape found nothing to quantify (`N` never appeared there structurally, only inside the body), so `rep` was reported with zero declared generics. Confirmed not turbofish-specific either: the identical root cause broke a const generic read as a body value with *no* turbofish at all (`impl<T, const N: i32> struct Box<T, N> { fn size(b) -> i32 { N } }`, called as `b.size()`, its own `N` pinned purely by a constructed array's own size) — just with a different symptom (`CPS: could not resolve method call`, or, depending on the exact shape, `CPS: unbound variable N` once the unresolved-but-generalizable-looking function's own unspecialized body got converted directly).

Three small, surgical fixes in `infer.rs`/`mlir_lower.rs` — no `Scheme`/`monomorphize.rs`/`cps.rs` redesign needed (an earlier round of analysis concluded a `Scheme`-level "phantom generics" side-channel plus a new explicit-turbofish-reading extension to `monomorphize.rs`'s own reverse-unification algorithm *would* be required; direct prototyping disproved that):

1. **`infer.rs::Subst::bind`** — a const generic's own value-var (identified via the existing `const_widths` side-table — any var with an entry there *is* a const generic's own value-slot, by construction) is never bound against an ordinary `Ty::Con` anymore; the check still succeeds, but the var itself stays free, preserving its own identity. This is what lets `N`'s own var survive `rep`'s own return-type check and — via the existing, unmodified self-reference tie-back `infer_fn_raw` already performs (`unify_at(ret_var, result)`) — naturally end up as part of `rep`'s own exposed return-type shape, where `generalize`'s existing, unmodified free-var scan now finds and quantifies it "for free."
2. **`infer.rs::unify`** — a new compatibility rule reconciling an already-resolved `Ty::Const` against an ordinary `Ty::Con` (`Ty::Const(Int(_))` accepted against any of `i8`/`i16`/`i32`/`i64`, `Ty::Const(Bool(_))` against `bool` — loose, not exact-width-checked, matching this codebase's own already-documented limitation elsewhere). Needed because once turbofish *does* pin `N` to `Ty::Const(Int(3))` (via the existing, unmodified `instantiate_with_mapping` + turbofish-unify machinery in `infer_call` — no changes needed there either, once `N` is a real, quantified scheme variable), that value still has to compare successfully wherever it flows into an ordinary `i32`-typed context; `unify` had no rule for this pairing at all before now.
3. **`mlir_lower.rs::ty_to_mlir`** — a new arm widening a bare `Ty::Const` to its own natural primitive MLIR type. Needed because, once (1) and (2) let `N`'s concrete value survive all the way to being *the* type of some expression (e.g. `rep::<3>(5)`'s own call-site result), `mlir_lower.rs` needs to know how to lower that type; `cps.rs` already had the *value*-side equivalent of this (`Ty::Const(Int(n)) => CVal::Int(n)`, in its own `ExprKind::Path` handling) — this is the missing type-side counterpart.

Verified via three new tests: an `infer.rs`-level (well, `callgraph.rs`-hosted, whole-program-pass) test confirming `f`'s own resolved type is exactly `Ty::Const(ConstValue::Int(3))` — not a bare `Ty::Con("i32")`, since once `N` is correctly pinned to `3`, that genuinely *is* `rep::<3>(5)`'s own call-site type — and two real end-to-end JIT-execution tests in `cleave/tests/mlir_lower.rs`: the exact backlog repro, and the non-turbofish struct-method sibling (proving the fix is general, not turbofish-specific). Full `cargo test --workspace` and `examples/*.cleave --run` sweep stayed green throughout; the original CLI repro re-run directly as the final sanity check.

**A known, deliberately out-of-scope limitation, found during testing**: a const generic used as a body value with *no* way to ever pin it (no turbofish, no inferable call-site evidence at all) still panics uncleanly at the CPS layer (`CPS: unbound variable N`) rather than a clean type error — confirmed this is not a new regression (the identical shape already failed some way before this fix, since `N`'s own value was never determined either way). Not attempted here — out of this item's own stated scope, which is specifically about the case where a concrete value *is* supplied.

### Complex literals

`3+4i` used to return a bare `<complex-not-yet-inferred>` placeholder, never really inferred — unrelated to `examples/complex.cleave`'s own user-defined `Complex<T>` struct, which already worked fine and needed no built-in literal syntax; that example turned out to be exactly the reusable foundation this item needed.

**The design question worked through first, at length, directly with the project owner**: does `2i + 4` need a general implicit-numeric-conversion mechanism to work? No — conflating two different things was the trap. *Ascription/defaulting* (an elastic literal settling on a concrete type — already how `Int`/`Float` shapes work, `infer.rs`'s `pending_defaults`/shape `Constraint`s) is a compile-time-only operation with no "value before"; *conversion* (transforming an already-concrete value, e.g. a variable, into a different concrete type) is a separate operation, decided to be **explicit-only**, never implicit (see the new "Explicit conversion between numeric types" item below, added but not implemented) — and literals don't need it at all: both `2i` and `4` are still-elastic, not-yet-concrete, so `2i + 4` is purely a defaulting question. `Int`/`Float` stay mutually exclusive with *each other* exactly as before (`1 + 2.0` still rejected, unaffected) — but `Int`- or `Float`-shaped literals widen freely into `Complex` (ℤ, ℝ ⊂ ℂ — a genuinely different relationship than `Int` vs `Float`, which is about precision, not subset-hood, and stays a real, checked distinction).

**The runtime representation already existed and already worked** — `examples/complex.cleave`'s own `struct Complex<T: Float> { real: T, imag: T }` + `impl<T: Float> Ring<Complex<T>> { add/sub/mul/div/neg }`, a real, generic, heap-allocated struct with correct arithmetic, already verified end-to-end by this project's own MLIR-lowering work. No new primitive type or MLIR representation was needed — `stdlib/complex/complex.cleave` moves that exact, proven definition into the stdlib (`use complex;` explicitly, not prelude, matching `io`'s own precedent) and adds a marker algebra `Complex<T> : Num` (mirroring `Int`/`Float`'s own pattern in `stdlib/num/num.cleave`) — legally sharing its own name with the struct, the same way `Int` marks `i32` without needing a distinct spelling.

Three small, targeted changes, no new runtime machinery:

1. **`infer.rs`'s `ExprKind::ImaginaryLit` arm** — replaced the hardcoded placeholder with the same shape `NumberLit`'s own unsuffixed-literal handling already has: a fresh var, `Num` + `Complex` shape `Constraint`s, and a `pending_defaults` fallback to `Complex<f64>` (`NumberDefault` gained a third variant, `Complex`, since its own default isn't a bare `Ty::Con` name the way `Int`/`Float`'s are).
2. **`infer.rs::check_pending_constraints`** — one targeted addition: an `Int`/`Float` shape constraint whose resolved type is `Ty::App("Complex", _)` is satisfied directly, without ever consulting `has_matching_impl`. Deliberately *not* expressed as an algebra bound (`algebra Int<T> : Complex` would be backwards — bound-inheritance answers "does concrete type X itself satisfy algebra Y," never "can a literal of shape X widen into a structurally different type Z"; confirmed by tracing `has_matching_impl`'s own reverse-witness/forward-aggregate walk, which has no mechanism for the second question at all).
3. **`cps.rs::convert_expr`** — new handling for `NumberLit`/`ImaginaryLit` whose own resolved type is `Complex<T>`: materializes a real `PrimOp::Struct("Complex", ["real", "imag"])` construction (the exact mechanism `ExprKind::StructLit` already uses) instead of a bare `CVal`, computing both fields from the literal's own text at `T`'s own concrete width.

**A real, separate limitation found by direct testing while writing the end-to-end tests, not fixed here**: unannotated field access on a value whose own type comes purely from deferred literal-defaulting doesn't resolve. `infer.rs`'s `ExprKind::FieldAccess` runs immediately and permanently records `<not-yet-inferred>` if the base's own type is still a bare `Ty::Var` at that point — which it is for `let z = 2i + 4; z.real`, since `apply_defaults` (what actually pins `2i + 4`'s own shared type to `Complex<f64>`) doesn't run until the very end of the whole function's inference, strictly after every statement has already been walked — `z`'s own later-defaulted type never gets a chance to flow back into `z.real`'s own already-recorded, already-wrong node type. An explicit annotation (`let z: Complex<f64> = 2i + 4;`) sidesteps this cleanly (pins `z`'s type immediately, no defaulting needed) and is what every test below actually uses — this is a pre-existing gap in how field-access resolution interacts with deferred defaulting generally, not specific to `Complex`, just newly exposed by it (no other built-in literal-defaulted type had fields to access before).

Verified via: an `infer.rs`-level test (`4i` alone infers as `Complex<f64>`), two real end-to-end JIT-execution tests in `cleave/tests/mlir_lower.rs` (`2i + 4` and `4 + 2i`, both actually run and checked field-by-field), and the pre-existing `1 + 2.0`-still-rejected test as a regression guard (confirms the `Complex`-widening special case doesn't loosen `Int`/`Float`'s own mutual exclusion). Full `cargo test --workspace` green; `examples/*.cleave --run` swept, including a direct run of `examples/complex.cleave` itself (its own output — `2 0 0 -1 -1 -1` — matches the file's own documented expected values exactly, confirming the stdlib addition doesn't disturb the independent user-space example, which never `use`s `complex`).

**Follow-up additions, same session**: `Complex<T>` gained real `magnitude_sq`/`magnitude` inherent methods (`stdlib/complex/complex.cleave`) — `magnitude_sq` stays `sqrt`-free (exact, `real*real + imag*imag`), `magnitude` layers `mlir::math::sqrt` on top through the same reserved, structurally-recognized `mlir::dialect::op(...)` mechanism every other primitive operation in this stdlib already goes through (confirmed `math.sqrt` is a real, already-registered MLIR op, not previously exercised anywhere in this codebase). `examples/mandelbrot.cleave` (new) renders the Mandelbrot set as ASCII art, real complex arithmetic end to end (`z := z*z + c`, escape-checked via `magnitude_sq() > 4.0`) — a genuine, if incidental, exercise of the whole `Complex` stack together, not just unit tests.

**A real, later-session bug in this same mechanism, found while extending `examples/complex.cleave` with more literal combinations and fixed**: `apply_defaults` processed `pending_defaults` in plain source order — when a bare `Float` literal and an `Imaginary` literal ended up sharing one merged variable (via `+`) with *no* enclosing annotation to pin the result early, whichever literal happened to be written *first* won the defaulting race. `5.0 + 7.5i` (float literal first) collapsed the shared variable to a bare `f32`, silently discarding the imaginary part and failing with `no impl Complex<f32>`; `7.5i + 5.0` (imaginary literal first) happened to work purely by accident of iteration order — every existing test for this item used an explicit `Complex<f64>` annotation, which pins the type during the main inference pass, well before `apply_defaults` ever runs, so this exact scenario had never actually been exercised. Fixed: `pending_defaults` is now stably sorted so every `Complex` entry is applied before any `Int`/`Float` one, order-independently — matches the ℤ, ℝ ⊂ ℂ direction (a bare shape only ever widens *into* `Complex`, never the reverse), and a stable sort means relative order within either group is otherwise untouched. Verified via a new `mlir_lower.rs` JIT test covering both operand orders (deliberately never consuming either result — any field access, method call, or annotation would itself force early unification and mask the exact bug), confirmed to genuinely reproduce the failure first (a native crash, not a clean error — the same pre-existing "a compile error inside `main` causes a rougher failure mode than a clean panic" gap noted earlier in this file, not fixed here either). Full `cargo test --workspace` green; `examples/*.cleave --run` swept, including `examples/complex.cleave` itself, since rebuilt around real complex literals and `.to()` (see "Explicit conversion between numeric types," below) instead of its own local `struct`/`impl` — its own output (`2 0 0 -1 -1 -1 5 34 41 1681`) matches hand-computed expected values exactly.

**A small inconsistency, noticed and fixed the same way**: a bare `4i` defaulted to `Complex<f64>` while a bare `4.0` defaults to `f32` — no principled reason for the two to disagree (`4.0i` isn't inherently "wider" than `4.0`). `NumberDefault::Complex`'s own fallback now builds `Complex<f32>`, matching `Float`'s own default width. `examples/complex.cleave`'s own unannotated field/method-access limitation (documented above) surfaced again while testing this, on a newly-added, unannotated binding — not a new gap, the same pre-existing one, fixed the same established way (an explicit `Complex<f64>` annotation). **Fixed for real, next item.**

### Deferred field-access/method-call resolution on a not-yet-defaulted value

The gap flagged twice above, fixed: `let z = 5.0 + 7.5i; z.magnitude();` (or `.real`/`.imag`) failed with `Print::print cannot be specialized for ((<not-yet-inferred>) -> <not-yet-inferred>))` even though `z` itself correctly defaulted to `Complex<f32>` — confirmed via `--dump-inference-pass` that the defaulting genuinely worked, the failure was entirely in `z.magnitude()`'s own return type.

**Root cause**: `ExprKind::FieldAccess`/`ExprKind::MethodCall` resolved their base's type immediately, during the ordinary top-to-bottom inference pass. If the base was still a bare `Ty::Var` at that exact point — true for any value whose only concreteness comes from `apply_defaults`, which runs once at the very end of the whole function's inference (`finish_fn`) — both arms gave up and returned the placeholder `Ty::Con("<not-yet-inferred>")`. Unlike a `Ty::Var`, that's a literal string sentinel: `Subst::apply`'s own re-resolution sweep (after defaulting) does nothing to a `Ty::Con`, so it survived, unrefined, forever.

**The fix, following the existing `pending_type_name_checks` precedent** (defer a question that isn't knowable yet, resolve it once, at the end): two new queues, `pending_field_accesses`/`pending_method_calls`. At the call site, only for the `Ty::Var(_)` case specifically (an *already*-placeholder base genuinely never resolves no matter how long this waits, and keeps returning the placeholder immediately, unchanged) — mint a fresh var, push a pending entry (for a method call, capturing the already-inferred argument types/spans too, since arguments never depend on the base's own resolution), and return the fresh var, threading through the rest of inference like any other still-open variable. Two new passes, `check_pending_field_accesses`/`check_pending_method_calls`, run right after `apply_defaults()`, at all three of the existing sites that pairing already runs from (`Infer::finish_fn`, `Infer::infer_inherent_impl_block`'s own group-wide equivalent, `callgraph.rs`'s whole-program SCC loop): resolve the base through `self.subst.apply` now; still a bare `Ty::Var` (or transitively a placeholder) means genuinely never pinned down by anything, unify the pending result against the same `<not-yet-inferred>` placeholder as before (the existing `check_no_placeholder` safety net catches it downstream, unchanged); otherwise resolve for real and unify the result against that.

The immediate-path resolution logic itself (`ExprKind::FieldAccess`'s "given a resolved base, find the field" match; `ExprKind::MethodCall`'s "given a resolved base and args, find and dispatch the method") was extracted into two standalone helpers, `resolve_field_access`/`resolve_method_call`, called from both the immediate path (unchanged behavior) and the two new deferred passes — no duplicated logic. `resolve_method_call` deliberately excludes the `in_progress_methods` self-recursion branch (a call back into a method *currently* having its own body inferred): those entries are always removed before that same call's own `finish_fn`/defaulting phase runs, so by the time a deferred call ever reaches the shared helper, `in_progress_methods` is structurally guaranteed not to contain it — the immediate call site keeps that check inline, before ever calling the shared helper.

Confined entirely to `cleave/src/infer.rs` (plus the three call sites in `callgraph.rs`) — no grammar/AST/registry/monomorphize/cps/mlir_lower changes, since this only changes *when* `infer.rs` learns a field/method's real type, not any new runtime representation.

Verified via: two new `infer.rs`-level tests (an unannotated deferred-defaulted value's field access, and its method call, both now resolving correctly, where both previously failed with the placeholder), a regression guard (a genuinely-unresolvable base — an unannotated function parameter with no other constraint — still fails cleanly via a real `Unify` error, not a silent wrong success), and two real end-to-end JIT-execution tests in `cleave/tests/mlir_lower.rs` (`z7.magnitude()` and `z7.real`/`z7.imag`, both unannotated, actually run and checked). Full `cargo test --workspace` green; `examples/*.cleave --run` sweep unaffected; the two original user-reported repros (`z7.magnitude()` and `(z7 + z8).imag`, both unannotated) re-run directly, now producing the correct values (`9.013878` and `3.5` respectively) instead of failing.

**Deliberately out of scope**: `ExprKind::Index` has a structurally similar `<not-yet-inferred>`-adjacent gap (a value indexed before its own array-ness is pinned down by defaulting) — not touched here, a separate expression kind with its own resolution shape, flagged rather than fixed opportunistically.

### Scheme satisfiability at generalization time

A scheme's own constraint set was only ever checked once something actually instantiated it — a mutually-recursive group whose members disagree on shape (`Int t` and `Float t` on the same quantified `t`) generalized completely silently if nothing ever called into it, confirmed directly:

```
fn f(x) { g(x); x + 1 }
fn g(x) { f(x); x + 1.0 }
```

`--dump-inference-pass` showed both generalizing cleanly (`fn f(x: 'a) -> 'a`), no error anywhere — even though their shared quantified `'a` carried both an `Int` shape constraint (`f`'s own `x + 1`) and a `Float` one (`g`'s own `x + 1.0`), which can never both hold for any single concrete type. Adding an external caller *did* correctly reject the call — confirming the gap's precise boundary: not "silently miscompiled," but "a provably-never-satisfiable scheme is published to `global_env` as if it were fine," a real soundness/hygiene gap for dead or not-yet-called code specifically.

**Root cause**: `check_pending_constraints` deliberately *skips* any constraint whose resolved type is (or contains) an already-quantified variable — correct and necessary in general (nothing to check *against* until instantiation pins it down), but it meant a scheme's own **internal** consistency (do *its own* constraints, taken together, admit any solution at all) was never verified at the one point it's actually knowable: right when the scheme is built.

**The fix**: a new check inside `Infer::generalize` itself (not bolted onto just `callgraph.rs`'s own top-level-fn path — `generalize` is shared with a generalized `let`-bound lambda too, via `infer_block`'s own `StmtKind::Let` handling, and the fix needed to catch both uniformly). `generalize`'s own signature changed from `-> Scheme` to `-> Result<Scheme, TypeError>`. Deliberately narrow, matching the concrete example above: only **single-target** constraints (`Constraint.tys.len() == 1` — the shape-constraint case, `Int`/`Float`/`Num`/a declared `T: Bound`) are checked, grouped by which quantified variable they touch; a multi-target constraint (a heterogeneous algebra call spanning several quantified variables at once, `MatMul<A,B,C>`) is a structural-match question, not a per-variable satisfiability one — not attempted, flagged not hidden.

For each quantified variable with two or more single-target constraints, a new `Registry::candidates_for(algebra) -> HashSet<String>` helper computes each constraint's own algebra's candidate concrete-type set — every non-generic, single-target, bare-path impl declared directly for it, plus (recursively, cycle-guarded the same way `Infer::has_matching_impl_inherited` already is) every candidate of any algebra bounding on it, since `Num` itself has zero direct impls anywhere (only reachable through `Int`/`Float`'s own bound) and the check must not false-positive on it. The intersection across all of a variable's own constraints must be non-empty, or `generalize` returns a new `TypeErrorKind::UnsatisfiableScheme { algebras }` (deduplicated, sorted, for a clean message) — reported against the specific member whose own scheme is unsatisfiable, not the whole mutually-recursive group (unlike `check_pending_constraints`'s own group-wide failure, which really is a property of the group's mutual definition as a whole).

An existing test (`conflicting_literal_shapes_across_a_mutually_recursive_group_are_rejected`) had been written earlier specifically to document the *old* behavior (its own comment: "a real, separate, deliberately-not-caught gap") — updated to assert the new one: the conflict is now caught directly on the group itself, no external caller needed, and its own external-caller half was removed as no longer the interesting part of the test.

Verified via: the exact repro above (now rejected with no caller at all), a regression guard (two genuinely *compatible* single-target constraints on one variable — `Int` and `Ord`, both satisfied by `i32` — still generalize cleanly, proving the fix only rejects a truly empty intersection), and a `let`-bound generalized lambda with the identical conflict (proving the fix lives in `generalize` itself, not just one caller). Full `cargo test --workspace` green; `examples/*.cleave --run` sweep unaffected; the original repro re-run directly via `--dump-inference-pass`, now reporting a real, readable error (`no single type can ever satisfy all of: Float, Int, Num, Ring — this generic can never be called`) instead of silently generalizing.

### Bound-satisfiability-aware overlap checking

`check_no_overlapping_impls` (`infer.rs`) rejects two `impl`s of the same algebra whose target *patterns* structurally unify — but it never asked whether the two impls' own bounds could actually be jointly satisfied by any real concrete type, a real false positive, confirmed directly:

```
struct Box<T> { value: T }
impl<T: Int> Ring<Box<T>> { fn add(a, b) { Box(value: a.value + b.value) } ... }
impl<T: Float> Ring<Box<T>> { fn add(a, b) { Box(value: a.value + b.value) } ... }
```

Rejected before the fix (`error: overlapping impls: impl Ring<Box<T>> and impl Ring<Box<T>> could both match the same type`), even though no concrete type is ever both `Int` and `Float` — the exact same mutual-exclusivity relationship "Scheme satisfiability at generalization time" (immediately above) already had to solve for `generalize` itself.

**The fix**: a new shared helper, `Infer::unsatisfiable_bounds`, factored directly out of `generalize`'s own satisfiability check (grouping bounds, intersecting `Registry::candidates_for` across them, empty intersection → conflict) — `generalize` and `check_no_overlapping_impls` were really asking the identical question over two different sources of "which bounds land on the same variable," so `generalize`'s inline logic became a call to the shared helper with no behavior change. In `check_no_overlapping_impls`, once `all_overlap` confirms two impls' target *shapes* coincide (unchanged — still a real, necessary check), `trial` — the very `Subst` those `unify` calls just populated — already records exactly how each side's own generic vars got merged; every `GenericParam::Type`'s bounds (from both impls) are grouped by their merged variable's resolved type via `trial.apply`, and `unsatisfiable_bounds` decides whether each group could really share a concrete type. If any group's intersection is empty, the shape-level "overlap" is skipped — it can never happen at any real instantiation. `Const` generics have no bounds at all, so nothing to check there. Deliberately narrow, same posture as the immediately-preceding item: no attempt at a fully general bound-satisfiability solver, just this now-cheaply-available `candidates_for` check closing the specific false-positive gap found.

**A real, separate discovery made while testing this**: `check_no_overlapping_impls` is called *only* from `dump.rs`'s own `--dump-inference-pass` path (before `callgraph::infer_program` even runs) — never from `callgraph::infer_program`, `monomorphize::monomorphize`, or `driver::compile`. The real `--run`/JIT pipeline never exercises this check at all today, so a JIT-level test of this fix would pass regardless of whether the fix exists (confirmed directly: an initial JIT-based test written for this item passed even *before* the fix was implemented, exposing itself as a false proof, and was discarded in favor of a direct `Infer::check_no_overlapping_impls()` test matching the existing tests' own established pattern). This fix genuinely closes the false positive wherever the check *does* run, but its real-world effect on ordinary compilation is currently nil — worth a separate look at whether `check_no_overlapping_impls` should be wired into the real compile pipeline at all, not attempted here.

Verified via: the exact repro above (`check_no_overlapping_impls()` called directly, now empty — no error), a regression guard (`overlapping_generic_impls_of_the_same_algebra_are_rejected`, `Float`/`Ord2` both satisfied only by `f64`, re-confirmed still rejected — a genuine overlap, unaffected by the fix), and the two other pre-existing overlap tests (different target shapes; a single impl never overlapping itself). Full `cargo test --workspace` green (162 `infer` tests); `examples/*.cleave --run` sweep unaffected; the original repro re-run directly via `--dump-inference-pass`, now compiling cleanly instead of being rejected.

### Explicit conversion between numeric types (`Convert<From, To>` + `.to()`)

`z + 2.0` (`z` an already-concrete `Complex`, `2.0` an ordinary float) has no way to work — literal-shape widening ("Complex literals," above) only ever applies to *elastic*, not-yet-concrete literals, never to an already-typed value like `z`. `i32`/`f64`/`Complex` don't relate to each other as a subset/superset hierarchy in cleave's own type system, unlike math (ℕ ⊂ ℤ ⊂ ℝ ⊂ ℂ). Decided explicit-only (Rust `From`/`Into`-style), never implicit (C#-style implicit conversion rejected for its silent-bug reputation — this project's own posture everywhere else is that nothing is guessed or silently inserted, always checked).

**The original design sketch ("no new compiler mechanism needed at all") was investigated directly and found incomplete in two real ways, both fixed as part of this item, not deferred:**

1. **`match_impl`'s own doc comment claimed dispatch-time commit was "safe specifically because `check_no_overlapping_impls` already guarantees at most one impl's target pattern can ever coherently match a given query tuple" — true only for two *declarations* unified against each other, not for a call site whose query still has a free position.** `Convert<i32, f64>` and `Convert<i32, Complex<f64>>` are fully concrete, differently-shaped targets that never unify against *each other*, so `check_no_overlapping_impls` never flags them — yet both match a call site whose `To` is still an unresolved `Ty::Var` (an output-only generic, like `MatMul`'s own `C`, is never gated by `infer_algebra_call`'s readiness check). Latent for `MatMul` (no realistic reason for two impls to share input shape but disagree on output) but the *central* case for `Convert` (one `From`, many legitimate `To`s). Fixed: `match_impl` split into `matching_impls` (collects *every* candidate's own trial `Subst`, commits nothing) and a simplified `match_impl` (pure existence probe, `commit` parameter dropped — its only `true`-caller was this same method). `dispatch_algebra_call` is now the sole committing path: zero candidates → no impl; one → commit; more than one → resolve the query through each candidate and compare — if they all agree (the ordinary case), commit any one; if they genuinely disagree on a still-free position, a new `TypeErrorKind::AmbiguousDispatch` is reported instead of silently picking whichever impl `Registry::all_impls` iterated first.
2. **Turbofish on an algebra-dispatched call was a documented no-op** (`infer_call`'s own comment: "not attempted this increment"). Confirmed there was no other way to pin `To` either — `StmtKind::Let`'s annotation unifies *after* the RHS is already fully inferred (ordinary, non-bidirectional HM order), so by the time an annotation could help, dispatch had already committed. Without turbofish, the new `AmbiguousDispatch` error would be a permanent, undisambiguable hard stop for exactly the motivating case. Fixed: `infer_algebra_call` gained an `explicit_generics: &[GenericArg]` parameter, threaded from `infer_call`'s previously-dropped one, unified against each declared generic's own fresh var (full arity required, same convention as the existing `let`-bound-lambda/top-level-fn turbofish path — no partial turbofish) *before* `param_tys`/`resolved_generics` are built. Pinning `To` this way collapses `matching_impls` back to a single candidate, resolving the ambiguity. `convert::<i32, f64>(n)` is the resulting escape hatch.

**A third, real gap found and *ruled out* as unreachable, not fixed**: `check_pending_constraints` (the deferred path a bare-literal argument like `widen(1)` takes, since its shape var isn't concrete until `apply_defaults` runs) looked like it needed the same ambiguity check. It doesn't: that function's own pre-existing gate already requires *every* position of a constraint's query — including any output-only generic — to be fully concrete before considering it at all; proved directly that unifying an impl's pattern against an already-fully-concrete query can only ever bind that pattern's own free vars *to* the query's values, so every matching candidate resolves back to the identical input tuple. Ambiguity is only possible while a position is still free, which this gate structurally excludes. Confirmed by writing the "obvious" test first (`widen(1); 0`, result discarded) — it passed without any fix, traced to the constraint never even being checked (an unrelated, pre-existing, genuinely separate gap: an algebra call whose *only* consumer is an unused output-only generic is silently never validated at all, dispatch ambiguity or not — exists for any multi-target algebra, not just `Convert`, not attempted here).

**`Convert<From, To>` itself** (`stdlib/convert/convert.cleave`): `algebra Convert<From, To> { fn convert(x: From) -> To; }`, `impl Convert<i32, f64>` (`mlir::arith::sitofp`) and `impl Convert<f32, f64>` (`mlir::arith::extf`) — deliberately dependency-free, like `stdlib/num`, not `use complex;` internally: confirmed directly that `driver.rs`'s own documented "one level deep only" `use` resolution means a crate's internal `use` is never followed when it's loaded transitively, so a `Convert<f64, Complex<f64>>` impl living here would force *every* `use convert;` program to also explicitly `use complex;`, even to reach the unrelated `f32 -> f64` impl. `examples/convert.cleave` demonstrates the `f64 -> Complex<f64>` conversion instead as a genuine user-space extension impl — arguably a better proof of the algebra's own openness than baking it in. `x.to()` (`lower.rs`'s `lower_postfix_op`) desugars to `Call(convert, [x])`, the same shape `fold_binary` already uses for operators — deliberately not a `MethodCall` (`ExprKind::MethodCall` resolves purely via inherent-method lookup, a wholly separate mechanism from algebra dispatch, confirmed by reading its own handling). Only the zero-argument spelling counts; `.to()` itself carries no turbofish (postfix method syntax has no turbofish grammar), so `convert::<From, To>(x)` is the only way to disambiguate — an accepted, deliberate tradeoff also shadowing any user-declared inherent method literally named `to`, matching this project's existing acceptance of reserved operator-sugar names (`and`/`or`/`not`/...).

**A separate, real bug found while implementing this, worked around at the time and properly fixed immediately after** (see "A generic impl's own generic gets silently defaulted away by a body literal," below): `impl<T: Float> Convert<T, Complex<T>> { fn convert(x) { Complex(real: x, imag: 0.0) } }` failed to monomorphize (`error: expected floating point type`, a native MLIR assertion). Worked around here by keeping the `Complex` conversion concrete (`impl Convert<f64, Complex<f64>>`, in the example, not the stdlib) — `stdlib/convert/convert.cleave`/`examples/complex.cleave` could now use the generic form instead, since the real bug is fixed, but weren't changed back as part of that follow-up item (not required, the concrete form works fine).

Verified via: the new `infer.rs` tests (ambiguous dispatch rejected via the immediate path; turbofish disambiguates; turbofish requires full arity; a single candidate still dispatches with no turbofish; `.to()`'s own desugaring reaches the identical `AmbiguousDispatch` check) and new `mlir_lower.rs` JIT tests (`.to()` on an already-typed value and on a bare literal, both running the real `sitofp`; turbofish `convert::<i32, f64>(...)` selecting the correct impl body at runtime against a second, competing, user-declared `Convert<i32, Widened>`). Full `cargo test --workspace` green; `examples/*.cleave --run` sweep (including the new `examples/convert.cleave`) unaffected.

### A generic impl's own generic gets silently defaulted away by a body literal

Immediate follow-up to "Explicit conversion between numeric types," above — `impl<T: Float> Convert<T, Complex<T>> { fn convert(x) { Complex(real: x, imag: 0.0) } }` failed to monomorphize (`error: expected floating point type`, a native MLIR assertion). That item's own Done entry logged a diagnosis ("a generic algebra impl fails to monomorphize when its own output-only target nests a struct built from its bound parameter") — **investigated further and that diagnosis was wrong**. The real bug was narrower and had nothing to do with output-only targets or nested structs.

**Root cause, confirmed directly via `--dump-inference-pass`**: a minimal repro — `algebra Widen<From, To> { fn widen(x: From) -> To; } impl<T: Float> Widen<T, Pair<T>> { fn widen(x) { Pair(a: x, b: 0.0) } }` — dumped as `fn widen(x: f32) -> Pair<f32>`. The impl's own generic `T` had been silently collapsed to a concrete `f32` in the *declaration-time template itself*, before any call site was even considered: `Pair(a: x, b: 0.0)` unifies the struct literal's declared field type (`Pair`'s own generic) against both `x`'s type (`T`) and `0.0`'s own literal shape-var, merging all three into one variable; `finish_fn`'s `apply_defaults` (run once per impl-method declaration) then found `0.0`'s entry, resolved it to that merged root, and — finding it "still a bare `Ty::Var`, not in `self.quantified`" — defaulted it to `Con("f32")` for real. This corrupted the whole template (`monomorphize.rs`'s own `ImplTemplate`), so `derive_impl_instantiation`'s later reverse-unification against a *different* concrete call site (`f64`) failed outright.

**Why this never surfaced before**: `apply_defaults` already has an escape hatch for exactly this — `self.quantified`, populated by `Infer::generalize` for a `let`-bound/top-level generic fn's own free type variables, *before* `apply_defaults` ever runs (confirmed directly: an explicitly-generic top-level fn with the identical body shape dumps as `fn f(x: 'a) -> 'a`, `T` correctly stays free, since `callgraph.rs`'s whole-program pass calls `generalize` before defaulting). An impl's own declared generics go through no analogous step at all — `infer_impl_fn_generic_with_env`, `infer_inherent_impl_fn_generic`, and `infer_inherent_impl_block` all mint the impl's own generic vars via `fresh_generics_mapping` directly, with nothing registering them in `self.quantified` first. No existing stdlib impl happened to use a bare literal in a generic method body (`stdlib/complex/complex.cleave`'s own `Ring<Complex<T>>`/`magnitude_sq` bodies only ever propagate already-typed values) — `Convert`'s `imag: 0.0` was the first one to, a real, previously-latent bug, not a regression.

**The fix**: a new `Infer::quantify_impl_generics(&mut self, mapping: &HashMap<String, Ty>)`, called at each of the three declaration-time-template sites, right *before* that template's own defaulting runs (after the method body has already been inferred) — resolves each of the impl's own generic vars through the *current* `self.subst` and marks whatever variable is still free at that point as quantified. Must resolve *now*, not when `mapping` was first built: an earlier version of this fix registered `mapping`'s own original fresh vars immediately after minting them, and still failed — `Subst::bind`'s own merge direction (`unify` binds *from* one operand *to* the other, order-dependent) can make the impl's own generic var become a mere *alias* of some other variable during body inference, so only resolving at the last possible moment finds the variable that actually survives.

Confirmed the fix doesn't weaken anything: `check_pending_constraints` already skips a not-fully-concrete constraint regardless of `quantified` (the well-behaved case was already deferred this way), and an impl's own declared bound (`T: Float`) is independently, authoritatively re-checked at real dispatch time anyway (`matching_impls`'s own `bounds_satisfied`, against the call site's real concrete types) — this was never the load-bearing check for an impl's own generics.

**A real, separate, tangential discovery made while chasing what first looked like a second bug**: after this fix, a single-instantiation JIT run of the exact repro still crashed (`expected floating point type`, again) — traced at length (temporary `eprintln!` instrumentation through `lower_struct_construct`/`lower_real_call`/`ty_to_mlir`) to a **self-inflicted test-authoring mistake, not a real compiler bug**: the test's own scratch source redeclared `algebra Float<T> {} impl Float<f64> {}` locally, colliding with the real, `#[mlir_type(f64)]`-tagged `Float` algebra `stdlib/num/num.cleave` already provides via the prelude. `cps::collect_mlir_types` scans `program.items` directly rather than through the registry, so both declarations coexist as separate items — but whichever of the two wins the registry's own same-key impl slot determines what `ty_to_mlir` actually sees for `f64` at the point that matters, and the untagged local one won, silently making `Ty::Con("f64")` fall through to the generic "struct pointer" arm instead of a real float type. **Not fixed** — worth its own look (flagged as a new open item below, "Redeclaring an algebra name that collides with a prelude algebra silently corrupts its MLIR type lowering") — but confirmed to have nothing to do with this item's own fix, which is genuinely complete once the collision is avoided.

Verified via: a new `infer.rs` test (the exact repro, asserting `param_types` stays a free `Ty::Var`, not concrete — failed before the fix, passes after) and a new `mlir_lower.rs` JIT test (the same generic impl invoked at *two* different concrete types in one program, both producing correct values — a single-instantiation test wouldn't have caught the original bug, since a corrupted template happens to still "work" for whichever one concrete type it got stuck at). Re-ran the original motivating case directly (`impl<T: Float> Convert<T, Complex<T>>`, invoked at both `f32` and `f64` via explicit turbofish to route around the unrelated, already-known `AmbiguousDispatch` from having two candidate `Convert<f32, _>` impls) — works end to end. Full `cargo test --workspace` green; `examples/*.cleave --run` sweep unaffected.

### Redeclaring an algebra name that collides with a prelude algebra silently corrupts its MLIR type lowering

Found while verifying the item above — a scratch test declared its own `algebra Float<T> {} impl Float<f64> {}` (a plain, throwaway test fixture, unaware `Float` is already a real prelude algebra from `stdlib/num/num.cleave`, tagged `#[mlir_type(f64)]` there). The program compiled and type-checked with no error or warning about the collision, but crashed at `--run` with a native MLIR assertion (`expected floating point type`).

**Root cause, traced precisely**: `driver::compile` merges the *entry file's* own items before any resolved `use`/prelude crate's (its own doc comment already says so). `merge_impl_fragment` (`driver.rs`) treats two `impl`s sharing the same (algebra, target, generics) key as *fragments* of one logical impl — a deliberate feature, letting one impl's own methods be declared across multiple files — but the merge only ever combined `.fns`; `.attrs` (`#[mlir_type(...)]`, an `impl`'s only attribute) was never touched at all. Whichever fragment got processed first silently became the accumulator, and a *later* fragment's own attrs were discarded with **zero diagnostic** — since the entry file merges first, a local, untagged `impl Float<f64> {}` always won over the prelude's own tagged one. `cps::collect_mlir_types` then never saw `f64`'s own MLIR type text at all, and `mlir_lower.rs::ty_to_mlir`'s `Ty::Con(name) if ... ctx.mlir_types.contains_key(name)` guard silently fell through to the generic "opaque struct pointer" arm instead of a real float type — a native MLIR assertion at codegen time, nowhere near the actual mistake.

**The fix**: `merge_impl_fragment` now reconciles `.attrs` explicitly, the same way it already reconciles `.fns` — if the incoming fragment declares attrs and the accumulator has none yet, adopt them (`Vec<Attribute>::clone_from`, so whichever fragment happens to carry the tag always survives, regardless of merge order); if *both* declare attrs and they disagree (compared by `name`+`args`, not derived `PartialEq`, since `Attribute::span` differs between fragments by construction and must never make two textually-identical tags look like a conflict — a new `attrs_match` helper), that's now a real, reported error instead of a silent pick.

Verified via new `driver.rs` tests exercising `merge_programs` directly (matching that file's own established pattern): an attr-less fragment adopts a sibling's attrs regardless of merge order (both orderings tested — confirmed to fail without the fix, pass with it), two fragments *disagreeing* on attrs is a reported conflict, two fragments *agreeing* on identical attrs merge cleanly (not a false-positive conflict). Full `cargo test --workspace` green (19 `driver` tests); `examples/*.cleave --run` sweep unaffected; the original collision repro re-run directly, now compiling and running correctly with the prelude's own `f64` tag intact.

### Deferred/symbolic constant folding

`[T; N+M]` (`N`/`M` const generics still abstract when written) didn't work — confirmed directly: `struct Buf<const N: i32, const M: i32> { data: [i32; N+M] }` constructed via `Buf::<2, 3>(data: [1,2,3,4,5])` failed with `type mismatch: expected \`<array-type-not-yet-inferred>\`, found \`['t8; 5]\``. `const_eval.rs` already folded pure-literal arithmetic and bare const-generic references; a computed expression that only becomes concrete *later* (at instantiation/monomorphization time) needed `Ty` itself to carry a small deferred-expression shape, not just a resolved `Const` leaf or an unresolved `Var`.

**Two genuinely separate sub-problems, found by direct testing:**
1. A tiny bug: `Infer::const_value_from_expr`'s `Path` arm returned the generics-mapping's *raw* entry (`mapping.get(name).cloned()`) without ever resolving it through `self.subst` — so even when an explicit turbofish (`Buf::<2, 3>`) already bound `N`/`M` concretely (via `unify_at`, earlier in the very same `StructLit` inference), this lookup still saw the original, unresolved fresh var. One-line fix: `mapping.get(name).map(|t| self.subst.apply(t))`.
2. The real, larger gap: a struct/fn signature that stays *generic* — `N`/`M` never resolved at declaration time, only later at monomorphization/a concrete call site — had no way to carry `N+M` symbolically through type-checking at all; `ty_from_ast_mapped`'s `TypeKind::Array` arm fell back to a permanent, un-refinable `Ty::Con("<array-type-not-yet-inferred>")` placeholder, never revisited once `N`/`M` became concrete.

**The fix**: a new `Ty::ConstExpr(String, Box<Ty>, Box<Ty>)` variant (operator name, matching `const_eval::eval_binop`'s own desugared names, plus two const-shaped operands). A full codebase survey (every match over `infer::Ty`, all 17 `cleave/src/*.rs` files) found 9 exhaustive match sites needing an update (`Subst::apply`, `Subst::occurs`, `Display for Ty`, `free_vars`, `substitute`, `is_fully_concrete`, `find_placeholder_name`, plus two "combined for exhaustiveness, never actually reached" arms) — all in `infer.rs`, plus one in `dump.rs`'s `fmt_ty_named`; `monomorphize.rs`/`cps.rs` needed no direct changes at all, relying entirely on `infer.rs`'s own `substitute`/`free_vars` doing the structural walk on their behalf; `registry.rs`/`print.rs`/`egraph.rs` never matched `infer::Ty` in the first place.

**The key design insight that kept this scoped**: `unify`'s existing `(Ty::Var(v), _)` arms already handle binding a bare var to a `ConstExpr` correctly, with zero new code — a `ConstExpr` is just another `Ty` value. The only genuinely new `unify` arm needed is `(ConstExpr, ConstExpr)` same-operator structural unification (mirrors `Ty::App`'s own same-name-then-zip-args arm). Fold-eagerly-when-possible lives in exactly two places, both already-existing structural-recursion functions — `Subst::apply` (called at the top of every `unify`, so a `ConstExpr` pinned concrete earlier in the same inference collapses to a real `Const` before `unify`'s own match ever runs) and `substitute` (the monomorphization-time mapper, where `N+M` actually turns into a real number once a generic template gets instantiated) — both sharing one new `fold_const_expr` helper that delegates to `const_eval::eval_binop` (already designed for exactly this reuse) when both operands resolve to `Const`, and stays symbolic otherwise.

**Deliberately not "solved" — a `ConstExpr` unified directly against a concrete `Const` (both operands still genuinely unresolvable) falls through to the ordinary `Mismatch` error, with no new code needed for that case either**: `N+M=5` alone never uniquely determines `N`/`M` individually (`Buf(data: [1,2,3,4,5])`, no turbofish, is genuinely underdetermined — many solutions), and guessing would contradict this project's own "never silently guessed, always checked" posture (matches the recent `AmbiguousDispatch` work). This is a real, honest improvement over the old placeholder text, not a full solve.

**A real, separate, narrower gap found while writing the end-to-end JIT test, flagged not fixed**: `monomorphize.rs`'s `derive_instantiation` (the pass that recovers a generic function's own concrete instantiation at a call site) works *purely* by reverse-unifying the call's own argument/return *value* types against the function's declared shape — it never consults an explicit turbofish at all (`collect_instantiations_expr`'s own `ExprKind::Call` arm literally discards it: `(path, _, args, ..)`). So a const generic that appears *only* combined inside a `ConstExpr` — never on its own, anywhere in the signature — can never be recovered for monomorphization purposes, even with an explicit turbofish supplying it directly (reverse-unifying `ConstExpr(N,M)` against a single concrete total is exactly the same underdetermined problem as above). Not a blocker in practice: the realistic shape this item's own example is actually about (`fn f<const N, M>(a: [T;N], b: [T;M], c: [T;N+M])`, each const generic *also* appearing directly somewhere) works correctly, verified end to end.

Verified via: three new `infer.rs` tests (turbofish-driven struct field resolves via the one-line fix; a generic function's own `[i32; N+M]` parameter stays a real `Ty::ConstExpr` at declaration time, not an error or a placeholder; the underdetermined no-turbofish case is now a clean `UnifyError::Mismatch` with no `<not-yet-inferred>` text) and one new `mlir_lower.rs` JIT test (a generic function combining two independently-inferred array parameters into a third, `N+M`-sized one, called with real concrete arrays, actually running and computing the right sum — the real proof that `substitute` folds `ConstExpr` into a real `Const` during monomorphization). Full `cargo test --workspace` green (171 `infer` tests, 75 `mlir_lower` tests); `examples/*.cleave --run` sweep unaffected, `matmul.cleave` (the codebase's own heaviest const-generic user) specifically re-checked given how many `Ty` match sites changed.

### `Vector`/`Matrix`/`Tensor` — ordinary stdlib structs backed by native MLIR `tensor`, no new `Ty` variant

`examples/matmul.cleave` was, until this item, exactly the "premature lowering" anti-pattern `doc/hld.md` warns about by name: `Matrix<T,R,C>` an ordinary array-backed struct, `matmul` a hand-written triple-nested loop — by the time either reached MLIR it was pure scalar `arith`/`scf` in a loop, the matmul structure gone, unreachable by any future cost-driven backend (a `cooperative_matrix`-capable Vulkan target, say) that might otherwise recognize and specially lower a real matmul node.

**First attempt, built, tested, then deliberately reverted**: a native MLIR `vector<NxT>` type, but as a new `Ty::Vector` Rust enum variant — real and working (full test suite green, `vector.contract`-backed matmul verified end to end), but on review it's exactly the "closing the loop" anti-pattern `doc/hld.md`'s own primitives-are-algebras-too section warns against: a hardcoded compiler type, touching every exhaustive match over `Ty` in `infer.rs`, plus a reserved-name construction hack (`Vector(...)` as a magic call) to work around structs having no positional constructor. The user's own call, after reviewing the diff: redo it as an ordinary stdlib struct instead. What follows is the replacement that actually shipped.

**`Vector<T, const N: i32> { data: [T; N] }` — an ordinary generic struct**, declared entirely in `stdlib/vector/vector.cleave`, no different in kind from `Complex<T>`. `Ty` itself needed **zero** changes — no new variant, no ripple through `unify`/`Subst::apply`/`Display`/etc. Construction is the ordinary named-field struct literal (`Vector(data: [1.0,2.0,3.0])`); positional/variadic constructor sugar is real, separate, unattempted future work, not squeezed in here.

**`#[mlir_type(...)]` generalized from a static string to a structural derivation** — its existing job (`stdlib/num/num.cleave`'s `#[mlir_type(i32)] impl Int<i32> {}`) was "this impl's target type's MLIR representation is exactly this text." The bare keyword `tensor` (or `vector`) now means something different: "this struct's own sole field — always an array — *is* its real representation, a native MLIR `tensor<...>`/`vector<...>` value, never the usual heap-allocated opaque-pointer struct." The shape (dims, element type) is derived structurally from the field's already-known `Ty::Array`, via the *existing* `flatten_array_dims` — no template-string placeholder substitution needed at all, which was the original (more complicated, ultimately unnecessary) plan for this. Since a bare `struct` declaration has no `attrs` field of its own (`ast.rs`'s `ImplDecl::attrs` only ever decorates an `impl`), the tag lives on a trivial, zero-axiom marker algebra built just to carry it: `algebra NativeShape<T> {}` plus `#[mlir_type(tensor)] impl<T: Float, const N: i32> NativeShape<Vector<T, N>> {}` — mirrors `Int`/`Float`'s own "empty marker impl, the real content lives in the tag" shape exactly.

**`mlir_lower.rs::tagged_struct_native_type`** (`ty_to_mlir`'s new first-checked arm) builds the real type via `Type::parse` (melior 0.27 has no `VectorType`/parametric-tensor Rust binding, same idiom `lower_raw_mlir_op` already used for attribute text, applied one level up to type construction). **`lower_tagged_struct_construct`** (a new `PrimOp::Struct` branch, checked via the same tag) converts the field's own already-built standalone array (an ordinary `memref`, built exactly like any other array — no special-casing of literal-vs-computed field values, deliberately: "let MLIR have fun with the optimization" was an explicit call, not a premature hand-optimization) into the real tensor/vector value via `flatten_memref_elements` (a new, small read-side mirror of the already-existing `copy_nested_array`'s write-side dims-walk) feeding one `{keyword}.from_elements`.

**Element read goes through a new `Index<Container, Elem, const K: i32>` algebra, not a field** — `Vector`/`Matrix`/`Tensor` have no `.x`/`.y`/`.z` of their own, only the whole `data` array. `ExprKind::Index` — hardcoded to `Ty::Array`, previously a hard `Mismatch` error on anything else — gained a fallback: a non-array base dispatches `index(base, idx)` through the ordinary algebra machinery (`infer_algebra_call`, `resolve_call`/`emit_call`, and a new `monomorphize.rs::collect_instantiations_expr` arm mirroring its own `ExprKind::Call` handling), the same way an operator call already does. `tensor.extract`'s own dynamic (non-compile-time-constant) index operands — unlike `vector.extract`'s simpler constant-only form — mean a genuinely runtime-computed `v[i]` just works, no restriction. Mutation (`v[i] = x`) deliberately stays array-only: `StmtKind::Assign` gained an explicit guard rejecting a non-array `Index` target with a clean `Unify` error rather than letting it silently reach `cps.rs`'s array-only `PrimOp::Store` path — a tensor-backed value is immutable by construction, no `IndexMut`-equivalent attempted. (`K`, the number of indices in one bracket group, was added in a follow-up pass — see "Multi-dimensional `Index` dispatch" below; the algebra originally shipped rank-1-only, `fn index(c: Container, i: i32) -> Elem`.)

**`Matrix<T,R,C> { data: [[T;C];R] }`** reuses the identical tag mechanism. `matmul` lowers to a single **`linalg.matmul`** on `tensor` operands — not `vector.contract` (the first attempt's own choice): `tensor` is the more principled pick per `hld.md`'s own "stay abstract, lower late" thesis, and `linalg.matmul` is a *named*, structurally-recognizable op, exactly what a future cost-driven backend would pattern-match on. `mlir::tensor::empty()` (zero operands, shape from its own result type alone) supplies the required `outs` operand — `linalg.matmul` computes the whole result itself, never accumulates into whatever `outs` held, so no real zero-initialization trick is needed here the way `vector.contract`'s own accumulator once needed one.

**`Matrix`/`MatMul` and a new `Tensor<T, D0, D1, D2>` (rank 3) all moved into `stdlib/vector/vector.cleave` alongside `Vector`**, in a follow-up pass — `Matrix` was initially left declared locally in `examples/matmul.cleave` (mirroring how `MatMul` itself always has been), but on reflection both are equally general-purpose linear algebra, not specific to that one example, so they belong in the stdlib the same as `Vector`. `Tensor` is new: the identical mechanism one axis further, confirmed via a real JIT test (`a_rank_3_tensor_constructs_and_reads_back_the_right_value`) that `tagged_struct_native_type`/`lower_tagged_struct_construct` really do scale past 2 dims with zero new Rust code, driven entirely by however many dims the field's own array type declares (`flatten_array_dims`, already fully shape-generic). `examples/matmul.cleave` now just `use vector;`s the stdlib types; a new `examples/tensor_demo.cleave` exercises all three together (elementwise `Ring` on `Vector`, a real `linalg.matmul` on `Matrix`, construction/read on a rank-3 `Tensor`).

**A real, deeper inference gap, found while writing `tensor_demo.cleave`'s own `print(v[i])` calls**: `check_pending_constraints` (the deferred half of algebra dispatch — see `infer_algebra_call`'s own "still abstract somewhere" branch) requires *every* position in a deferred `Constraint` to already be concrete before it will even attempt a match, including a generic that only ever appears in an algebra's *return* type (`Index<Container,Elem,K>`'s own `Elem`, `MatMul<A,B,C>`'s own `C`). But an output-only generic is, by design, never independently pinned by anything else — the *only* place it's ever supposed to get bound is inside a successful dispatch itself (`dispatch_algebra_call`, the immediate-path's own committing match). So when an algebra call's *input* side is deferred only because it depends on a numeric literal that hasn't been defaulted yet (`Vector(data: [1.0, 2.0, 3.0])`'s own element type, resolved only at `apply_defaults`, run *after* the whole function body — including the deferred `Index` call — has already been processed), the constraint recorded for it carries `Elem` as a totally free, never-otherwise-constrained variable. Once `apply_defaults` later makes the *input* side concrete, `check_pending_constraints` re-checks the constraint — but `Elem` is still a bare `Ty::Var`, so `!resolved.iter().all(is_fully_concrete)` is true and it's silently skipped (not errored) forever, discarded along with the rest of `self.constraints` (`std::mem::take`). The still-unresolved `Ty::Var` only ever surfaces later, as a Rust panic in `cps.rs`'s `resolve_call` ("could not resolve call to `print`"), not a clean type error. **Worked around in `tensor_demo.cleave`** the same way the `arith.index_cast`-on-a-bare-literal rough edge above already is: an explicit `let x0: f32 = v[0];` before `print(x0)` unifies the output-only generic with something concrete immediately, so it never needs the deferred path's own (currently broken) recovery. **Not fixed at the root** — a real fix needs `check_pending_constraints` (or `Constraint` itself) to distinguish an algebra's *input*-appearing generics (must be concrete before dispatch can even be attempted, exactly `infer_algebra_call`'s own `gating` set) from its *output*-only ones (should ride along into a real, committing `dispatch_algebra_call`-style match once the input side is ready, the same way the immediate-dispatch path already treats them) — today's gate wrongly demands the second group be concrete *before* the very mechanism that's supposed to concretize them ever runs. Likely affects any algebra with an output-only generic (`Index`, `MatMul`, `Convert`) whenever its input side depends on later numeric-literal defaulting, not just `Vector`/`Index` specifically — **confirmed directly**, not just predicted: `MatMul<A,B,C>`'s own `C` hit the exact same gate while building the `mc[i,j]` multi-index test below (`ma`/`mb`'s own element type undefaulted at `matmul(ma,mb)`'s own call site → deferred → `C` never independently pinned → `mc`'s type stayed a bare `Ty::Var` all the way to a `parse_number` panic on `58.0`, since `mc[0,0]`'s own dispatch could never even start) — the original version of the matmul JIT test never noticed only because it read `mc` back through a raw `mlir::tensor::extract` call, which needs no cleave-level type resolved on `mc` at all. Same workaround applies: `let mc: Matrix<f32,2,2> = matmul(ma, mb);`.

**One real, deliberate, dialect-family-wide exception to "no per-op-name Rust knowledge," found necessary and explicitly signed off on**: every *structured* `linalg` op needs a real payload region even in "named op" form — melior/mlir-sys exposes no C++ convenience builder for one, only the fully generic op-builder `lower_raw_mlir_op` already uses for everything else, which attaches no region at all (`'linalg.matmul' op requires one region`, a real verification failure, not guessed at). Raised directly as a genuine architectural fork (synthesize the region generically vs. fall back to an ordinary `tensor.extract`/`insert` loop, losing the one-recognizable-node structural goal) — user's call: synthesize it, scoped to the whole `linalg.` prefix, not one op by name, since every structured *contraction*-family op in it (`matmul`, `batch_matmul`, `dot`, `vecmat`, ...) shares the identical multiply-accumulate body (`out = out + in0*in1`, the dialect's own defining semantics for that whole family) — a real, principled, dialect-wide invariant, mirroring `bool`'s own already-existing status as `ty_to_mlir`'s one deliberate structural exception, rather than a new one-op special case. `mlir_lower.rs::build_linalg_region` synthesizes it: one block, one scalar argument per operand (element type recovered via `RankedTensorType`/`ShapedTypeLike`), every `ins` operand multiplied together, added to `outs`, `linalg.yield`s the result. **Not visible in `--dump-mlir`'s own output**, worth knowing when eyeballing a dump: `linalg.matmul`'s own pretty-printer elides the region entirely in its short `ins(...)/outs(...)` form (the body is implied by the op's own name/semantics, not printed) — the synthesized MAC region only becomes visible textually after `-convert-linalg-to-loops` (`--dump-mlir-lowered`, real `scf.for`/`arith.mulf`/`arith.addf`), or via MLIR's generic (not pretty) printer form, not wired up in `main.rs` today.

**Two more real bugs found by direct testing along the way, both the same root cause hit a third time now**: `lower_raw_mlir_op`'s "infer each operand's type from a `CVal::Var` sibling, else fall back to the *result* type" heuristic is wrong whenever every operand is a bare literal and the op's own operand type genuinely differs from its result type — a `let`-bound *literal* (`let zero_i: i32 = 0;`) never gets its own real SSA value at CPS-conversion time at all (just a compile-time alias for the constant), so `arith.index_cast(zero_i)`'s own operand-type inference silently fell back to the *destination* type ("index"), building an illegal `index -> index` cast. Worked around at the cleave-source level each time it was hit (`mlir::arith::addi(0, 0)` forces a genuine computed value) rather than further generalizing the Rust-side heuristic — flagged below as a real, recurring rough edge worth a proper general fix eventually, not a one-off.

**A real MLIR pass-pipeline addition, found the same way, and non-obvious in its own final shape**: `tensor`-backed values need `-one-shot-bufferize` (with `bufferize-function-boundaries=true` — melior's zero-argument `create_one_shot_bufferize_pass()` binding can't set this, so it goes in via `melior::utility::parse_pass_pipeline`'s real textual pipeline string instead, the pass registered by name first) plus `-convert-elementwise-to-linalg` (a bare `arith.addf` on tensor operands has no `BufferizableOpInterface` of its own, only a real structured op does) plus `-convert-linalg-to-loops` (turns the now-bufferized `linalg.matmul`-on-`memref` into real scalar loops, since even bufferized it has no direct LLVM translation) — after which everything is ordinary `memref`/`arith`/`scf`, handled by this project's existing pipeline unchanged. **Found by direct testing, not fully root-caused**: these passes had to be staged as three *separate* `PassManager`s, each run to completion before the next is even built — the identical passes combined into one `PassManager`/one `run()` call failed partway (`op was not bufferized`) even though every individual stage, run to completion first, succeeds cleanly; kept as the working shape (robust, and arguably clearer to read) rather than chased further.

Verified via: no `infer.rs` changes at all for the type system itself (the whole point) beyond the `ExprKind::Index`/`StmtKind::Assign` algebra-dispatch-fallback additions; six real end-to-end JIT-execution tests in `cleave/tests/mlir_lower.rs` (tagged-struct construction + `Index`-algebra element read, elementwise `Ring<Vector<T,N>>`/`Ring<Matrix<T,R,C>>` addition on `tensor`, the full `linalg.matmul` against the same hand-computed expected values the first attempt already used, and a rank-3 `Tensor` construction+read). Full `cargo test --workspace` green; `examples/*.cleave --run` sweep unaffected; `examples/matmul.cleave` itself re-verified both numerically (`--run`) and structurally (`--dump-mlir`, exactly one `linalg.matmul`, printed in its own idiomatic `ins(...)/outs(...)` pretty form — confirming the synthesized region and attributes are genuinely correct, not just verifier-satisfying noise); `examples/tensor_demo.cleave` verified numerically end to end (`--run`) across all three types together. A direct diff-level check confirms `infer.rs`'s own `Ty` enum and every exhaustive match over it are back to exactly their pre-`Ty::Vector` shape.

**A parallel-test-execution flake, noticed while adding the rank-3 `Tensor`/`Matrix`-`Ring` tests, not chased further**: `cargo test --workspace` (default, parallel) occasionally crashes outright (`STATUS_ACCESS_VIOLATION`) partway through `mlir_lower.rs`'s own test binary — never reproduces with `--test-threads=1` (100% green, repeatedly), and doesn't reproduce every parallel run either (genuinely flaky, not deterministic). Consistent with a thread-safety gap somewhere in melior/LLVM's own global JIT/pass-manager state when multiple `Context`/`ExecutionEngine`/`PassManager` instances run concurrently across threads, made more likely to actually surface by this item simply adding more tensor-pipeline-heavy tests (five now use the same three-stage `PassManager` shape, up from three) — not a correctness issue in this item's own code (`--test-threads=1` is fully deterministic and correct). Not root-caused; flagged so a future flaky CI run isn't mistaken for a real regression.

**Deliberately out of scope, flagged not fixed opportunistically:**
- **The bare-literal-operand-vs-`mlir::...`-result-type heuristic gap** (see above) — hit three times now (`vector.from_elements`, `vector.broadcast`, `arith.index_cast`), always worked around locally. A real general fix (e.g. never falling back to the result type for an op whose own operand/result types are known to differ) would need *some* per-op knowledge to know which ops that's even true for — not obviously resolvable without reintroducing exactly the kind of special-casing this project avoids; flagged as a recurring rough edge, not solved.
- **Positional/variadic struct constructors** (`Vector(1.0,2.0,3.0)` instead of `Vector(data: [1.0,2.0,3.0])`) — a genuine, separate language feature (no constructor mechanism beyond the named-field literal exists at all today), deliberately not designed here.
- **The e-graph reasoning about `linalg.matmul`/`tensor` ops at all** — the actual `hld.md`-cited optimization payoff (reassociating a matmul chain for FLOP count). This item gets a real structural node into MLIR, provably surviving un-scalarized; teaching `egraph.rs`'s `CleaveLang`/`Forward::walk` to treat it as an e-node, and writing real axioms for it, is separate, unstarted work.
- **Auto-derived light/heavy storage as a trait** (`hld.md`'s own "plausible future direction," explicitly not decided there either) — an array-backed struct stays either ordinary (heap-allocated reference) or explicitly `#[mlir_type(...)]`-tagged (native value), a real annotation, never inferred.

### Multi-dimensional `Index` dispatch (`m[i,j]`, `t[i,j,k]`)

Follow-up to the `Vector`/`Matrix`/`Tensor` item above, previously listed there as out of scope — `Index<Container,Elem>` only ever declared a single-index `fn index(c,i) -> Elem`, so `Matrix`/`Tensor` elements could only be read via a raw `mlir::tensor::extract(m, i, j)` escape hatch. The real blocker wasn't the algebra's own arity so much as the *grammar*: `m[i,j]` desugared into **nested** single-index `Index(Index(m,i), j)` AST nodes (the same trick that makes a real array's own `a[i,j]`/`a[i][j]` work, since a 2D array's own `a[i]` has a genuinely valid sub-array type to dispatch the next `[j]` against) — but a tagged tensor struct has no such intermediate "row" type, so the *inner* node (`Index(m,i)` alone, processed first by ordinary bottom-up inference) had nothing sensible to dispatch to.

**The fix: stop flattening a bracket group into nested nodes at all.** `ast.rs::ExprKind::Index` changed from `Index(Box<Expr>, Box<Expr>)` to `Index(Box<Expr>, Vec<Expr>)` — `m[i,j]` (one bracket group) is now **one** node carrying `indices = [i, j]` directly (`lower.rs::lower_postfix_op`, no more fold-to-nested loop). `m[i][j]` (two *separate* bracket pairs, written explicitly) still nests — one `Index` node per bracket, one index each — and deliberately stays **not** equivalent to `m[i,j]` for a tagged type (no `Index<Matrix<...>,...,1>` impl exists, so it's cleanly rejected): a tagged value has no meaningful single-step "row" the way an array's own partial index does, unlike the array case, where the two spellings stay fully equivalent either way (a real, well-defined sub-array type exists at every step regardless of how the indices are grouped into nodes).

- **Array base** (`infer.rs`'s `ExprKind::Index` arm): peels one array dimension per index in an explicit loop — the direct generalization of what nested-node recursion used to achieve per level, now inside one node/one handler. Running out of dimensions with indices still remaining (`a[i,j,k]` on a 2D array) is a direct `Mismatch`, reached immediately instead of indirectly through a failed `Index`-algebra lookup on whatever scalar leaf was left over — an equivalent rejection, not a behavior change (`over_indexing_a_plain_array_is_rejected`).
- **Non-array (tagged struct) base**: the algebra's own signature generalized to `fn index(c: Container, idx: [i32; K]) -> Elem;`, `K` a genuine algebra-level *const* generic — a real, already-proven mechanism (`algebra Sum<T, const N: i32> { fn total(x: [T; N]) -> T; }`, `cleave/tests/mlir_lower.rs::an_algebras_own_const_generic_actually_runs`), not new. Every index in the bracket group unifies against one shared fresh element type (mirrors `ExprKind::ArrayLit`'s own pairwise-unify loop exactly), becoming a real `Ty::Array(elem_ty, Const(K))` — unifying *that* against the algebra's own abstract `[i32;K]` pattern is what pins both `elem_ty := i32` and `K := indices.len()`, no special-casing needed. Each concrete type's own impl hardcodes its own fixed rank via a **literal**-sized `idx` parameter (`[i32;1]` for `Vector`, `[i32;2]` for `Matrix`, `[i32;3]` for `Tensor`) rather than leaving `K` free the way `Sum`'s own `N` is — this is what makes `m[i,j,k]` (3 indices on a rank-2 `Matrix`) a real, structural mismatch instead of a silently-ignored extra index.
- Building the real `[i32;K]` array **value** needed zero new lowering machinery: `cps.rs`'s own `ExprKind::Index` algebra-dispatch arm synthesizes an ordinary `PrimOp::Array` `LetPrim` directly from the already-converted index `CVal`s (CPS routinely builds intermediate values this way) and hands it to `index(...)` as the second argument — unpacking it back inside each impl body (`idx[0]`, `idx[1]`, ...) is just ordinary array reads, already fully working.
- `collect_index_chain` (`cps.rs`) — the array-side chain-walker, still needed for the `a[i][j]`/two-bracket-pairs *array* case (`StmtKind::Assign`'s own multi-index `Store` collapsing, and the array-read `PrimOp::Load` path) — now walks whole *groups* rather than single indices, reversing group order (not each group's own internal order) before flattening; the write-side collapsing this exists for is a real correctness requirement, not just an optimization (see the module's own "Arrays" doc comment), so it's kept exactly as conservative as before rather than risking the never-actually-exercised "partial `Load` producing a real intermediate array value, read further" path.
- `monomorphize.rs::derive_impl_instantiation` — refactored from `arg_ids: &[NodeId]` to `arg_tys: &[Ty]` directly (it only ever did `node_types.get(id)` per id; the synthesized idx-array has no real `NodeId` of its own to look up) — a small, safe simplification, the same `NodeId`→primitive-value pattern already used this session for `resolve_call`/`infer_algebra_call`.

**A real, separate subtlety, found by direct testing while writing the negative test**: `dispatch_algebra_call`/`matching_impls`'s own target-matching tuple only ever includes an algebra's *type* generics (`Container`, `Elem`) — a *const* generic like `K` is deliberately excluded (`infer_algebra_call`'s own `resolved_generics` loop only pushes `GenericParam::Type` entries), bound separately via ordinary `unify_at` against the impl's declared parameter type instead. So ordinary immediate dispatch accepts `m[0,0,0]` (3 indices on a `Matrix`) freely — nothing about `K` blocks it there — and the real rejection only surfaces one pass later, at monomorphization (`derive_impl_instantiation`'s own *full* signature match, which does see `Matrix`'s own literal `[i32;2]` and fails to unify it against a `[i32;3]` query). `cleave::dump::dump_program` (ordinary inference alone) wrongly reports such a program as accepted; `cleave::monomorphize::dump_monomorphized` (which `main.rs`'s own `check_type_errors` gate already uses) is what actually catches it — `over_indexing_a_matrix_is_rejected` uses the latter specifically for this reason.

Verified via: `cleave/tests/lower.rs` (the new one-node-per-bracket-group shape, plus a `separate_bracket_pairs_still_nest` regression confirming `a[i][j]` still desugars as before), `cleave/tests/mlir_lower.rs` (the matmul/`Ring<Matrix>`/rank-3-`Tensor` tests reworked to read back through real `mc[i,j]`/`t[i,j,k]` sugar instead of raw `mlir::tensor::extract`, plus `over_indexing_a_matrix_is_rejected` and `over_indexing_a_plain_array_is_rejected`), `cleave/tests/print.rs` (updated to the new direct-printing shape, `a[i, j]` rather than re-nested `a[i][j]`). Full `cargo test --workspace` green; `examples/*.cleave --run` sweep unaffected; `examples/tensor_demo.cleave` reworked to use the real sugar throughout, re-verified numerically end to end.

### `check_pending_constraints`'s output-only-generic gate, and `ExprKind::Index`'s own missing deferred-resolution path

Two stacked bugs, found and fixed together, both surfaced by trying to remove the explicit annotation workarounds the two items above had needed (`let mc: Matrix<f32,2,2> = matmul(...)`, `let x: f32 = v[i];`) — a bare `print(v[i])` or `mc[i,j]` right after `let mc = matmul(...)` used to panic in `cps.rs::resolve_call` ("could not resolve call") instead of compiling.

**Bug 1 — `check_pending_constraints` required *every* position in a deferred `Constraint` to already be concrete, including an algebra's *output-only* generic** (`Index<Container,Elem,K>`'s own `Elem`, `MatMul<A,B,C>`'s own `C`), which by design is never independently pinned by anything — the only place it's ever supposed to get bound is inside a successful *dispatch*, exactly the way the already-correct immediate-dispatch path (`infer_algebra_call`) already treats it (only its *gating*, input-appearing generics need to be concrete before `dispatch_algebra_call` — the committing match — even runs). `check_pending_constraints` had no equivalent split, so a deferred call's own output-only position could never be satisfied, and the whole constraint was silently dropped forever (`std::mem::take`), never erroring, never resolving.

**The fix**: `Constraint` gained a `gating_indices: Vec<usize>` field (`Constraint::all_gating` covers every existing single-target bound-check push site — `Num`/`Int`/`Float`/`Complex`/`for`-loop/`Index`'s-own-per-index-`Int`, all trivially "every position gates" — a pure rename, no behavior change) — `infer_algebra_call`'s own deferred pushes record the *real* gating subset alongside its existing `gating: Vec<Ty>` computation. `check_pending_constraints` now gates readiness on `gating_indices` only; once satisfied, if some non-gating position is *still* a bare `Ty::Var`, it calls `dispatch_algebra_call` (committing) instead of `has_matching_impl` (non-committing, existence-only — the actual root cause: it never bound anything) — otherwise (everything already concrete, the ordinary bound-check shape) the exact original path is unchanged, including the `Ty::Const`-width bridging and the `Complex`-widening special case.

**Bug 2 — `ExprKind::Index` had no deferred-resolution mechanism at all** for "I don't yet know if my base will end up an array or an `Index`-algebra target," found while testing bug 1's own fix: `matmul(ma,mb)`'s inferred type is a *bare, structurally unconstrained* `Ty::Var` (unlike `Vector(data:...)`'s own type, which is *always* `Ty::App("Vector",...)` from the moment it's constructed, even with an abstract inner element type) — until `MatMul`'s own dispatch actually runs. So `mc[0,0]`'s own `resolved_base` was `Ty::Var(_)`, and the *existing* `ExprKind::Index` code treated that identically to `is_placeholder` (a genuine dead end, e.g. `<unresolved-call:...>`): an immediate dead `Ty::Con("<not-yet-inferred>")`, with **no constraint or deferred work registered at all** — nothing ever revisited the node once `mc`'s type later resolved, since a `Ty::Con` is inert under `Subst::apply`, unlike a real `Ty::Var`.

**The fix mirrors `FieldAccess`'s own already-correct `pending_field_accesses`/`check_pending_field_accesses` mechanism exactly** (`Index`'s own old doc comments already said it *should*, but never actually did): a new `PendingIndex { base, base_span, index_tys, index_spans, result, span }` list — indices are still inferred (and `Int`-constrained) immediately either way, mirroring `PendingMethodCall`'s own "arguments never depend on the base" split; only "what does indexing mean" is deferred. `Ty::Var(_)` now mints a fresh real `Ty::Var` and queues a `PendingIndex` (returned immediately, so later unification can still pin it down) instead of the dead placeholder; `is_placeholder` keeps the old immediate-dead-end behavior, unchanged. `resolve_index` (extracted from the old inline match arms, same shared-helper precedent as `resolve_field_access`) is reused by both the immediate path and `check_pending_indices`.

**A third issue, found empirically while wiring the two together, not predicted in advance**: `check_pending_constraints`/`check_pending_indices` can depend on *each other's* output across a real chain — `print(matmul(ma,mb)[0,0])` needs `MatMul`'s own `C` bound (`check_pending_constraints`) *before* `mc[0,0]`'s own `Index` dispatch can resolve (`check_pending_indices`), which in turn needs to complete *before* `print`'s own deferred `Constraint` — queued right behind `MatMul`'s in the very same `Vec`, processed in one linear pass — can be satisfied. One back-to-back call of each wasn't enough: `check_pending_constraints`'s own single pass would reach `Print`'s entry, find it not yet ready, and — before this fix — permanently drop it, since neither method ever *requeued* an entry that wasn't ready, only ever a hard "give up now." Fixed by making both requeue (not drop) a not-yet-ready entry, and adding `check_pending_constraints_and_indices`, which loops both to a real fixpoint (terminates because each round either strictly shrinks the combined pending count or stalls) — replacing all three existing call sites (`infer.rs`'s own inherent-impl-group tail and `finish_fn`, plus `callgraph.rs`'s whole-program group pass, a call site the original two-part plan for this item had initially missed). On a genuine stall (nothing left in this function will ever pin a base down, e.g. `fn f(a) { a[0] }` with `a` never otherwise constrained), any leftover `PendingIndex` is collapsed to the same dead placeholder `check_pending_field_accesses`'s own "give up" case already uses — needed to avoid a real regression, found directly by this project's own pre-existing `indexing_an_unresolved_base_defers_as_not_yet_inferred` test: a bare requeue-forever would have let a genuinely-unresolvable function signature escape `check_no_placeholder`'s downstream safety net instead of being caught by it.

Verified via: two real end-to-end JIT tests in `cleave/tests/mlir_lower.rs` (`print_of_an_unannotated_index_result_no_longer_panics`, `print_of_an_unannotated_matmul_index_result_no_longer_panics` — both register `print_f32` for real and check the JIT-executed output, not just that the module verifies). Both the matmul JIT test and `examples/tensor_demo.cleave` had every workaround annotation removed as the actual end-to-end proof, re-verified numerically. Full `cargo test --workspace` green throughout, including the one pre-existing test (`indexing_an_unresolved_base_defers_as_not_yet_inferred`) that caught the stall-collapse regression before it shipped.

## Produce a real executable

Wire up an actual compile-to-object/link step (`-c`-equivalent) so a cleave program produces a standalone binary. Today's `--run` is JIT-only (`melior::ExecutionEngine`) — proves correctness end to end, but there's no way to hand someone an executable file.

**Deliberately not started — real design questions first, not just missing plumbing.** Investigated directly (not guessed): the `.o`-emission half is genuinely easy, already sitting there unused — `melior::ExecutionEngine::dump_to_object_file(&self, path: &str)` (`execution_engine.rs:83`, upstream melior, no patch needed) dumps a real object file, gated only by `enable_object_dump: true` in `ExecutionEngine::new`'s own 4th argument (today always `false`). Confirmed via melior's own passing test (`dump_to_object_file`). A separate, older assumption in this project's own history — "`mlirTranslateModuleToLLVMIR` isn't exposed at all" — is also now confirmed stale: `mlir-c/Target/LLVMIR.h` exists in the real LLVM 22 install this project builds against (`I:/Dev/llvm-mlir-22`), and `mlirTranslateModuleToLLVMIR`/`mlirTranslateModuleToLLVMIRToString` are both already present in `mlir-sys`'s own generated bindings (verified directly in the build artifact) — moot for this item specifically (`dump_to_object_file` is the more direct path), but worth knowing the raw LLVM IR text/module route is *also* open if ever needed.

**What actually blocks this, raised directly by the project owner and worth recording precisely:** a `.o` alone isn't a *linkable program* — turning it into a real `.exe`/binary needs an external linker (`cc`/`clang`/`link.exe`, driven as a subprocess, the same "shell out, don't write our own" posture `rustc` itself takes — no linker-writing attempted here) *and* `cleave-rt` compiled as a real `staticlib` (its `Cargo.toml` has no `[lib]` section at all today, so it's an ordinary `rlib`, not linkable by a system linker), cross-platform (Windows/`link.exe` vs. Unix/`cc` differ genuinely, not just naming).

**The deeper, still-open design question, not a plumbing gap**: does a "cleave library" — separately-compiled, linkable, with no source required downstream — make sense at all, given total monomorphization? A `.o` alone carries no metadata (declared signatures, generic templates, algebra impls) for a *downstream* cleave program to monomorphize *against* — unlike Rust's own `.rlib`/`.rmeta` split, which exists precisely to carry that metadata alongside compiled code. Without an equivalent, either (a) cross-crate cleave code always recompiles from source (the current `stdlib` model, extended — works, but risks "mega long" whole-program compile times as noted directly, and doesn't produce a distributable library at all), or (b) a real compiled-library-plus-metadata format gets designed, a genuinely new, nontrivial piece of infrastructure. `extern "C"`/`extern fn` already covers the *other* interop story fine (calling into/out of compiled cleave across a language boundary, already built and working) — this item is specifically about a *cleave-to-cleave* separately-compiled library, a different problem.

**Deferred deliberately**: needs a real design pass once the language itself is more stable — not attempted now. `--run` (JIT) stays the only way to execute a cleave program for the time being.

## A lambda returned from a function, or stored in a struct/array field

The other two shapes originally bundled with "Calling a lambda literal directly" (now Done, see above) — a lambda value that outlives the single call site its own closure-conversion unit is specialized against. Unlike calling a lambda literal directly (pure desugaring, no new runtime representation needed), these two are a genuinely harder problem: `hld.md`'s own "no runtime closure ABI" design (see "Closure conversion (lambdas)" above) means a lambda never becomes a real runtime value today — every call to one is resolved to a concrete, statically-known unit at compile time. A lambda *returned* from a function (potentially different lambdas on different branches) or stored in a struct/array field (potentially read back and called from code with no static knowledge of which lambda it is) both need some real runtime representation to call through — a function pointer plus a captures record, at minimum — not just more of the "resolve by static name" machinery `monomorphize.rs`/`cps.rs` already have. Needs its own design pass, not attempted yet.

## A generic call's own explicit turbofish is never consulted for monomorphization

Found while implementing "Deferred/symbolic constant folding," above — `monomorphize.rs`'s `derive_instantiation` (which recovers a generic function's own concrete instantiation at a call site, for real specialization) works purely by reverse-unifying the call's own argument/return *value* types against the function's declared shape; it never looks at the call expression's own explicit turbofish at all (`collect_instantiations_expr`'s `ExprKind::Call` arm: `(path, _, args, ..)`, the generics list discarded outright). Harmless for an ordinary generic parameter (always recoverable from *some* argument's own concrete type) but a real gap for a const generic that only ever appears *combined* with another one (`fn f<const N, M>(x: [T; N+M])`, no parameter mentioning `N`/`M` individually) — reverse-unifying `ConstExpr(N,M)` against one concrete total is exactly as underdetermined as inferring them from a single struct-literal field value (see the "Deferred/symbolic constant folding" item's own note on that), so monomorphization can never recover them, even given an explicit turbofish that supplies both directly. Needs `derive_instantiation` (and whatever else in `monomorphize.rs` shares this posture) to also unify a call's own explicit turbofish arguments against `scheme.vars`, as a first pass before or alongside reverse-unification from argument/return types.

## `break value` in loops

`for`/`while` can never produce a value (always `Ty::Con("()")`) — no `break value` mechanism. `let mut` plus a post-loop read is the only idiom today (and it actually compiles *and runs* correctly now, end to end).

## Qualified-call syntax

Two algebras legitimately declaring the same operator name (`AmbiguousOperator`) has no way to disambiguate at the call site — an unconditional hard rejection, no qualified-call syntax wired up to bypass it. This is exactly why `examples/matmul.cleave`'s own `MatMul::matmul` is an ordinary named method, not wired to `*` — a second algebra declaring `mul` would make *every* `*` in a program ambiguous, including a genuinely scalar one.

## More constant-folding operators

`const_eval::eval_binop` now knows `add`/`mul`/`sub` (see "Done" above, the egg-integration equality-saturation entry). `div`/`neg` remain — `div` needs a decision on divide-by-zero behavior first (this evaluator is also reused by `ConstantFold`, so "what happens at const-eval time" now has a *runtime-observable* consequence, not just a compile-time const-generic one); `neg` doesn't fit `eval_binop`'s binary signature at all (would need its own `eval_unop`, or folding into `Ring::sub<T>(0, a)`'s own existing shape first).

## No reserved-word list at all

A keyword (`let`, `if`, `and`, `not`, ...) is only special at its own specific grammar position — nothing stops it from *also* being used as an ordinary identifier elsewhere (`let and = 5;` presumably parses). Distinct from the word-boundary bug already fixed (see "Done" above, boolean logic): that was about a keyword wrongly matching as a *prefix* of a longer identifier; this is about a keyword being usable as a *complete* identifier at all. Not urgent, noted so it isn't lost.

## No opaque/foreign-pointer type for FFI-style resources

Every cleave type today is either a primitive, a struct (heap-allocated, but with a statically known field layout `mlir_lower.rs` builds directly), or an array — nothing represents "an opaque handle a C function handed back, whose own layout cleave has no business knowing" (a `FILE*` from `fopen`, a `malloc`'d buffer, an OS handle). The natural shape: an `extern fn` already returning an untyped pointer works today at the *value* level (`mlir_lower.rs`'s own `ty_to_mlir` fallback for a non-primitive `Ty::Con`/`Ty::App` already lowers to `!llvm.ptr`) — what's missing is a *declared* opaque type (something like `extern type Handle;`, parsed and registered the same way a `struct` is, but with no field list at all, existing purely so a `struct File { handle: Handle }`-style wrapper type-checks and a `File` value stays distinguishable from a bare `i64`/another opaque handle at the type level) rather than every FFI wrapper smuggling a handle through as a same-looking primitive int and losing type safety. Not a dependency of string support (see "Done" above) — stands on its own.

## Tuples as a language feature

Raised directly while designing multi-argument `print` (`print("x =", x, "y =", y)`): `doc/grammar.md`'s own already-documented `params`-style variadic model (`fn f(args: [T;N])`, `f(1,2,3)` desugars to `f([1,2,3])`, same posture as operators/structs) only covers *homogeneous* argument sequences — mixing a string and a number in one call doesn't fit a single array type. A real `(T1, T2, ...)` tuple type — heterogeneous, fixed-arity, structural rather than nominal — is the natural foundation instead. Genuinely its own design effort, comparable in size to string support itself: grammar (literal + type syntax), `ast.rs`, `infer.rs` (a new `Ty::Tuple(Vec<Ty>)`), CPS representation (likely close to a struct's own — fixed positional fields, probably reusable machinery), MLIR lowering. Deliberately not started — flagged so the `print`-multi-arg thread isn't lost, not designed further here.

**Consuming a tuple needs compile-time unrolling, not a runtime loop — established via direct discussion, worth recording precisely so it isn't re-litigated:** a tuple is heterogeneous, and MLIR/LLVM compiles one loop body once, with a fixed type per SSA value — there's no way for a single compiled loop iteration to handle a different concrete type (hence a different `Print<T>` dispatch) each time around, with no boxing/vtables/dynamic dispatch anywhere in this language. So `foreach p in some_tuple { body }` can only ever mean "expand `body` once per tuple position at compile time, each copy independently type-checked against that position's own concrete type" (`print(t.0); print(t.1); print(t.2);`, mechanically) — never a genuine runtime loop. Unlike a string literal's own parse-time-only `lower.rs` desugar (the byte count is already sitting in the source text), this expansion can't happen at parse time: a tuple *value*'s own arity isn't known until its type is — closer in spirit to how `[value; N]` with a still-abstract const-generic `N` stays a real AST node through inference and only resolves once something later (monomorphization) knows the concrete value. `foreach`-over-tuple would need the same treatment: kept as a real node through inference, expanded once the tuple's own concrete arity is known (monomorphization or CPS-conversion time), not at `lower.rs` time.

## `for x in array` — element-based array iteration (a real runtime loop, unlike tuple `foreach` below)

Only index-based iteration exists today (`for i in start..end { ... }`, reading `arr[i]` manually). An array is *homogeneous* — every element shares one type — so unlike tuple iteration (see below), this needs no compile-time unrolling at all: `for x in arr { body }` is an ordinary, thin desugar to the existing `for i in 0..arr's own known N { let x = arr[i]; body }` shape, reusing the `for`/indexing machinery already built and verified. Low risk, much smaller than the tuple case — flagged separately so the two don't get conflated (they compile in fundamentally opposite ways: one real loop, one compile-time expansion).

## Multi-argument, heterogeneous `print`

Depends on the "Tuples as a language feature" item above. Concrete mechanism, established via direct discussion (supersedes the vaguer "per-arity impls, or a recursive tuple-printing algebra" phrasing this item used to carry): `print("x =", x, "y =", y)` desugars to `print((a, b, c, d))` (an ordinary tuple construction, `params`-style, `doc/grammar.md`'s own posture) — consuming it is *exactly* the "tuple `foreach`, compile-time-unrolled" mechanism the tuples item above describes, specialized to `print`: `foreach p in the_tuple { print(p) }`, unrolled once the tuple's own arity is known, each `print(p)` independently dispatched to whichever `Print<T>` impl matches that position's own concrete type. No new `Print`-side machinery needed beyond what already exists (`Print<i32>`, `Print<[i8;N]>`, ...) — the unrolling *is* the whole mechanism. A `lower.rs`-only desugar into sequential single-arg `print(a); print(b); ...` calls was considered earlier and rejected as a `print`-specific hack that wouldn't generalize — this tuple-`foreach`-based version is that same shape, but as a real, reusable language primitive instead of a one-off.

## Multi-level call transparency in the e-graph forward translator

`Forward::walk`/`is_straight_line` (see "Done" above, equality saturation) only ever treats a real call to a pure unit as *one opaque node* — it never descends into the callee's own body, even when that body is itself pure and would expose more to rewrite/fold against. Bounded, well-understood follow-up (confirmed by direct discussion, not a "research frontier" the way the "Representing an `If`/join point" item below is): `Forward::walk`'s own `Fix` arm would need to recurse *into* the callee's body instead of stopping after adding one `Op` node, re-mapping the callee's own parameters to the caller's already-resolved argument e-classes first. The safety conditions are the *same* ones already enforced for single-level transparency (`is_pure_prim_op`, no `FieldStore`/`Store`/`Extern` anywhere) — nothing new to invent there. Would let e.g. `Ring<Complex<T>>::add`'s own body (itself a real call to `Ring::add<f32>`) become visible to the same segment translating its caller, which is one of the four reasons `examples/complex.cleave` is currently out of reach of this whole mechanism (see the equality-saturation "Done" entry's own Context).

## Representing an `If`/join point as an e-graph node (cross-branch propagation)

Today the e-graph never crosses a real `If` at all (see the "Multi-level call transparency" item above and the equality-saturation "Done" entry) — even the *trivial* case, `if cond { x } else { x }`, where both branches are already the exact same value, isn't seen. Confirmed via direct testing (`--dump-cps-equivalences` on a hand-built example: two branches passing the literal same `CVar` to their own join continuation) that nothing fires today, by design, not by accident.

Established via discussion, not yet built: the trivial "both branches already agree" case is *not* the hard part — representing the join point as one more e-graph node (a `phi`-like `Op`) and adding `phi(a, a) == a` as a rewrite would catch it directly (congruence closure alone doesn't give you this for free — `phi(a,a)==a` is a specific identity about the join operation, exactly analogous to `add_zero`, not a generic consequence of congruence). What's genuinely hard, and still out of scope: (a) either branch containing a real effect — a `phi` over two effectful computations can't be treated as "just a value" the same way a call already can't (`is_pure_prim_op`'s own reasoning applies identically here); (b) code motion — hoisting a sub-computation that's shared between two *different* (not syntactically identical) branches out of the `if` entirely needs real dominance reasoning to prove it's safe to place before the branch, not just a `phi` rewrite.

**The `phi(a,a)==a` rule alone is not sufficient — confirmed by direct testing, not just reasoning.** `examples/join_demo.cleave`'s own `--dump-mlir-lowered` output still shows the untouched `cond_br`/two-block join *and* a real, un-folded `Ring::add<i32>(_, 0)` call after it — both symptoms trace back to the *same* single root cause: `Forward::walk` stops translating entirely the instant it meets the `If` (`env` stays empty for the whole function), so a rewrite rule declared for `phi` would never even get a chance to fire — nothing built the `phi` node for it to match against in the first place, and nothing past the `if` (`b + 0`, here) ever gets translated either. Building the actual fix needs *two* pieces together, not one: (1) the `phi(a,a)==a` rule itself, and (2) extending `Forward::walk`'s own `If` handling so a *pure* `If` (same effect-freedom condition already enforced everywhere else in this module) doesn't stop the segment — it builds a `phi`/join `Op` node and *continues* translating into the join's own continuation, mirroring exactly how single-level call transparency already continues into `rest` after adding one opaque `Op` node for the call itself.

Also raised, genuinely undecided, worth a real design pass before committing either way: whether algebraic-law rewriting (the actual value-add — cleave's own mathematical semantics, which are largely control-flow-independent) belongs in a bespoke CPS-level e-graph pass at all, versus a real MLIR dialect with axioms expressed as canonicalization patterns (MLIR already owns dominance-aware CSE and a real sparse dataflow-analysis framework downstream). The concrete trade-off: MLIR's own canonicalizer is greedy term rewriting (applies one match, replaces immediately, one fixed rewrite order) — not equality saturation (many equivalent forms held simultaneously, cheapest extracted at the end) — which is `egg`'s actual value proposition over "just write MLIR patterns." Real prior art exists for hosting genuine equality saturation *inside* MLIR rather than beside it; not evaluated here.

## `CVal::Float` in the e-graph

Bare `f64` has neither `Ord` nor `Hash`, both required by `define_language!`'s own derives (see "Done" above, equality saturation) — `Forward::cval_to_id` returns `None` for any `CVal::Float`, so a segment touching one simply stops translating there rather than misbehaving. Would need `ordered-float` (or an equivalent wrapper) as a new dependency. One of the four reasons `examples/complex.cleave` is currently out of reach of the whole mechanism (its own `Complex<T>` construction args are always `CVal::Float`).
